# E2E (Playwright, blackbox)

Owns: how to run the suite against a named stack, the parallel state-ownership rulebook and the coverage map. Not here: each spec's actors, owned state and steps (`e2e/scenarios/<spec>.md`; the format is `e2e/scenarios/README.md`); the CI jobs (`ci.md`); gate times (`build-times.md`).

## Rules

- The tests treat the app as a **blackbox**: a real Chromium against the whole stack (SPA + server + Flyway + Postgres) served single-origin, **a stack you started and named** (see "Run"). The package is fully isolated from `web/`: it imports none of the app source and only speaks HTTP/DOM.
- **Playwright runs only against a stack somebody named.** The suite starts, builds, stops and tears down nothing, and never removes a service or a volume. Tests clean up only the records they own; existing data stays intact.
- **A new or behaviorally changed test lands with its scenario file and its line in "What's covered" in the same commit.** The scenario file is the design, the line is the coverage map. `npm run check:scenarios` enforces the parity mechanically (both directions, orphan files included); a backtick title with `${…}` holes (`accessibility.spec.ts`) is a template: a scenario heading must fit it.
- **Every spec file owns its server-side state exclusively.** The serial unit is the spec file; different files run concurrently. Each spec's scenario file declares its **Owns** line ("nothing — read-only" when applicable); a new or edited spec satisfies the rulebook in "Parallel execution".
- Artifacts are unique-named, and list asserts are filter- or sort-anchored, never bare page-1 assumptions.
- Every e2e-created entity's name and every e2e-created user's email contains `e2e`, and nothing that must SURVIVE runs is ever named that way. Each spec deletes its own state, so the rule is satisfied by self-cleanup; add a `sweep-residue` global-setup pass if aborted runs start leaving residue that self-cleanup misses.
- **Seeded accounts are never mutated.** The seed admin (`admin@adder.local`) is a shared read-mostly actor: specs sign in as it but must not change its password, roles, language or state; a spec that needs a mutated account creates a throwaway. Seeded accounts must stay English: every login applies the stored language to that session's UI, so a Polish seed admin would flip parallel specs mid-run. `mfa` never touches the seed admin's MFA flag (enabling it would make every spec's login demand a code).
- **The workflow-template registry is shared state too.** The seeded Default and Incident templates are shared and read-only: no spec edits or deletes them, and a spec only ever creates, edits and removes its OWN `e2e-tpl-*` templates (several specs read the list, and rooms copy a template at creation).
- **The tag registry is shared, append-only state too** (a tag name is unique for good, retired ones included): the `tags` spec creates and deletes only its own uniquely named category and tags (every name carries a per-run suffix) and never edits the seeded Kind and Area categories.
- **The Teams registry is shared, append-only state.** Several specs create teams concurrently (`teams`, `accessibility`, `list-mutation-refresh`), so a spec only ever appends and removes its OWN uniquely named `e2e-*` rows, never edits or deletes another's.
- A future spec minting globally-visible state (banners, org-wide notifications) runs in its own dependent project phase, not in the parallel pool.
- Specs log in with a throwaway through `helpers.login()`; the seeded admin only where it is the subject (`auth`, `users`) or the spec is read-only (`changelog`, `shell`): every other spec signs in as ITS OWN throwaway administrator (`helpers.specAdmins()`, "Rate buckets"); `helpers.loginViaForm()` only where the form, the credential or the language riding the login response IS the subject ("Logging in").

## Run

**Playwright runs only against a stack somebody named.** The suite writes rows through the API of the stack it is given (users, teams), so it never guesses a stack: the repository's default compose project (the app on host port 8087) is a working stack with your data, and nothing here falls back to it. Start a throwaway stack yourself (its own compose project name and host ports, torn down by you afterwards), then name its two addresses:

```bash
cd e2e
npm install
npm run install:browsers      # one-time: download Chromium
export E2E_BASE_URL=http://localhost:<app> E2E_MAILPIT_URL=http://localhost:<mailpit>
npm test                      # checks the named stack answers, runs the specs, leaves the stack intact
```

- Both variables are required, each an absolute `http(s)` URL (`target.ts` is the one reader of them; no other file under `e2e/` holds a host URL). With one missing, blank or malformed, `global-setup.ts` refuses to run before it makes a single request and names each variable at fault. When the app named by `E2E_BASE_URL` does not answer `/api/v1/ready`, it fails with "not ready: start that stack first"; when the Mailpit named by `E2E_MAILPIT_URL` does not answer `/api/v1/messages` (10 s timeout), it fails with "is not reachable" and names the variable: **Mailpit is REQUIRED**, so the two email specs never skip themselves and a stack without a catcher is a red run, not a silently green one. **The suite starts, builds, stops and tears down nothing** (no `docker` command lives in `stack.ts` or `global-setup.ts`), and it never removes a service or a volume. Tests clean up only the records they own; existing data stays intact.
- **A flaky test fails the run.** CI retries a failed test twice (`retries` in `playwright.config.ts`; 0 locally), and `failOnFlakyTests: true` makes the run exit non-zero when a test passed only on a retry, so a nightly that was green only thanks to a retry is red, uploads its report and opens the "Nightly e2e is failing" issue (`.claude/docs/ci.md` "Failure alerting"). Fix the race; do not raise the retries or turn the option off. `npm run test:setup` pins both the option and the absence of any `test.skip(` in a spec.
- The nightly `e2e.yml` builds the image and starts the stack in their own workflow steps (so the time is attributable per step, `.claude/docs/build-times.md`) and sets the two variables to that stack's published ports (8087 and 8030).
- `E2E_MAILPIT_URL` (the stack's Mailpit; the compose default is host port 8030) is the catcher the two email specs (`mfa.spec.ts`, `password-reset.spec.ts`) read; name the Mailpit of the same stack as `E2E_BASE_URL` (an isolated compose project has its own Mailpit port). Reading another stack's catcher makes those two specs fail.

Docker-free gates ride every spec change — run them before merging, like the web package's lint/knip:

```bash
npm run typecheck             # tsc --noEmit — Playwright only TRANSPILES TS, it never checks it
npm run check:scenarios       # spec ↔ scenario parity: files exist, test() titles == headings
npm run test:setup            # the refusal without a named stack, the readiness check, the source pins
```

`check:scenarios` enforces the same-commit rule mechanically (both directions, orphan files included); every spec is covered, and a template title (`accessibility.spec.ts`) is satisfied by a heading that fits it — the parameterized-title carve-out in [`scenarios/README.md`](scenarios/README.md).

Reports/artifacts land in `playwright-report/` and `test-results/` (git-ignored).

## Parallel execution

The suite runs on **4 workers by default** (`E2E_WORKERS` overrides; the `e2e.yml` `workflow_dispatch` form has a `workers` input for A/B runs; `E2E_WORKERS=1` restores fully-serial behavior). The serial unit is the **spec file** (`fullyParallel: false` — a file's tests may be order-dependent); different files run concurrently. That is only sound because **every spec file owns its server-side state exclusively** — the standing rulebook that any new or edited spec must satisfy:

- Each spec's scenario file declares its **Owns** line. Today: `auth`, `changelog` and `shell` (device-local localStorage only) are read-only; every other spec except `users` also owns its OWN throwaway administrator (`e2e-<spec>-admin-*`, `helpers.specAdmins()`: minted through the seed administrator's API in a `beforeAll`, deleted in an `afterAll` after the file's own teardown, the account its sign-ins use); `accessibility` owns four (`e2e-axe-admin-*`, deleted last; the first opens the pages whose scanned state depends on the reader, the others read the rest in turn), one API-seeded fixture team (`e2e-axe-team-*`), two fixture rooms (`e2e-axe-room-*`, owned by the first administrator, which adds the other three as plain members; one of them archived; the live one holds a seeded `e2e-axe-thread-*` thread) and one fixture teammate (`e2e-axe-mate-*`, a plain user and member of the live room whose messages and reactions fill the thread); `users` owns its throwaway accounts; `teams` owns its throwaway teams (unique `e2e-team-*` / `e2e-ro-team-*` / `e2e-roster-team-*` / `e2e-hnd-*` names, `e2e-h-*` handles) and users; `workflow-templates` owns its throwaway `e2e-tpl-*` templates and user (the seeded Default and Incident are read-only for every spec); `rooms` owns its throwaway `e2e-room-*` rooms, its one `e2e-room-team-*` team and users (cleanup through `deleteViaApi`, rooms first, then the team; every room is created by a throwaway user, never the seed admin, and only copies a seeded template); `room-workflow` owns its throwaway `e2e-room-*` rooms and users (the same cleanup and rules; the administrator writes only to those rooms, through the API); `threads` owns its throwaway `e2e-thr-*` rooms and users (cleanup through `deleteViaApi`, rooms first; every room is created by a throwaway user and only copies the seeded Default or Incident template; threads and messages are never deleted, a room's removal hides them); `find` owns its throwaway `e2e-find-*` rooms and users (one of them an administrator, minted through the seed administrator's API; cleanup through `deleteViaApi`, rooms first, then the users; every room is created by a throwaway user and only copies the seeded Default or Incident template; threads and messages are never deleted, a room's removal hides them; every search word is unique to its run); `live` owns its throwaway `e2e-live-*` rooms and users (cleanup through `deleteViaApi`, rooms first; every room is created by a throwaway user through the API and only copies the seeded Default template; the CSP scenario owns one throwaway user whose socket it watches); `watching` owns its throwaway `e2e-watch-*` rooms and users (cleanup through `deleteViaApi`, rooms first; every room is created by a throwaway user through the API and only copies the seeded Default template; threads are never deleted, a room's removal hides them; the per-user `read-state` and `chat-post` buckets are spent only by throwaway users); `social` owns its throwaway `e2e-soc-*` rooms and users (and, for the preferences scenario, one throwaway user's own switches) (cleanup through `deleteViaApi`, rooms first; every room is created by a throwaway user through the API and only copies the seeded Default template; threads, messages, reactions and pins are never deleted, a room's removal hides them; the per-user `live-ticket`, `chat-post`, `chat-write` and `read-state` buckets are spent only by throwaway users); `i18n` owns its throwaway Polish-language account (never the seed admin's language); `password-reset` owns its throwaway account (its reset requests use unique per-run emails against the in-memory per-email throttle, and both tests together stay under the per-IP 5/min request bucket and the 10/min confirm bucket); `mfa` owns its throwaway accounts and toggles ONLY their MFA flags; `tags` owns its throwaway categories, users and one `e2e-tags-room-*` room (unique names, deleted through the API, rooms before users; it never touches the seeded Kind and Area categories); `list-mutation-refresh` owns its own uniquely named users/teams, created and deleted through the real API; `telemetry` owns one throwaway user (the panel's figures are read-only).
- **Locks.** No spec holds a Playwright lock today. A spec that owns state the others read, or edits global settings, takes one (`test.describe.configure({ lock })`) rather than running at another time; the lock is held by the spec's whole run, and this section lists it.
- **Rate buckets.** Development stacks lift the per-IP login bucket (`security.rateLimit.loginPerMinute`, 1000/min in development vs 10/min in production), so the ~100 sign-ins of a run are not throttled; the two telemetry reads share one per-user bucket of 30 a minute (`telemetry.spec.ts` polls within it); `POST /rooms` and `PUT /rooms/{id}` share a per-user `room-name` bucket (30 a minute) and the member add has its own per-user `room-members` bucket (60 a minute): each spec creates a handful of rooms and adds a few people, and `rooms.spec.ts` and `room-workflow.spec.ts` mint everything as throwaway users, so no bucket is shared or approached; the thread and message POSTs share a per-user `chat-post` bucket (120 a minute), which `threads.spec.ts` stays far below; the other thread and message writes (details, status and owner PUTs, a message edit and delete) share a per-user `chat-write` bucket (240 a minute), also far above any spec; the searches (a room's and the one across rooms) share a per-user `search` bucket (60 a minute) that `find.spec.ts` spends only on its own throwaway users, a handful a scenario; the watch PUT rides its own per-user `thread-watch` bucket (30 a minute) that `watching.spec.ts` spends only on its own throwaway users, a couple of toggles a scenario; the live-socket ticket mint rides a per-user `live-ticket` bucket (60 a minute) and the upgrade a per-IP `live-connect` one (600 a minute). **Every full page load of the SPA mints exactly one ticket** (the shell opens the tab's one socket once; a client-side navigation mints none; `vite dev` mints two per load because React StrictMode runs the mount effect twice, a production build, which the compose stack serves, one), so a test that signs in (`login` loads `/`) and then `goto`s its page spends two. Seventeen specs signing in as the one seed administrator spent its bucket in a full run (163 mints, 116 in the busiest minute; the sweep's own administrator 152, 114: `rate_limit.exceeded bucket=live-ticket` in the server log, no test failed because the socket is not asserted there). Therefore: (1) every spec but `auth`, `changelog`, `shell` and `users` (about 22 mints between them, the seed administrator's only readers) signs in as its own throwaway administrator from `helpers.specAdmins(prefix, count)` (minted through the seed administrator's API, which mints no ticket, in `beforeAll`; deleted in `afterAll`, every one attempted, 204 and 404 pass); (2) `login(page, email, password, landOn)` opens `landOn` as its one load, so a test that goes straight to a page signs in onto it instead of loading `/` first; (3) `accessibility.spec.ts`, which loads ~90 pages in about 80 seconds, takes four administrators (`loginNext` rotates the three that are not the room owner) and signs in onto the page it scans. A full run at four workers now peaks at 23 mints a minute for any one user (the goal is about 30), and the server log carries no `live-ticket` refusal. A new spec that opens more than a handful of pages as an administrator calls `specAdmins` and signs in through it. The notification list (`notification-read`, 240 a minute) and the preferences PUT (`notification-prefs`, 30 a minute) have their own per-user buckets; the live-driven specs re-read the list a handful of times and the preferences specs save once or twice, far below both.

### Logging in

`createUserViaUi()` waits for the one-time password reveal to render before reading the password. A click on Show password alone is not evidence that the mask has been replaced. Every journey that creates a user through this shared helper inherits that synchronization.

`helpers.login()` signs in **without the form** (Flow's build-times.md WHY 37): the real `POST /api/v1/login` through the page's request context, the session written to `localStorage` under the `adder.auth.*` keys the SPA itself persists (`storeSession` in `web/src/api/session.ts`), then one load of `/` (or of `landOn`, the page the test opens first: each load mints a live ticket, so a test that goes straight to a page signs in onto it) — the tokens, the revocation blocklist and any per-request credential check are the server's own, nothing is forged or reused across tests (`signOut` revokes the pair, so a session is minted per call). It takes the seed admin by default or any account's credentials (a throwaway regular user reads the app as one; a spec's own administrator, `specAdmins(...).login(page)`), and falls back to the real form when the login is refused, answers a challenge (MFA) or the shell does not accept the session. `helpers.loginViaForm()` is the real form (clearing any leftover `adder.auth.*` localStorage session first — while one exists, `RedirectIfAuthed` bounces `/login` away and the form never renders): use it where the credential, the form or the language riding the login response IS the subject — `users` (the first sign-in with the revealed password), `password-reset` (the new password), `i18n` (the Polish throwaway and the English admin after it), `auth` and `mfa` (which drive the form inline). Development stacks lift the per-IP login bucket (`security.rateLimit.loginPerMinute`, 1000/min in development vs 10/min in production), so neither path is throttled.

## Deliberately not covered

- **The email digest of unseen notifications** — clock-driven (a delay of minutes, then one mail per recipient); covered by `NotificationDigestTest` (server), with the mail's wording pinned there.
- **Login lockout (429)** — five failed logins would lock the seed admin for 15 minutes in the shared database and poison the rest of the run. Covered by `LoginLockoutTest` (server).
- **Token refresh / expiry (clock-driven)** — real expiry needs clock control; covered by server tests and the `web/src/api/api.test.ts` unit tests.
- **The authz matrix** — covered by the server tests (`GuardsTest`, `AnonymousAccessTest`); E2E asserts only user-visible consequences.
- **Dark-mode rendering** — the palette is theme-owned (`web/src/theme.ts`); `shell.spec.ts` asserts the color-scheme attribute switches and persists, and `accessibility.spec.ts` scans the page sets in the dark scheme (contrast), but no e2e asserts rendered colors, and there is no visual-regression suite.
- **Cross-browser / visual automation** — the suite runs a single **Desktop Chrome (chromium) project** without screenshot comparison. The shell and room-directory specs exercise those layouts at a phone viewport within that project. Accessibility gets the `accessibility.spec.ts` axe smoke.
