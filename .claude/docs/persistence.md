### Persistence

PostgreSQL is the only database. Connection settings come from the `postgres:` block in
`application.yaml` (env-overridable via `POSTGRES_JDBC_URL`, `POSTGRES_R2DBC_URL`,
`POSTGRES_USER`, `POSTGRES_PASSWORD`); defaults match the `docker compose up postgres` service
(host port **5439** — the sibling repos occupy 5432–5438 on the same machine, table in `ci.md`;
in-network consumers use `postgres:5432`). There is one persistence stack:

- **Flyway** (`infra/db/Flyway.kt`) — runs schema migrations from
  `server/src/main/resources/db/migration/` at startup via the Java API, opening a short-lived
  JDBC connection. Migrations are the single source of truth for schema; do not call
  `SchemaUtils.create` anywhere. **An applied migration's bytes are immutable — comments
  included**: Flyway validates stored checksums at startup, so any edit to an existing `V*.sql`
  makes every long-lived database refuse to boot (a failure no fresh-container CI run can see).
  `MigrationChecksumTest` pins every file's checksum; a new migration adds one manifest line, and
  a red pin means REVERT the edit (clarifications go into this doc), never update the pinned
  value. **The one exception, an unreleased migration:** a migration may still change while NO released
  version has applied it (V36 shipped with 1.6.0 and its checksum is now immutable);
  the pin is then re-pinned in the same commit, and a dev database that booted an earlier checksum of such a file is reset (`docker compose down -v`) or repaired (`flyway repair`).
  **The lanes of one release land in any order, so a dev database can apply a later 0.6 migration before an earlier one (V20 before V18, say):** Flyway then refuses the
  lower number (`outOfOrder` is off) and the table it creates is missing, so reset such a database with `docker compose down -v`; a fresh one (a test container, CI) applies them in order.
  The exception ends with the release that contains the file. The range today is **V1–V56**: V1 `users`, V2 `revoked_tokens`, V3 the seed admin, V4 the
  `unaccent` extension, V5 `user_disabled_features` (V1–V5 are Flow's), V6 `teams` (with the optional
  manager), V7 `users.credential_revision`, V8 `password_reset_tokens`, V9 the `ops` telemetry
  schema, V10 `team_members` (the roster), V11 `workflow_templates` (the registry), V12 its two seed rows, V13 the room aggregate (`rooms`, `room_members`, `room_statuses`, `room_fields`), V14 the thread aggregate (`threads`, `messages`, `thread_events`), V15 the hashtag index (`message_tags`, `messages.tags_version`), V16 the search columns (`messages.search` and `threads.search`, the `adder_search` configuration; its GIN index was dropped before release), V17 the mention index (`message_mentions`), V18 the notices (`notifications`), V19 the read state (`room_members.seen_at` and `read_from`, `thread_reads`), V20 the reaction table (`message_reactions`), V21 the room pins (`room_pins`), V22 the digest's claim column and the email switches (`notifications.emailed_at`, `user_notification_preferences`), V23 the history scrub (data only: `thread_events.params`), V24 the per-actor digest budget (`notification_email_budget`), V25 the team mention handle (`teams.handle`, 1.1.0), V26 the thread watches (`thread_watches`, 1.1.0), V27 the notice reshape (`notifications.in_app`, one notice per message and recipient, 1.1.0), V28 the preference choices (`user_notification_preferences.enabled`, 1.1.0), V29 the wide-event budget (`notification_email_budget.broadcasts`, `broadcasts_exceeded_at`, 1.1.0), V30 the group-mention index (`message_group_mentions`, 1.1.0), V31 the thread hashtag index (`idx_message_tags_thread`, 1.2.0), V32 the tag registry (`tag_categories`, `tags` and the Kind and Area seed, 1.2.0), V33 the thread tags (`thread_tags`, 1.2.0), V34 the unseen-notice index by room (`idx_notifications_unseen_room`, 1.2.0), V35 the message quote (`messages.quoted_message_id` and `idx_messages_quoted`, 1.3.0), V36 room access (`rooms.access_type` and `room_join_requests`, 1.6.0), V37 personal room organization (`user_room_organizations`, 1.8.0), V38 room membership notices (1.14.0), V39 the grouped-reply index (1.17.0), V40 the sticky watch preference (`thread_watches.watching`). (The bootstrap renumbered the donor's history; from V10 on, migrations are append-only like any other.)
  V41 links workflow notices to events, V42 adds thread mutes, V43 foreground mention snapshots, V44 browser push, V45 reaction notices,
  V46 thread lifecycle, V47 revisions, V48–V50 chat search and cleanup indexes, V51 notice recipient guards, V52 digest pacing,
  V53 shared live tickets, V54 shared socket leases, V55 refresh replay grace and V56 shared account-attempt limits.
- **Exposed + R2DBC** (`infra/db/Database.kt` + the feature services) — runtime DB access.
  `Database.kt` connects the `R2dbcDatabase` and is the composition root (the chat's services are built by `ChatWiring.kt` beside it, called from `configureDatabase`): it constructs the
  services and publishes them into `Application.attributes` (`UserServiceKey`, `TeamServiceKey`,
  `WorkflowTemplateServiceKey`, `TagCategoryServiceKey`, `RoomServiceKey`, `RoomWorkflowServiceKey`, `TokenBlocklistServiceKey`, `PasswordResetServiceKey` today); each service itself lives next to the feature it serves
  (`users/UserService.kt`, `teams/TeamService.kt`, `rooms/RoomService.kt`, `auth/TokenBlocklistService.kt`, `auth/PasswordResetService.kt`). The Exposed
  table `object`s (e.g. `UserService.Users`, nested inside their service) are used for queries
  only, not DDL. Ids are `UIntIdTable` — unsigned end-to-end (the spec declares `minimum: 0`, and
  `ErrorHandling.kt` 400s negative path segments before kotlinx's `UInt` decoding can silently
  wrap them); one wrinkle inherited from Toadie: V1 creates `users.id` as `BIGSERIAL` (64-bit in
  SQL, 32-bit everywhere above it) while `teams` uses `SERIAL`/`INTEGER` — harmless at this scale,
  documented so nobody "fixes" one to match the other without a migration (an `INTEGER` FK column
  may reference the `BIGINT` id; Postgres compares them fine).

The `org.postgresql:postgresql` JDBC driver is on the classpath solely for Flyway; runtime queries
go through R2DBC.

### Connection pool

- **Applies when:** touching `infra/db/Database.kt`'s connect call, the `postgres.pool.*`
  configuration, or reasoning about how many PostgreSQL backends one Adder instance can hold.
- **Production reserve:** the bounded list, search, notice, and thread-detail caps total 19 with the defaults. Production starts
  only when at least four pool connections remain outside those caps for authentication, writes, and other work.
- **Requirement:** Exposed connects through ONE bounded `io.r2dbc:r2dbc-pool` `ConnectionPool`
  (ported from Lettuce via Flow) wrapping the plain PostgreSQL R2DBC factory, built by the one shared
  `connectPooledDatabase` (the test harness's direct `sharedDatabaseForTests()` uses it too, with a
  small pool of its own) — never a raw `r2dbc:postgresql://` connect, which opens one backend per `suspendTransaction` with nothing
  capping concurrency (measured in Lettuce: 120 parallel requests took ALL 100 backends of PostgreSQL's default `max_connections`;
  the JWT validation's blocklist read failed and surfaced as an invalid token — so a throwing blocklist lookup answers the
  catch-all's 500, never 401, see "JWT model" in `.claude/docs/security.md`).
  Bounds come from `application.yaml`'s `postgres.pool` block, each boot-validated (startup fails
  outside the range, via the shared `infra/config/` `requireConfigInt`/`requireConfigLong` helpers): `maxSize`
  (`POSTGRES_POOL_MAX_SIZE`, default 23, 1..1000), `initialSize` (`POSTGRES_POOL_INITIAL_SIZE`,
  default 2, 0..maxSize — the floor the pool fills up to on its FIRST acquire, not at
  construction: r2dbc-pool warms up lazily and `warmup()` is deliberately not called),
  `maxAcquireTimeSeconds` (`POSTGRES_POOL_MAX_ACQUIRE_SECONDS`, default 10,
  1..600) and `maxIdleTimeSeconds` (`POSTGRES_POOL_MAX_IDLE_SECONDS`, default 600, 1..86400). Every
  pooled connection carries `application_name = adder` (`postgres.pool.applicationName`, test-only
  override), so operators count this instance's backends with
  `SELECT count(*) FROM pg_stat_activity WHERE application_name = 'adder'`. The driver's per-connection
  prepared-statement cache is bounded (`PREPARED_STATEMENT_CACHE_QUERIES` = 256 in `Database.kt`, applied in
  `connectPooledDatabase`, so the test pool has it too; r2dbc-postgresql's default is unbounded and every cached text stays a
  named server-side statement for the connection's life) — it matters because `MultiRowInsert.kt`'s SQL text varies with the row count
  (quantized to a handful of sizes per table). **A multi-row statement is bounded in payload as well as in bind parameters**:
  `MultiRowInsert.kt` also splits a batch so one statement binds at most `MAX_PAYLOAD_CHARS` (1 MiB) of `String` values (a lone
  heavier row goes alone, never refused there). `insertRows` / `insertRowsIgnoringConflicts` build each row (run the caller's body)
  lazily, only while the statement that carries it is assembled, so the rows in flight are one statement's cap, not the call's, and
  each body runs exactly once. Exposed lists every
  statement a transaction ran until it ends (parsed SQL and encoded parameters included): `insertRows` clears the list after each statement.
- **Statement timeouts: use the transaction's `queryTimeout`, nothing else.** Exposed's R2DBC executor *requests* the
  transaction's `queryTimeout` (whole seconds, default 0, never null) from the driver before EVERY statement. The telemetry reads
  use it (`queryTimeout` 5 s, "Telemetry (V9)"). **The per-connection cache (`infra/db/StatementTimeoutCache.kt`).**
  r2dbc-postgresql answers each request with its own `SET STATEMENT_TIMEOUT` simple query that Exposed awaits — a large share of all
  round trips. `connectPooledDatabase` therefore wraps the RAW connection factory (below the pool) in
  `StatementTimeoutCachingConnectionFactory`: each physical connection remembers the value the server last confirmed, and the
  driver call is *sent* only when the requested value differs from it. No reset on release is needed — Exposed requests its
  value before every statement, so the borrower after a 30 s budget sees `0 != 30` and sends it, which is also why a budget
  never leaks to the next borrower. **The hazard it handles:** PostgreSQL reverts a session-level
  `SET` issued inside a transaction when that transaction rolls back, and a statement cancelled by the timeout aborts its
  transaction — a naive cache would then believe the budget is still set and run the next query unbudgeted. The remembered value
  is therefore forgotten on every rollback (also to a savepoint), on a failed commit and on `setAutoCommit(true)`, forgotten
  before a SET is sent and remembered only once it completed under an unchanged generation, and kept across a successful commit.
  **Rule: ONLY the transaction's `queryTimeout` may set the statement timeout.** A `SET LOCAL statement_timeout` may stay in
  force for the rest of its transaction (the cache no longer sends a request that matches its remembered value, so nothing
  overwrites it), and a session-level `SET`, `set_config(…, false)`, `RESET` or `DISCARD` on a pooled connection desyncs the cache
  from the backend. Deployment assumption: one client connection is one server session — a transaction-mode PgBouncer in front of
  Postgres would break the cache (none today). `StatementTimeoutCacheTest` (own one-connection pool) pins convergence, the
  rolled-back SET, the aborted-transaction canary, a budget enforced again after a cancelled statement, and the skip with its limit.
- **Sizing.** Size it as `(maxSize + 1) × replicas + 1` (the `+ 1` per replica is the live listener's connection, "The LISTEN connection" below; the last is Flyway's short-lived JDBC connection, `infra/db/Flyway.kt`) well under
  the server's `max_connections`. `maxAcquireTimeSeconds` is a per-attempt deadline, and the effective
  bound is about 2× the setting. r2dbc-pool 1.0.2's `ConnectionPool` builds `create()` as
  `Mono.defer { acquire.flatMap(…).timeout(maxAcquireTime) }.retry(acquireRetry)` and the builder default is
  `acquireRetry = 1`: the timeout is an ordinary error to `retry`, so a timed-out waiter is
  re-queued at the BACK of the acquire queue for a second full deadline before the failure surfaces. Adder keeps the
  default on purpose: the same retry is what transparently replaces a connection that fails `LOCAL` validation
  (`prepareConnection` invalidates it and the outer retry acquires another), so a connection closed from the driver
  side — a Postgres or pod restart, a FIN/RST on an idle socket — costs no request, whereas with
  `acquireRetry(0)` each such stale connection would fail one. After a Postgres restart the pool therefore heals itself as long as
  at most one stale connection is handed out per acquire; size `maxAcquireTimeSeconds` knowing a saturated pool fails after twice it
  (`ConnectionPoolTest` pins the ~2×). A caller that waits past the acquire deadline fails with the pool's timeout
  exception, which `plugins/ErrorHandling.kt`'s catch-all renders as a logged `500` — deliberately NOT a new declared status, since the
  OpenAPI conformance gate would need it on every operation. The pool is disposed on `ApplicationStopped`, so every `testApplication` the
  suite boots releases its connections. Every background loop (notification sweep, telemetry sampler, tag reindex, the live channel) therefore
  lives in an `Application.backgroundScope(...)` (`infra/BackgroundScope.kt`), which cancels AND joins it (1 s) on `ApplicationStopping`, earlier. Exposed's `R2dbcDatabase.connect(connectionFactory, databaseConfig)` derives the dialect from
  `databaseConfig.connectionFactoryOptions` alone, so the parsed options (still `driver=postgresql`) are threaded into the config
  unchanged while traffic goes through the pool. The same config pins `defaultMaxAttempts = 1`: Exposed would otherwise retry ANY
  `R2dbcException` three times, and the pool's acquire timeout is one — a saturated pool would cost 3 × the acquire budget per request.
  **Dependency alignment:** r2dbc-pool declares an older reactor-pool than the reactor-core Adder resolves, so
  `server/build.gradle.kts` imports the Reactor BOM (`reactor-bom` in `gradle/libs.versions.toml`) as a platform — it pins
  reactor-core, reactor-pool and reactor-netty as one release train, and `:server:checkDependencyAlignment` fails when any
  reactor module resolves to a version other than the BOM's. Move the `reactor-bom` catalog line together with the `netty` pin.
  Covered by `ConnectionPoolTest` (bounded concurrency, a saturated pool's acquire timeout, its ~2× deadline, disposal on
  `ApplicationStopped` and on a later module's failed startup, and the config range-check cases) and `checkDependencyAlignment`'s own Reactor guard.
- **A backend left holding its transaction.** Two defences, both on every pooled connection
  (built in `connectPooledDatabase`, so the test pool has them too). (1) `infra/db/LeakedSocketGuard.kt`: r2dbc-postgresql 1.1.3
  never closes the socket after a protocol-level connection error ("Response queue is full"). The backend then keeps its transaction
  and locks for the life of the process — `idle in transaction`, or `active` in `ClientWrite`, which no server timeout ends. A decorator
  on the RAW factory (below the pool, beside the statement-timeout cache) disposes the netty channel after the driver's close when the
  client is closed but the channel is open; the pool's release validation (`LOCAL`) fails such a connection at once and destroys it. It
  reads two private driver fields by reflection; `LeakedSocketGuardTest` pins them AND the driver bug on an unguarded connection (red
  after an upgrade = the upstream fix landed, delete the guard). (2) `idle_in_transaction_session_timeout`, sent as a startup parameter
  (`postgres.pool.idleInTransactionTimeoutSeconds`, `POSTGRES_POOL_IDLE_IN_TRANSACTION_TIMEOUT_SECONDS`, default 300, 0..86400, 0 = off;
  an operator's own `options=` key in the URL wins): the server ends any pooled session idle inside a transaction for longer — the
  backstop for a client that stopped talking with a transaction open (a coroutine stuck mid-transaction). No transaction may span an
  outbound call or a mail send. It is a different setting from the statement timeout, so the "only `queryTimeout`" rule is untouched.
  `LeakedSocketGuardTest` pins both.
- **A pooled connection must not pin the frame that created it.** reactor-netty keeps the subscriber
  chain of the `create()` that opened a channel on the channel (`ChannelOperations.listener`) for the channel's whole life
  (`maxIdleTimeSeconds` of idleness, never while the connection is reused). Through r2dbc-pool's allocator, the pool's borrower and
  Exposed's `awaitOne` that chain reached the continuation of the coroutine that happened to trigger the creation, so a finished
  request's frame stayed reachable from the netty selector for minutes. `infra/db/DetachingConnectionFactory.kt` ends the chain at a
  bridge: it subscribes to the real `create()` with a `DetachingBridge`, which forwards the one connection / error / completion to the
  pool and then DROPS the pool's subscriber. It offers the driver an EMPTY Reactor context (reactor-netty copies the subscriber context
  into the observer at connect time and keeps the copy for the channel's life). It is the OUTERMOST decorator of the raw factory in
  `connectPooledDatabase` so that a connection it closes is the decorated one (the close reaches the socket guard). It honours demand,
  delivers exactly once and CLOSES a connection nobody owns (it arrived after a cancel): never a leaked socket.
  `PooledConnectionPinTest` proves it with weak references on a fresh pool (a 16 MiB array held across the query, the function returned,
  the connection idle, `System.gc()` must clear it); its callers run on `Dispatchers.IO` (a test that runs the query directly on the
  `runBlocking` thread keeps a stale reference on that thread's own stack and is red either way). `DetachingConnectionFactoryTest`
  pins the contract without a database.
- **Exception:** the pool runs r2dbc-pool's defaults for liveness (`ValidationDepth.LOCAL`, no
  `maxLifeTime`): a connection killed server-side between uses is handed out once and fails that
  request with a 500 — accepted until a deployment introduces an idle killer or proxy.

### Cross-feature table reads AND writes (the service-layer rule, inherited from Lettuce)

A feature service MAY query — or WRITE — another feature's Exposed table objects directly when the
operation must run **inside its own transaction** (SQL joins, atomic snapshots, a single soft-delete that must also close a
dependent row elsewhere) — the transaction boundary must be explicit rather than relying on an unrelated
service to preserve it. Exposed reuses an enclosing transaction for nested `suspendTransaction`
calls on the same database. Route handlers never touch tables (services only). The reads/writes in
place:

- `HomeService` reads the caller's room memberships, rooms and join requests, workflow statuses, threads, watches, messages and read markers
  in one bounded read transaction. The quote query joins author names and uses the shared batched reads for mention metadata.
- `TeamService` reads `UserService.Users` for the manager: the active manager's display name (one
  batched lookup per page), the manager id check on create AND update, and `isActiveManager`'s `Teams` ⋈ `Users` join (the
  team-manager guard). `teams.manager_user_id` has no `ON DELETE` rule: users are only ever soft-deleted;
  a future hard purge of users must clear it first, and a future user RESTORE must clear or re-audit the
  manager grants the user held (a soft-deleted manager's id stays in the column, inert only while the user
  is deleted). A future user RESTORE must also deal with the roster rows the user kept and the 200 cap: a restored user's inert `team_members`
  rows become visible again and could push a team's `memberCount` past the 200 inline `members` list (clear them, or re-check the cap). It also owns the roster (V10): `TeamService.TeamMembers` JOINs `UserService.Users` for every roster read (`members`, the page's
  `memberCount`: the inner join drops a soft-deleted member, so a read never shows an inactive user) and for the add's active-user check
  and the cap count, all inside the roster write's own transaction, which first locks the active team row (`lockActiveForWrite`).
  `team_members.user_id` references `users` with `ON DELETE CASCADE` like every join here (users are only soft-deleted, so the rule
  never fires today). A room's team add reads the roster through `TeamService.activeRosterIds` (ACTIVE users only, null for a missing or deleted team), inside the room write's transaction.
- `RoomService` (V13) READS `UserService.Users` for every member count (`RoomMembers` ⋈ `Users`, the inner join keeps ACTIVE users only, one grouped query per list page) and,
  at creation, reads the template through `WorkflowTemplateService.read` INSIDE the room's own transaction (Exposed reuses the enclosing one), so the room, its
  OWNER row and the copy of the template's statuses and fields commit or roll back together; it writes only its own tables (`RoomWorkflowService` owns
  `room_statuses` and `room_fields`, and `RoomService.create` calls its `copyFromTemplate`). `rooms/` imports `workflows/` and `users/`; neither imports `rooms/`
  (`PackageBoundaryTest`). `room_members.user_id` references `users` with `ON DELETE CASCADE` like every join here (users are only soft-deleted, so it never fires);
  a future user RESTORE makes a restored user's inert membership rows visible again, so it must re-check the 500-member cap of every room they sit in AND treat the OWNER roles they bring back (a restored user may suddenly be the active OWNER of a room that had none, or one of several): clear or re-audit those roles instead of letting the restore silently re-grant ownership. `RoomMemberService` (0.2.0 C8) owns the membership writes (the only writer of
  `room_members` after `RoomService.create`'s OWNER row): every one runs inside `withRoomWrite`, so the room lock makes the 500-member cap (counted over ACTIVE users) and the last-OWNER
  count race-free. It READS `UserService.Users` (the active-user check of every named id, and the join under the member list, the cap count and the last-OWNER count) and, for a team add,
  `TeamService.activeRosterIds` (a `TeamService` method called inside the room's own transaction, Exposed reusing the enclosing one), so the roster SNAPSHOT and the rows it becomes
  commit together. The add is ONE multi-row `insertRows` after the existing members are subtracted (so the primary key is never hit), the last-OWNER rule is the last-admin check's shape
  (`UserService.updateGuarded`) without its row locks: "another `OWNER` joined to an active user exists" under the room lock. A member's removal is a hard `DELETE` of the row.
- `ThreadService` (V14, 0.3.0 S2) reads `UserService.Users` directly for display names (one batched `id IN (...)` lookup per list page or read: the owner, the creator and the users held by USER fields,
  soft-deleted accounts included, since a name outlives the account) and writes only its own `threads` and, through `MessageService.insertInTransaction` and `ThreadEventService.record`, `messages`
  and `thread_events`, all inside the create's ONE transaction under `withRoomWrite`, so a thread, its opening message and its `CREATED` event commit or roll back together. **Room data comes
  only through the `rooms/` services, never their tables:** `RoomWorkflowService.snapshot` (the room's statuses and fields, retired included), `RoomMemberService.activeMemberIds`
  (the active members among a set of ids) and `RoomService.touchActivity` (the room's `last_activity_at`), each running INSIDE the caller's transaction (Exposed reuses it). The history reads
  `UserService.Users` through the shared `infra/db/EventLog.kt` (the actor's name and deleted flag, joined in the rows' own transaction): `infra/` may not name `users/`, so `threads/` passes the
  table and its two columns in as an `EventLogActor`. `threads/` imports `rooms/`, `users/` and `workflows/`; `rooms/` never imports `threads/` (`PackageBoundaryTest`).
- `MessageService` (V15) WRITES `message_tags` through `MessageTagService` (its own package) inside the message's own write transaction under the room lock: `insertInTransaction` indexes a new body, an edit rewrites a changed tag set, a delete clears it. The tag list and the list filter read `message_tags` by its own `room_id`, never a `rooms/` table; the boot reindex touches `messages` (`tags_version`), reads `threads.room_id` (an inner join, locking the message rows only) and `message_tags`.
- `MessageMentionService` (V17) is a `MessageFollower` of `MessageService`: it WRITES `message_mentions` inside the message's own write transaction under the room lock, takes the room's active members through `RoomMemberService.activeMemberIds` (never `room_members`) and READS `UserService.Users` for the mentioned people's names (soft-deleted accounts included; one grouped read per message page, joined in the rows' own transaction); since V30 it also WRITES `message_group_mentions` and reads teams only through `TeamService` (`mentionableTeams`, `mentionableRosters`, `teamIdsOf`; "Group mentions (V30)"); since 1.3 it judges the author of the message a post quotes with the SAME `activeMemberIds` statement (merged with the mention check) and, for an edit, asks `MessageRef.quotedAuthor()` (one joined read of `messages` against itself, `authorQuotedBy`: `messages` is the chat's own table, no cross-feature read). `ThreadListFilter` reads `message_mentions` by its own `room_id`, `thread_id` and `user_id` (`threadMentionsAny`).
- `ThreadTagService` (V33) WRITES `thread_tags` and UPDATES `threads` (`revision`, `updated_at`) inside the tag save's thread write under the room lock, and READS the registry's `tags` rows through `TagCategoryService.Tags` (the first `threads/` read of `tags/`: names, the retired flag, the live check) in the caller's own transaction, for the save, the page's tags and the `threadTag` filter's names. It writes `thread_events` through `ThreadEventService` and reads no `rooms/` table. "Thread tags (V33)".
- `StaleDerivedRows` (`threads/StaleDerivedRows.kt`, run by the `MessageTagReindex.kt` boot task) DELETES from `message_mentions`, `message_group_mentions`, `message_here_mentions`, `message_reactions`, `room_pins` and `notifications` the rows of messages that are `marked_as_deleted`, walking V50’s partial tombstone index in id order and locking up to 1,000 messages per statement (`FOR NO KEY UPDATE OF messages SKIP LOCKED`), one transaction per batch. It names `notifications` (a `notifications/` table, which `threads/` otherwise reaches only through the `ThreadNotices` port) because the net exists for the messages the port was never told about (a 0.5.x delete); it uses the message indexes, including both partial notice indexes, and it never logs an id.
- `PinService` (V21) writes `room_pins` and reads `threads` (the pinned thread's number, title, status key and `closed_at`, never `fields`), the pinned messages through `MessageService.readInTransaction` and `UserService.Users` for names (`userNames`); it reads no `rooms/` table (the room lock, the archived flag and the member guard come from `withThreadWrite` / `withMessageWrite`). The list's count, rows and messages are separate READ COMMITTED statements in one transaction, so `total` can be one higher than the page for a read that races a delete.
- `NoticeWriter` (V18, `notifications/`, the top layer: the package imports `threads/`, `rooms/` and `users/`, and nothing imports it but the composition root (`ChatWiring.kt`)) is the implementation of the `ThreadNotices` port `threads/` declares and WRITES `notifications` INSIDE the caller's transaction (a message's, a hand-over's or a status move's write, under the room lock): the one insert for all recipients, the deletes and relabels of an edit and of a deleted message, and the "seen" stamps of a thread read; it READS `user_notification_preferences` of the recipients (its own feature's table, one statement, V28). `NotificationService` (same package, same table object) is the read side. `NotificationService`'s list READS `threads` (number and title of the page's threads: `ThreadService.Threads`), `UserService.Users` for the actors' names (`userNames`, soft-deleted accounts included) and the rooms only through `RoomService.memberRooms` (the caller's ACTIVE rooms, one array argument, the search across rooms' shape). The "seen" writes and the retention purge touch only `notifications` and, for the purge, its own `notification_email_budget` (the budget's days before the cutoff's: V24); the notice insert also reads and writes that table (locking the actor's row of the day). No `rooms/` table is read or written; the foreign key to `room_members` is the one link.
- `ThreadSearchService` (V16) reads `threads` and `messages` through their own table objects and the generated `search` vectors through `infra/db/Fts.kt`'s free expressions, `UserService.Users` for the owner and author names (`userNames`) and the rooms only through `RoomService.summary` (one ACTIVE room: id, name, archived) and `RoomService.memberRooms` (the search across rooms: the ACTIVE rooms the caller is an ACTIVE member of, membership only, an ADMIN's too), never a `rooms/` table. It writes nothing. One read transaction under `search.timeoutSeconds` as its `queryTimeout`.
- **`rooms/` reaches threads only through the `WorkflowUsage` port** (`rooms/WorkflowUsage.kt`); `threads/ThreadWorkflowUsage` implements it and writes `threads` (`status_key`, `updated_at`) and `thread_events` ON `rooms`' BEHALF

### Schemas

Adder's PostgreSQL database is split across schemas:

- **`public`** — the foundation tables (`users`, `teams`, `team_members`, `workflow_templates`, `tag_categories`, `tags`, `revoked_tokens`, `user_disabled_features`, `password_reset_tokens`), the
  room aggregate (`rooms`, `room_members`, `room_statuses`, `room_fields`, V13), the thread aggregate (`threads`, `messages`, `thread_events`, V14) and, later, the remaining chat tables (`chat-model.md`). Flyway's own history table also stays here — `flyway.schemas` is left at its default.
- **`ops`** — Adder's own operational telemetry (V9, "Telemetry (V9)" below): the process registry and the metric samples each
  process writes about itself. Numbers and labels only, never user or chat data.

**How Exposed addresses a schema-qualified table.** No Exposed `Schema` object and no
`search_path` override are involved: a table object simply passes the dotted, schema-qualified name straight to the `Table(...)`
constructor — e.g. `object Samples : Table("ops.telemetry_samples")` — and Exposed/R2DBC resolve it as-is, including a cross-schema
FK reference. `CREATE SCHEMA IF NOT EXISTS <schema>` runs in the first migration that needs the schema (V9 for `ops`) — never a
standalone "create schemas" migration.

### Team roster (V10)

`team_members (team_id, user_id)`: composite primary key, `team_id` → `teams` and `user_id` → `users` both `ON DELETE CASCADE`, an index on `user_id`
(Covenant's V6 shape). Reads resolve members through ACTIVE users (the inner join), so neither `members` nor `memberCount` ever shows a soft-deleted
user; a team's inline roster is bounded at 200 (`MAX_TEAM_MEMBERS`, the add's cap counts active members). Every roster write runs in one
transaction that locks the active team row `FOR NO KEY UPDATE` first, which serializes roster writes (a race-free cap and idempotent add) and
a manager change against them. Authorization: `authorization.md`.

### Workflow templates (V11, V12)

`workflow_templates (id, name, description, definition jsonb, revision, created_at, updated_at, marked_as_deleted)`: a registry row plus ONE
`definition` document `{statuses:[…], fields:[…]}` (Toadie's `blueprints.definition` shape; the statuses and fields are not rows, they are replaced
with the document). Stored through `canonicalJson` (`WorkflowTemplateService.encode`), decoded with a tolerant `Json { ignoreUnknownKeys = true }`;
a `CHECK (jsonb_typeof(definition) = 'object')` is the only DB-side shape rule, the Kotlin enums and `workflows/WorkflowRules.kt` are the whitelist
(the V5 rule). Soft-deleted with the partial unique index `uq_workflow_templates_name_active` (`LOWER(name)`, active rows only; its 409 wording is in
`UNIQUE_CONSTRAINT_DETAILS`), so a deleted template frees its name. `revision` (`BIGINT`, `CHECK > 0`, starts at 1) is the `X-Expected-Revision` token:
the PUT locks the active row `FOR NO KEY UPDATE`, THEN compares (`requireRevision`), THEN writes `revision + 1` in the same transaction. A room
COPIES a template at creation (V13), so a template edit or delete never touches a room. **V12** seeds Default and Incident (decision D3) with
`ON CONFLICT DO NOTHING`; their labels are an applied migration's bytes, so they change only through the ADMIN template editor, never by editing V12
(`WorkflowTemplateTest` decodes both seeds through the kernel and pins every label and both languages).
**The enum names inside the document are persisted values and are frozen:** `StatusColour`, `StatusCategory` and `FieldType` constants live as strings
in the JSONB (and, from V13, in room rows), so renaming or removing one needs a data migration, exactly like a persisted enum column. **Rolling back is
lossy across a definition-shape change:** the read is tolerant (`ignoreUnknownKeys`) but the PUT replaces the WHOLE document from the DTOs, so an older
build that reads a newer document and saves it drops the members it does not know. The list counts (`statusCount`, `fieldCount`) are computed in SQL
(`jsonb_array_length`, 0 for a missing or non-array member), so one undecodable document cannot 500 the list.

### Tag categories (V32)

`V32__create_tags.sql` (1.2.0; Hammurabi's V13 without its `adr_tags` join, itself Toadie's): `tag_categories (id, name VARCHAR(60), description VARCHAR(500) NULL, revision BIGINT DEFAULT 1 CHECK > 0, created_at, updated_at, marked_as_deleted)` and `tags (id, category_id -> tag_categories, name VARCHAR(40), marked_as_deleted)`; the join that puts a tag on a thread is V33's `thread_tags`. Nothing existing is rewritten and no older table references the new ones, so a 1.1.0 binary never names them (inert on rollback).

- **Soft delete, both tables** (the convention; `SoftDeletable`): a category frees its name (`uq_tag_categories_name_active`, `LOWER(name)`, active rows only; its 409 wording, "A tag category with this name already exists", is in `UNIQUE_CONSTRAINT_CONFLICTS`). A TAG row is never erased: `uq_tags_name` is unique over EVERY row, retired ones included, on purpose, because the threads that carry a tag (V33) keep a real row to point at. A tag is live exactly while `NOT marked_as_deleted`; dropping it from a category's list, or deleting the category, RETIRES it; adding the same name to a category again REVIVES the same row (same id, so those threads show it live again). A rename is a drop plus an add: a NEW row, the old one stays retired. A tag lives in exactly ONE active category (the one row plus the unique name; `idx_tags_category` is the partial index over live rows). A name is stored NORMALISED (trimmed, whitespace runs collapsed, lower-cased: `normalizedTagName`).
- **The registry lock.** Every registry write (`POST`, `PUT`, `DELETE`) runs in `lockingTransaction` (`infra/db/Locking.kt`, ported with the registry and used by NOTHING else: the room lock, `rooms/RoomLock.kt`, is a different mechanism and untouched): a READ COMMITTED transaction that first runs `LOCK TABLE tag_categories IN SHARE ROW EXCLUSIVE MODE`, which conflicts with itself and so serialises two admins, covers an empty registry (a row lock would not), and leaves ordinary SELECTs free. READ COMMITTED is explicit so a writer that waited sees the prior writer's committed rows before it decides; it is the server's own default and the override is per transaction, so it can leave nothing behind for the pooled connection's next borrower (`TagRegistryBusyTest` reads `transaction_isolation` back on a one-connection pool). **The wait is bounded like the room lock's** (`withRoomWrite`): the lock statement runs under `SET LOCAL lock_timeout = 3000` (`TAG_REGISTRY_LOCK_WAIT_MILLIS`, not configurable; `SET LOCAL` ends with the transaction and is put back to the default once the lock is held), and a wait that outruns it (SQLSTATE `55P03`) is the `429` of the shared type `urn:adder:problem:room-busy` with `Retry-After: 1`, audited `tag_category.busy`, nothing written; `lockingTransaction` itself only lets the `55P03` through (`infra/` may not name `authz`) and `registryWrite` in `TagCategoryRoutes.kt` maps it. `LockingTransactionUsageTest` pins that nothing outside `tags/` calls it. `TagCategoryTest` pins two admins saving one revision at once (one `204`, one `409`) and four claiming one new tag (one `201`, three `409`). Reads (`list`) are plain transactions.
- **`revision`** is the `X-Expected-Revision` token of a category's PUT and DELETE (a stale one is the typed `409`), compared under the lock after existence (a missing category is the route's `404` even when the payload claims a tag another category holds); every PUT and the DELETE bump it. Limits: at most 100 active categories (`400` when full), 1 to 100 tags a category, a name 1 to 60 characters, a description at most 500, a tag 1 to 40 characters of `[\p{L}\p{N}][\p{L}\p{N} ._/+#:-]*` (no comma: the history joins names with one).
- **The seed (V32).** Two categories stamped like V12's rows, tag names being their own stable keys (lower-case English; the registry has no per-language label, unlike a workflow status): **Kind** ("What sort of thread this is": `question`, `decision`, `action`, `announcement`, `postmortem`) and **Area** ("The part of the business a thread touches": `customer`, `security`, `data`, `infrastructure`, `process`). They are an applied migration's bytes: they change only through the ADMIN editor, never by editing V32 once released (`TagCategoryTest` pins the seed through the API, `PopulatedUpgradeTest` over a migrated 1.0.0 database).
- **One order of names.** Tag names sort by CODE POINT (`COLLATE "C"`, UTF-8 byte order; `collateC()` in `infra/db/Sql.kt`) in the database and `CODE_POINT_ORDER` in Kotlin (`tags/TagCategoryService.kt`), never by the server's libc (`a-c` before `ab`) or Kotlin's UTF-16 `sorted()` (which puts a supplementary letter before U+FF41), so a create's answer and a later read agree; categories order by `lower(name)` by code point, then id. A thread's tags (S7) and every other list of tag names sort the same way (the V20 emoji tie-break is the precedent). Names fold CASE, never accents (1.2 A2).
- **Rollback below 1.2.0 (V32).** A 1.1.0 binary never names `tag_categories` or `tags`: nothing to run (the runbook of the whole release is "Thread tags (V33)").
- **Tests clean up by raw delete.** A tag name is unique for ever, so a test removes its own categories and tags with a raw `DELETE` (tags first: the foreign key), never a soft delete (`TestTags.purge`, `TagFixtures.kt`); the seeded Kind and Area are never touched.

### Thread tags (V33)

`V33__create_thread_tags.sql` (1.2.0; Hammurabi's `adr_tags` for a thread): `thread_tags (thread_id -> threads ON DELETE CASCADE, tag_id -> tags, added_at, added_by -> users)`, primary key `(thread_id, tag_id)`, plus `idx_thread_tags_tag (tag_id, thread_id)`. **Delete class: HARD** (a join; every change is a `TAGS_CHANGED` row of `thread_events`). `tag_id` has NO `ON DELETE` rule on purpose: a registry tag is only ever retired, so the key never fires and a hard purge of a tag (a test, never the app) must clear its `thread_tags` first (`TestTags.purge` does). Nothing existing is rewritten and no older table references it, so a 1.1.0 binary never names it.

- **The write** (`ThreadTagService.replace`, `PUT .../threads/{number}/tags`): ONE thread write under the room lock (`withThreadWrite`, the room row is the thread lock; the room lock BEFORE the thread's, as every thread write), shaped like `ThreadStatusService.setOwner`: the whole set as a diff (a delete of the dropped ids, an insert per added one, at most 20), the thread's `revision` and `updated_at` bumped (`last_activity_at` and the room's activity are NOT: 1.2 A4), ONE `TAGS_CHANGED` event, the `thread.updated` hint. The same set again writes nothing. The `ThreadNotices` port is never called.
- **Cross-feature (the list IS the permission).** `ThreadTagService` READS the registry's `tags` rows through `TagCategoryService.Tags` (names, the retired flag, the live check; the first time `threads/` names `tags/`), always inside its own transaction: the write's, or the list's and the read's for `forThreads` (ONE `thread_id IN (...)` statement joined to `tags`, per page, inside the list's `ReadLimiter` budget) and `idsOf` (the `threadTag` filter's names resolved to ids, retired included, one statement). It UPDATES `threads` (`revision`, `updated_at`) and writes `thread_events` through `ThreadEventService`. It reads no `rooms/` table (the lock, the archived flag and the guards come from `withThreadWrite`).
- **The filter.** `threadTag` on the thread list and both searches is a correlated SCALAR probe, `(SELECT 1 FROM thread_tags WHERE thread_id = threads.id AND tag_id IN (<ids>) LIMIT 1) IS NOT NULL` (`threadCarriesAnyThreadTag`; any-of; the primary key `(thread_id, tag_id)` answers each probe), ANDed AFTER the caller's rooms (the list's `room_id`, the searches' `RoomService.memberRooms`: `thread_tags` has no room column, so the tag alone never scopes anything). **Never an `EXISTS` (1.2 branch audit, low):** PostgreSQL may flatten an `EXISTS` into a semi-join that starts from `idx_thread_tags_tag` and reads every thread that carries the tag, in EVERY room, so the answer's time followed the tag's GLOBAL usage (measured on a throwaway postgres:18.6, 1,000,000 threads in 1,000 rooms, the caller in 50 rooms / 50,000 threads, `EXPLAIN ANALYZE`: 15 ms for a tag on half the threads, 0.08 ms for one on 100, 0.01 ms for a tag nobody carries: a caller could read how many threads, in rooms they cannot see, carry a tag). A scalar subquery is never flattened: the same three tags now cost 24, 19 and 18 ms, one primary-key probe per thread of the CALLER's rooms (about 0.4 microseconds a thread, count plus page, inside the search's 5 s budget and the list's), whatever the tag's usage. The price is real and accepted: a rare tag in a very large room set now costs the caller's thread count, not the tag's (50,000 threads is under 25 ms, 500,000 about a quarter of a second); the budgets bound it. **A name the registry never held is probed as the id 0** (`NO_SUCH_TAG_ID`; registry ids are serial from 1) instead of short-cutting to `FALSE`/an empty page with no statement, so "never a tag", "retired" and "unused" run the same statements over the same rows and take the same time (`idsOf` itself is one indexed statement either way). `ThreadSchemaTest` and `ThreadTagSearchTest` pin the plan (a `SubPlan`, never a `Semi Join` nor a `Hash`, and `thread_tags` through an index, for tag ids that are popular, rare and 0, auto and generic) and the statements a never-held name sends; the list's filter and a page's read are index probes of `thread_tags`, never a scan.
- **One order of names.** A thread's tags come out in `CODE_POINT_ORDER` (the registry's, "Tag categories (V32)"), per thread, in Kotlin after the one read, and so do the two sides of a `TAGS_CHANGED` event.
- **A tag retired a moment earlier can still be attached (accepted).** The foreign key takes `FOR KEY SHARE` on the tag row and the registry's retirement is a non-key `UPDATE`, which does not conflict with it, so a save that read the tag live may commit after the registry retired it. Locking the live tags `FOR SHARE` would serialise the two, at the price of a possible deadlock with the registry's multi-row `UPDATE` (the lock order of rows inside one statement is not ours). The outcome is a state the design already allows (1.2 A6): the thread shows the tag struck through, exactly as it would a second later, and the next save drops it. No test pins the race.
- **A rename is a drop plus an add, so a thread keeps the old tag as retired** until its next tag save. A save that still carries a retired tag is a `400` (1.2 A6), so the SPA's picker DROPS retired tags from the set it sends: they are shown with a "will be removed when you save" cue and are not selectable; the first save that touches the thread's tags removes them (`ThreadTagsTest` pins a save that adds a tag to a thread carrying a retired one).
- **Delete order in tests.** A test removes its rooms and then calls `TestTags.purge()` in the SAME `@AfterTest`; `purge` itself deletes the `thread_tags` of its tags first, so the order of the two does not matter.
- **Rollback below 1.2.0 (runbook, the whole release).** A 1.1.0 binary starts against a V34 schema: `thread_tags`, `tag_categories`, `tags` and the two indexes (V31, V34) are unknown to it and inert, a `read_from` raised by "Mark all as read" is a column it has had since V19, and a thread `revision` the tag saves bumped is just a revision. What it CANNOT read is history: `ThreadEventService.list` decodes `event_type` with `ThreadEventType.valueOf`, so every thread that has a `TAGS_CHANGED` row answers its history with a `500` until the rows are gone. **Before starting 1.1.0** run (a one-off scan of `thread_events`, which is small; the deliberate exception to "append-only"):

  ```sql
  DELETE FROM thread_events WHERE event_type = 'TAGS_CHANGED';
  ```

  The tags themselves stay on their threads (`thread_tags` is untouched; 1.1.0 neither shows nor changes them) and the history of those tag changes is gone for good: on the way back UP to 1.2.0 a thread keeps its tags but shows no history line for the ones set before the rollback. Nothing else is needed: 1.1.0 writes no `TAGS_CHANGED` and ignores the rest. **A 1.1.0 binary boots on the V34 schema** because Flyway's default `ignoreMigrationPatterns` is `*:future`: applied migrations V31 to V34 that the old jar does not ship are ignored, not a validation failure; never set `ignoreMigrationPatterns` (or `validateOnMigrate`) in a way that turns that off. `RollbackRunbookTest` pins it: a Flyway over a copy of the V1 to V30 files (the 1.1.0 set, the same bytes), configured as `infra/db/Flyway.kt` configures the app, validates and migrates nothing against the migrated container, and the same set with `*:missing` as the only ignored pattern is refused. **Release-notes line:** *If you roll back from 1.2.0 to 1.1.0, run the `DELETE` of "Rollback below 1.2.0" (`persistence.md`) first, or every thread that had its tags changed answers its history with a 500.* `RollbackRunbookTest` reads the `sql` block of this item from this file and runs it against the migrated container (rolled back): the `TAGS_CHANGED` rows go, every other event stays, the tag rows stay, and a second run deletes nothing.

### Rooms (V13)

The whole room aggregate in ONE migration, so a room never exists without its workflow: `rooms (id, name, description, archived_at, workflow_revision, last_activity_at,
created_at, updated_at, marked_as_deleted)`, `room_members (room_id, user_id, role, added_at)`, `room_statuses` and `room_fields` (the room's own copy of a template's statuses
and fields; `position` is the array index, retired rows keep a stale one). Enum-valued columns (`role`, `colour`, `category`, `type`) carry no CHECK: the Kotlin enum is the
whitelist (the V5 rule), and the enum NAMES are persisted values, frozen like the template document's. Timestamps are epoch-millis `BIGINT`; ids are `SERIAL` (a
`room_id` is `INTEGER`, referencing `users` through `BIGINT`, the teams wrinkle above).

- **`rooms` is soft-deleted with a partial unique name** (`uq_rooms_name_active`, `LOWER(name)` over non-deleted rooms; an archived room keeps its name, a delete frees it;
  the 409 wording is in `UNIQUE_CONSTRAINT_DETAILS`). A clash therefore discloses only that a room of that name exists. `archived_at` (null = active) is state, not deletion.
- **`idx_rooms_last_activity`** (`last_activity_at`, partial over non-deleted rooms) serves the recent-activity sort of the rooms rail and the Rooms page.
- **`room_members` is a hard-delete join** (the `team_members` class: the audit trail holds adds and removals, a re-add must not collide with a dead row, nothing references
  a membership row). A soft-deleted user keeps an inert row; every read resolves members through ACTIVE users (the inner join), and the last-OWNER count (C8) does too (a role change or removal of a soft-deleted user's row is a `404`: it is not an active member).
- **`room_statuses` and `room_fields` are soft-deleted ("retired") with a FULL primary key `(room_id, key)`, deliberately NOT partial**: this is the documented exception to
  "free a unique field on delete". A retired key stays reserved for the life of the room and is revived, never minted twice, so a later thread's history and its
  `(room_id, status_key)` foreign key stay unambiguous. `uq_room_statuses_initial` is a partial unique index (`WHERE is_initial`): exactly one initial status per room, checked
  per row, so a write that moves the initial flag must clear it on every row first (C9).
- **`workflow_revision`** is the `X-Expected-Revision` token of the room workflow's PUT (C9; `BIGINT`, `CHECK > 0`, starts at 1), separate from the room row's own
  `updated_at`: a name edit never moves it.
- **The room lock.** Every write to a room goes through `withRoomWrite` (`rooms/RoomLock.kt`), which selects the ACTIVE room row `FOR NO KEY UPDATE` (the rule of "Row locks vs. FK
  locks" below: child inserts such as members and statuses take `FOR KEY SHARE` on the room, which does not conflict; 0.3 thread and message writes run under `withRoomWrite` themselves, because posting bumps `rooms.last_activity_at` and a lighter lock upgraded by that UPDATE would deadlock two concurrent posters), then re-reads the caller's membership
  and re-runs the route's guard on that locked standing, then runs the write. The role is read AFTER the lock is held (READ COMMITTED gives every statement its own snapshot), so a
  role change that committed while the caller waited is the verdict. The lock transaction also re-reads the CALLER's `users` row (active flag and role): a caller deleted while the write waited is the `404`, an ADMIN demoted meanwhile is judged as a plain user (the token's roles are only a hint); the membership role read joins ACTIVE users. A hard delete of a room (tests only) cascades to members, statuses and fields.
  **The wait for the lock is bounded** (the 0.3.0 security audit's M1): a writer queued behind the room holds a pooled connection while it waits (23 of them by default, with a 10 s acquire timeout), so unbounded waiters could stall every request. `withRoomWrite` therefore runs its first two statements as `SET LOCAL lock_timeout = <rooms.lockWaitMillis>` (default 3000 ms, `$ROOM_LOCK_WAIT_MILLIS`, boot-validated 100..30000 in `configureDatabase` through `requireConfigInt`, recorded per `R2dbcDatabase` by `useRoomLockWait`; a database nobody configured waits the default) and the lock select, and, once the lock is held, `SET LOCAL lock_timeout TO DEFAULT`. A wait that outruns the bound raises SQLSTATE `55P03` (`lock_not_available`; `Throwable.isLockNotAvailable()` in `ErrorHandling.kt`), which `withRoomWrite` alone catches and turns into the audited `room.busy` plus the typed `429 room-busy` with `Retry-After: 1` (`rooms/RoomProblems.kt`; the failed statement aborts the transaction, which rolls back). `lock_timeout` is NOT `statement_timeout`: the "only `queryTimeout`" rule of "Connection pool" stays, and `StatementTimeoutCache` neither sees nor needs to see this setting. `SET LOCAL` lasts to the end of the transaction (commit or rollback), so nothing can leak to the next borrower of the pooled connection, whatever the outcome; lifting it right after the lock is held keeps every other wait of the write (a unique-index wait on a room name, an FK `KEY SHARE` behind a role change) off the bound, so `55P03` can only come from the one place that maps it. `RoomBusyTest` pins it on a ONE-connection pool (the answer at the bound, `SHOW lock_timeout` = 0 afterwards and inside the block). **One lock inside the lock is deliberately unbounded (V24).** A write that makes notices (a mention, a hand-over) locks the ACTOR's `notification_email_budget` row for the day `FOR UPDATE` AFTER the room lock is held and the bound above is lifted, so that wait has no `lock_timeout`: one actor's notice-making writes serialise on the row, and the worst case is the wait for that actor's own in-flight notice-making writes, each a few milliseconds (the row is locked at the end of the write and released at its commit). While they wait, those writes hold their room locks and a pooled connection each. A timeout was NOT added: it would turn a harmless queue of one person's own posts into a failed post (and a `55P03` that `withRoomWrite` would map to `room-busy` for a lock that is not the room's); the actor's per-minute buckets (`chat-post` 120, `chat-write` 240) bound how many such writes can queue at all, and no two actors share a row, so it never couples users. The lock order is always room row then budget row, never the reverse.
- A room's labels are plain single-language text in `label` (`VARCHAR(60)`); `room_fields.options` is a `jsonb` array `[{key,label}]` written through `canonicalJson`
  (`RoomWorkflowService.copyFromTemplate`) and read with a tolerant decoder; `[]` for a kind without options.

### Credential revision (V7)

`users.credential_revision` is an internal nonnegative BIGINT generation, initially zero. Every
password update/reset and conditional bootstrap rotation increments it atomically in SQL with the
hash update. It is carried in signed access and refresh tokens and pending MFA challenges; the per-request access
check (`TokenBlocklistService.accessVerdict`), refresh and MFA acceptance compare it with the current user row.
Soft delete and role changes do NOT bump it (the access check compares the stored role separately; a delete
is `user_gone`). It is not exposed in user DTOs. A password-reset grant (V8) captures it and goes stale when it moves.
`password_changed_at` remains a timestamp, not an authorization boundary.

### Password reset tokens (V8)

`password_reset_tokens`: single-use grants, only the SHA-256 digest of the emailed token is stored (`token_hash` PK), with the
account snapshot (`email`, `credential_revision`) the link was issued against and `expires_at`; `user_id` references `users` with
`ON DELETE CASCADE`. A hard-delete table (expiring credentials, not history — see "Soft delete (convention)"); expired rows are
pruned opportunistically.

### Telemetry (V9)

`ops.telemetry_processes` and `ops.telemetry_samples` (V9; `telemetry/TelemetryStore.kt`, `.claude/docs/observability.md` "Telemetry")
are the tables of the `ops` schema (created by this migration, the "no standalone create-schemas migration" rule). A process row is one
JVM run (`role`, `instance`, `started_at`, `last_seen`, `build_version`/`build_commit`, `processors`, `heap_max_bytes`, nullable
`container_limit_bytes`; unique on `(role, instance, started_at)`; `role` is the constant `"app"` — Adder is one process; the column stays for a future split);
`telemetry_samples` is ONE narrow table for every metric —
`(resolution, metric, ts, process_id, label)` is the primary key (`resolution` = the sample width in seconds: a raw row stores the sampler's real interval, 60..1800 and a divisor of 3600, an hourly rollup 3600 - the tier is `resolution < 3600`; the CHECK enforces it), `n`/`avg`/`max` the figures, so a metric is added in
`TelemetryMetrics.kt` with no migration. Epoch-millis `BIGINT` timestamps, `SERIAL` ids, the cluster section's rows (its marker today) attributed to
the process that took the lock. Writes go through `infra/db/MultiRowInsert.kt`'s `insertRowsIgnoringConflicts`; every statement runs under
the transaction's `queryTimeout`.

**The telemetry prune is a hard-delete exception**: samples are regenerated, high-volume observations with no reader once old, so they
are deleted, not soft-deleted — raw rows older than 7 days, hourly rows older than 90, processes unseen for 90 days (their samples
cascade, `ON DELETE CASCADE`; an index on `process_id` keeps that cascade off a table scan). The prune runs inside the telemetry cluster
transaction under `TELEMETRY_LOCK_KEY`, and a row exactly at its cutoff stays. The tests own the schema:
`TelemetryStoreTest`/`TelemetrySamplerTest` empty `ops` before each test (the suite starts no sampler).

### Team handles (V25)

`teams.handle VARCHAR(30)`, nullable, no backfill, plus `uq_teams_handle_active (handle) WHERE NOT marked_as_deleted`: the optional lowercase token a group mention names a team by (`chat-model.md` "Group mentions"). **Delete class: SOFT, unchanged** (`teams` rows are flagged, never removed): a deleted team stops holding its handle through the partial index, exactly as it frees its name, and nothing needs a purge. ### Thread watches (V26)

`thread_watches (thread_id, user_id, room_id, created_at, watching)`, primary key `(thread_id, user_id)`: a member's own preference for a thread (`chat-model.md` "Watching (V26)"). `watching BOOLEAN NOT NULL` is the effective state; V40 adds it with `DEFAULT TRUE`, retaining every pre-change watch. **Delete class: HARD at the membership/thread boundary**: the preference is updated in place, while `thread_id` references `threads ON DELETE CASCADE` and **`fk_thread_watches_member (room_id, user_id)` references `room_members (room_id, user_id) ON DELETE CASCADE`**, so a watch for a non-member is a `23503`, a leaver's or removed member's preference goes with the row and rejoining starts clean (the `thread_reads` shape). There is no foreign key to `users` of its own: a soft-deleted user's membership row stays, and their preferences are inert (`ThreadWatchService.count`, `list` and `recipientIds` join ACTIVE users and require `watching`). `idx_thread_watches_user_room (user_id, room_id, thread_id)` serves "this person's watches in this room": the list page's one batched read (`WATCHING_AMONG_SQL`, constant text, the array keeps it so) and the `watching` filter's `EXISTS` (`threadWatchedBy`, the `threadMentionsAny` shape); each requires `watching`. The primary key serves the member-only watcher roster and effective audience; the same index serves the membership key's cascade. `ThreadSchemaTest` pins the cascade's shape on that index, auto and generic; the batched read is an index probe (this index or the key, whichever the planner prefers on a given table), never a sequential scan (pinned the same way); and the key, cascades and clean rejoin are pinned too. A preference row's `room_id` is read from its thread in each insert, never passed, so a row cannot name a room its thread is not in.

- **V26 rewrites data once (the backfill).** `INSERT INTO thread_watches SELECT t.id, m.user_id, t.room_id, t.created_at FROM threads t JOIN room_members m ON m.room_id = t.room_id AND m.user_id IN (t.owner_id, t.created_by)`: each existing thread's creator and current owner who still hold a membership row (a soft-deleted member's row included: inert; an owner who left the room gets none; one person who is both joins once) watch it from the upgrade on, stamped with the thread's own creation instant. It makes NO notice. `PopulatedUpgradeTest` runs it over a 1.0.0 database (`populated-v24.sql`) and reads the result through the API.
- **The writer takes NO room lock, and why that is safe.** The toggle (`ThreadWatchService.setWatching`, `PUT .../threads/{number}/watch`) runs ONE short transaction, like the read marker ("Read state (V19)"): it first holds the caller's OWN membership row `FOR KEY SHARE` (`RoomMemberService.holdMembership`; no row is the `404`, never a `500`), then finds the thread, then sets the explicit preference with one upsert, including an explicit off before a watch exists. Repeating the stored choice is a no-op; a member removal (which deletes the row under the room lock) waits for the share lock, so `fk_thread_watches_member` can never fail under an insert. Two holders never block each other (`ThreadWatchTest` holds the member row `FOR KEY SHARE` on a raw connection and the PUT completes), and the transaction never waits for the room lock (pinned with the room lock held on a raw connection).
- **The three auto-watches are written INSIDE thread writes, under the room lock:** `ThreadService.create` (creator), `ThreadStatusService.setOwner` (new owner) and the reply follower (reply author), through `ThreadWatchService.addInTransaction`; each has just judged the person an active member under that lock, so no share lock is needed. `ADD_WATCH_SQL` inserts only a missing row; its conflict is deliberately a no-op, so it never overrides an explicit inactive preference. Explicit Watch is the only way to reactivate it. A same-owner hand-over is a no-op before it gets there.
- **V40 rewrites no data.** `ALTER TABLE thread_watches ADD COLUMN watching BOOLEAN NOT NULL DEFAULT TRUE` keeps every existing row effective. Consumers that mean "currently watches" (`count`, the roster, notice and group-mention audiences, Home, list/search predicates and the batched flags) all require `watching`; raw inactive rows exist only to preserve the explicit choice. **Rollback to a pre-V40 binary:** stop application writes and back up the database. Delete inactive preferences with `DELETE FROM thread_watches WHERE NOT watching` before starting the older binary, which treats all rows as active. Active watches survive. The older app cannot carry the deleted opt-outs forward.
- **Cross-feature reads (the list IS the permission).** `ThreadWatchService` holds the caller's membership row for the TOGGLE through `RoomMemberService.holdMembership`, reads `threads` (the id by room and number), `users` (the active filter of counts and the roster) and, in `recipientIds` (the audience of a notice), `room_members` joined on the composite key `(room_id, user_id)` together with the ACTIVE `users` (a preference of someone who left or was deleted is inert), and writes `thread_watches`; the member-authorized roster goes through the same service. `ThreadService`, `ThreadStatusService` and the message follower write it only through the service; `ThreadListFilter`, `ThreadSearchService` and Home require an active preference by its `user_id`, `room_id`, `thread_id` and `watching`. `rooms/` never reads it.

### Soft delete (convention)

`users`, `teams`, `workflow_templates`, `tag_categories`, `tags` (V32: retired, never erased: "Tag categories (V32)"), `rooms`, `threads` and `messages` are **soft-deleted** (and a room's `room_statuses`/`room_fields` are retired, never removed: "Rooms (V13)"; `thread_events` is append-only: "Threads (V14)") — rows are flagged, never physically removed; every
business entity follows the same convention. Only join/token tables (today: `revoked_tokens`, a
pure token registry, `password_reset_tokens` (V8, expiring single-use credentials, not history), `user_disabled_features`, a pure flag join
whose PUT is a wholesale replace, `room_members` (V13, the room membership join, the same reasoning), `notification_email_budget` (V24, a counter of the day, deleted by the notice retention pass and with its user), `team_members` (V10, the roster join: the audit trail holds the adds and removals, a re-add must not
collide with a dead row, nothing references a membership row; a soft-deleted user keeps an inert row that reads skip), `thread_tags` (V33, a join: every change is a history row, "Thread tags (V33)"), `message_tags` (V15, a DERIVED index rebuilt from the bodies: "Hashtags (V15)"), `message_mentions` (V17, the same reasoning: "Mentions (V17)"), `message_group_mentions` (V30, the same again: "Group mentions (V30)"), `notifications` (V18, a pointer that goes with what it points at and by retention: "Notices (V18)"), `room_pins` (V21, a pointer, removed by unpinning and with its message: "Pins (V21)"), `thread_reads` (V19, a member's view state overwritten in place: "Read state (V19)"), `thread_watches` (V26/V40, a membership-scoped preference updated in place and deleted with membership/thread: "Thread watches (V26)"), `user_notification_preferences` (V22, a flag join with a wholesale-replace PUT, the `user_disabled_features` class: "Notices (V18)"), and the `ops.telemetry_*` samples (the prune above)) hard-delete — a new
hard-delete table needs a documented justification, exactly like Lettuce's exceptions list. Pure operational history with no reader once
old (job queues, samples) may be pruned by a fixed documented retention window, the same shape as the JWT blocklist's opportunistic
pruning of expired `revoked_tokens` rows. To add soft-delete to a new entity, follow the established pattern
(reference implementation: `users/UserService.kt`):

1. **Migration** — `marked_as_deleted BOOLEAN NOT NULL DEFAULT FALSE` in the CREATE (a retrofit
   adds the column plus `CREATE INDEX idx_<t>_marked_as_deleted ON <t>(marked_as_deleted);`).
2. **Exposed table** — declare the table `: UIntIdTable("…"), SoftDeletable` with
   `override val markedAsDeleted = bool("marked_as_deleted").default(false)`; the ONE `active()`
   predicate, `nowMillis()` and `lockActiveForWrite` come from `infra/db/SoftDelete.kt` (no
   private copies).
3. **Filter every read** — `read`, `list`, `count`, and any lookup (e.g. `findWithIdByEmail`) get
   `… and active()`. Apply it in the shared list predicate so the `count()` (total) and the row
   select stay consistent.
   **The one tombstone exception (`messages`, V14):** a deleted message is still LISTED (`MessageService.list` does not apply `active()`: the body is scrubbed to `''`, `deleted_by` is set, the row answers `body: null, deleted: true`), so the conversation keeps its shape and `message_count` never goes down. Everything else skips it: the single read, the edit and the delete (`MessageService.read`, `authorOf`, `withMessageWrite`) filter on `active()` and a deleted message is `404` there. **A quote outlives its message's delete (V35, 1.3):** `messages.quoted_message_id` is a reference between rows of this table, the delete is an UPDATE, so the reference of every quoting message survives it ON PURPOSE and reads as a deleted quote ("Message quotes (V35)"); `ON DELETE SET NULL` fires only on a hard delete.
4. **`delete` flips the flag** — `update({ (id eq id) and (markedAsDeleted eq false) }) { it[markedAsDeleted] = true }`,
   returning the affected-row `Int`; guard `update` mutations the same way. The route maps
   `0 → 404` (the `orNotFound` helper), so a missing-or-already-deleted row is `404` (not `204`)
   and delete stays idempotent in effect — `UserService.deleteGuarded` shows the shape, adding the
   last-admin check inside the same transaction.
5. **Routes need no special-casing** — they key `404`/`204`/`NoContent` off the row-count and the
   `active()`-filtered `read`.

**Freeing a unique business field on delete.** To let a value be reused once its holder is
soft-deleted, use a **partial unique index** over active rows instead of a global `UNIQUE`:
`CREATE UNIQUE INDEX uq_<t>_<col>_active ON <t>(<col>) WHERE NOT marked_as_deleted;`. Skip the
Exposed `.uniqueIndex()` on that column (Exposed defs are query-only — the DB enforces it). A
clash with an **active** row still raises `23505 → 409` (mapped centrally in
`plugins/ErrorHandling.kt`, which names WHAT clashed per constraint — extend
`UNIQUE_CONSTRAINT_DETAILS` when adding a partial unique index). In place today: `users.email`
(`uq_users_email_active`, `V1`) and the team name (`uq_teams_name_active`, `V6` — an expression
index over `LOWER(name)`), the team's mention handle (`uq_teams_handle_active`, V25), the workflow template name (`uq_workflow_templates_name_active`, V11), the tag category name (`uq_tag_categories_name_active`, V32; the tag name `uq_tags_name` is the deliberate non-partial one) and the room name (`uq_rooms_name_active`, V13). A team's two unique fields answer `keys: ["name"]` / `keys: ["handle"]` on the 409 (`UniqueConflict` in `ErrorHandling.kt`), which the SPA marks the field by.

**`infra/db/Sql.kt`** (ported from Lettuce with the first list endpoint): `containsNormalized` —
the case- AND accent-insensitive substring filter over `public.unaccent` (V4); every per-column
substring filter MUST use it. Also `orVanished` (post-commit read-back guard → 500, for every
create that reads its row back).

### Row locks vs. FK locks

PostgreSQL's foreign-key check takes `FOR KEY SHARE` on the REFERENCED row for every child insert and keeps it until the
inserting transaction ends. A long transaction whose inserts reference a parent row therefore holds key-share locks on every parent it
touched for its whole run; `SELECT … FOR UPDATE` on that parent conflicts with `FOR KEY SHARE` and would wait behind it (Flow hit this
with its long-running derive job against team rows; the chat writes — threads and messages referencing a room — are the same shape).

The rule: **lock a row `FOR NO KEY UPDATE` unless the write changes its key.** That mode conflicts with itself and with
`UPDATE`/`DELETE` (writers of the row, e.g. a soft delete racing a child insert, still serialize) but
NOT with `FOR KEY SHARE`, so FK locks never stall it. `lockActiveForWrite` (`infra/db/SoftDelete.kt`,
`FOR NO KEY UPDATE`), `withRoomWrite` (the room row, every room-scoped write; the thread and message inserts reference it), `TeamService.update` and `PasswordResetService.lockUser` (the active `users` row) follow it; none of them touches
`id`, and the unique indexes on these tables are partial or expression indexes (`uq_teams_name_active`, `uq_teams_handle_active`, `uq_users_email_active`), which
PostgreSQL does not count as key columns — a rename is still a non-key update. Plain `FOR UPDATE` is for a row nothing references from a
long transaction (`users` is referenced only by columns no long transaction inserts — `updated_by_*`, `teams.manager_user_id`,
`user_disabled_features.user_id`, `password_reset_tokens.user_id`, and the V14 columns `threads.owner_id`/`created_by`, `messages.author_id`/`deleted_by`, `thread_events.user_id` (short inserts only): `UserService.lockedActiveAdminCount`), or for
`SKIP LOCKED` claims. A new `FOR UPDATE` on an FK-referenced row needs that justification in a comment. Flow pinned both halves with `RowLockVersusDeriveTest` (a writer completes while another transaction holds `FOR KEY SHARE` on the row, and a second `FOR NO KEY UPDATE` writer still waits); Adder re-adds that test with the first long chat transaction.

### `infra/db/Jsonb.kt` and canonical JSON

`infra/db/JsonbOps.kt` holds `jsonbContains` (`@>`), the one jsonb predicate (the thread list's `field` filter).

`infra/db/Jsonb.kt` — a repo-local `jsonb` column type, because `exposed-r2dbc` 1.5.0 ships no
JSON column type of its own. It needs no reflection into the raw `io.r2dbc.spi.Statement`: Exposed
already ships a `JsonColumnMarker` interface plus a `PostgresSpecificTypeMapper` that specifically
recognizes any `IColumnType` implementing it (binding a null via `Statement.bindNull(index,
Json::class)`, a `String` via `Statement.bind(index, Json.of(value))` —
`io.r2dbc.postgresql.codec.Json`) — implementing the marker IS the whole binding. Values are the
caller's JSON text verbatim; PostgreSQL's own `jsonb` storage reformats regardless (whitespace, key
order), so "round-trips" means the same VALUES survive, not the same bytes. **The one exception to "same values" is U+0000**:
PostgreSQL `jsonb` and `text` cannot store a NUL (`unsupported Unicode escape sequence`, SQLSTATE 22P05 for jsonb; `22021` for
text). Every payload that goes through `canonicalJson` (`infra/json/CanonicalJson.kt`) therefore has each U+0000 in a string value AND
in an object key replaced with U+FFFD, before the text is hashed, so the stored text and its sha256 agree (U+FFFD marks that something
was there and cannot merge the tokens around it, which dropping the character would). The helper `String.replaceNul()` (same file)
applies the same rule to free text bound for a `text` column that is not a canonical JSON payload (a database exception's message can
quote the offending value). Covered by `JsonbColumnTest` (insert/select/update, null, nested objects/arrays) and `CanonicalJsonTest`.

`infra/json/CanonicalJson.kt` — canonical JSON for anything stored through `Jsonb.kt`: object
keys sorted RECURSIVELY (arrays keep their own order — position is meaning), rendered via
kotlinx.serialization's compact `JsonElement.toString()`, plus a `sha256Hex` digest of the result.
Two payloads that differ ONLY in object key order canonicalize to byte-identical text, so their
digests agree — this is key-order independence, not general structural equality: canonicalization
does not normalize number spelling (`1`, `1.0` and `1e0` stay distinct token text). The output must stay byte-stable, since stored
text and sha256 are compared against stored rows.

### Threads (V14)

The whole thread aggregate in ONE migration (`V14__create_threads.sql`, whose header comment states the delete class of each table): `threads (id, room_id, number, title, status_key,
owner_id, created_by, fields, revision, message_count, closed_at, last_activity_at, created_at, updated_at)`, `messages (id, thread_id, author_id, body, created_at, edited_at,
marked_as_deleted, deleted_by)` and `thread_events (id, thread_id, user_id, created_at, event_type, params)`. Ids are `SERIAL`, timestamps epoch-millis `BIGINT`, user references
`BIGINT` (the V1 wrinkle). `event_type` carries no CHECK (the Kotlin enum is the whitelist, the V5 rule), and its NAMES are persisted values, frozen like the template document's.

- **Delete classes.** `threads`: never deleted in 0.3 (a thread is closed, not removed; a room's soft delete hides its threads with it). `messages`: soft delete
  (`marked_as_deleted`), because a deleted message stays listed as a tombstone: the body is scrubbed to `''` and `deleted_by` records who removed it (D2: the author, a room OWNER or an
  ADMIN; set on EVERY delete). Three CHECKs pin the shape: a tombstone has an empty body and a `deleted_by`, a live message has a body (1 to 8,000 characters) and none (`ThreadSchemaTest`). `thread_events`: append-only (Toadie's `catalog_file_events` shape: no update, no delete; `user_id` is `ON DELETE RESTRICT`).
  A room's hard delete (tests only) cascades `rooms` to `threads` to `messages` and `thread_events`.
- **The composite status foreign key** `fk_threads_status (room_id, status_key) -> room_statuses(room_id, key)` keeps the default `NO ACTION` (checked at statement end). A room hard delete cascades into `room_statuses` and `threads` in one statement (`TestRooms.purge`); `ThreadSchemaTest` pins that the cascade passes (it passes under `RESTRICT` too on current PostgreSQL, so the choice is the conservative default, not a requirement). It is a backstop: every
  status-setting write holds the room lock and reads the status inside it, so a status in use cannot be retired under a thread write, and statuses are retired with a soft delete
  (never hard-deleted), so the FK can only fail when a write names a status that does not exist: a bug, a 500 (`ErrorHandling.kt` maps only 23505, the unique violation, and 22021, a character the encoding cannot hold; a foreign-key violation 23503 is not mapped).
- **Per-room numbers.** `uq_threads_room_number (room_id, number)`; `MAX(number) + 1` under the room lock, never reused. A clash (a lock bug) is a 23505, mapped to 409.
- **`closed_at` mirrors the status category** (set on a move into a CLOSED status, cleared on a move into an OPEN one) and stays exact because a status in use cannot change category and a
  replacement must have the same one. `message_count` counts every message, tombstones included, and never goes down. `fields` is a `jsonb` object (`CHECK jsonb_typeof = 'object'`) of
  field key to value; retired fields keep theirs. `revision` is the `X-Expected-Revision` token of the details PUT.
- **FK locks on `users`.** The references to `users(id)` (`threads.owner_id`, `threads.created_by`, `messages.author_id`, `messages.deleted_by`, `thread_events.user_id`) take `FOR KEY SHARE` on
  the actor's row for the inserting transaction. The last-admin `FOR UPDATE` on admin rows conflicts with it only for the length of a role change: the "short inserts only" justification of
  "Row locks vs. FK locks".
- **Indexes:** `idx_threads_room_activity (room_id, last_activity_at)` (the list order), `idx_threads_room_status (room_id, status_key)` (the usage counts), `idx_messages_thread (thread_id, id)`
  (the keyset list), `idx_thread_events_thread (thread_id, created_at, id)` (the history's `-createdAt,-id` page).
- The Exposed tables are nested in their services (`ThreadService.Threads`, `MessageService.Messages`, `ThreadEventService.ThreadEvents`); S2 ships the thread list, read and create and the history read; S5 adds `MessageService`'s list (tombstones included, `id[lt]` keyset), single read, post, edit and delete.
- **`MessageService` (S5)** reads `UserService.Users` for author names (soft-deleted accounts included) and writes only `messages`, its own thread's `message_count`/`last_activity_at` and (V15) the message's `message_tags` rows; every write is ONE `withThreadWrite` / `withMessageWrite` under the room lock (`ThreadLock.kt`), the message read joined to its thread with `threads.room_id` = the path's room, so a message of another room is a `404`. A post updates `messages`, `threads` (`message_count + 1`, `last_activity_at`) and, through `RoomService.touchActivity`, `rooms.last_activity_at` on ONE stamp; an edit sets `body`, `edited_at` and `tags_version` only; a delete scrubs the body and sets `marked_as_deleted` and `deleted_by`, and neither bumps the count or the activity.
- **The follower seam.** Whatever is derived from a message's body or lifecycle is written by a `MessageFollower` (`threads/MessageFollower.kt`, `internal`), never by a new line in `MessageService`: a post, a thread's opening message (`insertInTransaction` takes the thread's number for the `MessageRef`), an edit and a delete each call every follower INSIDE the write under the room lock, AFTER the row's own statement, the thread and room counters and the write's own live hint (`message.posted`, `thread.created`, `message.edited`, `message.deleted`), so a follower that throws rolls the message back, a follower may read the new row, and a hint a follower emits (`notification.created`) follows the write's own on the wire. `MessageService.insertInTransaction` inserts the row and its tags and answers an `InsertedMessage`; the caller runs `followPosted` once its counters and hint are written (the post and the thread create both do, `MessageDerivedRowsTest` pins both). `posted` and `edited` answer the ids of the people the follower notified; the service hands their union to the route (`PostedMessage`, `MessageEdit`, `CreatedThread` carry it as `notified`, never in a response body). The hashtag index (V15) is still `MessageService`'s own call; the mention index (V17) is the first follower (it also calls the `ThreadNotices` port, so a mention's notice is made in the same transaction) and `MessageService` always runs it before any other; a table that references `messages` is cleared by a follower, and `MessageDerivedRowsTest` asks `pg_constraint` which tables those are and asserts a deleted message has no row in any. An edit whose body is the same as the stored one calls no follower (and writes no hint): there is nothing to re-derive. The body parsers share one Markdown pre-pass, `threads/MarkdownText.kt` (`textOutsideCodeAndLinks`).

### Room access and join requests (V36)

`rooms.access_type` is fixed at creation. The column default `RESTRICTED_HIDDEN` applies to existing rows and to inserts by a binary
that predates V36. The directory filters discovery before returning rows. Room content authorization still uses the caller's membership
and restricts the global ADMIN exception to visible rooms.

`room_join_requests` stores one attempt per room and user. Requests have a generated id. Reapplying after rejection replaces the rejected
record under the room lock and creates a fresh id, so a stale decision cannot affect a later attempt. Approval and direct addition remove
the request in the membership write transaction. Only requests from active users are listed for owners.

**Rollback below 1.6.0.** V36 adds schema that older builds can leave present. An older binary restores its original access rule, which lets
nonmember administrators read hidden rooms. Use a build with V36 authorization if that privacy guarantee must hold.

### Personal room organization (V37)

`user_room_organizations` holds a private JSONB layout and a positive revision for each account that saves a layout. Reading an account
without a row returns revision 1 and an empty layout. A save locks the account's layout row, compares the revision, and replaces its
groups and placements together. Repeating the same layout at the current revision keeps that revision.

`RoomOrganizationService` checks submitted and returned room IDs against the caller's memberships and nondeleted rooms. Preferences
hold weak room references. Leaving or deleting a room removes it from the reads and allows the next save to omit the old placement.
A user who rejoins before that save can recover the placement. No room lock is needed to save personal organization. V37 adds one table
and needs no backfill. A 1.7.0 binary can run with the new table present.

### Message quotes (V35)

`V35__add_message_quotes.sql` (1.3.0, `chat-model.md` "Quotes (1.3)"): `ALTER TABLE messages ADD COLUMN quoted_message_id INTEGER CONSTRAINT fk_messages_quoted REFERENCES messages (id) ON DELETE SET NULL` and `CREATE INDEX idx_messages_quoted ON messages (quoted_message_id) WHERE quoted_message_id IS NOT NULL`. Nullable with no default (the table is not rewritten), no CHECK (the V15 rule). The Exposed column is `reference("quoted_message_id", this).nullable()` on `MessageService.Messages`; a self-reference leaves every implicit `Messages.innerJoin(Threads)` join as it was (the join key is looked up between the two tables, and the self-key points at neither: `MessageTest`, `PinsTest` and every message write run through those joins).

- **Delete class.** `messages` stays SOFT-deleted (V14, "Soft delete"): a delete is an UPDATE that scrubs the body, so a quoting message's reference survives it ON PURPOSE and every quote of the message then reads `deleted: true` with no text. `ON DELETE SET NULL` fires only on a HARD delete (a test purge, a thread or room cascade) and keeps a quoting row that outlives its quoted row in the same statement (`ThreadSchemaTest` pins both, and that a dangling id is a 23503). `MessageDerivedRowsTest` leaves the self-reference out of "the tables that reference `messages`" (`c.conrelid <> c.confrelid`) because it is not a derived row a delete must clear; the leak a delete must prevent is the quoted TEXT, which no row stores.
- **"Same thread" is not a constraint.** No composite key (it would need a second unique index over `(thread_id, id)` on the hottest table). The WRITE checks the thread under the room lock (`checkedQuote`, ONE statement: `id = ? AND thread_id = ? AND NOT marked_as_deleted`, selecting the author and `SUBSTRING(body, 1, 1001)`), and the READ scopes by thread twice: the one `id IN (...)` read of `quotedMessagesOf` carries `thread_id IN (<the quoting rows' threads>)` AND Kotlin keeps a quoted row only when its thread equals the quoting row's (the pins list reads rows of many threads in one call, so SQL alone cannot say it). `MessageQuotesTest` plants a reference to another thread's message by SQL, in both directions, and reads no quote in the list, the single read or the pins list.
- **The index is the foreign key's own probe.** For every hard-deleted message PostgreSQL runs `UPDATE ONLY messages SET quoted_message_id = NULL WHERE $1 = quoted_message_id`; without the index that is a scan of `messages` per deleted row. It is partial so only quoting messages are in it (a page of the application's own reads never uses it; it will serve "the replies to this message", a `BACKLOG.md` item). `ThreadSchemaTest` pins that the probe (the action's UPDATE and the `FOR KEY SHARE` check) is `Index Scan using idx_messages_quoted`, auto and generic, with the planner restricted as the other plan pins are; measured without any restriction on the 200,000-message table below, the planner chooses it by itself, in the custom and in the generic plan (`Index Cond: (quoted_message_id = $1)`, 2 buffers).
- **Substring over R2DBC.** Exposed's `body.substring(1, 1001)` renders `SUBSTRING(messages.body, 1, 1001)` over R2DBC and bounds what travels (a body is at most 8,000 characters); `MessageQuotesTest` pins the statement text through the driver's query log. The cut itself (`cutQuotedBody`, 1,000 code points) runs in Kotlin for every source, so a row of the page and a row read apart answer alike.
- **Statements a read adds.** A page whose quoted bodies hold no `<@` token sends at most ONE statement more than before (`quotedMessagesOf`: the quoted rows that are not on the page, by `id IN`; none when the page holds them all or quotes nothing). The quoted authors join the page's one names read, and the quoted messages whose CUT body holds `<@` join its mentions read and its group-mentions read: when the page has no `<@` token of its own, those two reads are NEW, and a team mention adds the teams lookup, so the true bound is FOUR statements more (the quote read, the mentions read, the group-mentions read, the teams lookup), pinned by `MessageQuotesTest` with a token-bearing off-page quoted body. The lists a quote carries are the quoted message's own and are empty when no token survived the cut (every source answers alike). The quote check of a post is one statement whether the quote exists or not, so the statement count tells nothing of the cause (`MessageQuotesTest` counts an unknown id, another thread's and a tombstone alike).
- **Measured** (throwaway `postgres:18.6-alpine` at the pinned digest, on its own container and port, V1 to V34 applied by `psql`, then 20 rooms x 1,000 threads x 10 messages = 200,000 messages of about 1.5 KB with their generated search vectors, 718 MB with TOAST, `VACUUM ANALYZE`d; developer laptop under OrbStack): `ALTER TABLE messages ADD COLUMN ... REFERENCES` **12.9 ms** (the foreign key's validation pass over the heap, every value NULL: about 6.5 ms per 100,000 messages) and `CREATE INDEX idx_messages_quoted` **33.8 ms** (an empty partial index, a second pass: about 17 ms per 100,000), against the plan's stop line of 5 s per 100,000 messages. The index is 8 KB while nothing quotes. **`TestRooms.purge` of one room with one thread of 5,000 messages** (a `DELETE FROM rooms` cascading through threads and messages, one statement, 200,000 other messages in the table): on the V34 schema (master) **51 to 64 ms** (3 runs); on V35 with no message quoting **66 to 70 ms** (3 runs); on V35 with every second message quoting a random earlier message of its thread (2,500 quoting rows, the `SET NULL` action firing for each quoted row deleted) **72 to 85 ms** (6 runs over two batches), so at most 1.6 times master, against the plan's stop line of twice; **without `idx_messages_quoted` the same purge took 138 s** (one table scan per deleted quoted row), which is why the index is not optional. The migration is a fraction of a second at these sizes, so neither the startup probe nor `ktor.application.startupTimeoutMillis` ("Search (V16)") needs changing.
- **Rollback below 1.3.0 (runbook).** Nothing to run. A 1.2.0 binary on the V35 schema boots (Flyway ignores a migration it does not ship, `*:future`; `RollbackRunbookTest` validates the V1 to V34 set against this schema and fails the day the default is turned off), never names the column (its posts carry no quote, its reads show none, the `RETURNING id` insert is unchanged), keeps the index maintained, and soft-deletes a quoted message as before, which reads as a deleted quote on the way back up. A message a 1.2.0 binary HARD-deletes does not exist (the application never hard-deletes one). **The notice kind (1.3 D2, no SQL to run):** a 1.2.0 binary does not know `MESSAGE_QUOTED`, so it does not list or count those notices (its `notification_type IN (<known names>)` whitelist; they sit unseen and invisible until the way back up), its digest drops them (kinds it does not know are claimed and never mailed; the 1.3 default is email off, so nothing was due anyway), and a preferences save under 1.2.0 replaces the person's deviations wholesale, so a switch they set for `MESSAGE_QUOTED` is gone (the kind returns to its default: the app on, email off). Quotes made under 1.3.0 notify nobody under 1.2.0; a reply that quotes still reads as a reply there. **Open tabs:** a 1.3 tab left open on a rolled-back 1.2.0 server gets `400`s on the addressed-notices read (`type=MESSAGE_QUOTED` is unknown to 1.2) and on a quoting post (`quotedMessageId` is an unknown member of its strict request), so after rolling back, users reload their open tabs; everything fails closed and nothing leaks.

### Hashtags (V15)

`V15__create_message_tags.sql`: `message_tags (message_id, thread_id, room_id, tag)`, primary key `(message_id, tag)`, all three foreign keys `ON DELETE CASCADE`, `tag VARCHAR(150)` with `CHECK (char_length(tag) >= 1)`, ONE index `idx_message_tags_room_tag (room_id, tag, thread_id)`; and `messages.tags_version SMALLINT NOT NULL DEFAULT 0` (no CHECK). The table is a DERIVED index of the hashtags in LIVE message bodies (`chat-model.md` "Hashtags (V15)" owns the grammar and the lifecycle).

- **Hard delete, justified.** Nothing references a row, it is rebuilt from the bodies at any time, and a deleted message's tags must not outlive its scrubbed body: a soft-delete flag would keep `#the-leaked-thing` findable. A moderator's delete clears the rows in the delete's own transaction; the cascades take them with a message, a thread or a room (a test purge).
- **The folded key** is `btrim(left(lower(public.unaccent(<kotlin-lower-cased tag>)), 150))`, the same expression on write and on filter (`foldedTagKey`), so a key that folding lengthened past 150 characters (a vulgar fraction becomes up to five: `⅒` is `" 1/10"`, so a 50-character tag can fold to 246) is cut on both sides and still matches itself: an overflow never fails a message write. `unaccent` puts a SPACE before a fraction (`½` is `" 1/2"`), and the cut can end on one, so the key is trimmed: a key never starts or ends with a space (the filter trims its values).
- **`tags_version`** is the grammar version a message's tags were written under (`TAGS_VERSION`, 2; 0 = never indexed). The constant default adds the column without rewriting `messages`, and V15 puts NO CHECK on it (only code writes it, and a new CHECK would scan the whole table under an exclusive lock). Every write of a body sets it; the boot reindex takes the live messages below the current version.
- **The reindex row lock.** `MessageTagService.reindexStale` selects batches of 200 `FOR NO KEY UPDATE OF messages SKIP LOCKED` (the thread rows stay free for the writers), ordered by `id` and keyset-paged (the primary key, no index on the version): a message a writer holds is skipped (the writer sets its own version) and found by the next boot; a writer arriving while a batch holds its row waits for the batch's commit. A batch is one delete and ONE `INSERT ... SELECT ... FROM unnest(<four parallel arrays>) ON CONFLICT DO NOTHING` (the statement text is constant), so the row locks are held for one round trip, not thousands. An edit and a delete run the message's row UPDATE BEFORE touching its tags: that statement is where they wait out a reindex that holds the row, and the tags they then write or clear are the last word (`MessageTagReindexTest` pins the order).
- **One index, chosen by `EXPLAIN`.** Both reads start at one room, so `idx_message_tags_room_tag (room_id, tag, thread_id)` serves them: on a throwaway postgres:18.6 with 100 rooms x 500 threads x 4 messages and ~99,000 tag rows (a room holds ~1,000 of them), the tag list is `Index Only Scan ... Cond: room_id = ?` (0 heap fetches after a VACUUM, 0.2 ms, the grouped count and the substring filter on the same scan), and the thread filter is `Index Scan ... Cond: room_id = ? AND tag = ANY(...)` feeding a semi-join with the room's threads (0.1 to 0.5 ms). A `(thread_id, tag)` index would only serve a per-thread probe, and with the room predicate nothing needs one: there is none, and the `thread_id` foreign key has no supporting index either (a thread is never deleted; only a test purge cascades through one). *[changed] by 1.2 (V31): a per-thread probe now exists, the `hashtags` of a list row, and `idx_message_tags_thread (thread_id, tag)` serves it (below); it also supports the `thread_id` foreign key's cascade.*
- **Rollback below 0.5.0 (runbook).** A 0.4.x binary knows nothing of `message_tags`: a message it DELETES keeps its tag rows, and a message it EDITS keeps its old tags at `tags_version` 1, so neither is seen by the reindex of live messages below the current version. The boot clears the first case by itself (`MessageTagService.purgeDeletedTags`, batches of 1,000 messages, before the reindex, at every boot whatever `threads.tagReindexOnBoot` says); the second needs `UPDATE messages SET tags_version = 0;` before the next 0.5.0 boot (the reindex then rebuilds every message's tags from its body). **Release-notes line:** *If you roll back from 0.5.0 to 0.4.x and later upgrade again, run `UPDATE messages SET tags_version = 0;` before starting 0.5.0, so hashtags of messages edited under 0.4.x are rebuilt (tags of messages deleted under 0.4.x are removed automatically).*
- **A second index for a thread's hashtags (V31, 1.2.0).** `V31__index_message_tags_by_thread.sql`: `CREATE INDEX idx_message_tags_thread ON message_tags (thread_id, tag)`, plain (a SHARE lock on `message_tags` for the build: writes to it wait, reads do not; the table is a row per distinct hashtag of a live message, 123,000 rows built it in well under a second); nothing is rewritten. The thread list and the thread read put `hashtags` on the wire, so ONE constant statement (`MessageTagService.hashtagsOf`, `HASHTAGS_OF_SQL`: `unnest(ids) CROSS JOIN LATERAL` a recursive loose index scan, below) reads a whole page, one bounded probe per listed thread, inside the list's read budget (and the detail read's, since the 1.2 branch audit). V15's room-first index cannot serve a probe by thread (and no longer needs to be the only one), so before V31 the same statement is a sequential scan of the table once per listed thread. *Measured at V31 with the first form of the probe, `SELECT DISTINCT tag ... ORDER BY tag LIMIT 20` (superseded, next item):* on a throwaway postgres:18.6 with ONE room of 300 threads and 69,840 messages (five threads of 5,000 messages, the rest about 150; 123,240 `message_tags` rows, the size the unread statements were measured at, "Read state (V19)"): a page of 50 threads is `Index Only Scan using idx_message_tags_thread ... Index Cond: (thread_id = t.id)` under a `Unique` and a `Limit`, **0.64 to 0.78 ms** after a VACUUM (0 heap fetches), 1.4 to 2.1 ms on a table never vacuumed (11,526 heap fetches), the same plan as a generic one; the five 5,000-message threads alone 0.34 ms (a long thread reads about 1,800 index entries for its 20 distinct keys); one thread, the detail read, 6 buffers; **without the index 150 ms** (a `Seq Scan` of 123,240 rows per thread, 39,250 buffers). The index is 2.2 MB beside the room index's 2.8 MB. `ThreadSchemaTest` pins the probe and its plan (the thread rides the index condition, never the room index nor a scan), auto and generic, on 100 threads and 20,000 rows of one room with the planner left alone (no `enable_seqscan` switch: it chooses the index by itself). A tag an index entry holds is a LIVE message's (a delete removes the rows in its own transaction), so a deleted message's hashtags never reach a row.
- **The probe is a loose index scan, so its cost no longer follows a thread's row count (1.2 branch audit, medium).** V31's first probe, `SELECT DISTINCT tag ... WHERE thread_id = t.id ORDER BY tag LIMIT 20`, stops after 20 DISTINCT keys, not after 20 index entries: a thread with 3 distinct hashtags over 60,000 rows (the detail read sits outside every bucket and ran with no deadline) read every one of its entries. **V31's own comment claims the LIMIT "stops the probe early"; that holds only for a thread with 20 or more distinct tags, and the file is immutable (applied bytes, `MigrationChecksumTest`), so the claim is corrected here and not there.** `HASHTAGS_OF_SQL` now reads each thread's keys with chained probes of the same index: `WITH RECURSIVE keys(tag, n) AS ((SELECT tag, 1 ... ORDER BY tag LIMIT 1) UNION ALL SELECT (SELECT tag ... WHERE thread_id = t.id AND tag > k.tag ORDER BY tag LIMIT 1), n + 1 FROM keys k WHERE k.tag IS NOT NULL AND k.n < 20)`: at most `MAX_THREAD_HASHTAGS` (20) index descents per thread, whatever its row count, and it needs no new index. **Measured** (throwaway postgres:18.6, `EXPLAIN ANALYZE`, index-only, 0 heap fetches after a VACUUM): three threads of 3 distinct tags x 20,000 rows each (60,000 rows a thread): 5.98 ms and all 60,000 entries of each thread read before, **0.06 ms** after (3 first-key descents and 9 chained ones, one entry each); a page of 100 threads with 30 tags x 200 rows each, the case where the old probe was already at its best (it stops after 20 entries): 0.9 ms before, **2.3 ms** after (2,000 descents, the bound); the 300-thread / 69,250-message / 115,417-row spread of this item, a page of 50 (five 5,000-message threads): 1.4 ms before, **0.65 ms** after, one big thread 0.20 ms before and **0.07 ms** after. So the worst page costs about 2.3 ms for a page of 100 threads, a constant, where the old probe's worst case grew with the rows of the heaviest thread. `ThreadSchemaTest` pins the plan of both shapes (the 30-tag spread, and the few-tags-many-rows spread: a `Recursive Union`, never a scan, and no more index entries read than probes made), auto and generic, and the keys the statement returns.
- **Rollback below 1.2.0 (V31).** A 1.1.0 binary never names `idx_message_tags_thread`; it keeps maintaining it through the same inserts and deletes. Nothing to run (V32 and V33 add the rest of the 1.2 runbook, V34 needs nothing, "Tag categories (V32)" and "Thread tags (V33)"; the V31 file's comment that the LIMIT "stops the probe early" is corrected in the item above).
- **No trigger, no SQL parsing.** The parser is Kotlin (`threads/Hashtags.kt` over the shared pre-pass `threads/MarkdownText.kt`): PostgreSQL's regex has no `\p{L}`, its classes follow the database locale, and SQL cannot skip code the way the SPA's Markdown tree does.

### Mentions (V17)

`V17__create_message_mentions.sql`: `message_mentions (message_id, user_id, thread_id, room_id)`, primary key `(message_id, user_id)`, all four foreign keys `ON DELETE CASCADE`, ONE index `idx_message_mentions_user_room (user_id, room_id, thread_id)`. A DERIVED index of the mentions in LIVE message bodies (`chat-model.md` "Mentions (V17)" owns the grammar and the lifecycle); its header comment states the delete class.

- **Hard delete, justified.** The `message_tags` reasoning: nothing references a row, the message's own write rebuilds it from the body, and a deleted message's mentions must not outlive its scrubbed body. `MessageMentionService` (a `MessageFollower`) clears the rows in the delete's own transaction, a moderator's too; a message deleted by a 0.5.x binary after a rollback is cleared by the boot purge `StaleDerivedRows` ("Rollback below 0.6.0"); the cascades take them with a message, a thread, a room or a user (a test purge).
- **No backfill, no version column.** A message written before V17 has no row, so an old literal `<@42>` stays plain text and no reindex exists. `thread_id` and `room_id` are copied from the message's thread (a message never changes thread, a thread never changes room), so the filter starts at one person in one room.
- **The edit diffs against its own rows, not against the old body**: a follower runs after the row was overwritten and sees only the new body. A person already indexed stays mentioned while the token stays, whatever happened to their membership since; a person not indexed yet is added only when an ACTIVE member of the room; an unchanged set writes nothing.
- **Names are not stored**: a read joins `users`, soft-deleted accounts included, so a rename shows at once and a mention of someone who left keeps the name.
- **Rollback below 0.6.0 (runbook).** A 0.5.x binary starts against a V17+ database and knows nothing of `message_mentions`, `notifications`, `message_reactions` or `room_pins`. Every table that references `messages` (`pg_constraint`, as `MessageDerivedRowsTest` asks) is `message_tags` (V15, handled by its own runbook above), `message_mentions`, `notifications`, `message_reactions` and `room_pins`, and none of them is cleared by a 0.5.x write: a message it DELETES keeps its mention, notice, reaction and pin rows, and a message it EDITS keeps its old mention rows and the notices made for them. The boot clears the first case by itself (`StaleDerivedRows.purge`, in the `MessageTagReindex.kt` boot task right after `purgeDeletedTags`, at every boot whatever `threads.tagReindexOnBoot` says: keyset batches of up to 1,000 deleted messages, `FOR NO KEY UPDATE OF messages SKIP LOCKED`, and one statement per batch clearing any stale rows; `StaleDerivedRowsTest`). The second needs SQL BEFORE restarting 0.6.x, because nothing can tell an edited message's mentions from the body (there is no version column and no reindex): with `<rollback start>` the epoch milliseconds at which the first 0.5.x binary started,

  ```sql
  DELETE FROM notifications WHERE notification_type = 'MENTIONED' AND message_id IN (SELECT id FROM messages WHERE edited_at >= <rollback start>);
  DELETE FROM message_mentions WHERE message_id IN (SELECT id FROM messages WHERE marked_as_deleted OR edited_at >= <rollback start>);
  ```

  The first line drops the mention notices (`notification_type = 'MENTIONED'`, the V18 column; a `THREAD_ASSIGNED` notice has no message and is not touched) made for those messages. It cannot tell a notice for a mention that the 0.5.x edit removed from one whose mention still stands, so a notice (seen or not) of someone who is STILL mentioned in an edited message is lost too, and because the second line also drops that message's mention rows, a later 0.6.x edit of it finds no row for anyone and notifies everyone it mentions again. The second drops their mention rows, and the deleted messages' too (the boot purge would do that half itself, it finds a row in any of the four tables, so the order of the two lines does not matter). A message edited under 0.5.x then shows its tokens as plain text (and is not found by `mentionedId`) until it is edited again under 0.6.x; reactions and pins of a LIVE message are still true and stay. Messages posted under 0.5.x carry no row either way (a literal `<@42>` stays text, as before V17). **Release-notes line:** *If you roll back from 0.6.0 to 0.5.x and later upgrade again, run the two `DELETE` statements of "Rollback below 0.6.0" (`persistence.md`) with the time the rollback started before starting 0.6.0, so mentions of messages edited under 0.5.x are not shown stale (rows of messages deleted under 0.5.x are removed automatically).*
- **Read state across a round trip through 0.5.x (V19).** A 0.5.x binary writes no marker and does not move `seen_at`: after the way back up, a post written under 0.5.x has no marker of its author's, so it shows as unread to its own author (and the room's dot may be set for the actor); the next read marker or "room seen" clears it. Nothing is lost or wrong beyond that; no SQL is needed.
- **One index, chosen by `EXPLAIN`** on a throwaway postgres:18.6 (900 threads, 87,250 messages): the filter's `EXISTS` is a `Bitmap Index Scan on idx_message_mentions_user_room` semi-joined with the room's threads, 0.09 ms in the generic plan.

### Notices (V18)

`V18__create_notifications.sql`: `notifications (id, recipient_id, room_id, notification_type, actor_id, thread_id, message_id?, created_at, seen_at?)`, ids and stamps ONLY (no name, title or body column: `chat-model.md` "Notifications (V18)" owns the rules, `security.md` "Notices" the leak rule). Foreign keys: `actor_id`, `thread_id` and `message_id` `ON DELETE CASCADE`; **`fk_notifications_member (room_id, recipient_id)` references `room_members (room_id, user_id)` `ON DELETE CASCADE`**. Indexes: `idx_notifications_created (created_at)` (the retention purge), `idx_notifications_recipient (recipient_id, id)` (the drawer, newest first, a backward scan), `idx_notifications_unseen (recipient_id, id) WHERE seen_at IS NULL` (the badge; replaced by V27's `idx_notifications_bell`) and the unique `uq_notifications_message (message_id, recipient_id, notification_type) WHERE message_id IS NOT NULL` (replaced by V27's `uq_notifications_message_recipient (message_id, recipient_id)`; the insert is `ON CONFLICT DO NOTHING`; a hand-over has no message, so each is its own row). The header comment states the delete class.

- **Hard delete, justified.** A notice is a POINTER, not a record: it goes with what it points at and with the membership it was made for. A message is only soft-deleted, so the message's own write removes its notices by hand (`ThreadNotices.messageRemoved`, a moderator's delete too; an edit calls `reviseMessage`); the cascades take them with a thread, a room, a user (a test purge) and a message row (the one other path: the boot purge `StaleDerivedRows` removes the notices of messages a 0.5.x rollback deleted without calling the port, see the cross-feature list); **the membership key is the leak rule in the schema**: removing a member (a leave, a removal) deletes that person's notices of the room in the removal's own transaction (bounded by one person's rows), and rejoining starts clean. The third way out is retention: `NotificationSweep` deletes rows older than `notifications.retentionDays` (90, 1..3650) at most once an hour, in its OWN scope and transaction after `ApplicationStarted` (`notifications.sweepEnabled` is false in the test harness, `sweepIntervalSeconds` 10..3600 is the tick), never inside a chat write (those hold the room lock).
- **A notice is made inside the write that caused it**, not after it: the insert and its `notification.created` hint commit with the post, the edit or the hand-over, so a rolled-back write announces nothing. The FK needs the recipient to be an ACTIVE member (the mention follower and the owner check already guarantee it, and since 1.3 so does the quoted author's filter in the same follower: `MessageMentionService.posted` judges the mentioned people AND the quoted message's author in ONE `activeMemberIds` statement, so an author who left the room or whose account is deleted is never a recipient and the post still answers 201; any other value is a 23503, never mapped, so a bug is a 500, not a silent notice).
- **No CHECK on `notification_type`** (the V5 rule): the Kotlin enum `NotificationType` is the whitelist, its names are persisted and frozen, and the list predicate `notification_type IN (<known names>)` keeps a name this build does not know invisible and uncounted.
- **Retention is batched and cap-counted.** `NotificationService.purgeOlderThan` deletes in batches of 1,000 (`PURGE_BATCH`), each its own transaction (`LIMIT 1000 FOR UPDATE SKIP LOCKED`, the `MessageTagService.reindexStale` shape), `ORDER BY created_at` straight off `idx_notifications_created` (the one index a retention purge needs: a binary search over the primary key on "ids follow time" was tried and dropped, because it skips an old row that sits behind a younger one). The list's count is `LIMIT 1001` inside (`MAX_COUNTED_NOTICES`), so `total` is capped at 1000, and a page starting at or past that cap is empty with no OFFSET read. `markAllSeen` updates in chunks of 1,000 ids (`SEEN_BATCH`), each its own short transaction, bounded to the newest id at its start. The insert is one `INSERT ... SELECT FROM unnest(CAST(? AS int8[])) ... ON CONFLICT DO NOTHING RETURNING recipient_id` with constant text.
- **The list's statements**: one predicate for the count and the rows in ONE read transaction (`recipient_id = ? AND room_id = ANY(CAST(? AS int4[])) AND in_app [AND seen_at IS (NOT) NULL] AND notification_type IN (<the `type` filter, else every known kind>)`), the rooms first from `RoomService.memberRooms`; since 1.1.0 the read runs through its own `ReadLimiter` (resource `notifications`: the same `threads.readTimeoutSeconds` deadline, a cap of 4 in flight in the process and 2 per user) under the per-user `notification-read` bucket, and a count of 0 skips the page statement. V27's `idx_notifications_recipient_type (recipient_id, notification_type, id) WHERE in_app` serves the `type` filter (partial on `in_app` because every list read filters it; `ThreadSchemaTest` pins it, auto and generic, with the person-only index dropped in a rolled-back transaction because an empty test table would otherwise prefer that one). Measured on a throwaway `postgres:18.6-alpine` (200,000 rows, generic plans): the badge page 0.06 ms (`idx_notifications_unseen`, since replaced by `idx_notifications_bell`), the drawer page 0.02 ms (`idx_notifications_recipient`, backward), the drawer's count 1.2 ms for a person with 3,390 rows, "seen" for one thread 0.1 ms. "Seen" is `UPDATE ... WHERE id = ? AND recipient_id = <caller> AND seen_at IS NULL`; a repeat probes the row once instead of rewriting it.

- **The email digest (V22): claim, then send.** `notifications.emailed_at BIGINT` (null until claimed) and the partial index `idx_notifications_email_due (created_at) WHERE seen_at IS NULL AND emailed_at IS NULL` serve ONE claim statement with constant text (`WITH eligible AS MATERIALIZED (... FROM picked RETURNING ..., rn`, per person so a flooded backlog is one slot AND one digest: every due notice of a taken person within the scan is stamped, the rank says which 50 are read for the mail): unseen, unclaimed, older than `notifications.email.delaySeconds`, younger than a day, of an active account, of a kind whose email switch is on for the person (V28: an opt-in), not of a person already mailed (or skipped) within `minIntervalSeconds` (`<> ALL(array)`); a constant `WITH scanned AS (the oldest 5000 due rows), doomed AS (... FOR UPDATE SKIP LOCKED) UPDATE ... RETURNING` before it, in the same transaction, settles (stamps) the notices among those 5000 of a switched-off kind or a deleted account. **Both statements are bounded**: the 5000-row scans (`DIGEST_SCAN_CAP`; a person beyond them waits for a later tick; rows the claim's filters reject are still walked to find them, which the settle and the timeout bound) and a 10 s `queryTimeout` on the transaction (`DIGEST_STATEMENT_TIMEOUT_SECONDS`; a cancelled statement is logged scrubbed and the run claims nothing). The cap and the timeout are the real bounds; the people limit bounds only the work AFTER the scan. The claim is its own short transaction and commits BEFORE any send; the send happens outside every transaction, preceded by one short read transaction per recipient that re-checks the account, the notice (still there, still unseen), the room membership and the switches (`NotificationDigest.resolve`), so no pooled connection spans an SMTP call. `user_notification_preferences (user_id, notification_type, channel, enabled)` holds the DEVIATIONS from the defaults in code (V28; no row = the default, in-app on and email OFF; `enabled = true` is an opt-in; no CHECK on either name, the Kotlin enums are the whitelists, a name this build does not know is ignored); the PUT replaces under `FOR NO KEY UPDATE` on the user row. `NotificationDigest` reads the other features' tables inside its re-check: `users` (name, email, language of an active user), `threads` (the number only, never the title), `rooms`/`room_members` through `RoomService.memberRooms`, and `userNames` for the actors; it writes only `notifications.emailed_at`. **Stops and failures:** the per-recipient re-check and the send share one catch (audited, not retried); a run ends after 3 failures in a row or on cancellation and RELEASES the claims of the recipients it never attempted (`UPDATE ... SET emailed_at = NULL WHERE id IN (...) AND emailed_at = <this run's stamp>`, in a `NonCancellable` finally, constant shape, one short transaction). What can still be lost: a recipient attempted when the process dies or is cancelled mid-send, and a release that itself failed; the rule stays at most once.
- **The per-actor digest budget (V24, additive).** `notification_email_budget (actor_id BIGINT -> users ON DELETE CASCADE, day INTEGER, recipients BIGINT[], exceeded_at BIGINT, PRIMARY KEY (actor_id, day))` plus `idx_notification_email_budget_day (day)`: one row per actor and UTC epoch day holding the people admitted to the digest (at most `notifications.email.maxRecipientsPerActorPerDay`, so the array is bounded by config). `NoticeWriter.insertNotices` runs INSIDE the write (under the room lock), after the notices' own `INSERT ... RETURNING recipient_id, id`: `INSERT ... ON CONFLICT DO NOTHING` ensures the row, `SELECT ... FOR UPDATE` locks it (writes of one actor in several rooms serialise here, after the room lock, never before it), the first N distinct people reached are saved, the rest are withheld by `UPDATE notifications SET emailed_at = created_at WHERE id = ANY(...)` (V22's settled-never-mailed stamp; no new column on `notifications`). **The row lock is unbounded on purpose** (no `lock_timeout`; the room lock's bound is lifted before it is taken): one actor's notice-making writes serialise on their day's row, the worst-case wait is that actor's in-flight writes (a few milliseconds each), and those writes hold their room locks and connections while they wait; a timeout would fail a person's own post for a lock that protects only their own budget. See "The room lock". Constant statement texts, every parameter cast. **Delete class: HARD** (a counter of the day, not a record): the notice retention pass deletes the days before its cutoff's, and an actor's rows go with the user row. It is deliberately NOT tied to the notices, so a leave, a removal or a message delete cannot reset a budget. Cross-feature: `notifications/` owns the table, reads and writes nothing of another feature's beyond what the notice insert already did. `MigrationChecksumTest` pins the file.

### Search (V16)

**Find in thread (1.10.0).** The existing message index on `(thread_id, id)` supplies both ranges of the context read. Each takes one extra
row to determine whether its side continues. Message search applies one predicate to the count and page, and only the page's hits are headlined.
Both use the existing schema and shared read budgets.

Structured search (1.9.0) uses the same schema and budget. Message predicates share one live-message probe per candidate thread.
Room restrictions are applied before text and filter matching, and only the page's matching messages feed snippets.

- **What V16 is.** `CREATE TEXT SEARCH CONFIGURATION public.adder_search (COPY = simple)` with `unaccent` (V4) as a filtering dictionary in front of `simple` for the six token types that can hold non-ASCII letters; then `search tsvector GENERATED ALWAYS AS (pg_catalog.to_tsvector('public.adder_search'::regconfig, body | title)) STORED` on `messages` and `threads`, and **no index in V16** (an early GIN index on `messages.search` was dropped; V48 adds the scoped index described below). `to_tsvector(regconfig, text)` is IMMUTABLE, so no trigger and no wrapper function is needed, and the `ALTER TABLE` is the backfill. **`STORED` must be written**: on PostgreSQL 18 a bare `GENERATED ALWAYS AS (...)` is VIRTUAL (computed again on every read; an index on it is not supported either; `ThreadSchemaTest` pins `attgenerated = 's'`). Neither vector has an index (`ThreadSchemaTest` pins that too, and that `idx_messages_thread`, the probe's index, exists): the match is a per-thread probe through `idx_messages_thread`, **linear in the searched rooms' own messages**. A tombstone's body is `''`, so its vector is empty; a token of 8,000 characters is skipped with a NOTICE and the INSERT still succeeds.
- **Never in an Exposed table object.** `selectAll()` would read a vector on every message read and the driver has no `tsvector` codec: `infra/db/Fts.kt` names the configuration and every search expression (`ftsVector`, `ftsMatches`, the query text, the headline) and refers to the columns as free expressions. A plain Exposed `insert` answers `RETURNING *`, which would send the vector (about 1.75x the body: 3 KB for a 1.8 KB body) back on every post, so `MessageService.insertInTransaction` uses `insertReturning(listOf(Messages.id))` (`RETURNING messages.id`; `ThreadSearchTest` pins it through the driver's query log). The thread INSERT still answers `RETURNING *` (its vector is the title, at most 200 characters).
- **Measured** (throwaway `postgres:18.6-alpine`, 200,000 messages of about 1.5 KB, 20,000 threads): the migration's `ALTER TABLE messages` took **14.4 s** (about **7 s per 100,000 messages**; the vectors of 1.76 KB Zipf-distributed bodies came to 3.1 KB each, the table 1.17 GB with its TOAST), `ALTER TABLE threads` 51 ms. The first V16 also built a GIN index (0.5 to 4 s, 82 to 214 MB per 200,000 messages: not built any more, so the backfill is the `ALTER TABLE` alone, about 7 s per 100,000 messages; the figures are the measured `ALTER TABLE`s, not re-run without the index, which only subtracted its build). - **The thread statements' plan, chosen by `EXPLAIN` (the search across rooms; the room search shares it).** The rooms come first as ONE array argument (`threads.room_id = ANY(CAST(? The trade is accepted: a rare tag in a huge room set costs what the caller's own threads cost, not what the tag costs. `ThreadTagSearchTest` pins the statement text (a scalar probe with `LIMIT 1`, never an `EXISTS`, rooms first) and the plan for tag ids 1, 7 and 0, custom and generic (`SubPlan`, no `Semi Join`, no `Hash`, no `Seq Scan`, an index of each table, no message table), and that a never-held name sends the same count and page statements as a registry tag nobody carries. **The watched view (1.1, `q` null, `watching=true`)** sends no query-text, snippet or title statement: the count and the page carry `threads.room_id = ANY(<the caller's rooms>) AND EXISTS (SELECT thread_id FROM thread_watches WHERE user_id = ? AND room_id = threads.room_id AND thread_id = threads.id)` (`NOT EXISTS` for `watching=false`), reading no message; `GlobalSearchTest` pins the statement text (the room `ANY` predicate ANDed with the watch probe, no message table, two thread statements) and, under the same generic plan with sequential scans off, that the page's plan names `idx_thread_watches_user_room` (the index is USED; the plan's cost is not measured here). The rooms come from the member-rooms read and the watches are only probed beside them, so a watch of a deleted room is never reached from the room list.
- **Recompute runbook.** The configuration is immutable by promise. After it changes, the stored vectors are stale until `ALTER TABLE messages ALTER COLUMN search SET EXPRESSION AS (pg_catalog.to_tsvector('public.adder_search'::regconfig, body));` and the same for `threads` over `title` rewrite them (no `STORED`: the column already is, and the keyword is a syntax error on PostgreSQL 18.6; `SET EXPRESSION` rewrites the stored vectors; PostgreSQL rebuilds the V48 expression index during the rewrite, so no separate `REINDEX`). A migration that alters the configuration runs both statements in the SAME file. **A PostgreSQL major upgrade** that changes `unaccent.rules` changes no configuration, so nothing in a migration file notices: run the two `ALTER TABLE ... SET EXPRESSION` statements by hand, or ship them in a new migration, with the application down. The cost and the exclusive lock are V16's (the rewrite time above). The configuration cannot be dropped while a column depends on it. A non-superuser owner can create it.
- **Disk space.** The rewrite writes a new `messages` heap and TOAST while the old ones still exist until commit, so plan for free space of roughly the table's old size plus 2.5 times that size (the vectors are about 1.75 times the body). If the volume runs out, the migration rolls back and the pod crash-loops on Flyway until space is freed.
- **Search never logs.** A term, a lexeme or a snippet reaches no log line: a failed statement logs class names and the SQLSTATE only (`security.md` "Log hygiene"), and the cancelled statement is caught in `ThreadSearchService` (`search.timeout`, ids only).

### Read state (V19)

`V19__create_read_state.sql`: `room_members` gains `seen_at` and `read_from` (BIGINT NOT NULL DEFAULT 0, "since joining": every read is `GREATEST(column, added_at)`, so a member row written by any path, a raw test helper too, needs neither named), and `thread_reads (user_id, thread_id, room_id, last_read_message_id, read_at)` is created, primary key `(user_id, thread_id)`, `last_read_message_id > 0` (CHECK), `thread_id` `ON DELETE CASCADE`, **`fk_thread_reads_member (room_id, user_id)` references `room_members (room_id, user_id)` `ON DELETE CASCADE`** (a marker for a non-member is a 23503, a leaver's markers go with the row, so rejoining starts clean). `last_read_message_id` is a position, not a reference: no foreign key to `messages`, so a deleted message needs no cleanup and a tombstone is still a place to have read up to. `chat-model.md` "Unread (V19)" owns the rules.

- **The baseline rewrites data once.** The migration's `UPDATE room_members m SET seen_at = r.last_activity_at, read_from = r.last_activity_at FROM rooms r WHERE r.id = m.room_id` stamps EVERY existing member row once (a small table) with its room's own `last_activity_at`: an instant of the application's clock (no database clock is read, as nothing else in the schema does), at or after every message and activity written so far, since a write stamps its message and its room with the same instant. So after the upgrade nothing already written is unread or new for anybody, and the first message written after it is strictly newer. The two columns are separate on purpose: `seen_at` is "when the member last looked at the room" (the rail's dot), `read_from` is the floor of unread counting (a later "mark all as read" raises it). A dev database that has already run V20, V21 or a later 0.6 migration without this one is reset (the out-of-order rule above); a fresh database applies them in order. `ThreadReadTest` runs the file's own `UPDATE` (scoped to one room) and pins both floors exactly (equal to the room's last activity) and "what existed is read, what comes later is unread".
- **Two writers that take NO room lock, and why that is safe.** The marker route (`ThreadReadService.markRead`) and `POST /rooms/{id}/seen` (`RoomMemberService.markSeen`) run ONE short transaction each, never `withRoomWrite`: they lock only the caller's OWN `room_members` row (`UPDATE ... SET seen_at = GREATEST(seen_at, now)`, which also answers "no row: the caller was removed meanwhile", a 404), then read the thread and the message and upsert the marker. A writer queued behind the room lock holds a pooled connection and thirty readers acknowledging a busy thread would queue behind the room's writers and behind each other; and they emit no NOTIFY (one global commit lock, "NOTIFY" above). They cannot deadlock with a room write, which takes the room row first and the member row second (`touchActivity` sets the actor's `seen_at`; a post's follower upserts the author's marker): the marker transaction never waits for the room lock, so it always finishes and releases the member row; and the `fk_thread_reads_member` check takes only `FOR KEY SHARE` on the member row, which neither this `UPDATE` (a non-key update, `FOR NO KEY UPDATE`) nor another KEY SHARE conflicts with. A member removal (under the room lock) deletes the member row and so waits for a marker write that holds it; one that came first leaves nothing to update, which is why the marker's own foreign key can never fail (never a 500). Every statement is scoped by the caller's id: a write never moves another person's marker.
- **Written by the chat, under the room lock:** a post and a thread's opening message upsert the author's marker (`AuthorReadMarker`, a message follower, always on), and `RoomService.touchActivity(roomId, at, actorUserId)` moves the actor's `seen_at` forward (an ADMIN outside the room has no row, so nothing moves).
- **The statements** (`ThreadUnread.kt`, constant text, the array keeps it so): one list page's counts are `SELECT t.id, (SELECT count(*) FROM (SELECT m.created_at FROM messages m WHERE m.thread_id = t.id AND m.id > COALESCE(r.last_read_message_id, 0) ORDER BY m.id DESC LIMIT 100) recent WHERE recent.created_at > ?) FROM threads t LEFT JOIN thread_reads r ON ... WHERE t.id = ANY(CAST(? AS int4[])) AND t.last_activity_at > ?`; a thread's count and first unread message are the same inner read with `count(*)` and `min(id)`. Both read `messages` BACKWARDS through `idx_messages_thread`, so the `LIMIT 100` stops early (`ThreadSchemaTest` pins the index and the backward scan as an auto and as a generic plan); measured on 300 threads and 69,250 messages: **0.7 ms** for a page of 50 threads (five of them 5,000 messages long, the same plan custom and generic), 0.86 ms when every thread reads its full 100, 0.02 ms for one thread's first unread. The marker is `INSERT ... ON CONFLICT (user_id, thread_id) DO UPDATE ... WHERE thread_reads.last_read_message_id < EXCLUDED.last_read_message_id`: it only moves forward, and is raw SQL (the `INSERT_TAGS` precedent) because it must not depend on how a library renders a conditional upsert.
- **Cross-feature reads (the list IS the permission).** `threads/` reads `room_members` only through `RoomMemberService` (`unreadSince`, `markSeenInTransaction`, and, since 1.2, `markAllReadInTransaction`: the one UPDATE that raises the caller's `seen_at` AND `read_from`); `threads/` reaches the notices only through the `ThreadNotices` port (`threadRead`, and since 1.2 `roomUnseenCeiling` and `roomSeenChunk` for "Mark all as read", which `NoticeWriter` runs in the service's own short transactions); `rooms/` reads `room_members.seen_at`, `added_at` for the caller in the room list and never `messages` or `thread_reads`; `ThreadReadService` writes `thread_reads` and reads `threads` (the id by room and number) and `messages` (the id, that it is the thread's: a tombstone counts), and tells `notifications` through the `ThreadNotices` port (`threadRead`).
- **The unread filter and "Mark all as read" (1.2, no migration).** *The filter:* `GET /rooms/{id}/threads?unread=` is `UNREAD_PREDICATE_SQL` (`ThreadUnread.kt`, constant text spliced into the list's predicate by one `Op`, arguments floor, member, floor): `threads.last_activity_at > floor AND EXISTS (SELECT 1 FROM (SELECT m.created_at FROM messages m WHERE m.thread_id = threads.id AND m.id > COALESCE((SELECT last_read_message_id FROM thread_reads r WHERE r.user_id = ? AND r.thread_id = threads.id), 0) ORDER BY m.id DESC LIMIT 100) recent WHERE recent.created_at > floor)`, the counts' own inner read, so a row it keeps is a row whose `unreadCount` is above 0 (`false` is `NOT` of it; never NULL). The floor is read ONCE per list in `ThreadService.list` (`unreadSince`, null = no read state, `true` is `Op.FALSE`) and shared by the filter, the counts and `mentionsMe`. It is the plain list's own count and page statements with one more conjunct; the planner walks `idx_threads_room_activity`, and each candidate costs one backward probe of `idx_messages_thread` (stops at the first hit) plus a `thread_reads` primary-key probe; `ThreadSchemaTest` pins both, auto and generic. Measured on 300 threads and 69,250 messages (five of 5,000, Bob's marker at the end of every even thread, a floor below everything): the count 1.5 ms, a page of 50 newest-first 0.5 ms (auto) and 1.5 ms (generic plan: a bitmap scan of the room's threads, 300 probes), the same through HTTP as the unfiltered list (about 13 ms median either way, the HTTP and auth share). *Mark all as read:* `POST /rooms/{id}/read-all` is TWO steps with no room lock and no transaction that holds the member row while it settles notices. **Step 1, one short transaction:** `UPDATE room_members SET seen_at = GREATEST(seen_at, now), read_from = GREATEST(read_from, now)` of the caller's own row (no row: `404`; `at` is taken BEFORE the wait for that row, so a notice or message made while it waits is newer than `at`), then the ceiling, `ROOM_UNSEEN_CEILING_SQL` (`max(id)` of the caller's unseen notices of the room, one probe of V34's index). Raising the floor reads EVERY thread of the room (closed and unopened ones too) as read at once, moves no `thread_reads` row, and a message or thread written after `now` is unread again. **Step 2, KEYSET chunks:** the caller's unseen notices of the room are marked seen 1,000 at a time, each chunk its OWN short transaction (`ThreadNotices.roomSeenChunk`, the shape of `NotificationService.markAllSeen`): `ROOM_SEEN_CHUNK_IDS_SQL` (`WHERE recipient_id = ? AND room_id = ? AND seen_at IS NULL AND id > after AND id <= ceiling AND created_at + 0 <= at ORDER BY id LIMIT 1000 FOR NO KEY UPDATE`, read off `idx_notifications_unseen_room`), then `MARK_IDS_SEEN_SQL` (the ids that are still unseen, `recipient_id` named again). `after` is the previous chunk's last id, so chunk k starts past what the earlier chunks stamped and never re-reads their index entries (a stamped row leaves a dead entry until vacuum): each chunk reads at most its own `LIMIT` live entries, so the whole settle is linear in the pile. The loop runs while the chunk SELECTED was full (with the rows locked by the select a short update cannot happen in practice, but the rule costs nothing and a stub test pins it). `id <= ceiling` and `created_at + 0 <= at` (the `+ 0` keeps `idx_notifications_created` out of a generic plan, which a bare `created_at <=` let it pick and walk the table) mean a notice made after the request is never settled by it. **Every kind and channel is settled, a mail-only notice (`in_app = false`) too: that cancels its pending digest, as the read marker does and `markAllSeen` (the bell's own "seen all", in-app rows only) does not.** **One in flight per person** (`ThreadReadService.inFlight`, in-process: it relies on the one-replica rule of `live.md`/`ci.md`, a second replica would allow one call per person each, still bounded by the `read-state` bucket and the pool): a second call is the typed `429` `read-busy` with `Retry-After: 1` and an audited `read.busy` line (`resource=read-all`), so queued calls can never hold the pool; nobody else's call is affected. **After a failure past step 1** the floor stays raised and some notices stay unseen: the client saw an error, the slot is freed, and calling again settles the rest (the ceiling is re-read from what is still unseen); the `room.read_all` line says `complete=false` with the count so far. **Locks:** step 1 holds the caller's member row for a few statements and no notice row; each chunk locks up to 1,000 of the caller's own notice rows in id order as its select reads them (`FOR NO KEY UPDATE`, `NotificationService.markAllSeen` does the same, so the two meet in the same order and a chunk and a "seen all" can never deadlock; one read-all runs per person) for one transaction of a few milliseconds, and NOT the member row, so a room writer (the room row, its ACTOR's member row, a notice row or two) waits at most for a chunk and the settle never waits for a room lock. What is left: (a) a room writer that touches TWO of the caller's notice rows in an order other than id order (a person holds one notice per message and one per thread-level kind, so one write reaches one of them: none known); (b) the V18 `ON DELETE CASCADE` of a MEMBER REMOVAL (under the room lock) deletes all the member's notices of the room in heap order while a chunk holds some of them in id order: PostgreSQL aborts one of the two with `40P01`, and EITHER side may be the victim (the removal is a `500` that the manager retries, the chunk an error that the caller's retry completes); the window is one chunk against one removal of that same person. *Measured* (11 rooms, 5,000 unseen in the target room and 5,000 in each of 10 others, 55,000 seen; `idx_notifications_unseen_room`; before the keyset bound, which only removes re-read entries): the ceiling 0.03 ms (one backward index-only probe), a chunk's id read 0.12 ms (1,000 entries, 19 buffers), **a whole chunk (read, stamp, commit) 5.5 ms**, 5,000 notices in five chunks **28 to 34 ms** of database time and about **100 ms** through HTTP (nine short transactions), 6 to 9 ms when nothing is unseen. `ThreadSchemaTest` pins the statements' plans on a spread of 30 rooms, auto and generic (the index, the `id >` bound, `LockRows`, no sort). *Audited:* one `room.read_all` line after the work (`byUserId`, `roomId`, `settled`, `complete`); no live hint (`ThreadReadAllTest` pins both).
- **`idx_notifications_unseen_thread (recipient_id, thread_id) WHERE seen_at IS NULL`** (also V19, on V18's table). The marker write marks the person's unseen notices of one thread seen (`NoticeWriter.threadRead`, the constant `MARK_THREAD_SEEN_SQL`); V18's `idx_notifications_unseen (recipient_id, id)` would walk all of that person's unseen notices to find one thread's, and this statement runs at the marker's rate (up to 240 a minute) without the room lock. `ThreadSchemaTest` pins the index in the plan of that statement, auto and generic.
- **Known limit: a "seen" stamp is taken at request time.** `seen_at` (room seen, a marker write, the actor's own activity) is stamped when the request runs, while a room write takes its stamp at its start under the room lock and commits later. A post whose stamp is earlier than a "seen" that committed before it can therefore be hidden from the rail's dot (`last_activity_at` not past `seen_at`). The window is one room write (milliseconds, bounded by the lock wait), and the thread counts stay right: they compare message ids with the marker, and a message newer than the floor is counted by id, not by time. **"Mark all as read" has the same limit in both of its halves (1.2).** `read_from` is the request's instant: a message stamped before `at` by a room write that commits after the floor is counted READ for good (its `created_at` is not past the floor), and a thread-level notice (a hand-over, a status move) that COALESCES into an unseen row the person already holds keeps that row's OLD `created_at`, so a status move or hand-over made in the same window can still be settled by the chunks (its `created_at + 0 <= at`); a notice or message made after `at` is never touched.

### Unseen notices by room (V34)

`V34__index_notifications_unseen_by_room.sql`: `idx_notifications_unseen_room ON notifications (recipient_id, room_id, id) WHERE seen_at IS NULL` (1.2.0), the index behind "Mark all as read"'s notice settle (`persistence.md` "Read state (V19)"): V19's `idx_notifications_unseen_thread (recipient_id, thread_id)` leads with the person and then the thread, so finding ONE room's unseen rows through it walks all of the person's unseen notices of every other room; V34 hands over exactly the room's, in id order, so the ceiling is one probe and a chunk reads its own 1,000 entries. A plain partial index on a derived table: nothing is rewritten, it is inert to a 1.1.0 binary (which keeps maintaining it through the same inserts and "seen" updates), and the delete class of `notifications` is unchanged (HARD). `CREATE INDEX` holds a SHARE lock for the build (a notice write waits; reads do not): the index is partial and the table is bounded by the 90-day retention, a fraction of a second. **Rollback below 1.2.0: nothing to run** (the index is unknown to a 1.1.0 binary and may stay). `MigrationChecksumTest` pins the bytes, `PopulatedUpgradeTest` the index on the populated database, `ThreadSchemaTest` the plans.

`V39__index_grouped_reply_notifications.sql`: `idx_notifications_grouped_replies ON notifications (recipient_id, room_id, id) WHERE in_app AND seen_at IS NULL AND notification_type = 'THREAD_REPLIED'` (1.17.0). The grouped bell feed takes at most 5,000 candidates from each known active room through one lateral backward index scan, then keeps the newest 5,000 globally before grouping by room/thread. The room key prevents retained history for a soft-deleted room from widening any active-room scan; work scales with current rooms rather than excluded history and remains under the shared notification-read deadline. A group carries its inclusive minimum and maximum raw notice ids. Its seen write advances an id keyset through only that interval, in 1,000-row transactions and with a hard 5,000-row call ceiling, so older deferred replies, concurrent newer replies and every other kind remain untouched. The index rewrites no row and preserves the notifications table's HARD delete class. Building it takes a SHARE lock, so notice writes wait during the partial-index scan while reads continue. **Rollback below 1.17.0: nothing to run**; an older binary ignores and maintains the extra index. `MigrationChecksumTest` pins the bytes.

`V41__link_workflow_notices_to_events.sql` adds nullable `notifications.event_id` referencing `thread_events(id)` with
`ON DELETE SET NULL` and a partial index on the non-null pointers. A status move or handover creates the event and stores its
pointer in the same transaction, including when an unseen notice is refreshed. The notification feed may read `thread_events`
for its authorized notice IDs on the current page only. The join requires the same thread and extracts only workflow labels or
ownership names. Existing notices keep a null pointer, and older binaries ignore the column.

`V42__create_thread_mutes.sql` adds one `thread_mutes` row per muted thread and member. The thread and the membership keys
cascade on deletion. `ThreadMuteService` holds the member row before writing, and toggles use the unique `(thread_id, user_id)` key.
`NoticeWriter` may read mutes of the current thread before delivery, and `NotificationDigest` may use the member's mute predicate
when resolving threads in a claim. Older binaries ignore thread mutes.

`V44__browser_push_subscriptions.sql` adds `browser_push_subscriptions` (one encrypted provider endpoint, its SHA-256 uniqueness
digest, owning user, credential revision and last registration stamp) and `notification_push_queue` (a hard-delete join of a newly
made in-app notice and the subscriptions active at that instant). The active user row serializes the five-device cap. The notice writer
adds queue rows inside the chat write; the sweep atomically deletes a bounded claim and commits before network I/O. A send-time read
rechecks account/revision, room, membership, unseen state and mute. The queue cascades with either side, claims older than 15 minutes are
settled without sending, endpoints older than 90 days are deleted, and provider 404/410 removes one subscription. Both tables are HARD
delivery state. Explicit unsubscribe removes the browser registration. Logout attempts the same removal before revoking the session.
Physical account deletion cascades. Soft deletion or a credential revision change makes existing registrations ineligible until
retention or re-registration removes them.

### Reactions (V20)

`V20__create_message_reactions.sql`: `message_reactions (message_id, user_id, emoji, created_at)`, primary key `(message_id, emoji, user_id)`, `message_id` and `user_id` `ON DELETE CASCADE`, no other index (the key groups a message's rows by emoji, which is how they are read, and a person's own reactions of a message are found through the same key). V17 to V19 are the other migrations of the same release; the number is never reused or shifted.

- **`emoji VARCHAR(32) COLLATE "C"`.** Equality and order are by BYTES whatever the database's locale: a heart with and without its variation selector are two values, and a thumbs up and the same with a skin tone are two reactions. 32 holds the longest accepted value (the Kotlin rule refuses more than 10 code points and 32 UTF-16 units; a family of four is 7 characters and 25 bytes). `CHECK (char_length(emoji) >= 1)` is the floor only: what counts as ONE emoji is a rule in `threads/Reactions.kt`, never a CHECK (the V5 rule). The value is stored as sent.
- **Delete class: HARD.** A reaction is a join toggled on and off (the audit line holds the changes), nothing references a row, and a re-add must not collide with a dead one. A deleted message (a soft delete, tombstone) loses its reactions in the delete's own transaction through the message follower (`MessageReactionService.follower`), and `MessageDerivedRowsTest` asks `pg_constraint` which tables reference `messages` and proves the delete cleared this one. The rows also go with their message or user (`ON DELETE CASCADE`: a test purge; users are only ever soft-deleted).
- **`MessageReactionService` (V20)** writes `message_reactions` inside ONE message write under the room lock (`withMessageWrite`, the member guard re-run on the re-read caller), so the two limits (20 distinct emoji on a message, 5 of one person's on it) are read and written under the same lock and two writers cannot pass them. It reads `messages` and `threads` through the message write's own row, `UserService.Users` for the reactors' display names (soft-deleted accounts included, `userNames`) and checks the author’s active membership via the room-standing helper. Eligible first reactions notify the author through `ThreadNotices`. A message read attaches the reactions of its page through ONE grouped statement (`GROUP BY message_id, emoji`, `bool_or(user_id = ?)`, the first three reactors by `array_agg(... ORDER BY created_at, user_id)`) inside the read's own transaction; it is the key's prefix scan, so no extra index is needed.

### Pins (V21)

`V21__create_room_pins.sql`: `room_pins (id SERIAL, room_id, thread_id, message_id NULL, pinned_by, pinned_at)`; `room_id`, `thread_id` and `message_id` are `ON DELETE CASCADE` (a test purge, and the rows of a hard-deleted message), `pinned_by` references `users` with no cascade (a user is soft-deleted; the pin keeps saying who made it). Two partial unique indexes, `uq_room_pins_thread (thread_id) WHERE message_id IS NULL` and `uq_room_pins_message (message_id) WHERE message_id IS NOT NULL`, so a thread and one of its messages can both be pinned and nothing is pinned twice; `idx_room_pins_room (room_id, pinned_at)` serves the list. A message pin carries its thread too, for the panel's link. The cap of 50 is code, not a constraint: counted under the room lock (`PinService.change`), so two concurrent writers of one room cannot both take the last place. `chat-model.md` "Pins" owns the rules.

- **Delete class: hard** (a pointer; unpinning removes the row). A message is soft-deleted, so the cascade never fires for it: `PinCleanup`, a `MessageFollower` (`threads/PinService.kt`, registered in `Database.kt`), deletes the message's pin in the delete's own transaction, whoever deletes it; `MessageDerivedRowsTest` proves it through the catalog.
- `PinService` reads `threads` (the number, title, status key and `closed_at` of the pinned thread; never `fields`), reads the pinned messages through `MessageService.readInTransaction` (the ordinary `MessageResponse`, one query, in the list's own transaction) and `UserService.Users` for names; it writes only `room_pins`. A pin is NOT activity: no `rooms.last_activity_at` or thread bump, no history event. Both PUTs are one `withThreadWrite` / `withMessageWrite` under the room lock with the member guard.

### History scrub (V23)

`V23__scrub_history_values.sql` is a DATA-ONLY migration (no DDL, no new object): the user's 1.0.0 decision (2026-11-20, checkup C-SEC-5/C-SEC-6, the 0.3.0 audit's M4) is that the append-only `thread_events` history keeps no raw TEXT or URL value and no title, because a credential pasted into one could never be taken back. The write path stopped recording them first (`threads/ThreadFieldEvents.kt`: an allow-list of the types whose values are recorded; `threadTitleChangedEvent()` and `threadCreatedEvent` carry no title; `chat-model.md` "History"); the migration removes them from the rows already written. Three `UPDATE`s of `params` (JSON TEXT), each touching only the rows that still hold a value:

- **`TITLE_CHANGED`**: `params` becomes `{}` (`from` and `to` both go; the new title is the next rename's `from`, and the thread shows the current one).
- **`CREATED`**: the `title` key is removed (the opening title); `status` and `statusLabel` stay.
- **`FIELD_CHANGED`**: `from` and `to` are removed UNLESS the room's field (`threads.room_id` + `room_fields.key` = `params->>'field'`) is a SELECT, MULTI_SELECT, USER, DATE or NUMBER field. **An allow-list, so doubt scrubs:** a TEXT or URL field, a retired TEXT or URL field (its `room_fields` row stays, the key is never minted twice, and `type` is immutable per key, so today's type is the type at the event), and an event whose field is not found in the room at all are all scrubbed. A retired SELECT/USER/DATE/NUMBER field keeps its stored values: they are hidden at READ time instead ("Retired fields", below), so a revived field gets them back. Another kind's own `from`/`to` (`STATUS_CHANGED`, `CLOSED`, `REOPENED`, `STATUS_REPLACED`) is never touched: the statements name their event type.

**Idempotent**: every statement's `WHERE` selects only rows that still hold a value, so a second run changes nothing (`ThreadHistoryScrubTest` runs the file twice). **The rewritten text** is jsonb's rendering of the same object (key order and one space after each colon differ), which `decodeParams` reads alike; rows the statements do not select are not rewritten at all. **The casts to jsonb cannot fail** on a row the app wrote (`params` is only ever `encodeParams` output, and the one thing jsonb refuses, U+0000, is refused by title and field validation); if one ever did, the migration fails loudly and rolls back whole (Flyway runs it in one transaction), never half-scrubs.

**Lock and duration.** Plain `UPDATE`s: `ROW EXCLUSIVE` on `thread_events` (reads and the appends of any other instance carry on) and a row lock only on the rows rewritten, which nothing else ever updates (the table is append-only; the only other writer is a cascade from a room purge). No batching: a `DO` loop cannot commit inside Flyway's transaction, and nothing waits on these rows. **Measured** on `postgres:18.6-alpine` (the test image), 200 rooms x 500 threads and 1.6 million events (500,000 renames, 500,000 TEXT/URL changes of 200 characters a side, 300,000 SELECT changes, 200,000 status moves, 100,000 creations): the three statements, in file order, took **1.6 s, 0.4 s and 5.3 s (about 7.3 s in all)** in one transaction, rewrote 1.1 million rows and grew the table and its index from 500 MB to 665 MB until vacuum; a second run took 1.4 s and rewrote nothing. A real table is a tiny fraction of that (a member's edits are bucketed at 240 a minute).

**WAL and disk space.** Every rewritten row is a new tuple, so the three statements write WAL and a second copy of each rewritten row's page content until vacuum: plan for free space of roughly the rewritten rows' size again on the data volume (the measured 1.1M rows added 165 MB) plus the WAL they produce (about the same order) and replicas' lag; if the volume runs out the migration rolls back whole and the pod crash-loops on Flyway until space is freed, as for V16's "Disk space".

**Deploy overlap.** The shipped compose file and the Kubernetes `Recreate` strategy (`k8s/app-deployment.yaml`) stop the old instance before the new one starts, so no old binary writes the old shape after V23; the re-run in the rollback runbook below matters only for a rolling deploy elsewhere or a rollback.

**What it does NOT do (say so to whoever asks).** The migration is logical: the old row versions stay in the heap (and in TOAST, and in any backup, replica or WAL archive taken before) until vacuum reclaims them, and autovacuum does that on its own schedule. To remove them physically at once an operator runs `VACUUM FULL thread_events` (an `ACCESS EXCLUSIVE` lock: a maintenance window) and treats older backups as holding the old text. **A secret that was already in a title or a field must still be rotated**: the scrub closes the leak for the future and for the API, not for a copy already taken.

**Retired fields (C-SEC-6).** `GET .../threads/{n}/events` answers a `FIELD_CHANGED` of a RETIRED field without its `from`/`to` (`ThreadService.history` reads the room's retired keys, `ThreadEventService.list` strips them): the entry stays, so the pages and `total` do not change, and the values return with a revived field. It is a read-time filter, not a second scrub, because the values are not secrets (they are option labels, names, dates, numbers) and the workflow editor can revive the field.

**Rollback below 1.0.0 (runbook).** A pre-1.0.0 binary starts against a V23 database without trouble (the migration changed no schema, and it reads the scrubbed rows: an absent `from`/`to` already means "unset" to it, `TITLE_CHANGED {}` shows no old/new line). But it writes the OLD shape for every title and field change made while it runs, and a rolling deploy does the same for as long as an old instance is alive. After the last old instance is gone (or after the way back up from a rollback), re-run the three statements of the file by hand against the database (`psql -f V23__scrub_history_values.sql` is exactly that: idempotent, and Flyway's checksum is untouched, being a run of the file's text, not a `flyway_schema_history` write).

### NOTIFY (live hints, 0.4.0)

Every chat write that changes something emits ONE `pg_notify('adder_live', <LiveHint JSON>)` from `infra/notify/Notify.kt` (`notifyLive`), inside the write's own transaction, right before
its change branch returns (the 15 sites, the catalog and the delivery rules are in `live.md` "Hints"). There is deliberately no hook in `withRoomWrite`: `RoomService.create` is not under
it and several writes return early on a no-op, which must emit nothing. It is a `SELECT 1 FROM pg_notify(...)` whose result is consumed (an R2DBC statement nobody subscribes to never runs;
the `MultiRowInsert.kt` `exec` precedent), so it needs a current transaction, and it holds NO table and writes NO row (no migration).

- **A hint is ids only** (the `LiveHint` type has no text field) and the payload is checked under 8000 bytes before the database sees it (`MAX_NOTIFY_PAYLOAD_BYTES`; PostgreSQL rejects 8000 or more).
  The worst case is a 500-id `room.member_added`, about 5.6 KB, so there is no chunking; `LiveHintTest` and `NotifyHintsTest` pin it.
- **PostgreSQL facts the design leans on:** a NOTIFY is delivered only when its transaction commits, in commit order, and is dropped on rollback (so a refused or rolled-back write cannot announce
  itself); identical payloads within ONE transaction collapse into one delivery (a write emits one hint, so this never bites); notifying transactions serialize on ONE global lock during commit (a
  cluster-wide cost, accepted at chat-write rates); the cluster's notification queue fills only if a LISTENing connection stops reading, after which EVERY notifying commit fails. That last hazard is why
  the listener (S2) drains with unbounded demand and never stops reading.
- **Private account hints** use the same channel with a version and account id. They commit with the exact access revocation or account write and ask each replica to re-evaluate affected sockets. Room hints keep their existing shape.
- **Tests read the channel through a plain JDBC `LISTEN`** (`NotifyCapture`), bracketed by a sentinel hint of its own, so "emits nothing" is proven by commit order, not by sleeping.

### The LISTEN connection (live, 0.4.0)

`infra/notify/NotifyListener.kt` is the **one documented exception to the bounded pool**: ONE dedicated, non-pooled R2DBC connection per process that `LISTEN`s on `adder_live` for the life of the process
(a pooled connection is borrowed and returned, a listening session must be neither). `configureDatabase` publishes its factory as `NotifyConnectionFactoryKey` (`infra/db/Database.kt`, `notifyConnectionFactory`); the
listener itself is built and started by the live feature (`live.md` "The listener"), lazily, on the first ticket mint. It adds ONE backend per replica, hence the sizing formula above.

- **Built differently on purpose.** Same `postgres.*` URL, user and password as the pool (`ApplicationConfig.r2dbcOptions`, extracted so the two cannot drift), but its `application_name` is
  `<postgres.pool.applicationName>-live` (`adder-live`; `ConnectionPoolTest` counts the pool's own name exactly, and `pg_stat_activity` shows the listener apart). The factory is the raw driver factory wrapped ONLY in
  `LeakedSocketClosingConnectionFactory`: no pool, no `StatementTimeoutCachingConnectionFactory` (the listener sets no statement timeout; a remembered one would be wrong for a session that outlives every request) and no
  `DetachingConnectionFactory` (nothing borrows it, so no frame to detach from). The session is never in a transaction, so `idle_in_transaction_session_timeout` has nothing to end.
- **It never stops reading.** r2dbc-postgresql 1.1.3 publishes notifications through a best-effort multicast sink: a subscriber without demand silently LOSES them. The listener subscribes to `getNotifications()` with
  unbounded demand (before `LISTEN`, so none falls between) and copies each payload into a `Channel<String>(1024)` with `trySend`; a payload that finds it full is dropped and reported as a gap. A listening connection that
  stopped reading would fill the cluster's notification queue and make EVERY notifying commit fail ("NOTIFY" above), which is why a slow consumer must cost `resync`s, never backpressure on the socket.
- **It heals itself.** A `SELECT 1` heartbeat every 30 s (5 s timeout; a half-open TCP connection leaves the session "up" but deaf, and only a statement notices), a flux error or completion, or a failed step closes the
  session (the close is bounded and reaches the leaked-socket guard) and reconnects with jittered backoff (1, 2, 4 ... 30 s, each wait 50 to 100 %). After EVERY successful LISTEN (the first included, and BEFORE
  the listener reports itself up) and for every dropped payload, `onGap` fires: hints committed while no session was listening (the first connect's own window, an outage) are gone (at-most-once, `live.md`), and the hub
  answers a gap with `resync`. `onGap` can be called from the driver's event loop and from the listener's coroutine, possibly at once, so the consumer's callback must be thread-safe, cheap, non-blocking and
  non-throwing (S4: an atomic flag or a conflated channel `trySend`).
- **Not config.** The capacity, heartbeat, step timeout and backoff are `NotifyListenerTimings` defaults, constructor parameters only so `NotifyListenerTest` (no app, shared container: committed vs rolled-back, a terminated
  backend, a full channel, a stalled heartbeat, the `-live` name and close on stop) can shrink them. Logs: `observability.md`.

### Backup and restore

A manual runbook (checkup C-ARCH-2, decided 2026-11-20: no scheduled job). The unit is `pg_dump -Fc` of the `adder` database,
taken INSIDE the Postgres container/pod and streamed out, so the host needs no Postgres client and no password (the image's
local socket trusts the in-container user). `scripts/db-backup.sh [OUT.dump]` and `scripts/db-restore.sh DUMP.dump [--replace]`
wrap it; both take the command that reaches the container from `ADDER_PG_EXEC` (also `ADDER_DB_USER`/`ADDER_DB_NAME`,
default `adder`/`adder`; the value is word-split on purpose):

| Where | `ADDER_PG_EXEC` |
|---|---|
| compose, default project | unset (default `docker exec -i adder-postgres`) |
| compose, another project | `docker compose -p NAME exec -T postgres` (a container name changed by an override: `docker exec -i THAT-NAME`) |
| Kubernetes (`adder` namespace) | `kubectl -n adder exec -i deploy/postgres --` |

- **Backup** (live, the app may keep running: one transaction, a consistent snapshot): `scripts/db-backup.sh`. The file is written
  `0600` (it holds every user, message and password hash; treat it like the database), never over an existing file, and only
  kept if `pg_restore --list` reads it and finds table data. The bare equivalent is
  `(umask 077; docker exec adder-postgres pg_dump -U adder -d adder -Fc > adder.dump)`.
- **Restore into an EMPTY database** (a new machine, a lost volume): bring up ONLY Postgres, restore, then start the app.
  Compose: `docker compose up -d --wait postgres && scripts/db-restore.sh adder.dump && docker compose up -d app`.
  Kubernetes: scale the app to zero (`kubectl -n adder scale deploy/app --replicas=0`), make sure the `postgres` pod runs on a
  fresh PVC, restore, scale the app back to 1. The app must NOT have booted against the empty database first: Flyway and the
  seed admin would have made it non-empty, and the script refuses (see below). On start the app finds the schema current
  (`Current version of schema "public": 22`, nothing applied). The restore is one transaction (`--single-transaction
  --exit-on-error`): all or nothing, and `--no-owner --no-acl` leaves everything owned by the connecting role.
- **Safe by default:** the restore refuses unless the target has NO table, view or sequence outside the system schemas AND no other
  client is connected (`pg_stat_activity`: the app still running; `--force-connected` overrides, for a client you know is idle), and
  changes nothing when it refuses. `--replace` is the explicit way over a non-empty database and DESTROYS what is there: in ONE
  explicit transaction it drops every extension (bar `plpgsql`) and every non-system schema (`public`, `ops`; V4 puts `unaccent` in
  `public`, V9 creates `ops`) with `CASCADE`, recreates an empty `public`, and replays the dump rendered by `pg_restore -f -`, so
  the result is exactly the dump even when the live database is AHEAD of it (a newer table with a foreign key into `rooms`, a higher
  Flyway history row; `pg_restore --clean` would trip over the first and leave the second). The script is fed to `psql` without `-1`
  and ends in `COMMIT;`, so a cut stream rolls back instead of committing half a restore (the rendered SQL goes through a `0600`
  temp file first, so a failed `pg_restore` never reaches the database). A future migration that creates another schema or an
  extension needs no change here: the drop is by catalog, not by name. Stop the app first (compose `docker compose stop app`; k8s
  scale to 0). To restore beside the data instead, make a scratch database (`ADDER_DB_NAME=adder_restored` after `createdb`) and compare.
- **Keys and application secrets** are stored separately from the dump. Keep `DATA_ENCRYPTION_KEY`, `JWT_SECRET`, and the previous
  encryption key when applicable. A restore needs the encryption keys covering the dump's browser push endpoints (`security.md`).
  It restores password hashes, credential revisions, and revocations from the snapshot. It also restores refresh rotation grace and
  replay counters with their original deadlines. State held in process memory starts fresh.
- **A dump restores into the same or a newer app version** (Flyway migrates forward on boot). An OLDER app against a newer database is
  not refused by Flyway (its default ignores `*:future` migrations; the config is unchanged), so never roll the app back past the
  schema without restoring a dump of that older schema, UNLESS that release's own rollback runbook says otherwise (1.2.0 to 1.1.0:
  "Rollback below 1.2.0" under "Thread tags (V33)": V31 to V34 are inert to a 1.1.0 binary, one `DELETE` first, no dump; a release
  with no such runbook has none, and the dump is the only way back). Restore into the same Postgres major (18).
- **Tested** 2026-11-20 against a throwaway compose project (own `-p`, ports, volume): seed rows through the API, dump, `down -v`,
  fresh Postgres, restore, app start (Flyway "Current version … 22", 0 migrations applied), same row counts and logins; the
  non-empty and app-still-running refusals, and `--replace` over a database AHEAD of the dump (an extra table with a foreign key into `rooms`
  plus a fake higher Flyway row: afterwards exactly the dump, app boots). Repeat that drill after a migration that adds a schema or extension.

### Reaction notices (V45) and thread lifecycle (V46)

V45 separates the ordinary message-notice uniqueness key from the reaction key, which adds the reacting actor to the message and
recipient. V46 adds a soft-delete flag and a same-room merge link on threads. Active canonical threads participate in workflow status
counts and the main thread list. Direct reads include active merged histories. Thread numbers are allocated across all rows and remain
unique. The merge link has a foreign key to the room and thread number pair. Only the room lock permits writes to that link.

On rollback to a version before V45, remove reaction rows before recreating the previous
`uq_notifications_message_recipient` index for all non-null message IDs. Preserve the V45 shape if the operation is only a forward
upgrade. A rollback to a binary predating V46 requires restoring a pre-upgrade database backup once thread deletion or merging has
been used. An older binary would expose deleted threads and cannot decode the merge history event types.

### Markdown index upgrade

The boot reindex advances existing messages to parser version 2. In the same bounded batches and under the same message locks,
it rebuilds hashtags and removes mention and presence rows that the current parser no longer recognizes. Historical notice rows
remain subject to normal retention. The reindex never adds mention recipients or replays notices.

### Message revisions (V47)

The message service writes one prior body to `message_revisions` before replacing it. `message_id` references the live message,
and `(message_id, id)` serves the authorized paged read. Recording begins with a changed edit after deployment. Message and thread
deletes physically remove the associated revisions. The room write lock serializes both operations with edits.

For rollback to a binary predating V47, stop writers and run `DELETE FROM message_revisions` before starting the previous binary.
This discards saved history. The old binary lacks the purge on message and thread deletion. Preserve the table and Flyway history.

### Search, workflow field and boot purge indexes (V48–V50)

- V48 installs `btree_gist` and indexes the exact message full-text search expression together with `thread_id`, for live messages only. The existing thread probe retains the same membership checks and result ordering. In a warm synthetic PostgreSQL 18 benchmark with 100,000 messages, the generic plan across rooms took 69.36 ms for an absent term and 77.12 ms for a rare term before the index, and 6.27 ms and 6.26 ms after. The common term took 5.09 ms after and 6.99 ms before. The 22 MB index increased insert time by about 4.5% in that corpus and more for narrower rows.
- V49 installs `btree_gin` and indexes room id with `fields jsonb_path_ops` on canonical live threads. The synthetic 100,000-thread run measured an absent filter around 0.66 ms before and 0.03 ms after; the index used 1.1 MB. A synthetic batch of 10,000 creates rose from 22 ms to 40 ms. Keep the canonical predicate on list queries that use the index.
- V50 indexes only deleted message ids. The boot sweep advances by id even when a batch has no derived rows. Each delete uses the message ids from that batch to probe its derived table’s index. A tombstone held by another transaction is skipped and can be revisited at the next boot. The batch’s 30-second statement limit still applies. On PostgreSQL 18, a warm synthetic batch with 100,000 messages, 600,000 derived rows and 50 tombstones ran in about 88 ms with the former union and 1.5 ms with the indexed batch.

The Flyway migration role needs permission to install the two trusted PostgreSQL extensions, or the operator must install them before startup. Flyway builds these indexes transactionally; schedule the migration in a deployment window where writes to the affected tables can wait. A rolling application rollback can leave the indexes installed.

### Notification retention and digest pacing (V51–V52)

V51 adds a guard row per notification recipient. A room write locks its complete recipient set in increasing id order before the actor budget and before changing notices. Room locks alone leave room for concurrent arrivals from different rooms. A set-oriented probe finds recipients over 5,000 unseen rows across channels. Trim selects the oldest available rows with `SKIP LOCKED` to avoid waiting behind a read or another delete. If too few rows can be removed, the operation discards its own new notices. Only surviving notices count as creations or enter the browser push queue. Deleting a notice removes its push queue entries by foreign key.

Thread-read settlement and a departing member's cleanup select and change at most 1,000 notice rows per statement in ascending id order. The work stays in the original transaction, so every batch rolls back together. The limit bounds each statement's work. A large removal can still hold locks across batches.

V51 seeds only recipients exceeding the cap. Each sweep tick visits a bounded number of marked recipients and clears up to 1,000 excess unseen rows apiece. An old writer can create more excess during a rolling upgrade. Stop old writers before asserting that every recipient meets the bound. The standard Recreate deployment satisfies this. Use `SELECT recipient_id, count(*) FROM notifications WHERE seen_at IS NULL GROUP BY recipient_id HAVING count(*) > 5000` to check normalization. Leave the additive migration tables installed on rollback. The older app resumes the earlier notice policy.

**Returning from an old writer.** If an older binary wrote to a database that already applied V51, stop those writers and reflag oversized recipients before starting the upgraded app. This also applies after any mixed-version overlap. The repair is idempotent:

```sql
INSERT INTO notification_recipient_guards (recipient_id, needs_normalization)
SELECT recipient_id, TRUE
FROM notifications
WHERE seen_at IS NULL
GROUP BY recipient_id
HAVING count(*) > 5000
ON CONFLICT (recipient_id) DO UPDATE SET needs_normalization = TRUE;
```

The next sweeps drain the flagged recipients. Check the excess query above before declaring normalization complete.

V52 stores the last digest SMTP attempt by actor and recipient. Claiming skips currently paced pairs. Just before send, the digest locks pairs in sorted order and timestamps eligible reservations after the locks are acquired. This transaction is separate from claim and delivery. A racing pair's notices stay pending. A failed or interrupted SMTP attempt consumes the interval. Expired pacing rows are cleared in bounded transactions on sweep ticks. Pacing begins with the first reservation made by 1.21 and remains durable across restarts. Stop older digest senders before upgrading. If an older sender runs during a rollback, its attempts are outside the V52 pacing history.

### Shared live tickets (V53)

The server stores ticket digests and their authorization binding in `live_tickets`. The raw bearer never reaches storage. Minting locks the fixed capacity guard, uses PostgreSQL time to bound the pending 30-second lease, removes at most 256 expired rows, and checks the shared active ticket limit. Redemption deletes the digest and returns its binding atomically. The server then rechecks the token and account. Rollback may leave V53 installed. Tickets minted by the old in-memory store naturally expire or trigger a new mint during the deployment change.

### Shared live socket and foreground leases (V54)

`live_session_leases` uses random session and process IDs and stores account ID and PostgreSQL-clock deadlines. It contains no
JWT, ticket or access-token ID. A per-user guard row serializes shared socket admission. The process retains its own global and
pending handshake caps. Configure the same per-user cap on every instance using the database.

Each process renews its own leases in batches of 1,000 every 20 seconds. A socket lease lasts at most 60 seconds and never
outlasts its access token. Foreground expiry is independent, and `@here` checks only current room members against fresh
foreground leases in the message transaction. Socket I/O uses a monotonic deadline derived conservatively from the database
response. Close releases the row by its owning process and session IDs. Crash residue expires and is removed in bounded batches.

### Shared refresh replay grace (V55)

V55 links bounded `refresh_rotations` to `revoked_tokens`, with at most 10,000 preallocated slot IDs and indexes for the grace
and token expiry paths. Only the JTI and identifiers needed to clear grace are stored. Revocation prunes expired blocks in
bounded batches, cascading their rotation rows. The user guard joins refresh and logout transactions for the same account.
Logout orders the account guards and JTIs when two different principals are involved. No scripts should delete revocations to
reset grace. Existing V54 or older denylist rows have no grace. Keep the old process stopped while upgrading to V55.

### Shared account-attempt limits (V56)

`account_login_attempts` stores the ordinary credential-failure counter, active lock, MFA escalation and fixed-window code-guess
budget under a domain-separated HMAC digest of the normalized submitted identity. Per-identity advisory transaction locks serialize
preflight, failure and success across instances. A fixed guard serializes only the unknown-identity capacity decision. Known-account
failures may exceed that configured cap because their key space is bounded by `users`. PostgreSQL time supplies all deadlines, and
each capacity path removes at most 64 wholly expired rows. No submitted identity or credential is stored.
Password-reset confirmation clears this row through the reset service's existing transaction, so grant consumption, password change,
credential revision and lockout clearing commit or roll back together.

`password_reset_cooldowns` uses a different HMAC derivation label and capacity guard. A reset request locks the guard, removes at
most 64 expired rows and atomically claims the database-clock interval. Both tables are operational hard-delete state. A rollback
may leave them installed; an older single-instance binary ignores them and resumes with empty process-local counters.
