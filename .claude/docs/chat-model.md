# The chat domain

Owns: the chat domain model — rooms, membership, workflows (statuses and fields), threads, messages, history, mentions, reactions, pins, unread, watching, notice kinds, curated tags, the profile page, the tab title and quotes.
Not here: the live channel (`live.md`), the roadmap and decisions (`product.md`). **Status:** rooms and workflows (0.2) and threads and messages (0.3) are binding rules;
Find (0.5) is binding too (its code lands step by step); 0.6 is binding too (mentions, notifications, unread, reactions, pins; its code lands step by step); 1.1 (watching, group mentions, notice kinds), 1.2 (room view, tags, unread) and 1.3 (quotes) are binding as rules and their code lands step by step (see the last three sections); later versions are still open, and each turns its part into rules in its own plan first. `workflows/` and `rooms/` (0.2.0) are the first chat packages; the room routes landed commit by commit (the record and its read-only workflow in C7, members in C8, the workflow PUT in C9).

## Rules

Binding for 0.2.0 (rooms and workflows) and, from "Threads and messages (0.3)", 0.3.0. The code lands commit by commit; where a rule names a file, that file is the destination. The user's
decisions and the defaults taken without asking are in `product.md` ("Decisions", "Assumptions"); the per-route matrix and the audit events move to
`authorization.md` and `observability.md` with the route that introduces them.

### Rooms

- **Members only.** `room_members(room_id, user_id, role OWNER|MEMBER)`. Any signed-in user creates a room and becomes its OWNER. A non-member
  gets `404` (existence is not disclosed; the denial is audited `room.access_denied`, the response stays 404); an ADMIN reads and manages every
  room. OWNER or ADMIN edits name and description, manages members and the workflow, archives and unarchives; soft delete is ADMIN only
  (reader `404` first, then `403`), with no restore API in 0.2.
- **Guard order, every room route:** 401; visibility (404 for a missing room and a non-member alike); role (403); the `X-Expected-Revision`
  header, then the body (400); then, under the room lock, the guard again, the state checks (409) and the write. A non-member's malformed body is
  still 404, a plain member's still 403.
- **Membership.** A person or a whole team. A team add is a **snapshot** of the active roster at that moment: a later roster edit never follows
  (a live link would eject people mid-incident and break per-member roles and the last-OWNER rule). Add is idempotent (existing members are
  skipped and counted) and always adds as MEMBER; promotion is a separate audited step. The last OWNER cannot leave, be demoted or be removed
  (`409`, `urn:adder:problem:last-owner`): after the write the room keeps at least one OWNER whose user is active. A member leaves by deleting their
  own membership; an OWNER or ADMIN removes others.
- **Deleted users.** Their membership rows stay, inert: lists and the last-OWNER count resolve through active users, a room whose owners are all
  deleted is managed by ADMINs, and deleting a user is never blocked by room ownership.
- **Room names** may not contain invisible formatting characters (Unicode category Cf, U+2028/U+2029): a `400`, applied to room names only (`rooms/Room.kt`), so two rooms never look identical and a bidi override cannot reorder a name.
- **Archived = read-only** for name, description, workflow and (0.3) content (`409`, `room-archived`); membership management stays allowed, so
  access to the record stays manageable. Archive and unarchive are no-ops (and unaudited) when already in that state.
- **Names** are unique among non-deleted rooms, case-insensitively (a partial unique index; archived rooms keep theirs; a delete frees the name).
  A clash discloses only that a room of that name exists. No slug: URLs use the numeric id.
- **Activity.** `last_activity_at` equals creation time in 0.2 and 0.3 bumps it. The rail shows the caller's member rooms, most recent first; an
  ADMIN gets every room on the Rooms page.
- **Limits:** room name <= 80, description <= 500; 500 members per room, 200 user ids per add; 200 members per team.

### Workflows

- **Vocabulary.** A room owns its workflow: ordered **statuses** `{key, label, colour GRAY|BLUE|GRAPE|TEAL|RED|ORANGE, category OPEN|CLOSED,
  initial}` and **fields** `{key, label, type TEXT|NUMBER|DATE|SELECT|MULTI_SELECT|USER|URL, options[{key,label}] (SELECT kinds only), required}`.
  Wire enums are UPPER_CASE; the SPA lowercases to the Mantine hue in one util. A position is the array index on the wire, never a field.
- **Kernel** (`workflows/WorkflowRules.kt`, pure, shared by templates and rooms): 2-20 statuses, 0-20 fields, 1-50 options per select; exactly one
  initial status and it is OPEN; at least one CLOSED status; keys unique per list and matching `^[a-z][a-z0-9]*(-[a-z0-9]+)*$` (<= 40 chars);
  labels <= 60; options only on SELECT kinds. At most 200 status keys and 200 field keys per room, retired ones included.
- **Templates.** An ADMIN-curated registry `workflow_templates` (any signed-in user reads; writes are ADMIN with guard-before-read), one JSONB
  `definition` document plus a `revision`. Name (<= 100) and description are plain registry text. Labels are a language map `{en, pl?}` (EN
  required, PL optional, Lettuce's dictionary shape; per language, labels are unique among the statuses, among the fields and among a field's options,
  case-insensitively after trimming, a duplicate being a 400 that names the label; a room's own labels follow the same rule in its ONE language, `rooms/RoomWorkflow.kt`). Seeds by migration, never edited afterwards: *Default* (Open initial, In progress, Waiting,
  Done CLOSED, Won't do CLOSED) and *Incident* (Triage initial, Investigating, Mitigating, Monitoring, Resolved CLOSED; optional fields Severity
  S1-S4 SELECT, Component TEXT, Jira link URL, ETA DATE), in English and Polish. Deleting a template never touches rooms; there is no
  "last template" rule.
- **Copy at creation.** A room copies statuses and fields once, with labels resolved to ONE language from the request's `language` (the SPA sends
  its UI language; default `en`; EN fallback per label). When per-label resolution would clash within a list, that whole list is copied in EN. Room labels are plain text afterwards: a room's statuses are shared vocabulary people name in
  chat, and two-language rooms breed stale half-translations. There is no re-apply; afterwards OWNER or ADMIN edits the room's copy in place only.
- **Whole-document PUT under `X-Expected-Revision`** (templates and rooms; Toadie's guard, `infra/revision/ExpectedRevision.kt`). The header is
  REQUIRED: missing or malformed is `400`, stale is `409` (`revision-conflict`); every successful PUT bumps the revision. `infra/` carries it so
  0.3 threads reuse it. Adder has no legacy client, which is why it is not optional as in Toadie.
- **Keys are immutable slugs, reserved for the life of a room.** Removing a status or field **retires** it (soft delete: `marked_as_deleted`); adding
  a retired key back revives the row. A field's `type` is immutable per key (`409`, `field-type-immutable`, carrying `keys`). The PK
  `(room_id, key)` is deliberately NOT partial: a retired key is never minted twice, so 0.3's history and the thread FK stay unambiguous. This
  is the documented exception to "free a unique field on delete".
- **A workflow edit never closes or reopens a thread behind its history.** A status's category is editable only while no thread uses it, and a
  retired status's replacement must have the same category. Fields and options need no mapping.
- **Stored values survive a workflow edit** (decided in 0.3; `threads.fields` is a jsonb object keyed by field key). A **retired field's value is kept,
  hidden** (not returned, not validated, and left out of the history's `FIELD_CHANGED` entries), and **comes back when the field is revived**. A **removed option's stored key is kept and shown as removed**
  (a "removed option" hint) until someone changes it; a newly chosen value must be a live option. **Unchanged values skip validation**, so a stale value
  never blocks a save; a value the caller changes is validated against the current definition. The kernel is `threads/ThreadFields.kt`.

### Data model (V10-V13)

All timestamps are epoch-millis `BIGINT`; no CHECK on enum-valued columns (the Kotlin enum is the whitelist, the V5 rule).

- `V10 team_members(team_id, user_id)`: the team roster, a pure join. `V11 workflow_templates`, `V12` the two seeds, `V13` the whole room aggregate
  in one migration so a room never exists without its workflow: `rooms`, `room_members`, `room_statuses`, `room_fields`.
- **Hard-delete** the pure joins `team_members` and `room_members` (the audit trail holds adds and removals; a re-add must not collide with a dead
  row). **Soft-delete with a partial unique name** `rooms` and `workflow_templates`. **Soft-delete with a full key** `room_statuses` and
  `room_fields`. A template's statuses and fields are not rows; they are replaced with the document.
- `rooms.workflow_revision` is the room workflow's revision; `room_statuses` has a partial unique index on the one initial row per room.

### Locking and the room write

- **One lock, one helper.** `withRoomWrite(roomId, callerUserId, guard) { ... }` (`rooms/RoomLock.kt`, after Astrolabe's `withPlanWrite`), in one
  transaction: select the active room row `FOR NO KEY UPDATE` (child inserts take `FOR KEY SHARE`, which does not conflict), re-read the caller's
  membership and re-run the same guard (only this verdict authorises the write), then run the block. Every room-scoped write goes through it:
  metadata, archive, members, roles, workflow. That makes the last-OWNER count, the revision compare and the archived check race-free without
  locking member rows. Toadie's table-level `lockingTransaction` is deliberately NOT ported: the invariants are per room, and a table lock would
  serialise every room. *[changed] by 1.2: ported for the tag registry ONLY.*
- **Workflow PUT inside the block:** archived -> 409; `requireRevision`; select the room's status rows `FOR NO KEY UPDATE`; plan the change with
  the pure kernel (`RoomWorkflowPlan.kt`: retired, revived, added, re-categorised); field-type and key-budget checks; the replacement checks (400), then the
  usage counts (409 `status-in-use`); clear `is_initial` on every row (first: the partial unique index is checked per row); retire absent keys; upsert payload
  rows by key with `position = index` (reviving retired keys); THEN `usage.moveThreads` (after the upsert: a replacement may be a status this
  very PUT adds or revives, and 0.3's thread rows reference `room_statuses`, so the target row must exist and be live when the threads move);
  bump `workflow_revision`. Per-row Exposed statements (<= 20 rows each).
- **409 problem types** (`urn:adder:problem:`): `revision-conflict`, `last-owner`, `room-archived`, `status-in-use` and `field-type-immutable`
  (both carrying `keys`, the `ProblemDetail` extension member), plus the plain key-budget conflict.

### Live hints (0.4.0)

Every write above that changes something emits one id-only `adder_live` NOTIFY hint from its own transaction (`notifyLive`, `infra/notify/`): a no-op, a refused or a rolled-back write emits none. The catalog is `live.md` "Hints"; the Postgres facts are `persistence.md` "NOTIFY". 0.6 adds three kinds: "Deletes, hints, buckets, audit and logs" below.

### The mapping contract 0.3 plugs into

> **Revised for 0.3** by two plan findings, **as built (0.3.0 S6)**: `moveThreads` runs **after** the status upsert (a replacement the same PUT adds would otherwise hit
> the FK, a SQLSTATE 23503 that `ErrorHandling.kt` would answer as a 500), and the status-row `FOR SHARE` is **dropped** (every thread write and the workflow PUT hold
> the same room lock, so the status read inside the lock is current; the FK stays as a backstop). `threads/ThreadWorkflowUsage.kt` is the real port, registered by
> `Database.kt` under `WorkflowUsageKey`; `NoThreadsYet` and the `?: NoThreadsYet` fallback are gone, and the routes read `attributes[WorkflowUsageKey]` per request.

Retiring a status that threads use needs a replacement mapping `replacements: {retiredKey: replacementKey}` in the PUT body. `400` when a key is
not a status this PUT retires, or the target is absent from the new document or has another category; `409 status-in-use` with `keys` when a retired
or re-categorised status has threads and no valid replacement. `rooms/` never imports `threads/`, so the seam is a port:

```kotlin
interface WorkflowUsage {   // rooms/WorkflowUsage.kt; both run inside the caller's transaction
    suspend fun threadCounts(roomId: UInt, keys: Collection<String>): Map<String, Long>
    suspend fun moveThreads(roomId: UInt, from: String, to: String, byUserId: UInt): Long
}
val WorkflowUsageKey = AttributeKey<WorkflowUsage>("WorkflowUsage")   // Database.kt registers ThreadWorkflowUsage under it
```

Routes read `attributes[WorkflowUsageKey]` per request, so a test's `application { }` block can overwrite the real port with a fake (`FakeWorkflowUsage`; Ktor runs the
`application.yaml` modules, `configureDatabase` included, before that block; `test-fixtures.md`). **As built**, the contract is:
`GET` calls `threadCounts` with every live status key; the `PUT` calls it with the keys it retires or re-categorises (`RoomWorkflowPlan.statusesToCount`), after the
`FOR NO KEY UPDATE` lock on the status rows and the mapping's `400` checks, and answers `409 status-in-use` (`keys` = the offending statuses) for a counted status that is re-categorised
(no mapping can help: only retired statuses take one) or retired without an entry in `replacements`; `moveThreads(roomId, from, to, byUserId)` is called once per retired status that has
threads AND a mapping (in the order retired; never for a status with no threads), inside the same transaction, AFTER the status upsert (so the target may be a status this PUT adds or revives; pinned by `FakeWorkflowUsage`'s `targetLiveAtMove` and, with real threads, by `ThreadWorkflowUsageTest`) and
before the revision bump, so any later failure rolls the moves back; the sum is the audited `threadsMoved`. A revived status may change category freely (a retired status has no threads: they were moved when it retired).

`ThreadWorkflowUsage`: `threadCounts` is ONE `SELECT status_key, count(*) ... GROUP BY status_key` over `idx_threads_room_status`, for the keys asked (a status with no thread is absent).
`moveThreads` selects the ids of the room's threads in `from`, runs one `UPDATE threads SET status_key = to, updated_at = now` over them and appends one `STATUS_REPLACED`
event per thread (`{from, to, fromLabel, toLabel}`, one multi-row insert, by `byUserId`, on the move's own instant), then returns the count. The labels come from `RoomWorkflowService.snapshot`
(retired rows included: the source is already retired when this runs). A workflow move is **not activity**: `last_activity_at` (the thread's and the room's rail order), `message_count` and
the thread `revision` (the details token) stay; `closed_at` is untouched because the replacement has the source's category (so a CLOSED to CLOSED replacement keeps the original close time, as the status route's does).
Thread rows reference `(room_id, status_key)` with an FK to `room_statuses(room_id, key)` (`fk_threads_status`): a backstop, since every thread write runs under `withRoomWrite`, the same room lock as the workflow PUT (race 6: a status move waiting
on the lock while a PUT retires its target re-reads the status inside the lock and answers `400`).

## Threads and messages (0.3)

Binding for 0.3.0; the code lands commit by commit (plan steps S1-S6), and where a rule names a file, that file is the destination. D1 and D2 below are the
architect's recommended options taken as assumptions (`product.md` "0.3.0 threads and messages"); changing one changes one predicate and a few matrix cells.

### Data model (V14)

- **One migration, `V14__create_threads.sql`**, the whole aggregate: `threads`, `messages`, `thread_events`. Its header comment states each table's delete class:
  `threads` are **never deleted** in 0.3 (close one as *Won't do*; a room's soft delete hides them with the room); `messages` are **soft-deleted** with a
  listed tombstone; `thread_events` is **append-only** (Toadie's `V23__create_catalog_file_events.sql` shape). No CHECK on enum-valued columns (the V5 rule).
- `threads`: `id`, `room_id` (FK `rooms` ON DELETE CASCADE), per-room `number` (`#42`, unique `(room_id, number)`), `title` <= 200, `status_key`, `owner_id`
  (the creator at first), `created_by`, `fields` jsonb object, `revision`, `message_count`, `closed_at`, `last_activity_at`, `created_at`, `updated_at`.
  The composite FK `(room_id, status_key)` -> `room_statuses(room_id, key)` keeps the default `NO ACTION` (checked at statement end); the room hard-delete
  cascade into both tables at once is pinned by a test (`ThreadSchemaTest`).
- **`closed_at` mirrors the status category**: set on a move into a CLOSED status (kept across a CLOSED to CLOSED move), cleared on a move into an OPEN one. It stays exact because a category
  cannot change on a status in use and a replacement has the same category (Workflows, above).
- `messages`: `thread_id` (CASCADE), `author_id`, `body` <= 8,000, `created_at`, `edited_at`, `marked_as_deleted`, `deleted_by` (set on every delete, the author's own included; `deletedByModerator` = it differs from `author_id`). CHECKs: a tombstone has an empty body and a `deleted_by`, a live message has a body and none.
- `thread_events` (Toadie's/Lettuce's event log): `thread_id`, `user_id` (RESTRICT), `created_at`, `event_type`, `params` (a string map via `infra/json/JsonParams.kt`).
- **Numbers** are `COALESCE(MAX(number), 0) + 1` per room under the room lock and are never reused; a clash on `uq_threads_room_number` (23505) maps to 409.
- **`message_count`** counts every message, the opener and tombstones included, and never goes down (the sketch's "reply count"; the UI says "N messages").

### Who may do what

Four groups (D1 and D2 are the architect's recommendations, taken as assumptions):

- **Speech** (start a thread, post a message): **members only**. An ADMIN who is not a member gets `403` and joins through the Members page first
  (only members read and post, for the sake of the audit trail).
- **OPEN-side metadata** (a move between OPEN statuses, title, fields): any reader, member or ADMIN.
- **Stewardship** (close, reopen, CLOSED->CLOSED moves, passing ownership; D1): the thread owner while a member, the room OWNER, or an ADMIN. Closing stops
  everyone, so it belongs to whoever can undo it; the rule is `ThreadStatusRules.kt` plus `requireThreadSteward`.
- **Messages:** an author edits and deletes their own while a member. The room OWNER or an ADMIN may **delete, never edit**, someone else's message (D2):
  it becomes a tombstone ("Removed by a room owner or an administrator", `deletedByModerator`) and the audit line says `moderated`. Incident chat leaks
  credentials and the author may be asleep.

### Closed and archived

- **Closed** = the status's category is CLOSED. A closed thread refuses posts, message edits and deletes (moderator ones included), the details PUT and the
  owner hand-over: `409`, `urn:adder:problem:thread-closed`. Stewards still move it between statuses (reopen, or CLOSED->CLOSED); to delete a message in a
  closed thread a steward reopens it, deletes and closes it again, and the history shows all of it. (A reaction is refused the same way: "Reactions (V20)".)
- **Reopen** is recorded in the history (`REOPENED`), by the thread owner, the room OWNER or an ADMIN.
- **An archived room refuses every content write** (`409`, `room-archived`); reads still work.
- **Owner hand-over:** the new owner must be an active room member (else `400`); a removed or deleted owner keeps the thread, inert, until a steward passes
  it on. Setting the current status or owner again is a `204` with no event and no audit line.

### Guard order and locking

- **Guard order, every thread and message route:** 401; visibility via `visibleStanding` (404 for a missing room and a non-member alike, audited
  `room.access_denied`); the **pre-check before the body** (403): member for the two POSTs, steward for the owner PUT, author for the message PUT (the last two
  from a lock-free read of the owner or author; a missing thread or message is `404` here); the header, then the body (400); then, under the room lock: the
  room guard again on the fresh caller, the thread or message (404), the act guard again (403), archived (409), closed (409), revision (409), the
  state-dependent 400s, then the write, its events and the activity bump.
- **The status PUT is the one body-dependent guard**: whether a steward is needed depends on the target's category, so that check runs under the lock after
  the target resolves. An unknown or retired key is a `400` first (every reader can read the workflow, so it discloses nothing).
- **The room lock is the thread lock.** Every content write goes through `withRoomWrite` (`rooms/RoomLock.kt`): posting updates `rooms.last_activity_at`,
  i.e. the room row, so a lighter lock upgraded by that UPDATE would deadlock two posters; edits and deletes take the same lock, so the closed and archived
  checks cannot race a close or an archive. Writes serialise per room (a few ms each, fine at incident scale) and **the wait is bounded**: a writer queued behind a busy room holds a pooled connection, so the lock statement runs under `SET LOCAL lock_timeout` (3 s, `rooms.lockWaitMillis`) and a wait past it is the audited `429 room-busy` with `Retry-After: 1` (`persistence.md` "Rooms (V13)", `security.md`); the non-POST writes (the reaction and pin PUTs included) also ride the per-user `chat-write` bucket, so one member cannot queue a room's lock full. **No thread-row or status-row locks.** The
  block receives the fresh caller and standing (`ThreadLock.kt`: `withThreadWrite`, `withMessageWrite`). The lock order is the room row first; the FK
  checks' `FOR KEY SHARE` on `rooms`, `room_statuses`, `threads` and `users` rows does not conflict with `FOR NO KEY UPDATE`.
- **Single messages live at `/rooms/{id}/messages/{messageId}`** (API-RES-006 bans three path parameters); the route checks the message belongs to that
  room, and a message in another room, unknown or deleted is a uniform `404`.

### API (rule form; the spec is `documentation.yaml`, the matrix `authorization.md`, the events `observability.md`)

- `GET /rooms/{id}/threads?closed=`: reader; paged; sortable `id`, `number`, `title`, `lastActivityAt`, `createdAt`, `status` (0.5, workflow order); `closed` is the only filter (a strict
  boolean on `closed_at`; omitted = both; 0.5 adds the rest: "Find (0.5)"). `POST` (member, `chat-post` bucket) takes `{title, body, fields?}` and answers `201` +
  `Location`; it starts in the initial status with the creator as owner, required fields must be supplied, and the opening message is part of the create.
- `GET /rooms/{id}/threads/{number}`: reader. `PUT` takes `{title, fields}` under `X-Expected-Revision` (REQUIRED; `204`, a no-op when nothing changed and
  then no revision bump). `PUT .../status` `{status}` and `PUT .../owner` `{ownerId}` are single-value sets: last writer wins by design, the history records
  each change.
- `GET .../events`: reader; paged; sortable `id`, `createdAt`, default `-createdAt,-id`.
- `GET .../messages?id[lt]=`: reader; keyset paging through the `id[lt]` filter inside the standard envelope (`total` counts after the filter, so
  `total > items.length` means older messages exist); sortable `id`; tombstones included (`body: null`, `deleted: true`). `POST` (member, `chat-post`
  bucket) answers `201` + `Location: /api/v1/rooms/{id}/messages/{messageId}`. **[changed] by 1.3:** the POST takes `MessagePostRequest` `{body, quotedMessageId?}` (the edit PUT keeps `{body}`), and a message carries `quote`; the guard order gains one step and a typed `400`: "Quotes (1.3)".
- `GET|PUT|DELETE /rooms/{id}/messages/{messageId}`: GET is reader (a deleted message is `404`); PUT is author-only and last-writer-wins (`204`, a no-op on an
  unchanged body); DELETE is the author, the room OWNER or an ADMIN. Every write on a deleted message is `404`.
- **Rate limits (per user, fixed in every mode):** `chat-post` 120/min on the two POSTs; `chat-write` 240/min, ONE bucket shared by the thread details, status and owner PUTs, the message edit and the message delete, and, since 0.6.0, the reaction PUT and the thread and message pin PUTs, and, since the 1.0.0 checkup, the room-lock writes of the room itself: archive, unarchive, delete, a member's role PUT and removal (a leave included) and the workflow PUT (the room rename and the member add keep `room-name` and `room-members`). Those take the room lock like the POSTs, so leaving them unbucketed (the original reasoning: guard-gated, one row each) let one member queue writers behind a room and hold the DB pool; the audit (M1) bucketed them and bounded the lock wait. `chat-read` 300/min, ONE bucket shared by the thread list, the tag list and (1.2) the tag registry read (the two reads that scan a room's rows, and the registry document of up to about half a megabyte; sized against the SPA's refetch rate, `security.md`). The buckets sit before the guards. A room whose lock stays busy past the wait answers `429 room-busy` (`Retry-After: 1`) on any of the writes; the reads (thread list, tag list, and since the 1.2 branch audit the thread detail) are bounded by a deadline (`429 read-timeout`, `Retry-After: 2`) and by in-flight caps (`429 read-busy`, `Retry-After: 1`): the lists at most 8 per user and `threads.readMaxConcurrent` (8) per process, the thread detail its own 2 per user and 3 per process (a separate pool: it is not in the bucket).
- **Body ceilings:** 64 KiB for a message POST/PUT, 192 KiB for a thread POST and the details PUT (`security.md` "Request body ceilings"); `413` beyond.
- Limits: title single line <= 200 (`sanitizeSingleLine`); a message body is Markdown, 1 to 8,000 UTF-16 units after CRLF and a lone CR become LF and the leading blank lines and the trailing whitespace are dropped (the first line's indentation stays, so an indented code block survives), `\n` and `\t` allowed,
  other control characters and the hidden direction and separator characters (U+202A-202E, U+2066-2069, U+2028/2029) a `400` (`sanitizeMultiLine`; titles and TEXT values use `sanitizeSingleLine`, the same hidden-character rule; the zero-width joiner of emoji is fine); stored raw, rendered without HTML.

### Field values

Checked by the pure kernel `threads/ThreadFields.kt` against the room's field definitions (active and retired) and the active member ids; `null` clears a field.

| Type | Valid value |
|---|---|
| TEXT | single line <= 500, no control or hidden direction characters; blank means unset |
| NUMBER | strict JSON number grammar (<= 32 characters), finite, \|x\| <= 1e15; stored as one canonical number (`7` and `7.0` are the same) |
| DATE | strict `YYYY-MM-DD`, a real calendar day |
| SELECT | one option key |
| MULTI_SELECT | 1 to 50 distinct option keys; empty means unset; stored in option order, kept removed options last |
| USER | the id of an active room member |
| URL | absolute `http`/`https`, trimmed, <= 2,000, no control or hidden direction characters (`sanitizeSingleLine`), **no user info** (`https://trusted.example@evil.example/` is a `400`) |

An unknown key is a `400`, and so is a changed or new value for a retired key (an UNCHANGED retired value, e.g. from a stale form, is ignored); a required field is supplied at create and cannot be cleared once set (one never set may stay unset after create);
unchanged values skip validation (see "Stored values" under Workflows).

**Shape and size of `fields` (audit M2, M3).** The request's `fields` is shape-checked right after the body decodes and before the room lock (`requireFieldShape`, run by the route and the service through `validateThreadCreate`/`validateThreadUpdate`): at most 20 keys (`MAX_FIELDS`, the live-field maximum), each value a JSON primitive, `null`, or an array of at most 50 (`MAX_OPTIONS`) string primitives; anything else, a nested object or array included, is a `400` with a fixed detail that echoes nothing. The stored document has a ceiling too: `MAX_FIELDS_DOCUMENT_LENGTH` = **439,001** UTF-16 units of canonical JSON, checked on the merged document in the create and in a changing details PUT (`400` "The field values are too large to store"). Why that number: the kernel already bounds every value, so this is a backstop that a legitimate write never meets, and it is sized as the worst legitimate document - a room may use 200 field keys over its life (`MAX_FIELD_KEYS_PER_ROOM`, retired ones keep their last value and stay in the document), each key 40 units and each value at its widest, a 50-option MULTI_SELECT (2,151 units; a 2,000-unit URL and a 500-unit TEXT with every unit escaped are narrower): `2 + 200 x (40 + 3 + 2,151) + 199`. The live 20 alone are under 44,000. The thread list never reads `fields` (it selects the list columns only: a page of 100 would otherwise load megabytes the row never shows).

- **Message edits and deletes go to the audit trail only**, not to the history.

### Hashtags (V15)

**[changed]** from the sketch (`#[\p{L}\p{N}_-]{1,50}` into `message_tags`): the same table, but a parsed grammar with boundaries, parsed in Kotlin only, backfilled by a boot reindex. PostgreSQL's regex has no `\p{L}` and its classes follow the database locale, and SQL cannot skip code the way the SPA's Markdown tree does, so **no tag is parsed or backfilled in SQL**.

- **What a hashtag tags (0.5 D3): the message.** A thread has a tag while one of its LIVE messages has it; editing a tag away or deleting the message removes it. No tag management screen; `#Wdrozenie` and `#wdrozenie` (case and accent folded) are one tag.
- **Grammar** (one rule, Kotlin and TypeScript; the case table `server/src/test/resources/hashtag-cases.json` is read by `HashtagsTest.kt` and by the SPA parser's test): `(?<![\p{L}\p{N}#&/])#([\p{L}\p{N}_-]{1,50})(?![\p{L}\p{N}_-])` and the capture holds a `\p{L}`. The Kotlin parser (`threads/Hashtags.kt`, pure) checks the left boundary on the code point before the `#`, not with a lookbehind (Java's lookbehind reads one UTF-16 unit and would miss a supplementary-plane letter); every pass is linear (`HashtagsTest` runs 400,000-character hostile bodies). A run of 51 or more characters is no tag; `#42` is a thread number, not a tag; `#fff` is a tag (accepted). The body is NFC-normalised for parsing only; canonical reordering is quadratic in a run of misordered combining marks, which the 8,000-unit body cap bounds (10 to 20 ms measured at the cap, `HashtagsTest`), and a `tag` filter value is length-checked before it is normalised. Fenced code, inline code, link destinations (the run after `](` up to `)` or whitespace, at most 2,000 characters; link TEXT is searched, which the SPA's tree does not link: a known disagreement, with two harmless edge cases of the same kind: `foo\#a` and `&amp;#a`, where the server indexes `a` and the SPA, reading the unescaped text `foo#a` or `&#a`, sees the hash glued to something and does not link it; and `https://x.com/a<#b`, which the SPA links as `b` and the server's bare-URL replacement swallows), link reference definitions, `<autolinks>` and bare `http(s)://` and `www.` URLs are replaced by a space first. The first 20 distinct tags of a message are indexed, the rest ignored, never refused.
- **`message_tags (message_id, thread_id, room_id, tag)`**, primary key `(message_id, tag)`, all three FKs `ON DELETE CASCADE`, ONE index `idx_message_tags_room_tag (room_id, tag, thread_id)`; `thread_id` and `room_id` are copied from the message's thread (a message never changes thread, a thread never changes room) so both reads start at one room's rows: the tag list is an index-only scan of the room and the list's filter semi-joins that scan with the room's threads (`persistence.md` "Hashtags (V15)" has the `EXPLAIN` evidence). `tag` is the folded key (`btrim(left(lower(public.unaccent(<kotlin-lower-cased tag>)), 150))`, one expression on write and on filter), `VARCHAR(150)` because folding can lengthen a tag (a vulgar fraction becomes up to five characters, `⅒` is `" 1/10"`, so a 50-character tag can fold to 246: the key is cut, never refused; the leading space `unaccent` puts before a fraction is trimmed). `messages.tags_version SMALLINT NOT NULL DEFAULT 0` (0 = not indexed yet; the constant default adds the column without rewriting the table, and there is no CHECK: a new one would scan `messages` under an exclusive lock). **The table is a derived index: hard-deleted, rebuilt from the bodies, nothing references a row, and a deleted message's tags must not outlive its scrubbed body.**
- **Lifecycle**: the NEW body is parsed once, after validation and BEFORE the room lock (it is the sanitised body that is stored, and the parse is pure); the writes run inside the message's own write under the room lock (`MessageService.insertInTransaction`, the edit, the delete): post and a thread's opening message insert, ONE `INSERT ... SELECT ... FROM unnest(...) ON CONFLICT DO NOTHING` per message (two spellings can fold to one key) and set `tags_version = 1`; an edit (under the lock) parses the OLD body only when the message's `tags_version` is current and, if the lower-cased sets differ (or the message's `tags_version` is below the current one: it was never indexed, so an unchanged-looking set still has no rows), deletes and inserts, and sets `tags_version`; a delete, a moderator's too, deletes the message's rows AFTER the row's own update (the statement that waits out a reindex holding the row). The message's own `UPDATE` is first in both, so the tags are written last. No new hint, audit line or `MessageResponse` field: the edit's `message.edited` hint already covers a tag change.
- **Reindex at boot** (`MessageTagService.reindexStale`, once, in its own scope, when `threads.tagReindexOnBoot` is true; the test harness turns it off): batches of 200 live messages with `tags_version < 1`, `FOR NO KEY UPDATE OF messages SKIP LOCKED`, one delete and ONE insert statement per batch, then the version. A racing edit waits and writes its own tags, or holds the row and is skipped. Before it, `purgeDeletedTags` removes the tag rows of DELETED messages (at EVERY boot, whatever `threads.tagReindexOnBoot` says: it only deletes rows that must not exist) in batches (a 0.4.0 binary after a rollback deletes without knowing the index; `persistence.md` has the runbook). After it, `StaleDerivedRows.purge` (0.6.0, the same every-boot rule) removes the mention, notice, reaction and pin rows of DELETED messages in batches (`FOR NO KEY UPDATE OF messages SKIP LOCKED`; a 0.5.x binary after a rollback deletes without knowing them; the runbook is in `persistence.md` "Mentions (V17)"). Each of the three steps logs counts and fails alone: a failure logs class names only, leaves that step's rows for the next boot and does not skip the others. Bumping `TAGS_VERSION` reindexes everything after a grammar change.
- **`GET /rooms/{id}/tags`** (`listRoomTags`, reader): `{tag, threadCount}` rows in the paged envelope (`RoomTagPage`); sortable `tag`, `threadCount`, default `-threadCount` (the helper's `id` tiebreaker maps to `tag`, as the members list maps `id` to the user id); filter `q` (API-LIST-005, renamed from `tag` before 1.0.0: `tag` is the thread list's exact, repeatable key), a `containsNormalized` substring of at most 50 characters, optional, for the picker. **A returned `tag` is a valid `tag` filter value** (`requireTagFilter` accepts the stored-key shape, 1-150 code points without `#` or control characters, because folding adds punctuation and length: `ʻ` becomes `'`, `ß` becomes `ss`, `½` becomes `1/2` once trimmed), and the 10-value bound counts values after case folding. `threadCount` counts distinct threads with a live message carrying the tag, open and closed. Reader-only, on the `chat-read` bucket shared with the thread list and under the same read deadline (`read-timeout`). Statuses: 200/400/401/404/429/500.
- **The SPA renders a tag as a link** (a remark plugin that walks the Markdown tree and skips `code`, `inlineCode`, `link`, `linkReference`, `definition`, `html` and `image`) to the thread list with `tag=<as typed>&scope=all`; the server folds it.
- **Not in 0.5.0:** tags in titles, a thread's tag list on rows or in the side panel, a rename or merge of tags, `#42` as a link.
- **[changed] by 1.2** ("Room view, tags and unread (1.2)"): a thread's hashtags are now on the wire (`hashtags` on `ThreadListItem` and `ThreadResponse`) and shown on rows, in the thread header and in the side panel, and `#42` is a link to that thread (SPA only). The grammar, `hashtag-cases.json`, `TAGS_VERSION` and the wire name `tag` do not move; `idx_message_tags_thread` (V31) is added beside the room index. Curated **tags** are a different thing (V32, V33).

### Search (V16)

**[changed]** from the sketch (a trigger-maintained `tsvector`, an immutable `unaccent` wrapper, the `simple` configuration, a GIN index that was built at first and dropped again): `unaccent()` is STABLE, so it cannot feed a generated column or an expression index, and the trigger and the wrapper were two workarounds for one problem. PostgreSQL's own answer is a **text search configuration with `unaccent` as a filtering dictionary**: `to_tsvector(regconfig, text)` is IMMUTABLE, so the vector is a **stored generated column**, with no trigger and no wrapper, and the `ALTER TABLE` is the backfill. `ts_headline` with that configuration marks hits in the ORIGINAL text (a wrapper design would headline unaccented text or miss accented hits).

```sql
CREATE TEXT SEARCH CONFIGURATION public.adder_search (COPY = pg_catalog.simple);
ALTER TEXT SEARCH CONFIGURATION public.adder_search
    ALTER MAPPING FOR hword, hword_part, word, numword, numhword, hword_numpart WITH public.unaccent, pg_catalog.simple;
ALTER TABLE messages ADD COLUMN search tsvector GENERATED ALWAYS AS (pg_catalog.to_tsvector('public.adder_search'::regconfig, body)) STORED;
ALTER TABLE threads  ADD COLUMN search tsvector GENERATED ALWAYS AS (pg_catalog.to_tsvector('public.adder_search'::regconfig, title)) STORED;
```

**No index on either vector, deliberately.** The match is a per-thread probe: the search restricts to the searched rooms' threads first, then reads each thread's messages through `idx_messages_thread` and stops at the first live message that matches, so the work is **linear in the searched rooms' own messages** (a room's, or a caller's across rooms), never in the table. A GIN index on `messages.search` was part of V16 until the cross-room search was measured: no statement reads it (`persistence.md` "Search (V16)" has the `EXPLAIN` evidence), it would cost about 100 MB per 100,000 messages and slow every post, and a table-wide match is the cost the search avoids. When a room's or a caller's message count makes the probe too slow, `BACKLOG.md` holds the options (`btree_gin` over `(thread_id, search)`, or a `room_id` on `messages`): a LATER migration, with its own measurement.

- **`STORED` must be written**: on PostgreSQL 18 a bare `GENERATED ALWAYS AS (...)` is VIRTUAL, and is computed again on every read, and indexes on virtual generated columns are not supported. The six token types are the ones that can hold non-ASCII letters; the ASCII types keep `simple` alone. `threads.search` gets no index: the room index drives that scan and the title match is a filter on it.
- **Backfill cost:** each `ALTER TABLE` rewrites its table and computes every row (about 7 s per 100,000 messages of 1.4 KB; no index is built: `persistence.md` "Search (V16)"); the app is not serving while Flyway runs and the Kubernetes startup probe allows about 150 s. **Never declare `search` in an Exposed table object** (`selectAll()` would read a vector on every message read, and the driver has no `tsvector` codec): `infra/db/Fts.kt` refers to the columns as free expressions. After the configuration changes, or a PostgreSQL major upgrade changes the `unaccent` rules, recompute with `ALTER TABLE ... ALTER COLUMN search SET EXPRESSION AS (...)`, in the same migration file that alters the configuration. A non-superuser owner can create the configuration; it cannot be dropped while a column depends on it.
- **What matches (0.5 A2, 0.5 A3):** **[changed]** message bodies and thread titles, never field values, never tombstones. All terms are required within one message or one title; **[changed]** `simple` does not stem, so every term of three or more characters matches as a prefix and shorter ones match exactly (`awaria w bazie` becomes `'awaria':* & 'bazie':* & 'w'`); case and accents are ignored; no operators, no ranking. Parser facts that need a doc line: `PROD-123` indexes as `prod` and `-123` (searching `PROD-123` finds it, `123` alone does not: BACKLOG); `foo_bar` splits in two; `#db-outage` indexes `db-outage`, `db` and `outage`, so hashtag text is searchable; a token of 8,000 characters is skipped with a NOTICE and the INSERT still succeeds.
- **No input is a syntax error.** The tsquery is built from `to_tsvector`'s own lexemes (documents and queries share one parser and one folding), so `'; DROP TABLE messages; --` comes out as plain terms; input with no letter or digit (`!!!`) is a `400` (`validateSearchQuery`), and input with no indexable word despite one (`<script>`, a tag to the parser) gives a NULL query, which matches nothing and raises nothing.
- **Endpoints:** `GET /rooms/{id}/search` (`searchRoom`, reader) and `GET /search` (`searchRooms`, any authenticated caller, over the rooms they are an ACTIVE member of). `q` is REQUIRED (**[changed] see 1.1:** optional only with `watching=true` *[changed] by 1.2 D3: or a `threadTag`*; the spec parameter `SearchQ`, 2-100 code points after trimming, `sanitizeSingleLine`, a letter or a digit), `closed` and `watching` (1.1) are strict booleans (omitted = both), `sort` is `lastActivityAt`, `createdAt` or `id` (default `-lastActivityAt`), `pageSize` default and maximum 20 (`SearchPageSize`). **Check order:** 401; the `search` bucket (429); for the room route, visibility (404, audited `room.access_denied`); the parameters (400); the query. Statuses: room 200/400/401/404/429/500; global the same without 404. `q` stays in the query string (API-LIST-005) and out of every trail: audit lines and problem bodies carry the path only.
- **One item is a thread** (`ThreadSearchHit`: room id, name and `roomArchived`; thread number, title and `titleSnippet`; status key, `closed`, owner, `messageCount`, `lastActivityAt`; `matchCount`; `messages`, the three newest matching live messages with their `snippet`; and, since 1.2, `tags`, the thread's curated tags), in the page envelope (`total` counts matching threads, no shape exception). A title-only hit has no messages and `matchCount` 0. A snippet is a list of typed segments `{text, hit}`: `ts_headline` returns markup untouched, so the wire never carries a marked-up string; the server headlines with the markers U+0002 and U+0003 (unforgeable, because every title and body refuses control characters), splits on them and collapses whitespace. A snippet is a fragment of the Markdown source as plain text. Only the page's rows are headlined.
- **The search across rooms (`GET /search`)** reads the caller's rooms first (`RoomService.memberRooms`: ACTIVE rooms of an ACTIVE membership, an archived one included, a deleted one never; membership only, an ADMIN's too) and passes them as ONE array argument (`threads.room_id = ANY(...)`); no rooms is an empty page without a search; there is no room filter. The thread predicate probes a thread's messages through a correlated scalar subquery on `COALESCE(search, '')` (never `EXISTS`, never the bare column), so the work is bounded by the caller's own threads in every plan mode: the evidence is in `persistence.md` "Search (V16)". The room search takes the same path with one room.
- **Statements**, one read transaction under ONE deadline of `search.timeoutSeconds` (5, 1..30): the query text (`string_agg` over `unnest(to_tsvector(...))`, quoted and cast to `tsquery::text`; Kotlin keeps it and later statements cast it back); the count and the page of threads (`t.search @@ q OR (the first live message of the thread with m.search @@ q) IS NOT NULL`, `ORDER BY t.last_activity_at DESC, t.id`); the snippets for the page's thread ids only (a `row_number()` over the thread's matching messages, `rn <= 3`, `count(*)` as `hits`); the title headlines with `HighlightAll`. **[changed] see 1.1:** with no `q` (the watched view; *by 1.2 D3 also the tag view*) the query-text and the two snippet statements are never sent, only the member-rooms read, the count, the page and the names. *[changed] by 1.2:* every non-empty page also adds ONE `thread_tags` read for the hits' `tags` (a search with a `q` too), and the tag view adds the name-to-id read of `tags` before the count (each statement armed under the one deadline). **One deadline for the request** (`SearchBudget`): each statement's `queryTimeout` is the whole seconds LEFT of `search.timeoutSeconds` (rounded up, the driver takes whole seconds), the member-rooms read included, and a deadline already passed between two statements sends no further statement, so a request ends within the budget plus at most one second whatever its number of statements. Past it (`isQueryCanceled()` or the spent deadline) the service answers a typed `429` `urn:adder:problem:search-timeout` with `Retry-After: 2`, audited `search.timeout` (ids only, never the term); the throwable is not logged. **At most `search.maxConcurrent` (4, 1..16) searches run in the process at once, both routes together**: a `Semaphore` `tryAcquire` before any pool connection is asked for (never a wait), and a refusal is the typed `429` `urn:adder:problem:search-busy` with `Retry-After: 1`, audited `search.busy` (ids only). ### Reactions (V20)

- **[changed] One single-value set with a body, not a route per emoji.** The sketch's `PUT|DELETE /rooms/{id}/messages/{messageId}/reactions/{emoji}` has three path parameters (API-RES-006 allows two, which is why single messages live at `/rooms/{id}/messages/{messageId}`) and would put chosen text into every `path` field (`authz.denied`, `rate_limit.exceeded`, the access log, the route metrics). The route is `PUT /rooms/{id}/messages/{messageId}/reaction` with `{emoji, reacted}`, 204, like `status` and `owner`.
- **The rule: one emoji, in its one fully qualified spelling** (`threads/Reactions.kt`, pure; no dependency). The value is stored as sent and compared by bytes, so a rule that only checked WHICH code points occur would store one emoji as many look-alike values (a thumbs up with a selector, with a trailing joiner, with four skin tones) and four people could fill a message's 20 places with copies (tag characters could also smuggle invisible ASCII). So the STRUCTURE is checked: 1 to 32 UTF-16 units and at most 10 code points (0.6 A23); exactly one extended grapheme cluster (`BreakIterator.getCharacterInstance`); then exactly one of (a) a flag, a PAIR of regional indicators; (b) a keycap, `0-9`, `#` or `*`, the variation selector (U+FE0F, REQUIRED: the unqualified `1` + U+20E3 is a second spelling of one emoji, so it is refused; V20 was unreleased, so the rule could change) and U+20E3, last; (c) one of the three tag flags (a black flag, its tag characters spelling `gbeng`, `gbsct` or `gbwls`, the cancel tag U+E007F); (d) one or more elements joined by single zero-width joiners (never first, last or doubled), where an element is an emoji that is not ASCII, not a skin-tone modifier and not a regional indicator, followed by nothing, or by ONE skin tone (only after an emoji modifier base, `Character.isEmojiModifierBase`), or by the variation selector once (only after an emoji without emoji presentation of its own, where it is required: a heart needs it, a thumbs up refuses it); a skin tone and a selector never meet. Accepted: a thumbs up, with a skin tone, a flag pair, a ZWJ family, a keycap, a tag flag, a heart with its selector, a rainbow flag. Refused: a digit, `#` with a selector, a letter, a heart without its selector, a lone ZWJ, selector, skin tone or regional indicator, two emoji, an emoji and a space, three regional indicators, an emoji with a combining accent or a bidi override, a thumbs up with a selector (once or three times), a trailing joiner, four skin tones or the combining keycap, tag characters after anything but a black flag or spelling anything but the three flags, `#` with two selectors or three keycaps, a regional indicator and a skin tone, a chain of more than 10 code points. **What it cannot check** is membership of the official emoji list: a chain of up to five pictographs joined by single zero-width joiners is one valid arrangement and passes. The SPA sends the picker's fully qualified form (emoji-mart's data spells every keycap with U+FE0F: pinned by `emojiKeycaps.test.ts`). The case table is `server/src/test/resources/reaction-cases.json`, read by the server's test only (the SPA picks from a list and validates nothing).
- **`message_reactions(message_id, user_id, emoji VARCHAR(32) COLLATE "C", created_at)`**, key `(message_id, emoji, user_id)`; hard-deleted, a join toggled on and off (the audit line holds the changes; a re-add must not collide). `COLLATE "C"` compares by bytes whatever the database locale, so a heart with and without its selector are two values.

- **A reaction is speech, not activity** (0.6 A24): members only, refused in a closed thread (the closed-thread rule above) and an archived room; no rail bump, no unread, no notice.
- **On the wire:** `MessageResponse` gains `reactions: [{emoji, count, reacted, names}]`, at most 20, in the order each emoji first appeared, empty on a tombstone; `names` is the first three reactors by time (0.6 A25). One grouped read per page (`GROUP BY message_id, emoji`, `bool_or(user_id = ?)`, `(array_agg(user_id ORDER BY created_at, user_id))[1:3]`). A deleted message loses its reactions in the delete's own transaction.
- **In the code:** `threads/MessageReactionService.kt` holds the table (`Reactions`), `set` (ONE message write under the room lock: `withMessageWrite` with the member guard), `summaries` (the grouped read; it runs inside the message read's own transaction) and the follower that clears a delete; `MessageService` always runs that follower and its reads take the viewer (`list(..., viewerId)`, `read(roomId, messageId, viewerId)`), so a post answers `reactions: []` and a tombstone never carries any. `threads/ReactionRoutes.kt` is the route (the `chat-write` bucket, then visibility, member, body; audit `message.reaction_changed` on a change only). The body ceiling is the small one (16 KiB).
- **Not in 0.6.0:** the full list of reactors; a notice for a reaction; a moderator removing someone else's reaction.

### Pins (V21)

- **A pin is of a thread or of a message; 50 per room** (0.6 A27). `room_pins(id, room_id, thread_id, message_id?, pinned_by, pinned_at)`: partial unique indexes `(thread_id) WHERE message_id IS NULL` and `(message_id) WHERE message_id IS NOT NULL`, so a thread and one of its messages can both be pinned; a message pin carries its thread for the panel's link. Hard-deleted (a pointer; unpinning removes it); no history event.
- **Who pins (0.6 D4): any member pins and unpins.** Every pin says who made it and each change is audited. The member guard is the same as for a post.
- **`GET /rooms/{id}/pins`**: reader; the paged envelope `RoomPinPage`; sortable `id`, `pinnedAt`, default `-pinnedAt,-id`; no filter; statuses 200, 400, 401, 404, 500. An item: `{id, kind THREAD|MESSAGE, threadNumber, threadTitle, threadStatus, threadClosed, message?, pinnedById, pinnedByName, pinnedAt}`; a thread pin has `message: null`, a message pin carries the ordinary `MessageResponse`. At most 50 rows exist, so one page of 50 is the whole set; it still answers the envelope.
- **`PUT /rooms/{id}/threads/{number}/pin`** and **`PUT /rooms/{id}/messages/{messageId}/pin`**, `{pinned}`, 204, single-value sets like the reaction. Order: 401; `chat-write` (429); visibility (404); member (403); the body (400); then under the room lock: the thread or message (404); archived (409); the state it already has (204, nothing written); the 51st pin (409, `urn:adder:problem:pin-limit`); the write; one hint; the audit line. A closed thread is NOT refused: a pin is the room's, and "pin the thread that explains what happened" is the use. An archived room refuses.
- A deleted message loses its pin in the delete's own transaction, through a follower (`PinCleanup`, `threads/PinService.kt`; `message.deleted` already tells every subscriber). The list reads the pinned messages in its own transaction (`MessageService.readInTransaction`, one query); a message pin whose message was deleted a moment before is simply left out of that read. A pin is not activity (no rail or thread bump, no history event), so the 51st-pin count and the state check run under the room lock and nothing else moves. ### Watching (V26)

- **Term.** UI: Watch / Watching / Stop watching, "watchers" (the pane's toggle keeps ONE label with `aria-pressed`, the pin precedent: "Watch this thread", the count beside it) (PL: Obserwuj / Obserwujesz / Przestań obserwować, "obserwujący"). API and schema: `watching`, `watcherCount`, `/watch`, `thread_watches`, the token `<@watchers>`, the kind `WATCHERS_MENTIONED`. The composer's list also matches the typed word `observers`; "observe" appears nowhere else.
- **Who watches (1.1 D1).** Any member of the room watches or unwatches any thread of it, a closed thread and an archived room included. A non-member ADMIN cannot (403). The creator watches a new thread and each new owner watches the thread they receive, automatically, and each may stop; a later hand-over to the same person watches again. Replying or being mentioned does NOT make a watcher (1.1 D10).
- **The table** `thread_watches(thread_id, user_id, room_id, created_at)`, primary key `(thread_id, user_id)`; `thread_id` cascades with the thread, and `(room_id, user_id)` references `room_members ON DELETE CASCADE`, so leaving or being removed drops the watches and rejoining starts clean. Delete class HARD (a join toggled on and off; no soft delete, no version column). Index `idx_thread_watches_user_room (user_id, room_id, thread_id)`. V26 backfills each existing thread's creator and current owner who are still members; the backfill creates no notice.
- **`PUT /rooms/{id}/threads/{number}/watch`** with `{watching}`, 204. Guard order: 401; its own `thread-watch` bucket, 30 a minute (429); visibility (404, audited `room.access_denied`); `requireRoomMember` (403, a non-member ADMIN) BEFORE the body; the body (400); then one transaction WITHOUT the room lock: hold the caller's own member row (`RoomMemberService.holdMembership`, `FOR KEY SHARE`; gone is a 404, never a 500), the thread (404), the same state (204, nothing written), the write. Watching is the caller's own state, like read state: no room lock, no live hint (`LiveKind` and the spec enum are untouched), its own bucket (the toggle is audited, the read-state writes are not). 16 KiB body ceiling (`THREAD_SMALL_PUT_PATH`). Audited `thread.watch_changed` on a change only, because it changes who a write notifies.
- **On the wire:** `ThreadResponse.watching` and `watcherCount`; `ThreadListItem.watching` (one batched read per list page, beside the unread counts). The list of watchers is not on the wire (`BACKLOG.md`). A deleted user's watches are inert.
- **The filter (1.1 D2).** `GET /rooms/{id}/threads` and both searches gain `watching` (strict boolean). The thread list also gains `mentionsMe` (strict boolean, below). On the search routes `q` becomes optional ONLY with `watching=true` *[changed] by 1.2 D3: or a `threadTag`* (the spec parameter `SearchQ`; the shared `Q` of the directory is untouched): that is the cross-room "Threads I watch" view; without `q` a hit has `messages: []`, `matchCount: 0` and the title as one non-hit segment, and the query-text and snippet statements are skipped. The search budget and the concurrency cap are unchanged. Search has no `mentionsMe`. **Rules (S4):** `q` is validated whenever it is given (a short one is still a `400` with `watching=true`; a blank one counts as none); without `watching=true` a missing `q` is a `400`, so `watching=false` alone is a `400`; `watching=false` WITH `q` keeps the matches the caller does not watch. The predicate is the thread list's `threadWatchedBy` correlated on each thread's own room (`threadWatchedByInRoomOf`: `idx_thread_watches_user_room` leads with the person and the room), ANDed with `threads.room_id = ANY(<the caller's rooms>)`. **The cross-room view starts from `RoomService.memberRooms`, never from `thread_watches`**: a deleted room's watches stay in the table, inert, and are never listed; a removed member's go with the membership; an ADMIN who is not a member watches nothing, so their `watching=true` is an empty page (the room route admits them, with nothing watched). **Order:** the request's `sort`, default `-lastActivityAt` then `id` ascending (the same as every search; no other order is introduced). `GlobalSearchTest` pins that the watched view's two thread statements carry no message table and reach the watches through the index.
- **What counts as activity for a watcher (1.1 D3):** a reply, a status change (close and reopen included) and an owner change. Not a title or field edit, a message edit as such, a delete, a reaction, a pin or the workflow PUT's `moveThreads`.

### Notice kinds (V27, V28)

- **[changed] by 1.3 D2: twelve kinds.** `MESSAGE_QUOTED` is the second name of both enums, right after `MENTIONED`, and the kind of a quoted message's author; the list, the priority line, the addressed kinds and the audit bound below are read with it: "Quotes (1.3)" "The notice".
- **Eleven kinds, persisted and frozen** (the Kotlin enum is the whitelist, no CHECK; the type IS the reason, there is no reason column): `MENTIONED`, `TEAM_MENTIONED`, `WATCHERS_MENTIONED`, `EVERYONE_MENTIONED`, `THREAD_REPLIED`, `THREAD_CREATED`, `THREAD_ASSIGNED`, `THREAD_OWNER_CHANGED`, `THREAD_STATUS_CHANGED`, `THREAD_CLOSED`, `THREAD_REOPENED` (three status kinds, 1.1 D11). A type per reason because the grid is per kind and muting `@everyone` apart from direct mentions is the main use. Other new names: `NotificationChannel.IN_APP`; `MentionGroupKind { TEAM, WATCHERS, EVERYONE }`.
- **Who gets which kind.** Message event (a post or a thread's opening message): every ACTIVE member other than the author gets ONE notice, the most specific that applies, in this priority: `MENTIONED` > `TEAM_MENTIONED` > `WATCHERS_MENTIONED` > `EVERYONE_MENTIONED` > `THREAD_REPLIED` > `THREAD_CREATED`. The base reason is `THREAD_CREATED` for every member on an opening message (1.1 D4) and `THREAD_REPLIED` for the watchers on a reply. Hand-over: the new owner is added as a watcher first, then gets `THREAD_ASSIGNED` unless they took the thread themself; the other watchers get `THREAD_OWNER_CHANGED` (`THREAD_ASSIGNED` > `THREAD_OWNER_CHANGED`). Status move: the watchers except the actor, by transition: `THREAD_STATUS_CHANGED` (within a category), `THREAD_CLOSED`, `THREAD_REOPENED`; never the other members (1.1 D4). One notice per recipient per event; the actor never gets one (1.1 D6). `<@watchers>` in an opening message is shown as a mention and reaches nobody (only the author watches).
- **[changed] The unique index** becomes `uq_notifications_message_recipient (message_id, recipient_id) WHERE message_id IS NOT NULL` (one notice per message and recipient; it replaces the 0.6 index that included the type). V27 also adds `in_app BOOLEAN NOT NULL DEFAULT TRUE` and replaces the unseen index by `idx_notifications_bell (recipient_id, id) WHERE seen_at IS NULL AND in_app`.
- **The grid, no master switch (1.1 D7).** Every kind has an in-app switch and an email switch; none is locked on. **Defaults live in code** beside the enum (`NotificationType.defaultOn(channel)`, an exhaustive `when`) and are frozen with the name: **in-app is ON for every kind and email is OFF for every kind, the two 1.0 kinds included** (**[changed]**, reverses 0.6 D2's "on by default"; `defaultOn(EMAIL)` is false everywhere). `user_notification_preferences` stores DEVIATIONS only; V28 adds `enabled BOOLEAN NOT NULL DEFAULT FALSE`: `enabled = false` is exactly V22's "switched off" row, `enabled = true` is an opt-in. No seeding of rows (the V5 seeding precedent is not followed: it would make `users/` write a `notifications/` table).
- **Preferences API (additive).** Channel gains `IN_APP`; GET kinds gain `inApp`; PUT keeps `disabled` (pairs that are off) and gains optional `enabled` (pairs that are on); anything unlisted takes its default. A pair listed twice, or in both lists, is a 400 (a 1.0 client cannot switch a default-off kind on by accident). Audit `user.notification_preferences_changed` lists the deviations as `TYPE:CHANNEL=on|off`.
- **Channels are judged when the notice is made.** Both off: no row. In-app off and email on: a row with `in_app = false`, never listed, never counted, never in the bell. Email off: `emailed_at = created_at` (V22's "settled, never mailed" stamp; required, or default-off rows would fill `idx_notifications_email_due` and exhaust the digest's 5,000-row scan). Switching a kind back on covers notices made from then on. The digest honours `enabled` and the defaults, and reads effective preferences.
- **Account email is not a notification kind.** The MFA code and the password-reset link are sent directly, never through the digest or the preferences, and always go. Adder sends no "password changed" or "account created" email; Lettuce's locked-on kinds are not ported (`BACKLOG.md`).
- **Edit rules (an edit re-derives who the new body addresses, groups resolved now, against the message's existing notices):** none and addressed: insert; a less specific notice and addressed: delete and insert (a fresh, unseen notice); a more specific mention kind and the new body addresses them less specifically: relabel in place; a mention kind and no longer addressed: fall back to `THREAD_CREATED` (opening message) or `THREAD_REPLIED` (they watch now), else delete (0.6 A6); a base kind and no longer addressed: keep.
- **The port** `threads/ThreadNotices` replaces its two string constants by `enum NoticeReason` (the eleven names) and `Notice(userId, reason)`; calls `forMessage`, `ofMessage`, `reviseMessage`, `messageRemoved`, `forThread`, `threadRead`, all INSIDE the caller's transaction; `notifications/` maps `NoticeReason` to `NotificationType` by an exhaustive `when`. The audience is computed by the pure kernel `threads/NoticeAudience.kt`; the write is `notifications/NoticeWriter`: one preferences read for the recipients, one constant-text `INSERT ... SELECT FROM unnest(...) ON CONFLICT DO NOTHING RETURNING recipient_id`, at most 500 rows.
- **The bell, the rail and the `@` mark (0.6 D1 stays).** The rail's count and the thread list's `@` mark count only the ADDRESSED kinds, the four mention kinds plus `THREAD_ASSIGNED`; activity notices appear in the bell and its badge, never there. `GET /notifications` gains a repeatable `type` (any-of; an unknown name is a 400) and lists `AND in_app`; `seen-all` is `AND in_app`. A notice about the thread the reader is looking at (visible, at the end) must not raise the badge; the pane acknowledges it through the read marker.
- **Retention stays 90 days, no per-recipient cap** (`BACKLOG.md`: the per-recipient unseen cap is more pressing now).
- **What is made when (S5, S6).** The port, the eleven kinds, the channels and the grid shipped first (S5); S6 adds the audience kernel `threads/NoticeAudience.kt` (pure, `NoticeAudienceTest` is its table), so the routes now make `MENTIONED` (a direct `<@id>`), `THREAD_CREATED` (an opening message, every active member), `THREAD_REPLIED` (a reply, the watchers), `THREAD_ASSIGNED` and `THREAD_OWNER_CHANGED` (a hand-over), `THREAD_STATUS_CHANGED`, `THREAD_CLOSED` and `THREAD_REOPENED` (a status move, the watchers); the group tokens (S7) add `TEAM_MENTIONED`, `WATCHERS_MENTIONED` and `EVERYONE_MENTIONED` (the audience is `MessageMentionService`'s, read inside the write: a team's active roster intersected with the room's active members, the watchers, the room), see "Group mentions (V25, V30)". `NoticeWriterTest` drives every reason through the port, `ThreadWatchNoticesTest` the audience inside real writes. `NoticeOutcome` (`recipients`, `kinds`, `addressed`) is what a call answers and the route audits (the post, the thread POST, the edit, the status PUT and the owner PUT each emit ONE `notification.created` line). The email budget runs BEFORE the insert, on the recipients whose email is on for the kind.
- **The audience is read inside the write (S6).** The recipients of a reply, a status move or a hand-over are `ThreadWatchService.recipientIds`: ONE joined statement (`thread_watches` with `room_members` on the composite key and with `users` active) for the thread, read under the room lock, so a watcher who left or whose account is deleted is never in it; `thread_watches` is never read raw for an audience (a deleted account's or a left member's watch is inert, and an ADMIN who is not a member is never a recipient). The members of an opening message are `allActiveMemberIds`. `MessageRef.opening` says which: it is exact for a post and an edit (an edit asks whether its message is the thread's first). The caller lists the audience in PRIORITY order (the order of `NoticeReason`), because the email budget admits people in the order given.
- **An edit (S6) tells only the NEWLY addressed (1.1 A34, 0.6 A6).** "Newly addressed" is judged per reason (S7, 1.1 A39): a person is newly addressed at reason R when the new body addresses them at R and the old body addressed them neither at R nor at anything more specific (`NoticeAudience.ofEdit` takes `before`, the most specific mention reason each person had from the old body: its direct rows and its old group rows, their audience read as of the edit). A KEPT group token addresses nobody again; a person the edit now names DIRECTLY is always newly addressed at `MENTIONED`, whatever group reached them before. `NoticeAudience.ofEdit` reads that against `ThreadNotices.ofMessage`: `add` (the "less specific, now more specific" upgrade included, which is a `remove` plus an `add`, a fresh unseen notice) only for the newly addressed; a mention the edit KEPT whose notice is gone (retention, a switch, a leave and rejoin) stays without one; a person who keeps a notice is never in `add` (the budget counts `add` before the insert); a mention kind that fell to a base kind is RELABELLED in place, in ONE `UPDATE` for all of them with the deletes in ONE `DELETE`; a base notice is never added by an edit. A "delete and insert" upgrade whose chosen kind (after the fallback below) is the one the person already holds is skipped: the row stays, no fresh unseen row and no second budget charge. On an opening message the fallback to `THREAD_CREATED` is available to the people the edit adds as well as to those it drops. A relabel judges the person's channels again with the fallbacks below, counting email as reachable ONLY while the row is unmailed (`emailed_at IS NULL`: the stamp is never reopened), deletes a row that is neither shown nor mailable, and sends the people whose bell changed (a row that started or stopped showing, or moved in or out of the addressed kinds) ONE `notification.created` hint. With no mention added or removed nothing is read (the thread's first-message question is asked lazily, only then).
- **Fallback when the top kind is fully off (1.1 A36).** Each notice carries the person's other applicable reasons in priority order (`Notice.fallbacks`: a mentioned watcher is `MENTIONED`, then `THREAD_REPLIED`; a mentioned member of an opening message `MENTIONED`, then `THREAD_CREATED`; the new owner `THREAD_ASSIGNED`, then `THREAD_OWNER_CHANGED`). The writer uses the first reason whose kind is on for the app or for email; there is no row only when every applicable reason is off on both channels. Over the wide-event budget a named person loses the fallbacks (only `MENTIONED` and `THREAD_ASSIGNED` can be told). One preferences read covers all the reasons and the insert stays one statement.
- **Repeated thread-level notices coalesce (S6, security review).** `THREAD_STATUS_CHANGED`, `THREAD_CLOSED`, `THREAD_REOPENED`, `THREAD_OWNER_CHANGED` and `THREAD_ASSIGNED` have no message to be unique by, so a status toggled ten times used to make ten rows per watcher. A recipient who already holds an UNSEEN row of the same kind about the same thread that can still deliver (it shows, or its mail is still to come: `in_app OR emailed_at IS NULL`) has it REPLACED (deleted, and a NEW id inserted), in one statement (`DELETE ... RETURNING` feeding an `INSERT`) before the budget and the plain insert: a NEW id, so the row tops the bell and a `seen-all` already running cannot swallow it; the actor, the person's CURRENT in-app verdict, and the old `emailed_at` carried over (not counted against the email budget again, an already-mailed row not mailed again); the live hint still goes to them. A row still waiting for the digest also carries its `created_at` (the FIRST event's instant): the digest is due `notifications.email.delaySeconds` after it, so a churning thread's mail is never postponed, and a waiting row already older than the delay is not coalesced into (the event makes a fresh row). A dead row (not shown, mail settled) is left alone. The lookup is `idx_notifications_unseen_thread (recipient_id, thread_id) WHERE seen_at IS NULL` (V19), so no new index. Once seen, the next event is a new row. Replies and mentions stay one row per message and person. **Two effects follow, both accepted (the 1.1.0 branch audit, L5; 1.1 A37):** (1) a SETTLED unseen row (it shows in the app and its mail is withheld or already sent) absorbs every later move of that kind: it is replaced in place, keeps its `emailed_at`, and so nothing more is mailed for that thread and kind until the person has seen it; the bell is what tells them. (2) a row still WAITING for the digest, refreshed by a SECOND actor, takes that actor (the new row names the latest actor, the `created_at` stays the first event's), so the one mail it becomes names that second actor, never an extra mail for the first.
- **A steward can re-subscribe a member who opted out** by handing the thread to them (they watch the thread they receive, 1.1 D1) and back, or by taking it themself; it is accepted (1.1 A32): bounded by `chat-write` only (the auto-watch and `THREAD_ASSIGNED` are direct, outside the wide-event budget, which limits just the `THREAD_OWNER_CHANGED` fan-out), and traced by `thread.owner_changed`.

### Group mentions (V25, V30)

- **Grammar**, one rule in Kotlin and TypeScript, same pre-pass and same backslash rule as `<@id>`: `<@(?:([1-9][0-9]{0,9})|team:([1-9][0-9]{0,9})|(watchers|everyone))>`. All three forms start with `<@` on purpose: `<!...>` is an HTML declaration to CommonMark and `<team:42>` is an autolink to both micromark and the server's autolink regex, while `<@...>` is literal text to both. Lowercase and exact (`<@Everyone>`, `<@here>`, `<@teams:4>`, `<@team: 4>`, `<@team:0>`, `<@team:042>`, an eleven-digit team id are plain text). Counted per message: the first 20 distinct users (unchanged), the first 5 distinct teams, each keyword once. The shared case table (`mention-cases.json`) gains optional `teams`, `everyone`, `watchers` members, absent meaning none.
- **Who may use them (1.1 D5).** Any member. No confirm before `@everyone` (the composer shows a non-blocking `role="status"` line with the room's member count). Old bodies are not reindexed: a literal `<@everyone>` written before 1.1.0 stays text (the V17 rule).
- **Team handle (V25).** `teams.handle VARCHAR(30)`, optional, 2 to 30 characters, `^[a-z][a-z0-9]*(-[a-z0-9]+)*$`; unique among ACTIVE teams (`uq_teams_handle_active (handle) WHERE NOT marked_as_deleted`), freed on delete; no backfill. Uppercase is a 400, never folded. Reserved (400): `everyone`, `watchers`, `observers`, `here`, `all`, `channel`, `room`, `team`. API: `handle` (nullable) on the team create and update requests, `TeamResponse` and `TeamListItem`; `GET /teams` gains a `handle` substring filter (`containsNormalized`) and `sort=handle`; a PUT without it clears it (full replace, the `managerId` rule). The clash is a 409 through `UNIQUE_CONSTRAINT_DETAILS`.
- **A team mention reaches** the team's active roster (the set a room's team add uses, `TeamService.activeRosterIds`) that are also active members of the room, at write time. The manager counts only when on the roster. A team that is unknown, deleted or has no handle is plain text. The notice does not name the team (`BACKLOG.md`).
- **The index** `message_group_mentions(message_id, group_kind, team_id, thread_id, room_id)`, V30: a derived index of the group mentions in LIVE bodies, delete class HARD (the `message_mentions` reasoning), `UNIQUE NULLS NOT DISTINCT (message_id, group_kind, team_id)`, written and cleared by the message's own write; `threads/StaleDerivedRows.kt` knows the table.
- **On the wire:** `MessageResponse.groupMentions: [{kind, teamId?, teamHandle?, teamName?}]`, at most 7 (5 teams, 2 keywords), empty on a tombstone; `mentions` is unchanged. Names and handles are read at request time (a renamed handle shows the new one on old messages). The SPA shows `@handle`, `@everyone` or `@watchers` only when `groupMentions` lists the token (the SPA follows the server); search snippets still show raw tokens.
- **`mentionsMe`** on the thread list (a strict boolean, `false` the complement) matches a thread with a live message that mentions the caller directly, a team the caller is on now (a mentionable team: active, with a handle), everyone, or the watchers while the caller watches the thread now; the group part applies only to a MEMBER of the room (an ADMIN outside it is addressed by name only). The URL key `mention=me` stays; the SPA's "Mentions me" sends `mentionsMe=true`; `mentionedId` stays direct only (1.1 A40).
- **Implementation (S7).** `threads/Mentions.kt` answers `ParsedMentions(users, teams, watchers, everyone)` (a full linear pass: a later keyword still counts after twenty people); `threads/GroupMentions.kt` holds the index (`MessageGroupMentionIndex`: `resolve`, `insertInTransaction`, `heldBy`, `replaceInTransaction`, `groupsOf`), `GroupReach` (the audience reads, each at most once per write, lazily: the room's members, the thread's watchers, a team's roster intersected with the members) and `threadMentionsMe`. A post reads only what the body needs (a reply with no group token reads the watchers as before; the members are read for an opening message, `@everyone` or a team). An edit reads the held group rows, replaces them, and returns at once when neither the direct set nor the group tokens changed; otherwise it reads the held notices, the new body's audience and, only when the old body had groups AND the new one has groups, the old body's audience (A39; `<@watchers>` of an opening message is no old reason and costs no read). The kernel `NoticeAudience.ofMessage`/`ofEdit` take the three group arguments (`teamMentioned`, `watchersMentioned`, `everyoneMentioned`); `<@watchers>` in an opening message reaches nobody. `TeamService.mentionableTeams`, `mentionableRosters` and `teamIdsOf` are the only reads of `teams` the chat does.
- **Wide events and edits (A38).** An edit is ONE event, wide when the people it adds (actor left out, BEFORE the channels are judged) or the people whose bell its relabels change exceed 20. Refused, it still writes, adds only the directly named, and relabels in place but sends the relabelled no hint (`notification.created` carries `relabelled`). An upgrade deletes the old notice ONLY when its replacement is made (the budget, the person's switches or the email budget can each refuse it): `NoticeWriter.deliver` takes a `beforeInsert` hook that runs ONCE with the people who really get a row. A dropped upgrade keeps the old notice only while its kind is still one of the body's reasons for the person (judged against the FULL revision, fallbacks included); otherwise it is relabelled in place (`NoticeJudge.relabel`, no budget charge, deleted when nothing applies), so no notice says what the body no longer says. One edit sends ONE hint (the made notices and the relabelled people together). The common token-unchanged edit (the teams as a SET, in any order, when every parsed team id is a held one) returns before any team is read; a parsed team that is not mentionable costs one resolve and then the same early return. A group kind switched off on both channels falls back like any (a watcher muted on `EVERYONE_MENTIONED` keeps `THREAD_REPLIED`; a non-watcher is not told), and over the budget a group kind is not direct, so only `MENTIONED` and `THREAD_ASSIGNED` stay.

### Bounds, budgets, live and audit

- **Recipients per event:** at most `MAX_ROOM_MEMBERS` = 500, structurally (each recipient is an active member by the foreign key): 499 when a member acts, 500 when an ADMIN who is no member acts (closing a thread all members watch, handing it over). **Live:** `notification.created` stays `Audience.TARGETS`, ONE hint per event with up to 500 recipient ids (about 5.6 KB at ten-digit ids, under the 8,000-byte limit `live.md` pins), the recipients with an in-app row only. A room-wide hint is wrong: a notice is personal, and subscriptions cover only the rail's first 100 rooms. No new live kind.
- **Wide events (1.1 D9).** An event that would notify more than 20 people is a "wide event". Each actor gets `notifications.maxBroadcastsPerActorPerDay` (`NOTIFICATIONS_MAX_BROADCASTS_PER_ACTOR_PER_DAY`, 500, 1..10000) wide events per UTC day, counted on the actor's `notification_email_budget` row (V29: `broadcasts`, `broadcasts_exceeded_at`). Past it the write STILL succeeds and only direct `<@id>` mentions (`MENTIONED`) and the hand-over (`THREAD_ASSIGNED`) notify. First overrun of an actor's day: audit `notification.broadcast_budget_exceeded` (`actorId`, `roomId`, `budget`, `withheld`). **Implementation (S6):** an event is wide when the audience, after the actor and duplicates are dropped and BEFORE the channels are judged, is larger than `WIDE_EVENT_RECIPIENTS` (20); `NotificationEmailBudget.admitBroadcast` runs `INSERT ... ON CONFLICT DO NOTHING` (the row) then `UPDATE ... SET broadcasts = broadcasts + 1 WHERE broadcasts < <budget> RETURNING` (atomic: the row lock lasts to the commit, so concurrent writes of one actor cannot overshoot), and on a refusal stamps `broadcasts_exceeded_at` once. Refused events do not count; the counter resets with the UTC day. An event of 20 people or fewer never touches the row (an email-eligible recipient locks it through the digest budget as before). Edits count as events too (the people they add).
- **Email budget (1.1 D8).** The V24 budget (20 distinct recipients per actor per UTC day, ADMIN included) stays and is ONE pool for every kind. It counts only recipients whose email is on for that kind, admitted in order of specificity (a message naming people and everyone admits the named first). The in-app notice is made as usual only if the recipient's in-app switch is on; a person whose in-app is off gets a row (`in_app = false`) only when their email is on, mailable (a mailer exists) and inside the budget, and NO row otherwise; the budget withholds only the email (`emailed_at` stamped at insert). The knob is `NOTIFICATIONS_EMAIL_MAX_RECIPIENTS_PER_ACTOR_PER_DAY` (`notifications.email.maxRecipientsPerActorPerDay`, 20). Consequence: one `@everyone` to 20 mailable people spends the actor's whole budget for the day. With email off by default the budget now binds only for opted-in recipients.
- **Audit:** `notification.created` becomes one line per event: `recipients` (count), `kinds` (`KIND:count`, sorted), `recipientIds` (the directly addressed only, at most 21); `thread.watch_changed` (`byUserId`, `roomId`, `threadId`, `number`, `watching`); `notification.broadcast_budget_exceeded`; `team.created` and `team.updated` gain `handle`. The list is owned by `observability.md`.
- **Write path.** A plain reply in a watched thread adds four short statements under the room lock (the watchers, the room's active members, the recipients' preferences, the insert). The 499-row insert is measured on the pinned Postgres image (`NoticeWideEventTest`): about 21 ms (median) for the whole `forThread` call and 30 to 38 ms for the whole opening-message write in a full room against 8 to 18 ms in a room of two, recorded in `persistence.md` "Notices (V18)".
- **Rollback below 1.1.0** (runbook: `persistence.md` "Rollback below 1.1.0"): a 1.0.0 binary still inserts (its bare `ON CONFLICT DO NOTHING` works with the new index), lists `in_app = false` rows of the two kinds it knows, claims and drops notices of unknown kinds in its digest, reads a 1.1 opt-in as off (fail-safe), and wipes a person's in-app mutes and opt-ins on a preferences save. Before starting it, seed an explicit EMAIL-off row for every account and 1.0 kind (no row meant off in 1.1 and means ON in 1.0.0); `MAIL_TRANSPORT=disabled` is not a substitute.

The header's tag row and a list row show three pills and a "+N" (a button opening the details in the header, words in a row); the picker's pills have named remove buttons. Not in 1.2: tags in the new-thread form, colours, a per-room subset, facet counts (1.2 A1, 1.2 A19).

### Unread filter and "Mark all as read" (1.2 A10 to 1.2 A12)

- **`GET /rooms/{id}/threads?unread=`** (strict boolean, a repeat or any other word a `400`; `false` is the complement, `NOT` of the same predicate, never NULL). The predicate is the count's own definition, so it cannot disagree with `unreadCount > 0`: `last_activity_at > floor AND EXISTS` a message among the newest 100 after the caller's marker with `created_at > floor` (`ThreadUnread.kt`; the SQL, its plan and its measurement: `persistence.md` "Read state (V19)"). It combines all-of with every other filter (`closed`, `status`, `ownerId`, `watching`, `mentionsMe`, `tag`, `threadTag`, `field`), closed threads are counted like any other, and `total` is on the same predicate. The floor is read once per list and shared with the counts; a thread whose only recent activity is a status, owner, title or field change (`last_activity_at` past the floor, no message past it) is NOT unread. A caller with no read state (an ADMIN outside the room): `true` is an empty page, `false` is everything. The SPA's toggle sits beside "Mine", "Mentions me" and "Watching" (URL `unread=me`, hidden for an ADMIN outside the room). Not on the searches.
- **`POST /rooms/{id}/read-all`**, `204`. Order: 401; `read-state` (429); visibility (404, audited); member (403). No room lock, and no transaction that holds the member row while it settles notices. Step 1, one short transaction: the caller's own member row (`read_from` and `seen_at` raised to now with `GREATEST`; no row is a 404) and the newest id among their unseen notices of the room (the ceiling). Step 2: those notices (every kind and channel; nobody else's) made no later than that instant and up to the ceiling are marked seen in chunks of 1,000, each its own short transaction (`ThreadNotices.roomUnseenCeiling` and `roomSeenChunk`, V34's index). One call per person at a time (a second is the typed `429` `read-busy`). A failure after step 1 leaves the floor raised and some notices unseen: the client sees an error and calling again settles the rest. Raising the floor reads EVERY thread of the room as read at once, closed and never-opened ones included, in one statement whatever their number, and moves no `thread_reads` marker; a message or thread written after the instant is unread again (a message committed in the same instant may be swallowed). Idempotent, `204` whether anything was unread or not; an ARCHIVED room is marked like any other (view state, like the read marker); an ADMIN outside the room is `403` (no read state). NO live hint (the sending tab re-reads its own caches, others catch up on focus) but an audit line, `room.read_all` (ids and the count settled), because unlike the marker it settles an unbounded number of rows: ONE line for a call that settled at least one notice, and one with `complete=false` for a call that failed or was cancelled after step 1; a call with nothing to settle writes none (1.2 branch audit: 240 a minute of identical lines), and a refused second call is a `read.busy` line coalesced to one a minute per person. Cached search results keep their old `unreadCount` (search is not live and the filter is not on it). The SPA asks first (`ConfirmActionModal`) and afterwards re-reads the room's thread tree, the rail and `["notifications"]`. A message committed in the same instant may be swallowed.

### The tab title and the hidden tab (1.2 D8, 1.2 D9)

No number when signed out, `connecting`, `paused` or `idle` (the 8-hour close), and none once the socket has been `down` for 5 s (the "Reconnecting…" badge's grace, so a re-mint or a restart does not blink the title) (1.2 A17).

## Quotes (1.3)

Binding for 1.3.0. The code lands in steps (plan steps S1 to S7; where a rule names a file, that file is the destination). The user's decisions 1.3 D1-1.3 D3 (2026-11-22) and the assumptions 1.3 A1-1.3 A17 are in `product.md` "1.3.0 Quotes". Deviations from earlier rules are marked **[changed]**. One migration, V35 (in number order; `outOfOrder` is off; an applied file is never edited; it gets its checksum pin and its delete-class line in `persistence.md`). No new dependency, no new `LiveKind`, no new rate bucket, no new body ceiling. Everything on the wire is additive inside `/api/v1`: the edit's `MessageRequest`, `ThreadCreateRequest` and the meaning of `mentionedId`, `mentionsMe` and `MessageResponse.mentions` do not change.

### The words (1.3 D1)

- **Quote** is the word, in the UI (EN "Quote" / PL "Cytuj"), on the wire (`quotedMessageId`, `quote`, `MessageQuote`, `MessagePostRequest`, `urn:adder:problem:quote-unavailable`), in the schema (`messages.quoted_message_id`) and in the notice kind (`MESSAGE_QUOTED`). "Reply" keeps meaning any message of a thread (the box, `THREAD_REPLIED`, "replied in #42"); the two words never name each other's thing. No donor has this feature: what is reused is Adder's own (the excerpt helper, the `message=<id>` jump, `TypedBadRequestException`, the notice machinery).

### The rule

- **A message may quote ONE message of its own thread.** Who: whoever may post (a member, an open thread, a room that is not archived); there is no new guard. What: a LIVE message of the same thread, one's own and the thread's opening message included, a tombstone never. The opening message of a new thread quotes nothing (`ThreadCreateRequest` is untouched).
- **A live reference, never a copy.** The quoting message stores an id and nothing of the text; the quote shows the quoted message as it reads NOW. Once that message is deleted every quote of it says so and carries no text, which keeps a moderator's delete of a leaked credential effective (0.3 D2).
- **Set when posted, never changed.** An edit keeps the quote and cannot add, change or remove it (the strict request decoding does this with no code: the PUT's body has no `quotedMessageId` member, so naming one is a `400`). Deleting the QUOTING message leaves an ordinary tombstone (`quote: null`). Deleting the QUOTED message leaves the reference in place: it now reads as a deleted quote.
- **One level.** A quote shows the quoted message's own text, never what that message quoted.
- **A quote is not a mention.** No `message_mentions` row is written, and `mentionsMe`, `mentionedId` and `MessageResponse.mentions` keep their meaning.
- **Same thread only.** Whoever reads the thread can read the quoted message, so no authorization rule is new. Quoting across threads or rooms is a `BACKLOG.md` item (it needs a reader check per quoted message).

### Storage (V35)

- **`V35__add_message_quotes.sql`:** `ALTER TABLE messages ADD COLUMN quoted_message_id INTEGER CONSTRAINT fk_messages_quoted REFERENCES messages (id) ON DELETE SET NULL`, and `CREATE INDEX idx_messages_quoted ON messages (quoted_message_id) WHERE quoted_message_id IS NOT NULL`. Nullable with no default, so the table is not rewritten; no CHECK (the V15 rule). Its header comment (the style of V15 and V31) says what the column is, its delete rule, the cost of the file and what a 1.2.0 binary does with it.
- **Delete class.** `ON DELETE SET NULL` fires on a HARD delete only (a test purge, a thread or room cascade). The application soft-deletes a message, which is an UPDATE, so the reference survives it on purpose. The index is the foreign key's own: for every hard-deleted message PostgreSQL looks for the rows that quote it, and without the index a room purge scans `messages` once per deleted row; it is partial so only quoting messages are in it, and it will serve "the replies to this message" when that is built.
- **"Same thread" is not a constraint.** No composite key (it needs a second unique index over `(thread_id, id)` on the hottest table). The WRITE checks the thread under the room lock and the READ is scoped by thread; a test plants a foreign reference by SQL and reads no quote.
- **`MessageDerivedRowsTest`** asks the catalog which tables reference `messages` and leaves the table itself out (`c.conrelid <> c.confrelid`); with V35 that clause matters and stays, and the test's KDoc names `messages.quoted_message_id` as the self-reference it leaves out and why.
- **Measured before the commit** (`persistence.md` "Message quotes (V35)"): V35 on at least 100,000 messages, the `ALTER TABLE` and the `CREATE INDEX` apart, and `TestRooms.purge` of a room holding one thread of 5,000 messages, half of them quoting. A migration over 5 s per 100,000 messages, or a purge more than twice as slow as on master, stops the step.

### The write

- **Body.** `POST /rooms/{id}/threads/{number}/messages` takes a NEW body, `MessagePostRequest` `{body, quotedMessageId?}`; the edit PUT keeps `MessageRequest` `{body}`. `quotedMessageId` is int32, 1 to 2147483647 (the `requireReadMarkerMessageId` shape; a plain `400` outside it), checked by the route AND the service.
- **Order (unchanged up to the body):** 401; `chat-post` (429); visibility (404, audited); member (403) BEFORE the body; the body (400: the message rules, and the id's range). Then under the room lock (`withThreadWrite`): the guard again; the thread (404); archived (409); closed (409); **the quote**; the write.
- **The quote check** is ONE statement inside the lock: the quoted row by `id = ? AND thread_id = <this thread> AND NOT marked_as_deleted`, selecting its author and `SUBSTRING(body, 1, 1001)`. No row is the typed `400` `urn:adder:problem:quote-unavailable` with a fixed detail that echoes no id: an unknown id, another thread's or another room's message and a tombstone are ONE answer. Never a `404` (on this POST a `404` means the thread or the room is gone, and the SPA re-reads the room on it; precedent `template-gone`). Nothing is written, hinted or audited.
- **Races.** A delete of the quoted message takes the same room lock, so either the post sees a tombstone (the `400`) or the delete follows the post (the quote then reads as deleted).
- **The insert** writes `quoted_message_id`; counters, activity, the hint, hashtags and followers are as for any post. `MessageService.post` gains a defaulted last parameter `quotedMessageId`, and `insertInTransaction` the same, so existing callers compile unchanged. The POST's `201` is built from what the write already read (the check's row): no re-read under the lock.

### The read

- **`MessageResponse.quote`** (`MessageQuote`, nullable and always written, like `editedAt`; `null` when the message quotes nothing) rides the thread's message list, the single read, the POST's `201` and a pin's `message`. A quote is API-STRUCT-003's read-only summary of a related resource; the write refers to it by id, and the POST's `quotedMessageId` is answered as `quote.messageId`, not as a top-level mirror.
- **Fields:** `messageId` (the quoted message); `authorId`, `authorName` (by current name; a removed account keeps its name); `deleted` (a tombstone now: then `body` is `null`, `truncated` is `false` and both lists are empty); `body` (its CURRENT Markdown, at most 1,000 characters); `truncated`; `editedAt` (epoch millis of the quoted message's last edit, `null` while as posted and when deleted: a quoted author can rewrite the text under someone's "Agreed", so the SPA marks an edited quote; always present, like `MessageResponse.editedAt`); `mentions`, `groupMentions` (the quoted message's own, so the excerpt can show names, and empty when no `<@` token survived the cut).
- **The cut** is one pure function (`threads/MessageQuotes.kt`): at most `MAX_QUOTED_BODY` = 1,000 code points; when longer and the code point right after the cap is whitespace, exactly 1,000 (the cut is already on a word end); otherwise cut back to the last whitespace inside the final 100, so no word, link or mention token is halved; with no whitespace there, cut at 1,000 exactly; never inside a surrogate pair. The SQL only bounds what travels (`SUBSTRING(body, 1, 1001)`); the rule runs in Kotlin for every source. The server makes no excerpt (the SPA's helper does, from the Markdown and the message's own mention lists): Adder has no Markdown-to-text code on the server and a second implementation would drift.
- **Cost.** The quoted rows of a page are taken from the page's own rows first. ONE `id IN (...)` statement reads the rest, and none is sent when the page needs none. The quoted authors join the page's ONE names read; the quoted messages whose cut body holds `<@` join the page's ONE mentions read and ONE group-mentions read. A page whose quoted bodies hold no `<@` token costs at most ONE statement more than today (the quote read); a page whose only `<@` tokens sit in an off-page quoted body adds up to FOUR (the quote read, the mentions read, the group-mentions read and the teams lookup of a team mention); a page that holds its quoted messages adds none for the quote read. The three message reads (`list`, `read`, `readInTransaction`) share one assembly (`threads/MessageAssembly.kt`, step S1) so the quote is added in one place; `post` builds its own answer.
- **The leak rule of the read.** A quoted row counts only when its `thread_id` equals the quoting row's; anything else reads as `quote: null`.
- **Tombstones.** A deleted QUOTING message answers `quote: null` (like its `mentions`). A deleted QUOTED message answers `deleted: true` with no text.

### The notice (1.3 D2)

- **The kind** `MESSAGE_QUOTED` is the second name of BOTH enums (`NoticeReason`, `NotificationType`), right after `MENTIONED`: the order is the priority. Defaults: in-app on, email off. Never renamed or reordered once released; it is not in `MENTION_REASONS`.
- **Who.** The quoted message's author, when they are an ACTIVE member of the room now and not the author of the quoting message (`RoomMemberService.activeMemberIds` inside the write, one statement, merged with the mention check when the body mentions people). A quoted author who left the room or whose account is deleted is not told and the post still answers `201` (`fk_notifications_member` would answer a `500` for a non-member recipient, so the filter is load-bearing). Quoting yourself tells nobody.
- **One notice per message and person**, as today: `MENTIONED` > `MESSAGE_QUOTED` > `TEAM_MENTIONED` > `WATCHERS_MENTIONED` > `EVERYONE_MENTIONED` > `THREAD_REPLIED`. The other reasons that apply ride as fallbacks, so a person who switched quotes off on both channels still hears "a reply in a thread I watch" if they watch.
- **Direct.** It joins `DIRECT` (`notifications/NoticeWriter.kt`), so a refused wide event keeps it, and `ADDRESSED_KINDS` (`notifications/NoticeJudge.kt`): the rail's number, the thread's `@` mark and the bell's "Mentions" view count it. `MAX_AUDITED_ADDRESSED` goes from 21 to 22 (20 mentions, the quoted author, one that says "or more"). A quote adds at most one more directly addressed person per message.
- **Edits.** A quote never changes, so an edit never adds or removes `MESSAGE_QUOTED` by itself, and an edit that changes no mention still returns before anything is read. `NoticeAudience.ofEdit` takes the quoted author too, with ONE change to its table: "newly addressed" is judged on the person's most specific MENTION reason among all that apply, no longer on their top reason (the two are the same for everybody today, so every existing row of `NoticeAudienceTest` passes unchanged; a quote is the first reason that can sit above a group mention). For the quoted author: holding `MESSAGE_QUOTED`, an edit that adds a direct mention makes a fresh `MENTIONED` (replacing it); holding `MENTIONED`, an edit that drops the token relabels it to `MESSAGE_QUOTED` in place, never deleted; holding `MESSAGE_QUOTED`, an edit that adds `@everyone` does nothing; holding `THREAD_REPLIED` or nothing (quotes switched off), an edit that adds `@everyone` tells them like any member, with the first of their reasons that is switched on; holding nothing, an edit that addresses them no more than before does nothing (a base notice is never added by an edit).
- **How the follower learns it.** `MessageRef` gains `quotedAuthor()`, lazy like `opening()`: a post knows it (the quote check read it), an edit asks only past its early returns (one joined read of the message's `quoted_message_id` and that row's author), a delete never.
- **Lifecycle.** Deleting the quoting message removes the notice (`messageRemoved`, as for every notice of a message). Deleting the quoted message leaves it: the notice is about the reply.
- **Words.** Bell: "{{actor}} quoted your message in #{{number}} {{title}}" / "{{actor}} cytuje Twoją wiadomość w #{{number}} {{title}}". Preferences row, in the Mentions group after "Someone mentions me": "Someone quotes my message" / "Ktoś cytuje moją wiadomość". Digest: "%s quoted your message in #%d (%s)" / "%s cytuje Twoją wiadomość w #%d (%s)".

### Wire and rollback

- **Wire summary** (all additive): `MessagePostRequest` on the message POST; `MessageResponse.quote` (`MessageQuote`); the problem type `urn:adder:problem:quote-unavailable` (400; `infra/ProblemTypes.kt` and the spec's `ProblemDetail.type` list); `NotificationType.MESSAGE_QUOTED` (the notifications `type` filter's bound 11 becomes 12, the two preference lists' 22 become 24). `NotificationType` is also sent back by a client: a 1.2 tab that saves preferences leaves the new kind at its default (1.3 A16).
