# Web internals (read on demand)

Mechanism and narrative text kept out of `web/CLAUDE.md` so that file stays a lean always-loaded-in-`web/` rule set. The binding rules (every never/must/always) stay in `web/CLAUDE.md` as one-liners; this doc holds the mechanics behind them. **Read the relevant section before changing the transport/session layer, the user/feature-flag pages, the language switcher, the colour tokens or logo, or the changelog wiring.**

### `http.ts` — the transport's refresh internals

- **`http.ts`** (transport): `authedFetch()` with the **single-flighted silent refresh** — on a
  401 it exchanges the stored refresh token once (concurrent 401s from the same session share one
  in-flight `/refresh` call) and retries once; a DEFINITIVE rejection (no refresh token, or
  401/403 from the server) clears the originating session and signs out only if that session is
  still current, while a TRANSIENT failure (network/timeout/5xx/429/malformed body) keeps the
  session so a later retry can succeed — **never collapse the two** (a network blip must not
  erase a valid session). Stale requests and refresh completions must not publish credentials,
  clear a newer login or retry across session identities. **The server rotates the refresh token** (each works once, plus a
  60 s server-side replay grace for a lost response; after that a replay is a 401), so two tabs on one session can race on
  `/refresh`: `doRefresh` serialises them with a Web Lock (`adder.auth.refresh`, where the browser has `navigator.locks`; a lock
  that cannot be acquired falls back to an unserialised refresh) and, inside it and again after a 401/403, adopts a pair already
  stored by another tab (same session identity, different refresh token) instead of replaying or clearing; a different login (new identity) is never adopted. **Why a 401 can now come at any time:** the server checks every access token against the user row per request (`security.md` "JWT model"), so a delete, a demotion/promotion, a password change or a logout elsewhere turns the NEXT request into a 401 (one text). The transport needs no special case: the 401 -> silent refresh -> retry path handles all of them - a role change refreshes successfully into the NEW roles (`persistRefreshedSession` republishes them and `notifyAuthChange` re-renders the nav and `RequireAdmin`, pinned in `http.test.ts`), a delete or password change makes the refresh a DEFINITIVE rejection and signs the user out. `ApiError` (status + parsed body; read
  RFC 7807 fields via the `detail`/`instance`/`type` getters, never hand-cast `err.body`; `retryAfterMs` is the parsed `Retry-After` (null when absent) that `jsonRequest`/`voidRequest` fill, and `LiveMintError` extends `ApiError`), and the two
  standard wrapper shapes **`jsonRequest<T>()`/`voidRequest()`** every ordinary endpoint wrapper
  uses, plus **`buildQuery()`** — the query-string builder behind the list wrappers (skips
  null/undefined/""; `false` and `0` ARE sent, so an omit-when-false param is passed as
  `value || undefined` at the call site). Reach for the raw `authedFetch`/`safeJson` primitives
  only when a wrapper genuinely inspects the Response. Every transport fetch carries
  `timeoutSignal()` (30 s, feature-detected for happy-dom) — a hung request rejects with a
  `TimeoutError` DOMException instead of pending forever; new `fetch` call sites in `api/` must
  attach it.

### `session.ts`

- **`session.ts`**: token/roles/userId storage under the `adder.auth.*` localStorage keys, written
  by `persistSession(LoginResponse)` on login/MFA and conditionally by `persistRefreshedSession`
  on refresh, and the render-time accessors (`isAdmin()`, `getUserId()`, …). Components whose
  controls or queries depend on ADMIN use `useAdmin()` from `auth.tsx`; it subscribes to role
  changes from silent refresh and other tabs. A random stored identity distinguishes sign-ins,
  while credential snapshots guard refresh publication; renewing tokens preserves the logical
  session so staggered 401s can reuse the new token.

### Session boundary

- **Session boundary** (`components/SessionBoundary.tsx` + `utils/sessionQueryCache.ts`): bind the
  root `QueryClient` to logical session identity changes, and key the mounted app subtree by that
  identity. A different sign-in, definitive automatic sign-out, explicit sign-out, or a change
  from another tab must synchronously cancel and remove caller-scoped query data and discard
  mounted form/mutation results before the next account renders; an access/refresh token rotation
  within the same identity must retain them. Keep this at the session boundary rather than
  clearing individual page keys, because user/team/account queries all contain caller-specific
  projections. Late requests from the previous identity must not repopulate the new account's UI
  or cache.

### Sign-out and the return destination

Explicit sign-out opens `/login` without a saved return destination, so the next sign-in opens
Home even when a different account signs in. Anonymous access to a protected link still preserves
its path, query and hash. Test logout navigation with the real route guards from a non-home page;
a root-only menu test cannot detect a stale return destination. Reading the signed-out notice
during render must be side-effect free. Acknowledge it only after the login page commits, so a
suspended or retried render cannot discard the notice. The flag carries a reason (`SignedOutReason` in `auth.tsx`: `sessionEnded`, the default, or `passwordChanged`; `pendingSignedOut()` reads it, `consumeSignedOut()` clears it) and `pages/Login.tsx` picks the notice from it. **The self password change signs the device out explicitly** (`pages/ChangePassword.tsx`): the PUT bumps the account's credential revision, which ends every access and refresh token including this device's, so after the success toast the page runs `clearSession()`, `flagSignedOut("passwordChanged")` and `navigate("/login", { replace: true })` (the notice reads "Your password was changed. Sign in with your new password."). No `/logout` call - nothing is left to revoke, and the stale access token would only 401; no broadcast, for the same reason as `UserMenu`'s sign-out.

### Password reset (confirm link)

`pages/ResetPassword.tsx` only REQUESTS a reset (a uniform 202: the server emails a single-use link and changes nothing). The link lands on `pages/ConfirmPasswordReset.tsx` at `/reset-password/confirm#token=…`, which is NOT behind `RedirectIfAuthed` (a signed-in device may finish a reset). The token travels in the URL fragment, so it never reaches a server log or a Referer: the page reads it once into component state, strips the fragment and any query from the address bar and history (`navigate(…, { replace: true })`), keeps it in memory only (never storage) and sends it to nothing but `confirmPasswordReset` (a plain `fetch`, never `authedFetch`, so it can never refresh or retry a session). Loading the page consumes nothing; the form shows for any well-formed 43-character token and an unusable one is learned at submit (401: the token is dropped and "Request another reset link" shows; 429, 400 and network failures keep it for a retry). The new-password rule is `newPasswordValidation` (`utils/userForm.ts`), shared with `ChangePassword.tsx`. On success the page runs `clearSession()`, `queryClient.clear()` and `notifyAuthChange()` and shows the teal notice: no `/logout` call (the reset bumped the credential revision, so nothing is left to revoke) and no return destination.

## User management (`pages/Users|CreateUser|EditUser|ChangePassword.tsx`)

Passwords are generated client-side (`utils/password.ts`) and revealed exactly once: the modal
(`components/OneTimePasswordModal.tsx`) sets `closeOnClickOutside={false} closeOnEscape={false}`,
renders `components/RevealablePassword.tsx` (masked by default, eye toggle, copy), and closing
drops the plaintext from state for good — the server never returns it. The admin Reset-password
action (`hooks/useResetPassword.ts`) reuses the same generate→PUT→reveal flow. `NavLeaf.adminOnly`
gates the Users nav item (the Shell filters by `isAdmin()`); the management routes sit under ONE
`<Route element={<RequireAdmin />}>` in `App.tsx` (`auth.tsx`, beside `RequireAuth` — a regular
user is sent home), so no page redirects itself; their queries additionally stay
`enabled: isAdmin()` so a redirected caller fires no request. UX only — the server's
`requireAdmin` is the rule. The pages live under `/users` (`utils/userLinks.ts` is the one place the family is spelled out; Flow's `/flow-users` rename and its legacy `/users…` redirect do not exist here).

#### The list's state in the URL (since 0.5.0)

`utils/threadListParams.ts` is the pure half, `hooks/useThreadListParams.ts` the hook. Keys: `scope` (`closed`, `all`; Open omitted), `order` (`newest`, `number`, `status` = the workflow's order; activity omitted), `status` (repeated status keys), `owner` (`me` or a user id), `mention` (only `me` is read: "Mentions me"; any other value is the default), `watching` (the same: only `me`; "Watching", sent as `watching=true`, the server knows the caller), `tag` (repeated hashtags, 1 to 150 characters each, no `#` and no control character: a spelling as typed in a message, or a key as the room's tag list returned it, which can hold `'`, `/` or a space, so the key grammar does not apply; the URL keeps at most 10 distinct, the server's folded limit), `field` (repeated `key:value`) and `page` (a positive integer; 1 omitted).
Parsing drops junk (an unknown value reads as the default, a repeated scalar key reads its first value; `status` and `field` keep every valid value, distinct, at most 20 each; `tag` at most 10) and a write omits defaults, so a URL spells only what differs from the plain list. Keys the list does not own pass through a write. Two of them are the room view's, parsed and written in the same file but deliberately NOT list keys (`hasListKeys`, the remembered query and `withListParams` ignore them, so a link back to the list never lands in the focus view and a restored query never carries a stale jump): `focus` (`parseFocus`: only `focus=1` is on; `writeFocus`) and `message` (`parseMessageAnchor`: a positive integer of at most 15 digits, else none). Neither is remembered.
To add a list key: extend `ThreadListParams`, `DEFAULT_THREAD_LIST_PARAMS`, `LIST_KEYS`, `parseThreadListParams` and `serialize`; `hasListKeys`, `withListParams` and the remembered query follow. A multi-value key (repeated in the URL) needs `.getAll` in the parse and an emptiness check (not `!==`) in `serialize`'s default test; `writeThreadListParams` already deletes every list key and re-adds with `append`, so repeats survive a write. A write to the remembered query files it under the room of the LATEST render (a ref), so a stale handler never writes one room's key with another's params.

**The filter panel** (`components/ThreadFilters.tsx` inside the shared `FilterPanel`, stacked for the narrow rail; storage key `roomThreads`): status (`FilterMultiSelect`, Lettuce's, with `accessiblePill.tsx`: a named, focusable remove button on every pill; the options carry the workflow's `threadCount`), the hashtags (`RoomTagSelect`, a `FilterMultiSelect` over `GET /rooms/{id}/tags`, the most used first: the server searches with the 300 ms debounced term, a leading `#` dropped and at most 50 characters; an option is `#tag (threadCount)` and a pick is the tag as the list spells it; a value the current search does not return, such as the spelling from a hashtag link, stays an option labelled by itself so its pill keeps its name; at most 10 picks; the options sit under `roomKeys.threadTags`, inside the list prefix, so the live hints that refresh the list refresh them), the owner (a "Mine" toggle that writes `owner=me`, disabled without a session user id, and `MemberFilterSelect` over `RoomMemberSelect` for any member; beside "Mine" a "Mentions me" toggle that writes `mention=me`, also disabled without a session user id, and `toApiQuery` resolves it to `mentionedId=<the session's id>` exactly as `owner=me` is resolved, never in the parser) and one control per ACTIVE SELECT, MULTI_SELECT or USER field of the workflow (`filterableFields`; the server answers 400 for any other type). Everything the panel draws comes from the URL: `MemberFilterSelect` holds only the id, so a label it did not pick itself (a reload, a shared link) is looked up in the picker's own unfiltered head (the shared `roomMemberPickerKey` cache entry), else it reads `#id`. **`toApiQuery(params, workflow, me)` is the one place the state becomes a request**: `owner=me` resolves to the session's id there (never in the parser, so a shared "my threads" link means the opener's), and a `field` entry the workflow cannot judge (`pruneFieldEntries`: a key that is not an active filterable field, or a value of the wrong shape for its type, `severity:7` on a SELECT, `lead:abc` on a USER field) is DROPPED, not sent (the server would answer 400). Once the workflow is read, `ThreadList` also prunes those entries from the URL and the remembered query by `replace` (same page), so the badge, Clear and the 20-entry cap never count them. A request with field filters waits for the workflow (`toApiQuery` answers `null`; the list shows the spinner, or the load error when the workflow read failed). The badge counts filters: the statuses are one, the owner one, "Mentions me" one, the hashtags one, each field key one; scope and order sit outside the panel. "Clear filters" is the hook's `clear()`: it drops ONLY the panel filters (status, owner, "Mentions me", hashtags, field) and the page; the scope and the order stay, and the remembered query becomes what remains (forgotten when that is the plain list). An empty answer under a panel filter reads "No threads match these filters." without the start-one hint.

- **Writes** (`update(patch)`, `clear()`) go through `hooks/useLiveSearchParams.ts` (Flow's, ported: the functional form gets the LATEST params, so a handler captured by an older render never overwrites a newer change; the setter is stable; two writes in one event compose), use `replace` (a filter is not a history entry) and keep `location.state` (the pane-focus hand-off). A change of anything but the page deletes `page` in the same write, which is why a changed filter's FIRST request is page 1 (nothing is derived or reset in an effect). A page the server answers empty (the list shrank, or a hand-edited `page=99`) steps back to page 1 by `replace`.
- **The remembered query**: the last non-default query of a room, the page left out, is kept under `adder.viewSettings.roomThreads.<id>.query` (a string; the old `roomThreads.<id>.scope|order` keys are no longer read). When the Threads view opens on a URL that spells no list key, the hook reads it at once (so the first request already carries it, never the defaults first) and an effect writes it into the URL by `replace`. Every write updates what is remembered (the plain list remembers nothing), so the restore happens once: choosing the plain list leaves a bare URL AND nothing kept. `clear()` removes the panel filters (status, owner, tag, field) and the page, keeps the scope, the order and the other keys, and updates the remembered query to what remains (forgotten when nothing non-default remains).
- **Links keep the list's keys**: `withListParams(path, search)` (`utils/roomLinks.ts`) carries the normalized `scope`/`order`/`page` of the current URL into the list's rows, "New thread", "Back to threads" (`RoomHome`), the new-thread form's Cancel and the navigation after a started thread. The room's tabs and the rail link to the bare room route on purpose: that is where the remembered query comes back.

### The conversation (messages and the composer)

`ThreadPane` renders the header, then `MessageList` (key = room id and thread number, so a visit starts clean) and `MessageComposer`; `api/messages.ts` has the four wrappers the UI uses (list, post, edit, delete; the single-message GET is not used). The wire types (`MessageResponse`, the page, the request bodies) are the generated `schema.ts` types, pinned equal by `expectTypeOf` in `api/messages.test.ts`; a tombstone has `body: null` and `editedAt: null`.

- **The list** (`["rooms", "threads", roomId, "messages", number]`, a `useInfiniteQuery`): the server pages NEWEST first (`sort=-id`, 50 a load) and `id[lt]` keeps the older ones, so the next page param is the oldest id loaded, offered while a page's `total` (counted after the filter) exceeds its items. The display order is the pages flattened and reversed (oldest at the top, newest at the bottom). A refetch re-reads every loaded page with each cursor taken from the page just read (TanStack v5), so a new message pushing the 50th off page 1 loses nothing. The scroller (`MessageList.module.css`) is a focusable labelled `region` ("Messages", axe `scrollable-region-focusable`) sized by the structural-height rule ("The room view": wide, the pane is a viewport-bounded column and the scroller its `flex: 1` part, at least 16rem; narrow, the page scrolls and the composer sticks), so the header above and the composer below stay in reach. It scrolls to the bottom on open (a layout effect on the first non-empty list), after the caller's own post and, since 0.4, when the list grows, or its newest message is replaced or edited (the newest `id` or `editedAt` changes), under a reader who is at the bottom (an `atBottom` ref, updated on the scroller's scroll event: within 48 px of the end; a reader who scrolled up is never moved, and the open, own-post and load-older anchor paths come first and are unchanged): the pane holds `{threadNumber, messageId}` of the 201's message and hands the list `scrollToId`; once the list shows that id or a newer one it scrolls and clears the request (waiting for the id, not for the refetch's timing). "Load older messages" remembers `scrollTop` and `scrollHeight` and restores the reader's place after the prepend (a failed load drops the anchor). "Load older messages" stays enabled and focused while it loads (`aria-busy` and a spinner, never `disabled`; a second press during the load asks for nothing). A failed FIRST read shows the alert with Retry; a failed load of older ones keeps the button. When the load that finishes the history removes the button (the focus was on it), focus moves to the oldest loaded message, unless the reader has moved it meanwhile. No polling and no optimistic update (the live hints of 0.4 arrive as invalidations of this key; the list never cancels a fetch for them). **Refresh scope:** the caller's own post, edit and delete re-read `["rooms","threads",roomId]` and `["rooms","rail"]` (`refreshAfterMessageWrite` in `utils/messageForm.ts`; a message changes no workflow count and no room header); an access refusal (403/404/409) re-reads the whole `["rooms"]` prefix.
- **A jump to a message** (`MessageList`'s `anchorId`, from the pane's `?message=<id>`, a search hit's link; the id is validated as a positive integer, junk reads as none): the list does NOT open at the bottom (`openedOnAnchor`; the own-post, grow-under-a-reader-at-the-bottom and load-older paths above are unchanged, and a reader who was sent to an anchor counts as not at the bottom). An effect loads older pages (`fetchNextPage({ cancelRefetch: false })`, so it never cancels a refetch that is in flight: it waits until nothing is, then asks) until the id is listed, at most 10 loads (`MAX_JUMP_LOADS`), counted from the moment the anchor arrives (the page count then is the baseline, so a reader's earlier "Load older" presses do not spend the budget), and never after a failed load (the alert and the button take over). **Live hints during the search:** the live channel's invalidation (the default, which DOES cancel an in-flight next-page fetch) re-reads the loaded pages and the loop then asks again, so a hint is never lost and nothing extra is invalidated after the loop (pinned in `MessageListJump.test.tsx`). Once listed, a layout effect centres the message inside the scroller (`centreInScroller`: only the scroller moves, never the page), focuses it without a second scroll (the item's `tabIndex={-1}`, found by `data-message-id`), and marks it `data-anchor` for 5 s: a heavy outline plus a tint (a shape, so not colour alone) and a visually hidden `role="status"` line "Found the message by {author}." that is mounted from the first render (also while loading), so the text that appears in it is announced. ### Hashtag links in messages

`MarkdownView`'s message variant takes a `tagHref(tag)` prop (`MessageItem` passes `tagFilterPath(roomId, message.threadNumber, tag)`); without it a tag is plain text, and the document variant (the changelog) never links one. With it the message renders `remarkHashtags` after gfm and gemoji: a plugin that walks the Markdown tree by hand (no new dependency; `unist-util-visit` is only transitive) and splits each text node into text and `link` nodes marked `data-hashtag`, which the variant's `a` component renders as a react-router `Link` (an in-app navigation: no `target`, no `rel`) around the `#Tag` text. An external link still opens a new tab. The grammar is `utils/hashtags.ts`, a JS regex with the `u` flag (the lookbehind reads code points) and NFC-normalised text, the server's rule (`chat-model.md` "Find (0.5)"); a node is entered unless it is `code`, `inlineCode`, `link`, `linkReference`, `definition`, `html` or `image`, and a bare URL is a `link` through gfm's autolinks, so `https://example.com/#frag` is skipped. A tag in the text of a `[link](…)` stays text where the server indexes it (a link inside a link is invalid HTML): a known difference, with three harmless edge cases of the parsers reading different things (the server the source text, the SPA the unescaped tree): `foo\#a` and `&amp;#a` are indexed by the server and not linked by the SPA (the unescaped text `foo#a` / `&#a` has the hash glued to something), and `https://x.com/a<#b` is linked by the SPA as `b` and not indexed by the server. A tag is text inside its `Link`, never HTML. The link is `tagFilterPath` (`utils/roomLinks.ts`): the thread that is open, `scope=all` and `tag=<as typed>`, the value URL-encoded; the list's other filters are not carried (a status filter would hide threads that have the tag), and the server folds case and accents. One case table pins both sides: `server/src/test/resources/hashtag-cases.json`, read by the server's `HashtagsTest` and by `utils/hashtags.test.ts` through the real Markdown pipeline (distinct by lower case, the first spelling, at most 20, compared after NFC).

### Mentions in messages

A message body names a person with the token `<@id>` (`chat-model.md` "Mentions, notifications, unread, reactions, pins (0.6)"); the body is stored as sent and the SPA turns the token into a name at render. `MarkdownView`'s message variant takes a `mentions` prop (`MessageItem` passes `message.mentions`, `[{userId, name}]`, empty on a tombstone) and, when it is non-empty, adds `remarkMentions` after the hashtag plugin: a hand-written tree walk (no new dependency) that splits each text node on the grammar of `utils/mentions.ts` (`<@([1-9]\d{0,9})>`, the id at most 2147483647) into text and `mention` nodes, each a `span` with `data-mention` (`data.hName`, a custom node type the real pipeline renders). Every node is entered except `code`, `inlineCode`, `definition`, `html` and `image`; unlike a hashtag, a mention in a link's text is shown (a span inside a link is valid HTML). The `span` renderer is part of the ONE module-level components map and reads the names and the reader's id from a context (as `tagHref` does), so a re-render remounts nothing. **The SPA follows the server:** a token becomes `@Name` only when its id is in the message's `mentions`; any other id stays the raw token, so where the two parsers read differently (an escaped `\<@5>`: the SPA reads the unescaped tree, the server the source; a token glued to a bare URL) the reader sees text, never a wrong name. **Known disagreement (server indexes, SPA shows raw):** a token in an INDENTED code block (four spaces, then `<@5>`), in a raw HTML block, or in an image's alt text. The server's pre-pass (`threads/MarkdownText.kt`) does not blank those regions, so it lists the id and notifies the person, while the SPA's tree is `code`, `html` or `image` there (skipped) and the reader sees the raw token, no name; `utils/remarkMentions.test.ts` pins what is shown. Likewise an escaped backslash before a token (`\\<@5>`: Markdown reads a backslash and a token, the server reads a backslash before the token and lists nothing), so the SPA shows the raw text. Closing the first gap means blanking those regions in the shared pre-pass, which would change hashtags too (`BACKLOG.md`). The reader's own mention is marked (`data-self`, a heavier weight and an underline: a shape, not colour alone). A listed person's mention is a router link to `/people/:id` and a listed team's to `/teams/:id` (1.2 D6; `.mention` on a link, text colour on the tint), except inside a link's own text: `remarkMentions` flags that case `data-in-link` and the renderer keeps a span (a link may not hold a link); `@everyone` and `@watchers` are never links. The message variant therefore needs a router wherever it shows a mention. The name is a React text child: `**x**`, a link or markup in a display name is text. The document variant (the changelog) never reads a token. One case table pins both parsers: `server/src/test/resources/mention-cases.json`, read by the server's `MentionsTest` and by `utils/mentions.test.ts` through the real Markdown pipeline (every id the server found is shown, nothing else is); the Dockerfile's web stage copies it beside `hashtag-cases.json` because `npm run build` type-checks the tests. `utils/knownNames.ts` is the names the session has seen (a message's `mentions` are remembered by the message variant; the composer's picks join them): an in-memory store provided in the shell above the routes, inside the session boundary (`KnownNamesContext`, `useKnownNames`), so a new sign-in starts with none; it is never the authority for a token.

**Mentioning (the composer).** `components/MentionTextarea.tsx` is the box of all three writers (the reply box, the edit form, the new-thread body) over `EmojiTextarea`. The caller keeps the CANONICAL text, tokens and all (what is stored, sent, counted and kept as a draft: the drafts stay strings); the box SHOWS `@Name` for every token whose name the session knows (`utils/knownNames.ts`: filled by `MarkdownView` from messages' `mentions`, by `MessageEditForm` for the body it edits, and by a pick) and the raw token for one it does not know. `utils/mentionText.ts` is the pure mapping and is table-tested: `toShown` (canonical to shown, in runs that keep ids apart, so two members with one name stay two ids), `editCanonical` (an edit of the shown text back to the canonical one: the changed range is found from the caret the box reports, falling back to the common prefix and suffix when there is none, as for the emoji picker's splice; **an edit that touches any part of a mention removes the whole token**, the typed text going in its place; the box reports its selection from before the edit (`select` events), because the text alone cannot tell typing over a selection from a deletion; a paste is cut to what still fits in the stored text, and an edit the cap cuts to nothing puts the caret back where it was), `mentionQuery` (the `@term` at the caret: the `@` starts the text or follows whitespace, so an address is none; the term is at most 50 characters, no line break, may hold spaces; it never reaches into a mention already placed) and `pickMention` (the token and a space, the caret after it). The list's highlight is clamped to the rows there are, a pick that does not fit in the limit closes the list, and Escape's dismissed `@` is kept as a canonical offset that moves with edits before it and ends when the `@` is replaced or gone (not when the caret merely leaves it). A name containing `<`, `*` or `@` is only ever text: nothing re-parses the shown text. Known limits: a native undo that restores a removed mention brings back its shown text, not its token; a composition that touches a mention removes it mid-composition.
Typing `@` and letters opens a list of the room's members (`listRoomMembers` with `name`, eight rows, `sort=name`, the term debounced 300 ms, under `roomMemberPickerKey(roomId)` so any room refresh re-reads it; until the read for the current term is back the previous rows are narrowed by the term, so a quick Enter never picks someone the letters no longer match). ArrowDown/ArrowUp move (wrapping), Enter or Tab picks (Enter picks whatever else is held, Ctrl/Cmd included, while the list is open; closed, Enter is a newline and Ctrl/Cmd+Enter is the caller's send), Escape closes until that `@` is gone, a click picks and keeps the caret, and nothing opens during an IME composition (`compositionstart` closes it, `compositionend` looks again). **Group mentions (1.1.0 S7).** The grammar of `utils/mentions.ts` has three forms, `<@id>`, `<@team:id>` and `<@watchers>`/`<@everyone>` (segments carry a `kind`: `user`, `team`, `watchers`, `everyone`); `remarkMentions` marks a team token `data-mention-team` and a keyword `data-mention-group`. `MarkdownView`'s message variant also takes `groupMentions` (`MessageResponse.groupMentions`, passed by `MessageItem` and `PinnedPanel`): a team reads `@handle` only when the list names its id, a keyword reads itself only when listed, any other group token stays the raw token (the SPA follows the server; the handle is a React text child). `utils/knownNames.ts` also remembers team handles (`rememberTeams`, `getTeam`), filled by `MarkdownView`, by `MessageEditForm` and by a pick, so the edit form and composer show `@handle`; the keywords always show `@everyone`/`@watchers`, and all of them are atomic like a name (`mentionText.ts`: `toShown(canonical, nameOf, handleOf)`, `pickToken`). The composer list is ONE labelled listbox of three `group`s (People, Teams, Groups) built by `hooks/useMentionCandidates.ts`: members as before, teams from the first typed letter, only for a folded lowercase term a handle can hold (`^[a-z0-9-]{1,30}$`; `GET /teams?handle=`, five rows, under `["teams", "mention", term]`), `@everyone` and `@watchers` (also found by `observers`) by their first letters; `MentionTextarea`'s `offerWatchers={false}` (the new-thread body) hides `@watchers`. The thread list's "Mentions me" sends `mentionsMe=true`.

### Search

Two pages, one body: `pages/RoomSearch.tsx` (`/rooms/:id/search`, the room's "Search" tab in `RoomTabs`, inside `RoomPage`) and `pages/Search.tsx` (`/search`, the "Search" leaf of the Overview section in `utils/navigation.ts`, so the sidebar and the palette both get it). Both render `components/SearchBody.tsx`, which owns the URL state, the query and the triage (form, error, loading, count, empty, results, pager); the pages only say which request, which query-key prefix and whether the hit shows its room. `api/search.ts` wraps `GET /rooms/{id}/search` and `GET /search` (types from `schema.ts`).

- **State is the URL** (`utils/searchParams.ts` pure, `hooks/useSearchUrl.ts` over `useLiveSearchParams`): `q` (trimmed), `scope` (`open`, `closed`; **all** is the default and omitted, unlike the thread list's Open), `watching` (`1`, 1.1: the "Threads I watch" switch) and `page`. A new term and a page are history entries, the scope is a `replace`; anything but the page goes back to page 1 in the same write. Keys the page does not own pass through. A search is **submitted**, not run as you type; submitting the term that is already searched reads it again (the way to retry a failed search).
- **The term is checked before it is sent** (`queryProblem`, the server's `validateSearchQuery` mirrored): no control or hidden direction character (`\p{Cc}`, U+202A-202E, U+2066-2069, U+2028/2029), 2 to 100 code points after trimming, at least one letter or digit. A 400 never echoes the term, so the client is the only place that can say what is wrong; a bad term (typed, or hand-edited into the URL) shows its words under the box and is never requested. The palette offers its Search actions only for a term that passes the same check.
- **The box** (`SearchForm.tsx`): a labelled `type="search"` input, the rules of matching as its description (no stemming; a term of three or more characters matches the start of a word, a shorter one exactly; every term within one message or the title; case and accents ignored), a submit button, the scope control and the "Threads I watch" `Switch`. With the switch on, an EMPTY box is a search (`isSearchable`: the watched list, `q` omitted from the request; the server makes `q` optional only with `watching=true`), a term narrows it and a bad term is still refused; the empty state has its own words, and a hit has no messages and no marked words (the server sends none). Live hints never re-read the search keys (they sit outside `["rooms"]`); the caller's own watch write does: `refreshAfterWatchWrite`, and the two automatic-watch paths (a new thread, a hand-over) through `WATCH_SEARCH_KEYS` (`utils/watch.ts`). The palette's "Threads I watch" action (Pages group, any session) opens `/search?watching=1` (`watchedThreadsPath`). It follows the URL's term (Back, the palette) without losing focus.
- **Results** (`SearchResults.tsx`): an `ol` of `article`s, one per thread; the thread's title is an h3 whose link goes to the thread and is named by the PLAIN title (`aria-label` `#42 Title`: `<mark>` splits the visible words); the three newest matching messages are links to `threadMessagePath(roomId, number, messageId)` (`?message=<id>`; the thread view reads it); a count (`N matching messages`) heads them. A title-only hit has no messages. In a room the status is the room's workflow pill (as the thread list draws it); across rooms a hit carries no workflow, so it is an Open or Closed pill from `closed`, the room name and an Archived badge for an archived room. A `role="status"` line announces "N threads found". A page the results no longer reach steps back to page 1 by `replace`. No page-size picker (20 a page, the server's maximum).
- **A snippet is a list of typed segments** (`Snippet.tsx`): each `text` is a text node, a `hit` one is wrapped in `<mark>` (Mantine's `Mark`). Never `dangerouslySetInnerHTML`, never Markdown: the text is a fragment of a title or of a message's Markdown source and can hold anything a person typed (`Snippet.test.tsx` pins an `<img onerror>` segment). A snippet is a fragment: the server's `ts_headline` can drop a short word at its edge.
- **Errors** (`searchErrorMessage`, `utils/problems.ts` `searchTimeout` / `searchBusy`): the generic `search` bucket 429 (`about:blank`: wait), `urn:adder:problem:search-timeout` (it took too long: narrow it) and `urn:adder:problem:search-busy` (the server is loaded: retry shortly) each have their own words; a 404 (room route only) means the room is gone, and the room page re-reads the room so it shows its not-found state.
- **Keys** (`utils/roomKeys.ts`): `searchAllKey` = `["search"]` for the search across rooms (`["search", q, scope, page, watching]`) and `roomKeys.search(room)` = `["search", "room", R]` for one room's (`[…, q, scope, page, watching]` appended). **Both sit outside `["rooms"]` and outside the room's thread tree**, so the hints that re-read the tree (`subscribed`, a thread or message hint without its number, an unknown kind, `resync`) never re-read an open search: each re-read would spend a token of the reader's `search` bucket and one of the server's few search slots. Only the frames that take the room away name them: `revoked` (the room's own results and `["search"]`, so a lost room's hits leave an open search across rooms) and `room.deleted` (the room's own); `liveKeys.test.ts` pins that no other frame does. Each reader keeps `staleTime` 30 s and `keepPreviousData` (the previous hits stay dimmed under `aria-busy`); the room page keys its `SearchBody` by the room, so a switch to another room whose record is cached never shows the old room's hits as a placeholder. **Results are not live** (a busy room would spend the reader's bucket on refetches); the session boundary clears them.
- **Links**: `searchPath`, `roomSearchPath(id)` and `threadMessagePath(roomId, number, messageId, search?)` in `utils/roomLinks.ts`; `search` (a URL query) passes the thread list's keys through `listSearch` when a link should keep them, and a search page's own `q`, `scope` and `page` are never carried (they would read as the list's). `searchResultsPath(path, q)` (`utils/searchParams.ts`) builds the palette's links.

### Room settings under live updates

`RoomSettings`' `DetailsForm` is keyed by the room id ALONE, so a change of the room's data under it (a live `room.updated`, the caller's own save, an archive) never re-mounts it or drops a draft. It keeps the server's values it was seeded from in state (`seed`) and applies the thread details form's seed rule to `toRoomDetails(room)`: when they move, the draft follows silently while the form is clean, while it already equals the new values (the caller's own save) and while the form is read-only (archived or not the caller's to change); otherwise the draft is kept and a `RevisionConflictAlert` ("This room changed while you were editing", with Reload, `rooms.settings.moved.*`) says the next save keeps the caller's version (the room PUT carries no revision: last write wins). A save in flight makes both fields `readOnly` (nobody types during it) and the notice is not shown; on success the sent (trimmed) values become the seed, so the refetch of the caller's own save never counts as the room having moved. Reload re-seeds from the room's current values and moves focus to the name field (it reuses `workflows.conflict.reload`, the alert's default label); Cancel resets to the last adopted values (the seed, or the server's if the form followed them); both clear the page-level save error.

### Names as links (1.2 D6)

A name that stands on its own is a link: a person's to `/people/:id` (`PersonLink`), a room's to `/rooms/:id` (`RoomLink`), a team mention's to `/teams/:id`. Two rules decide every site. **A row that is itself ONE link keeps its names as text** (no link in a link: the thread-list rows, a search hit's matching-message rows) — or is a card with several links (the bell row: its notice link, actor link and room link are siblings, see below). **Underline: always, unless the line is a dense column of names**, where `quiet` keeps the underline but mutes its ink (gray-6 on light: 3.3:1 on white, 3.1:1 on the canvas and the pinned tint; gray-5 on dark: 6.5:1 or more; pinned in `theme.test.ts`; the accent returns on hover): a name that is not underlined at rest reads as a plain label, and WCAG 1.4.1 wants a cue besides colour for a link inside text (axe `link-in-text-block`), so no site is hover-only.

| Site | Link | Underline |
|---|---|---|
| a message's author (`MessageItem`) | person | quiet (a column down the conversation) |
| "Pinned by {name}" on a message, in a pin card, `Message by {author}` in the drawer, the strip's author (`PinCard`) | person | always (inside a dimmed sentence, `inherit` size) |
| the pane header's "Owner: …" and "Started by …" (`ThreadPane`), the side panel's read-only owner (`ThreadOwnerSelect`) | person | always |
| a USER field's value (`ThreadFieldValue`; an id the thread names no more stays `#id`, text) | person | always |
| the history's actor (`ThreadHistory` → `EventTimeline` `who`; a call site that KNOWS the person is gone, `actorDeleted`, draws plain text with its note instead of a `PersonLink`) | person | quiet |
| the room's members table, a team's roster, a team's manager (list and page) | person | always |
| a search hit's owner and, across rooms, its room (`SearchResults`) | person, room | always |
| a mention in a message body | person, team | the body's own link rule (underlined, text colour on the chip's tint); `@everyone`/`@watchers` and a mention inside a link's text stay spans |
| a bell row's actor and room (`NoticeRow`) | person, room | always |

Not links: the thread-list rows (the owner, per D6), a matching message's author inside its search row, reaction names (the wire has names, no ids), the ADMIN Users table, `OWNER_CHANGED`'s old and new names in a history sentence, the steward's owner picker (the name sits in an input; the header's "Owner" line carries the link) and the "Found the message by …" status line.

**"No dead links" holds only for ids a site can judge:** a mention whose id is not in the message's list stays text, a USER field the thread no longer names stays `#id`, an `actorDeleted` actor stays text. A person who is listed but has since been soft-deleted (a message author, a manager, a mentioned person) still links, to the profile's "not available" page (1.2 A15). **A translated sentence that holds a link is not `<Trans>`.** `utils/slots.tsx`: the sentence is translated with a marker as the value (`t("threads.pane.owner", { name: slot("name") })`) and `fillSlots(text, { name: <PersonLink …/> })` cuts it at the markers, so the keys stay plain `{{name}}` placeholders (EN/PL parity unchanged) and the other values (a thread's title, a display name) stay text children. `<Trans>` would parse the interpolated string as markup, and these values are what people typed (`<strong>`, or a tag named like one of the components, would become elements). **The bell row** (`components/NoticeRow.tsx`, `NoticeRow.module.css`): the notice link holds the sentence AFTER the actor's name as its text (so it has a box of its own, which locators and magnifiers need: an empty link reads as hidden), is named "Unseen" (while unseen) plus the whole sentence (the visible words are inside the name; the room and the time follow as the room link and the row's text); a SEEN row stays dimmed (the notice link and the names inherit the colour, the underline is the cue) and stretches over the row through `::after` (its focus ring is drawn there); the actor and room links sit beside it in the DOM, above it in the paint order. A screen reader therefore reads the sentence once as text and once as the notice's link. **A drawer that is a modal over the page closes when the page changes under it** (`hooks/useCloseOnPageChange.ts`, used by `PinnedPanel` and `NotificationsButton`: the path it opened on is compared during render), so a person's link inside it never leaves the drawer covering the profile. Focus does not return to the trigger (the room page's "Pinned" button is gone on the destination); it goes to `#main-content` (the skip link's target), except on a thread route, whose pane or message takes focus itself. Tests that match a whole sentence by text use the link's name (`findByRole("link", { name: /Ada mentioned you/ })`) or the element's `toHaveTextContent`, since `getByText` sees only an element's own text nodes.

### The thread side panel

`ThreadPane` is a grid of three parts in this DOM order: the header, the side panel (`ThreadSidePanel.tsx`) and the conversation. **The header is two rows** (1.2 D4): the `#42 Title` h3 with the status pill, and on the right the actions as icon buttons (`HeaderIconButton.tsx`, an `ActionIcon` in a `Tooltip`; the tooltip words ARE the accessible name, so by-name locators and `aria-pressed`/`aria-expanded` are unchanged) — focus, pin (`ThreadPinButton`), watch with its visible "Watchers: N" (`ThreadWatchButton`) and Details; then one dimmed line (owner, message count, started by, last activity; it may wrap to a second line). The title takes up to two lines and then an ellipsis (the h3's text, and so the region's name, stays the whole title; clamped to two lines), sharing the first row with the pill and the icons down to 8rem, under which the icons drop to a row of their own. The panel lives INSIDE the pane's labelled `region`, after the h3, because its four sections (Status, Owner, Details, History) are **h4s** and the outline may not skip a level; it is only PLACED beside the conversation. **It takes space only when opened:** collapsed by default at every width (`data-open="false"` is `display: none`, so it leaves the tab order and the accessibility tree), and the header's "Details" button (`aria-expanded`, `aria-controls`) is the way in at every width. Open or closed is ONE switch per person per browser, the same for every room and thread: `useStoredState("threadPane.detailsOpen", false, isBoolean)` under `adder.viewSettings.threadPane.detailsOpen` (guarded localStorage; a corrupt value or a browser that refuses storage falls back to collapsed and the switch still works for the visit). `ThreadPane.module.css` answers to the main area's container (the same one as `RoomHome.module.css`) and builds its three-column grid only while the pane carries `data-side="open"`: from **62rem** the open panel is a third column (`18rem`; the conversation keeps about 19rem at the threshold and 20rem in a 1280px window, a 63rem container, beside the 22rem list); open below that it sits between the header and the conversation; closed, the conversation takes the whole pane. The panel scrolls on its own (beside the conversation it is exactly as tall as the pane; stacked above it, it is capped at 40dvh). The panel fetches nothing about the thread itself: it takes the loaded thread from the pane and reads the room's workflow through the shared `useRoomWorkflow`, so the sections that need it (status options, fields) wait for it and say so if it failed.

- **Who may do what (UX only; the server guards; D1).** `utils/threadAccess.ts`: `isThreadSteward` (the thread's owner while a member, a room OWNER, an ADMIN), `statusMoveBlock` (a move between OPEN statuses is open to every reader; entering or leaving a CLOSED one needs a steward; an archived room blocks all but the current status) and `threadEditBlock` (a closed thread and an archived room refuse the details and the hand-over).
- **Status** (`ThreadStatusControl.tsx`): a Select grouped Open/Closed in the workflow's order. A blocked option is DISABLED WITH its hint, never hidden. Closing an OPEN thread asks first (`ConfirmActionModal`); reopening and CLOSED to CLOSED go straight through. A status key the workflow no longer lists still shows as the current choice.
- **Owner** (`ThreadOwnerSelect.tsx`): for a steward on a live, open thread a `RoomMemberSelect` (its "Owner" label is the accessible name only, `labelHidden`: the h4 above is the visible one) plus an explicit "Pass on" button (choosing a name never hands the thread over by itself); everyone else, a closed thread and an archived room read the name under the reason ("reopen it first" only for a steward; anyone else gets the plain rule). The pick resets after the refresh, so the picker never shows the old owner for a frame.
- **Details** (`ThreadDetails.tsx` read view, `ThreadFieldValue.tsx`, `ThreadDetailsForm.tsx` editor). The read view shows the active fields with option LABELS, a stored key the workflow dropped as the key plus "(removed option)", a USER as the name in `fieldUserNames` (or `#id`), a URL as a new-tab `noopener` link (http/https only), and "Not set". "Edit details" swaps in the editor (title + the same fields through `ThreadFieldInput`, which marks a removed option too and does not offer it as a new choice). **Draft rules (binding, from the server review):** the draft is seeded from the thread's `revision` (and the workflow's) and re-seeded ONLY when that revision changes under a CLEAN form, after Reload, or by closing and reopening the editor after its own save; a refetch caused by a status or owner change, a message or a focus never touches a dirty draft (those do not bump the revision). A newer revision under a DIRTY form shows `RevisionConflictAlert` at once (the editor's own words), as does a `409 revision-conflict` on save; the draft is kept and Reload (a `fetchQuery` of the thread, then re-seed) is the one way the newer version replaces it. A change to the room's fields (the workflow revision) under a dirty draft gets its own alert with the same Reload. A MULTI_SELECT compares as a set. The server's English `detail` is appended to a 400 message in English only (`withServerDetail`).

### The live channel

One WebSocket per tab, opened by `useLiveUpdates` (`hooks/useLiveUpdates.ts`) in `Shell`, beside `useRailRooms`; the protocol, the close codes and the catalog are `live.md`. Writes stay REST: a hint says THAT something changed, the SPA refetches through the ordinary reads. The files, all under `web/src/`:

- `api/live.ts`: `mintLiveTicket()` (`authedFetch` + `timeoutSignal()`, reading the response itself so a refusal is a `LiveMintError` carrying `retryAfterMs`).
- `utils/liveProtocol.ts`: the frame types (the generated `schema.ts` ones, pinned by `expectTypeOf` in `liveProtocol.test.ts`; only an event's `kind` is widened to `string`, because a newer server may add kinds), `parseServerFrame` (lenient: an unknown type or malformed members are ignored, never thrown) and `liveUrl(location, apiBase)`: the socket URL follows the SAME base as the REST calls (`VITE_API_BASE`, `API_BASE` in `api/http.ts`, passed in by `useLiveUpdates`). **The choice (0.4.0 audit L9): derive, don't disable.** An empty base is the page's own host (`ws:` on http, `wss:` on https); a relative base (`/adder`) is a path prefix on that host; an absolute `http(s)://host[:port][/prefix]` base maps to `ws(s)://` on THAT origin, and the server then needs the page's origin in `http.corsHosts` for the Origin check, exactly as REST needs it for CORS (an unusable absolute base falls back to the page's host). Adder's own CSP (`connect-src 'self'`) blocks a cross-origin socket exactly as it blocks the REST calls, so an absolute base only works when the SPA is served from somewhere else, under that host's CSP. A relative base without a leading slash resolves against the page's path, as REST's `fetch` does. The ticket is never in the URL, API-AUTH-002. Tests: `liveProtocol.test.ts`, `useLiveUpdates.base.test.tsx`.
- `utils/liveClient.ts`: the state machine, no React (`LiveClient`; everything outside is injected: `socketFactory`, `clock`, `mintTicket`, `onFrame`, `onStatus`). Statuses `connecting | live | down | paused | idle | stopped` (`idle` = closed on purpose after 5 minutes hidden; a suspended tab shown while offline is `down`). Mint, open, the `auth` frame on `open`, `live` on `ready`; one **generation** per socket (every event of an older one is ignored, so a late close or a late mint never touches its successor). Backoff 1, 2, 4, 8, 16, then 30 s, each times a random 0.5 to 1, reset after 60 s live (a socket that flaps does not reset it); a `Retry-After` longer than the step wins (capped at 5 minutes, plus up to 1 s of jitter). `online` and a shown tab reconnect after a random 0 to 1 s, never at once (a whole office coming back must not arrive in one instant). Randomness is `crypto.getRandomValues` through the injected clock. Close codes: 1001 a random 1 to 5 s; 4001 and 4003 re-mint after a random 0 to 1 s (tokens minted together expire together; twice within 10 s: backoff); 4429 and a `429 live-socket-limit` mint pause for 60 s; every other code (1003, 1008, 1009, 1011, 4401, 1006) backs off. A socket that is not `ready` within 10 s, an `error` and a missing pong (an application `ping` every 25 s while visible, a pong or ANY frame within 10 s) are failures. Hidden for 5 minutes closes with 1000 and goes `idle` (everything stops; shown again it connects afresh); `offline` closes and goes `down` without retrying, `bindBrowserSignals` (bound AFTER `start()`) feeds both. The caller's wanted rooms go in through `setRooms` (open room first, trimmed to `maxSubscriptions`) and leave as a diff (unsubscribe first, then subscribe), coalesced for 100 ms so quick navigation stays far below the server's 30 inbound frames per 10 s (`ready` subscribes at once); a room the server `refused` or `capped` is not asked for again until `forgetRefused()` (the hook calls it when the OPEN room changes), and a `revoked` room is dropped from the socket's set.
- `utils/liveKeys.ts`: `keysForFrame` (the table below) and `createLiveInvalidator(queryClient, clock)`. Focused keys settle 300 ms after the last hint and are flushed within 1 s of the first; the aggregate keys (`["rooms","rail"]`, `["rooms","list"]`, a room's thread list, and the caller's `["notifications"]`) at most once per 3 s; `resync`, `ready` and `subscribed` (the frames that mean "you may have missed something") wait a random 0 to 2 s, so tabs reconnecting after a restart do not refetch together. A "slow" frame (`isSlowFrame`: `message.reaction_changed`) asks for the same gap on its own key, the conversation: a storm of reactions is one re-read per 3 s, while a `message.posted` for that conversation settles on its own 300 ms clock and brings a waiting re-read forward. Every flush is stamped with its time (a conversation re-read that a post drove included, so a reaction right after it keeps the gap); a wider re-read stamps the aggregates it covers (`["rooms","threads",R]` its list, `["rooms"]` the rail and the rooms list), so the 3 s gap holds. **It NEVER cancels**: `invalidateQueries` cancels an in-flight fetch by default (a "Load older messages" click would be dropped and its scroll anchor left armed), so while `queryClient.isFetching({queryKey})` is above 0 the key is re-queued (300 ms) and invalidated once it is idle; `invalidateQueries` refetches only ACTIVE queries, the rest are marked stale. The caller's own writes still refetch through `refreshQueriesAfterMutation`, so the writer tab reads twice (accepted, A7); own echoes are not skipped.
- `utils/roomKeys.ts`: the key PREFIXES of a room's data, spelled once. The readers (`useQuery`), the refresh-after-write calls and `keysForFrame` all build from it, so a rename cannot desync a hint from its page; `liveKeys.test.ts` checks every hint key is a prefix of a reader's key and that no source spells a prefix by hand. A new reader of room data takes its key from `roomKeys` (a new part is added there).
- `hooks/useLiveUpdates.ts`: the wanted set (the open room from `matchPath("/rooms/:id/*")` + `parseRoomId`, then the ACTIVE rail's ids; the archived rail and "All rooms" keep refreshing on focus) and the status. It runs inside `SessionBoundary`/`RequireAuth` and keys the client on the session IDENTITY: a new sign-in is a new socket, sign-out closes it (1000), a token rotation keeps it. It mints ONE ticket per connect (a page load of the production build is one; `vite dev` under StrictMode two: `live.md` "Web"; `useLiveUpdates.test.tsx` pins the count). Its third argument (`clock`, `socketFactory`, `mintTicket`) is for tests.
- `components/LiveStatus.tsx`: see `web/CLAUDE.md` (the shell header). The 5 s grace means a token expiry or a server restart reads as nothing.
- `vite.config.ts`: the `/api` proxy has `ws: true` and no `changeOrigin` (the Host is kept, so the server's Origin check matches). The CSP is unchanged (`connect-src 'self'` covers the same-host socket).

**The key map** (R = room id, N = thread number; every key is a prefix; the unit of truth is `liveKeys.test.ts`):

| Frame / kind | Invalidates |
|---|---|
| `thread.created` | threads list R, workflow R, workflow-edit R, rail |
| `thread.updated`, `thread.owner_changed` | thread detail R/N, thread events R/N, threads list R, rail |
| `thread.status_changed` | the above + workflow R, workflow-edit R |
| `message.posted` | messages R/N, thread detail R/N, threads list R, rail |
| `message.edited` | messages R/N, threads list R (an edit can add or drop a hashtag), pins R (a pinned body shows in the panel) |
| `message.reaction_changed` | messages R/N only, with the 3 s gap (a reaction moves no count, order or rail) |
| `message.deleted` | messages R/N, thread detail R/N, threads list R, pins R (a deleted message loses its pin), `["notifications"]` (the notices about it went with it; also when the hint names no thread) |
| `room.pin_changed` | pins R (`["rooms","pins",R]`) |
| `notification.created` | `["notifications"]` (outside `["rooms"]`, like `["search"]`; the recipient's sockets only; it re-reads the badge and the addressed count, and the drawer's page when open: up to two list reads per tab, three with the drawer open, under the `notification-read` bucket; a `429` shows nothing new and schedules ONE re-read after `Retry-After`, `hooks/useNotificationRetryAfter.ts`; **not re-read at all for the thread the reader is looking at**, see "Unread": the pane acknowledges it through the read marker) |
| `room.created` | rail, rooms list |
| `room.updated`, `archived`, `unarchived` | room detail R, rail, rooms list |
| `room.workflow_updated` | workflow R, workflow-edit R, threads list R, `["rooms","threads",R,"detail"]`, `["rooms","threads",R,"events"]` |
| `room.member_added`, `member_role_changed`, `member_removed` | `["rooms","members",R]` (table and picker), room detail R, rail, rooms list |

| `resync` | `["rooms"]`, `["notifications"]` |

`revoked` goes through the same settle, so the caller's own Leave or Delete navigates first and no not-found flashes (`RoomMembers.test.tsx` pins it). The `subscribed` ack and `ready` close the gap between a page's own first read and the subscription becoming active, so a page load (and a reconnect) re-reads what is on screen once more, behind the 0 to 2 s spread. **Skipping a key whose cached data is newer than the socket's open time was considered and rejected**: a fetch that completes after the socket opened may still have STARTED (and read the server) before the subscription was active, so an event in that window would be lost until the next hint or focus; the extra read costs one request per active query and is the whole point of the gap-closing ack.

## Storage keys, Web Locks and telemetry (reference)

- **localStorage:** `adder.auth.*` (session), `adder.viewSettings.*` (`useStoredState`), `adder.lang`, `adder.changelog`. **sessionStorage:** `adder.chunkReloadedAt` (the one-shot reload after a failed lazy chunk, at most one a minute, `main.tsx`). **Web Lock:** `adder.auth.refresh`. **CSS variables:** `--adder-*`. None of Flow's `flow.*` keys exist; there are no legacy redirects.
