# Web internals (read on demand)

Mechanism and narrative text kept out of `web/CLAUDE.md` so that file stays a lean always-loaded-in-`web/` rule set. The binding rules (every never/must/always) stay in `web/CLAUDE.md` as one-liners; this doc holds the mechanics behind them. **Read the relevant section before changing the transport/session layer, the user/feature-flag pages, the language switcher, the colour tokens or logo, or the changelog wiring.**

### `http.ts` — the transport's refresh internals

- **`http.ts`** (transport): `authedFetch()` with the **single-flighted silent refresh** — on a
  401 it exchanges the stored refresh token once (concurrent 401s from the same session share one
  in-flight `/refresh` call) and retries once; a DEFINITIVE rejection (no refresh token, or
  401/403 from the server) clears the originating session and signs out only if that session is
  still current, while a TRANSIENT failure (network/timeout/5xx/429/malformed body) keeps the
  session so a later retry can succeed — **never collapse the two** (a network blip must not
  erase a valid session). Stale requests and refresh completions must not publish credentials,
  clear a newer login or retry across session identities. **The server rotates the refresh token** (each works once, plus a
  60 s server-side replay grace for a lost response; after that a replay is a 401), so two tabs on one session can race on
  `/refresh`: `doRefresh` serialises them with a Web Lock (`adder.auth.refresh`, where the browser has `navigator.locks`; a lock
  that cannot be acquired falls back to an unserialised refresh) and, inside it and again after a 401/403, adopts a pair already
  stored by another tab (same session identity, different refresh token) instead of replaying or clearing; a different login (new identity) is never adopted. **Why a 401 can now come at any time:** the server checks every access token against the user row per request (`security.md` "JWT model"), so a delete, a demotion/promotion, a password change or a logout elsewhere turns the NEXT request into a 401 (one text). The transport needs no special case: the 401 -> silent refresh -> retry path handles all of them - a role change refreshes successfully into the NEW roles (`persistRefreshedSession` republishes them and `notifyAuthChange` re-renders the nav and `RequireAdmin`, pinned in `http.test.ts`), a delete or password change makes the refresh a DEFINITIVE rejection and signs the user out. `ApiError` (status + parsed body; read
  RFC 7807 fields via the `detail`/`instance`/`type` getters, never hand-cast `err.body`; `retryAfterMs` is the parsed `Retry-After` (null when absent) that `jsonRequest`/`voidRequest` fill, and `LiveMintError` extends `ApiError`), and the two
  standard wrapper shapes **`jsonRequest<T>()`/`voidRequest()`** every ordinary endpoint wrapper
  uses, plus **`buildQuery()`** — the query-string builder behind the list wrappers (skips
  null/undefined/""; `false` and `0` ARE sent, so an omit-when-false param is passed as
  `value || undefined` at the call site). Reach for the raw `authedFetch`/`safeJson` primitives
  only when a wrapper genuinely inspects the Response. Every transport fetch carries
  `timeoutSignal()` (30 s, feature-detected for happy-dom) — a hung request rejects with a
  `TimeoutError` DOMException instead of pending forever; new `fetch` call sites in `api/` must
  attach it.
- A protected call with no access token returns a local 401 response. Queries that briefly remain mounted during sign-out can
  settle without sending anonymous requests. Login and password reset use their existing public transport calls.

### `session.ts`

- **`session.ts`**: token/roles/userId storage under the `adder.auth.*` localStorage keys, written
  by `persistSession(LoginResponse)` on login/MFA and conditionally by `persistRefreshedSession`
  on refresh, and the render-time accessors (`isAdmin()`, `getUserId()`, …). Components whose
  controls or queries depend on ADMIN use `useAdmin()` from `auth.tsx`; it subscribes to role
  changes from silent refresh and other tabs. A random stored identity distinguishes sign-ins,
  while credential snapshots guard refresh publication; renewing tokens preserves the logical
  session so staggered 401s can reuse the new token.

### Session boundary

- **Session boundary** (`components/SessionBoundary.tsx` + `utils/sessionQueryCache.ts`): bind the
  root `QueryClient` to logical session identity changes, and key the mounted app subtree by that
  identity. A different sign-in, definitive automatic sign-out, explicit sign-out, or a change
  from another tab must synchronously cancel and remove caller-scoped query data and discard
  mounted form/mutation results before the next account renders; an access/refresh token rotation
  within the same identity must retain them. Keep this at the session boundary rather than
  clearing individual page keys, because user/team/account queries all contain caller-specific
  projections. Late requests from the previous identity must not repopulate the new account's UI
  or cache.

### Sign-out and the return destination

Explicit sign-out opens `/login` without a saved return destination, so the next sign-in opens
Home even when a different account signs in. Anonymous access to a protected link still preserves
its path, query and hash. Test logout navigation with the real route guards from a non-home page;
a root-only menu test cannot detect a stale return destination. Reading the signed-out notice
during render must be side-effect free. Acknowledge it only after the login page commits, so a
suspended or retried render cannot discard the notice. The flag carries a reason (`SignedOutReason` in `auth.tsx`: `sessionEnded`, the default, or `passwordChanged`; `pendingSignedOut()` reads it, `consumeSignedOut()` clears it) and `pages/Login.tsx` picks the notice from it. **The self password change signs the device out explicitly** (`pages/ChangePassword.tsx`): the PUT bumps the account's credential revision, which ends every access and refresh token including this device's, so after the success toast the page runs `clearSession()`, `flagSignedOut("passwordChanged")` and `navigate("/login", { replace: true })` (the notice reads "Your password was changed. Sign in with your new password."). No `/logout` call - nothing is left to revoke, and the stale access token would only 401; no broadcast, for the same reason as `UserMenu`'s sign-out.

### Password reset (confirm link)

`pages/ResetPassword.tsx` only REQUESTS a reset (a uniform 202: the server emails a single-use link and changes nothing). The link lands on `pages/ConfirmPasswordReset.tsx` at `/reset-password/confirm#token=…`, which is NOT behind `RedirectIfAuthed` (a signed-in device may finish a reset). The token travels in the URL fragment, so it never reaches a server log or a Referer: the page reads it once into component state, strips the fragment and any query from the address bar and history (`navigate(…, { replace: true })`), keeps it in memory only (never storage) and sends it to nothing but `confirmPasswordReset` (a plain `fetch`, never `authedFetch`, so it can never refresh or retry a session). Loading the page consumes nothing; the form shows for any well-formed 43-character token and an unusable one is learned at submit (401: the token is dropped and "Request another reset link" shows; 429, 400 and network failures keep it for a retry). The new-password rule is `newPasswordValidation` (`utils/userForm.ts`), shared with `ChangePassword.tsx`. On success the page runs `clearSession()`, `queryClient.clear()` and `notifyAuthChange()` and shows the teal notice: no `/logout` call (the reset bumped the credential revision, so nothing is left to revoke) and no return destination.

## User management (`pages/Users|CreateUser|EditUser|ChangePassword.tsx`)

Passwords are generated client-side (`utils/password.ts`) and revealed exactly once: the modal
(`components/OneTimePasswordModal.tsx`) sets `closeOnClickOutside={false} closeOnEscape={false}`,
renders `components/RevealablePassword.tsx` (masked by default, eye toggle, copy), and closing
drops the plaintext from state for good — the server never returns it. The admin Reset-password
action (`hooks/useResetPassword.ts`) reuses the same generate→PUT→reveal flow. `NavLeaf.adminOnly`
gates the Users nav item (the Shell filters by `isAdmin()`); the management routes sit under ONE
`<Route element={<RequireAdmin />}>` in `App.tsx` (`auth.tsx`, beside `RequireAuth` — a regular
user is sent home), so no page redirects itself; their queries additionally stay
`enabled: isAdmin()` so a redirected caller fires no request. UX only — the server's
`requireAdmin` is the rule. The pages live under `/users` (`utils/userLinks.ts` is the one place the family is spelled out; Flow's `/flow-users` rename and its legacy `/users…` redirect do not exist here).

#### The list's state in the URL (since 0.5.0)

`utils/threadListParams.ts` is the pure half, `hooks/useThreadListParams.ts` the hook. Keys: `scope` (`closed`, `all`; Open omitted), `order` (`newest`, `number`, `status` = the workflow's order; activity omitted), `status` (repeated status keys), `owner` (`me` or a user id), `mention` (only `me` is read: "Mentions me"; any other value is the default), `watching` (the same: only `me`; "Watching", sent as `watching=true`, the server knows the caller), `tag` (repeated hashtags, 1 to 150 characters each, no `#` and no control character: a spelling as typed in a message, or a key as the room's tag list returned it, which can hold `'`, `/` or a space, so the key grammar does not apply; the URL keeps at most 10 distinct, the server's folded limit), `threadTag` (repeated CURATED tag names, 1.2: the registry grammar, 1 to 40 characters, lower-cased on read, at most 20 distinct; the Tags control offers the registry's LIVE tags grouped by category, a retired one can only come from the URL and keeps its pill), `field` (repeated `key:value`) and `page` (a positive integer; 1 omitted).
Parsing drops junk (an unknown value reads as the default, a repeated scalar key reads its first value; `status` and `field` keep every valid value, distinct, at most 20 each; `tag` at most 10) and a write omits defaults, so a URL spells only what differs from the plain list. Keys the list does not own pass through a write. Two of them are the room view's, parsed and written in the same file but deliberately NOT list keys (`hasListKeys`, the remembered query and `withListParams` ignore them, so a link back to the list never lands in the focus view and a restored query never carries a stale jump): `focus` (`parseFocus`: only `focus=1` is on; `writeFocus`) and `message` (`parseMessageAnchor`: a positive integer of at most 15 digits, else none). Neither is remembered.
To add a list key: extend `ThreadListParams`, `DEFAULT_THREAD_LIST_PARAMS`, `LIST_KEYS`, `parseThreadListParams` and `serialize`; `hasListKeys`, `withListParams` and the remembered query follow. A multi-value key (repeated in the URL) needs `.getAll` in the parse and an emptiness check (not `!==`) in `serialize`'s default test; `writeThreadListParams` already deletes every list key and re-adds with `append`, so repeats survive a write. A write to the remembered query files it under the room of the LATEST render (a ref), so a stale handler never writes one room's key with another's params.

**The filter panel** (`components/ThreadFilters.tsx` inside the shared `FilterPanel`, stacked for the narrow rail; storage key `roomThreads`): status (`FilterMultiSelect`, Lettuce's, with `accessiblePill.tsx`: a named, focusable remove button on every pill; the options carry the workflow's `threadCount`), the hashtags (`RoomHashtagSelect`, a `FilterMultiSelect` over `GET /rooms/{id}/tags` through `listRoomHashtags`, the most used first: the server searches with the 300 ms debounced term, a leading `#` dropped and at most 50 characters; an option is `#tag (threadCount)` and a pick is the tag as the list spells it; a value the current search does not return, such as the spelling from a hashtag link, stays an option labelled by itself so its pill keeps its name; at most 10 picks; the options sit under `roomKeys.roomHashtags`, inside the list prefix, so the live hints that refresh the list refresh them), the owner (a "Mine" toggle that writes `owner=me`, disabled without a session user id, and `MemberFilterSelect` over `RoomMemberSelect` for any member; beside "Mine" a "Mentions me" toggle that writes `mention=me`, also disabled without a session user id, and `toApiQuery` resolves it to `mentionedId=<the session's id>` exactly as `owner=me` is resolved, never in the parser) and one control per ACTIVE SELECT, MULTI_SELECT or USER field of the workflow (`filterableFields`; the server answers 400 for any other type). Everything the panel draws comes from the URL: `MemberFilterSelect` holds only the id, so a label it did not pick itself (a reload, a shared link) is looked up in the picker's own unfiltered head (the shared `roomMemberPickerKey` cache entry), else it reads `#id`. **`toApiQuery(params, workflow, me)` is the one place the state becomes a request**: `owner=me` resolves to the session's id there (never in the parser, so a shared "my threads" link means the opener's), and a `field` entry the workflow cannot judge (`pruneFieldEntries`: a key that is not an active filterable field, or a value of the wrong shape for its type, `severity:7` on a SELECT, `lead:abc` on a USER field) is DROPPED, not sent (the server would answer 400). Once the workflow is read, `ThreadList` also prunes those entries from the URL and the remembered query by `replace` (same page), so the badge, Clear and the 20-entry cap never count them. A request with field filters waits for the workflow (`toApiQuery` answers `null`; the list shows the spinner, or the load error when the workflow read failed). The badge counts filters: the statuses are one, the owner one, "Mentions me" one, the hashtags one, each field key one; scope and order sit outside the panel. "Clear filters" is the hook's `clear()`: it drops ONLY the panel filters (status, owner, "Mentions me", hashtags, field) and the page; the scope and the order stay, and the remembered query becomes what remains (forgotten when that is the plain list). An empty answer under a panel filter reads "No threads match these filters." without the start-one hint.

- **Writes** (`update(patch)`, `clear()`) go through `hooks/useLiveSearchParams.ts` (Flow's, ported: the functional form gets the LATEST params, so a handler captured by an older render never overwrites a newer change; the setter is stable; two writes in one event compose), use `replace` (a filter is not a history entry) and keep `location.state` (the pane-focus hand-off). A change of anything but the page deletes `page` in the same write, which is why a changed filter's FIRST request is page 1 (nothing is derived or reset in an effect). A page the server answers empty (the list shrank, or a hand-edited `page=99`) steps back to page 1 by `replace`.
- **The remembered query**: the last non-default query of a room, the page left out, is kept under `adder.viewSettings.roomThreads.<id>.query` (a string; the old `roomThreads.<id>.scope|order` keys are no longer read). When the Threads view opens on a URL that spells no list key, the hook reads it at once (so the first request already carries it, never the defaults first) and an effect writes it into the URL by `replace`. Every write updates what is remembered (the plain list remembers nothing), so the restore happens once: choosing the plain list leaves a bare URL AND nothing kept. `clear()` removes the panel filters (status, owner, tag, field) and the page, keeps the scope, the order and the other keys, and updates the remembered query to what remains (forgotten when nothing non-default remains).
- **Links keep the list's keys**: `withListParams(path, search)` (`utils/roomLinks.ts`) carries the normalized `scope`/`order`/`page` of the current URL into the list's rows, "New thread", "Back to threads" (`RoomHome`), the new-thread form's Cancel and the navigation after a started thread. The room's tabs and the rail link to the bare room route on purpose: that is where the remembered query comes back.

### The conversation (messages and the composer)

`ThreadPane` renders the header, then `MessageList` (key = room id and thread number, so a visit starts clean) and `MessageComposer`; `api/messages.ts` has the four wrappers the UI uses (list, post, edit, delete; the single-message GET is not used). The wire types (`MessageResponse`, the page, the request bodies) are the generated `schema.ts` types, pinned equal by `expectTypeOf` in `api/messages.test.ts`; a tombstone has `body: null` and `editedAt: null`.

- **The list** (`["rooms", "threads", roomId, "messages", number]`, a `useInfiniteQuery`): the server pages NEWEST first (`sort=-id`, 50 a load) and `id[lt]` keeps the older ones, so the next page param is the oldest id loaded, offered while a page's `total` (counted after the filter) exceeds its items. The display order is the pages flattened and reversed (oldest at the top, newest at the bottom). A refetch re-reads every loaded page with each cursor taken from the page just read (TanStack v5), so a new message pushing the 50th off page 1 loses nothing. The scroller (`MessageList.module.css`) is a focusable labelled `region` ("Messages", axe `scrollable-region-focusable`) sized by the structural-height rule ("The room view": wide, the pane is a viewport-bounded column and the scroller its `flex: 1` part, at least 16rem; narrow, the page scrolls and the composer sticks), so the header above and the composer below stay in reach. It scrolls to the bottom on open (a layout effect on the first non-empty list), after the caller's own post and, since 0.4, when the list grows, or its newest message is replaced or edited (the newest `id` or `editedAt` changes), under a reader who is at the bottom (an `atBottom` ref, updated on the scroller's scroll event: within 48 px of the end; a reader who scrolled up is never moved, and the open, own-post and load-older anchor paths come first and are unchanged): the pane holds `{threadNumber, messageId}` of the 201's message and hands the list `scrollToId`; once the list shows that id or a newer one it scrolls and clears the request (waiting for the id, not for the refetch's timing). "Load older messages" remembers `scrollTop` and `scrollHeight` and restores the reader's place after the prepend (a failed load drops the anchor). "Load older messages" stays enabled and focused while it loads (`aria-busy` and a spinner, never `disabled`; a second press during the load asks for nothing). A failed FIRST read shows the alert with Retry; a failed load of older ones keeps the button. When the load that finishes the history removes the button (the focus was on it), focus moves to the oldest loaded message, unless the reader has moved it meanwhile. No polling and no optimistic update (the live hints of 0.4 arrive as invalidations of this key; the list never cancels a fetch for them). **Refresh scope:** a reply re-reads the room thread tree, rail, Home and watched searches (`refreshAfterReply`). An edit or a delete uses the cache refresh described in “Reusing a mutation refresh”. An access refusal (403/404/409) re-reads the whole `["rooms"]` prefix.
- **A jump to a message** uses `message=<id>` or the first-unread action. `MessageList` requests the context around that message directly and renders up to 51 messages.
  It centers and focuses the target once, highlights it briefly, and announces the author. The context is a child key under the conversation's message prefix, so live edits and deletes refresh it without moving focus.
  Earlier and Later select an overlapping context window. An in-app quote jump also carries its containing reply in transient router state, so **Back to reply** replaces the anchor with that reply, clears the transient state and focuses it through the same context read. Reloading that history entry keeps the action. Copied links and modified clicks open without it. Back to latest clears the URL anchor and any quote-return state, keeps room filters and focus view, and restores the current conversation.
  The read marker moves only when the reader reaches the end of the thread, including a context window that reaches the latest message. Posting a reply resumes the latest view. A missing anchor shows a note and a return action.
- **An item** (`MessageItem.tsx`): the author as a bold run (never a heading: the outline stays the pane's one h3), the time in the browser's zone, an "edited {time}" marker (the time is visible text) and the `message` Markdown variant with hashtag links (below); a tombstone (`deleted`) shows "This message was deleted." or, for `deletedByModerator`, "Removed by a room owner or an administrator." and has no menu. ### Hashtag links in messages

`MarkdownView`'s message variant takes a `tagHref(tag)` prop (`MessageItem` passes `tagFilterPath(roomId, message.threadNumber, tag)`); without it a tag is plain text, and the document variant (the changelog) never links one. With it the message renders `remarkHashtags` after gfm and gemoji: a plugin that walks the Markdown tree by hand (no new dependency; `unist-util-visit` is only transitive) and splits each text node into text and `link` nodes marked `data-hashtag`, which the variant's `a` component renders as a react-router `Link` (an in-app navigation: no `target`, no `rel`) around the `#Tag` text. An external link still opens a new tab. The grammar is `utils/hashtags.ts`, a JS regex with the `u` flag (the lookbehind reads code points) and NFC-normalised text, the server's rule (`chat-model.md` "Find (0.5)"); a node is entered unless it is `code`, `inlineCode`, `link`, `linkReference`, `definition`, `html` or `image`, and a bare URL is a `link` through gfm's autolinks, so `https://example.com/#frag` is skipped. A tag in the text of a `[link](…)` stays text where the server indexes it (a link inside a link is invalid HTML): a known difference, with three harmless edge cases of the parsers reading different things (the server the source text, the SPA the unescaped tree): `foo\#a` and `&amp;#a` are indexed by the server and not linked by the SPA (the unescaped text `foo#a` / `&#a` has the hash glued to something), and `https://x.com/a<#b` is linked by the SPA as `b` and not indexed by the server. A tag is text inside its `Link`, never HTML. The link is `tagFilterPath` (`utils/roomLinks.ts`): the thread that is open, `scope=all` and `tag=<as typed>`, the value URL-encoded; the list's other filters are not carried (a status filter would hide threads that have the tag), and the server folds case and accents. One case table pins both sides: `server/src/test/resources/hashtag-cases.json`, read by the server's `HashtagsTest` and by `utils/hashtags.test.ts` through the real Markdown pipeline (distinct by lower case, the first spelling, at most 20, compared after NFC).

### Mentions in messages

A message body names a person with the token `<@id>` (`chat-model.md` "Mentions, notifications, unread, reactions, pins (0.6)"); the body is stored as sent and the SPA turns the token into a name at render. `MarkdownView`'s message variant takes a `mentions` prop (`MessageItem` passes `message.mentions`, `[{userId, name}]`, empty on a tombstone) and, when it is non-empty, adds `remarkMentions` after the hashtag plugin: a hand-written tree walk (no new dependency) that splits each text node on the grammar of `utils/mentions.ts` (`<@([1-9]\d{0,9})>`, the id at most 2147483647) into text and `mention` nodes, each a `span` with `data-mention` (`data.hName`, a custom node type the real pipeline renders). Every node is entered except `code`, `inlineCode`, `definition`, `html` and `image`; unlike a hashtag, a mention in a link's text is shown (a span inside a link is valid HTML). The `span` renderer is part of the ONE module-level components map and reads the names and the reader's id from a context (as `tagHref` does), so a re-render remounts nothing. **The SPA follows the server:** a token becomes `@Name` only when its id is in the message's `mentions`; any other id stays the raw token, so where the two parsers read differently (an escaped `\<@5>`: the SPA reads the unescaped tree, the server the source; a token glued to a bare URL) the reader sees text, never a wrong name. The server blanks indented code, raw HTML and image labels using CommonMark source spans, matching the nodes skipped here. The renderer also skips these nodes for legacy messages carrying obsolete mention metadata. The reader's own mention is marked (`data-self`, a heavier weight and an underline: a shape, not colour alone). A listed person's mention is a router link to `/people/:id` and a listed team's to `/teams/:id` (1.2 D6; `.mention` on a link, text colour on the tint), except inside a link's own text: `remarkMentions` flags that case `data-in-link` and the renderer keeps a span (a link may not hold a link); `@everyone` and `@watchers` are never links. The message variant therefore needs a router wherever it shows a mention. The name is a React text child: `**x**`, a link or markup in a display name is text. The document variant (the changelog) never reads a token. One case table pins both parsers: `server/src/test/resources/mention-cases.json`, read by the server's `MentionsTest` and by `utils/mentions.test.ts` through the real Markdown pipeline (every id the server found is shown, nothing else is); the Dockerfile's web stage copies it beside `hashtag-cases.json` because `npm run build` type-checks the tests. `utils/knownNames.ts` is the names the session has seen (a message's `mentions` are remembered by the message variant; the composer's picks join them): an in-memory store provided in the shell above the routes, inside the session boundary (`KnownNamesContext`, `useKnownNames`), so a new sign-in starts with none; it is never the authority for a token.

**Mentioning (the composer).** `components/MentionTextarea.tsx` is the box of all three writers (the reply box, the edit form, the new-thread body) over `EmojiTextarea`. The caller keeps the CANONICAL text, tokens and all (what is stored, sent, counted and kept as a draft: the drafts stay strings); the box SHOWS `@Name` for every token whose name the session knows (`utils/knownNames.ts`: filled by `MarkdownView` from messages' `mentions`, by `MessageEditForm` for the body it edits, and by a pick) and the raw token for one it does not know. `utils/mentionText.ts` is the pure mapping and is table-tested: `toShown` (canonical to shown, in runs that keep ids apart, so two members with one name stay two ids), `editCanonical` (an edit of the shown text back to the canonical one: the changed range is found from the caret the box reports, falling back to the common prefix and suffix when there is none, as for the emoji picker's splice; **an edit that touches any part of a mention removes the whole token**, the typed text going in its place; the box reports its selection from before the edit (`select` events), because the text alone cannot tell typing over a selection from a deletion; a paste is cut to what still fits in the stored text, and an edit the cap cuts to nothing puts the caret back where it was), `mentionQuery` (the `@term` at the caret: the `@` starts the text or follows whitespace, so an address is none; the term is at most 50 characters, no line break, may hold spaces; it never reaches into a mention already placed) and `pickMention` (the token and a space, the caret after it). The list's highlight is clamped to the rows there are, a pick that does not fit in the limit closes the list, and Escape's dismissed `@` is kept as a canonical offset that moves with edits before it and ends when the `@` is replaced or gone (not when the caret merely leaves it). A name containing `<`, `*` or `@` is only ever text: nothing re-parses the shown text. Known limits: a native undo that restores a removed mention brings back its shown text, not its token; a composition that touches a mention removes it mid-composition.
Typing `@` and letters opens a list of the room's members (`listRoomMembers` with `name`, eight rows, `sort=name`, the term debounced 300 ms, under `roomMemberPickerKey(roomId)` so any room refresh re-reads it; until the read for the current term is back the previous rows are narrowed by the term, so a quick Enter never picks someone the letters no longer match). ArrowDown/ArrowUp move (wrapping), Enter or Tab picks (Enter picks whatever else is held, Ctrl/Cmd included, while the list is open; closed, Enter is a newline and Ctrl/Cmd+Enter is the caller's send), Escape closes until that `@` is gone, a click picks and keeps the caret, and nothing opens during an IME composition (`compositionstart` closes it, `compositionend` looks again). ### Search

**Status and hashtag suggestions (1.11.0).** The query assistant offers `status:` and `hashtag:`, with room-specific values on the room
and thread views. In global search, select a joined room with `in:` to see its values. The status suggestion shows its workflow label
and inserts the stable key. Hashtag suggestions use the existing room index.

**Find in thread (1.10.0).** The thread header opens a keyboard-accessible in-thread search panel. The submitted query uses the same syntax
and suggestions as room and global search. Results are a page of matching messages, including author, date and a highlighted excerpt.
Selecting one closes the panel and follows the regular message anchor. The panel retains its draft and result page while the reader stays in
the same thread. On narrow screens the search temporarily takes the place of the conversation and reply box. Read markers pause while
search is open. Routine live hints leave search results alone. Revocation and room deletion reset the affected search and context reads,
so an in-flight response cannot repopulate them under the old permissions.

**Search clauses (1.9.0, unified in 1.36.0).** The forms share the query assistant. It inserts example clauses such as `word:disk`, suggests joined rooms and people using their stable IDs, and offers operator corrections for the reader to accept. The form selects syntax from the submitted query. Bare keyword searches use the plain-text request. Searches with clauses use `syntax=unified`, which applies the same prefix rule to bare words. The client checks the 512-code-point bound for clause queries. The API checks the 24-clause limit and grammar. The URL and cache key carry the syntax and the browser's `timeZone`. Explicit `syntax=structured` links carry their previous whole-word default. The API uses UTC if a clause query supplies no zone. See `chat-model.md` "Structured search (1.9.0)".

Two pages, one body: `pages/RoomSearch.tsx` (`/rooms/:id/search`, the room's "Search" tab in `RoomTabs`, inside `RoomPage`) and `pages/Search.tsx` (`/search`, the "Search" leaf of the Overview section in `utils/navigation.ts`, so the sidebar and the palette both get it). Both render `components/SearchBody.tsx`, which owns the URL state, the query and the triage (form, error, loading, count, empty, results, pager); the pages only say which request, which query-key prefix and whether the hit shows its room. `api/search.ts` wraps `GET /rooms/{id}/search` and `GET /search` (types from `schema.ts`).

- **State is the URL** (`utils/searchParams.ts` pure, `hooks/useSearchUrl.ts` over `useLiveSearchParams`): `q` (trimmed), `scope` (`open`, `closed`; **all** is the default and omitted, unlike the thread list's Open), `watching` (`1`, 1.1: the "Threads I watch" switch), `unread` (only `me`, sent as strict API boolean `true`), the repeated `threadTag` (1.2, the curated tags: the thread list's key and grammar through `threadTagValues`, lower-cased, at most 20, a refinement written by `replace` like the scope) and `page`. A new term and a page are history entries, the scope is a `replace`; anything but the page goes back to page 1 in the same write. Keys the page does not own pass through. A search is **submitted**, not run as you type; submitting the term that is already searched reads it again (the way to retry a failed search).
- **Plain text is checked before it is sent** (`queryProblem`, the server's `validateSearchQuery` mirrored): no control or hidden direction character (`\p{Cc}`, U+202A-202E, U+2066-2069, U+2028/2029), 2 to 100 code points after trimming, at least one letter or digit. A 400 never echoes the term, so the client is the only place that can say what is wrong; a bad term (typed, or hand-edited into the URL) shows its words under the box and is never requested. The palette offers its Search actions only for a term that passes the same check.
- **The box** (`SearchForm.tsx`): a labelled `type="search"` input, its description is ONE short line per state (default: three or more characters match the start of a word, case and accents ignored; with a personal switch or a tag: what the list is and "type to narrow them"); the full matching rules live in `chat-model.md` "Search (V16)", not under the box, a submit button, the scope control and labelled "Threads I watch" and "Unread" switches. Either switch makes an EMPTY box a search (`q` omitted from the request), a term narrows it, and a bad term is still refused; the empty state has its own words, and a hit has no messages and no marked words. Live hints never re-read the search keys (they sit outside `["rooms"]`); the caller's own watch write does through `WATCH_SEARCH_KEYS` (`utils/watch.ts`). **The "Tags" control** is the thread list's grouped `FilterMultiSelect` over `useTagCategories`, written to `threadTag`; with a tag picked an EMPTY box is a search too, a term narrows it, and a retired tag keeps its pill. The palette's "Threads I watch" action opens `/search?watching=1` (`watchedThreadsPath`). It follows the URL's term without losing focus.
- **Results** (`SearchResults.tsx`): an `ol` of `article`s, one per thread; the thread's title is an h4 within a room or an h3 across rooms, and its link goes to the thread and is named by the PLAIN title (`aria-label` `#42 Title`: `<mark>` splits the visible words); the three newest matching messages are links to `threadMessagePath(roomId, number, messageId)` (`?message=<id>`; the thread view reads it); a count (`N matching messages`) heads them. A title-only hit has no messages. A hit's curated `tags` are plain pills (`TagPills`, no link) in a `role="group"` named "Tags", a retired one struck through and said in words. In a room the status is the room's workflow pill (as the thread list draws it); across rooms a hit carries no workflow, so it is an Open or Closed pill from `closed`, the room name and an Archived badge for an archived room. A `role="status"` line announces "N threads found". A page the results no longer reach steps back to page 1 by `replace`. No page-size picker (20 a page, the server's maximum).
- **A snippet is a list of typed segments** (`Snippet.tsx`): each `text` is a text node, a `hit` one is wrapped in `<mark>` (Mantine's `Mark`). Never `dangerouslySetInnerHTML`, never Markdown: the text is a fragment of a title or of a message's Markdown source and can hold anything a person typed (`Snippet.test.tsx` pins an `<img onerror>` segment). A snippet is a fragment: the server's `ts_headline` can drop a short word at its edge.
- **Errors** (`searchErrorMessage`, `utils/problems.ts` `searchTimeout` / `searchBusy`): the generic `search` bucket 429 (`about:blank`: wait), `urn:adder:problem:search-timeout` (it took too long: narrow it) and `urn:adder:problem:search-busy` (the server is loaded: retry shortly) each have their own words; a 404 (room route only) means the room is gone, and the room page re-reads the room so it shows its not-found state.
- **Keys** (`utils/roomKeys.ts`): `searchAllKey` = `["search"]` for the search across rooms (`["search", q, scope, page, watching, threadTag, syntax, timeZone]`) and `roomKeys.search(room)` = `["search", "room", R]` for one room's (`[…, q, scope, page, watching, threadTag, syntax, timeZone]` appended). **Both sit outside `["rooms"]` and outside the room's thread tree**, so the hints that re-read the tree (`subscribed`, a thread or message hint without its number, an unknown kind, `resync`) never re-read an open search: each re-read would spend a token of the reader's `search` bucket and one of the server's few search slots. Only the frames that take the room away name them: `revoked` (the room's own results and `["search"]`, so a lost room's hits leave an open search across rooms) and `room.deleted` (the room's own); `liveKeys.test.ts` pins that no other frame does. Each reader keeps `staleTime` 30 s and `keepPreviousData` (the previous hits stay dimmed under `aria-busy`); the room page keys its `SearchBody` by the room, so a switch to another room whose record is cached never shows the old room's hits as a placeholder. **Results are not live** (a busy room would spend the reader's bucket on refetches); the session boundary clears them.
- **Links**: `searchPath`, `roomSearchPath(id)` and `threadMessagePath(roomId, number, messageId, search?)` in `utils/roomLinks.ts`; `search` (a URL query) passes the thread list's keys through `listSearch` when a link should keep them, and a search page's own `q`, `scope` and `page` are never carried (they would read as the list's). `searchResultsPath(path, q)` (`utils/searchParams.ts`) builds the palette's links.

### Names as links (1.2 D6)

A name that stands on its own is a link: a person's to `/people/:id` (`PersonLink`), a room's to `/rooms/:id` (`RoomLink`), a team mention's to `/teams/:id`. A multi-target card uses sibling links and a covering pseudo-element instead of nesting controls: this is used by the bell, thread list and search-message rows. **Underline: always, unless the line is a dense column of names**, where `quiet` keeps the underline but mutes its ink (gray-6 on light: 3.3:1 on white, 3.1:1 on the canvas and the pinned tint; gray-5 on dark: 6.5:1 or more; pinned in `theme.test.ts`; the accent returns on hover): a name that is not underlined at rest reads as a plain label, and WCAG 1.4.1 wants a cue besides colour for a link inside text (axe `link-in-text-block`), so no site is hover-only.

| Site | Link | Underline |
|---|---|---|
| a message's author (`MessageItem`) | person | quiet (a column down the conversation) |
| "Pinned by {name}" on a message, in a pin card, `Message by {author}` in the drawer, the strip's author (`PinCard`) | person | always (inside a dimmed sentence, `inherit` size) |
| the pane header's "Owner: …" and "Started by …" (`ThreadPane`), the side panel's read-only owner (`ThreadOwnerSelect`) | person | always |
| a USER field's value (`ThreadFieldValue`; an id the thread names no more stays `#id`, text) | person | always |
| the history's actor (`ThreadHistory` → `EventTimeline` `who`; a call site that KNOWS the person is gone, `actorDeleted`, draws plain text with its note instead of a `PersonLink`) | person | quiet |
| the room's members table, a team's roster, a team's manager (list and page) | person | always |
| a search hit's owner and, across rooms, its room (`SearchResults`) | person, room | always |
| a mention in a message body | person, team | the body's own link rule (underlined, text colour on the chip's tint); `@everyone`/`@watchers` and a mention inside a link's text stay spans |
| a bell row's actor and room (`NoticeRow`) | person, room | always |

Not links: compact reaction tooltip names (the summary has names, no ids), the ADMIN Users table, the steward's owner picker (the name sits in an input; the header's "Owner" line carries the link) and the "Found the message by …" status line. The full reaction roster, thread-list owners, matching-message authors and both people in an `OWNER_CHANGED` history sentence use `PersonLink`.

**"No dead links" holds only for ids a site can judge:** a mention whose id is not in the message's list stays text, a USER field the thread no longer names stays `#id`, an `actorDeleted` actor stays text. A person who is listed but has since been soft-deleted (a message author, a manager, a mentioned person) still links, to the profile's "not available" page (1.2 A15). **A translated sentence that holds a link is not `<Trans>`.** `utils/slots.tsx`: the sentence is translated with a marker as the value (`t("threads.pane.owner", { name: slot("name") })`) and `fillSlots(text, { name: <PersonLink …/> })` cuts it at the markers, so the keys stay plain `{{name}}` placeholders (EN/PL parity unchanged) and the other values (a thread's title, a display name) stay text children. `<Trans>` would parse the interpolated string as markup, and these values are what people typed (`<strong>`, or a tag named like one of the components, would become elements). **The bell row** (`components/NoticeRow.tsx`, `NoticeRow.module.css`): the notice link holds the sentence AFTER the actor's name as its text (so it has a box of its own, which locators and magnifiers need: an empty link reads as hidden), is named "Unseen" (while unseen) plus the whole sentence (the visible words are inside the name; the room and the time follow as the room link and the row's text); a SEEN row stays dimmed (the notice link and the names inherit the colour, the underline is the cue) and stretches over the row through `::after` (its focus ring is drawn there); the actor and room links sit beside it in the DOM, above it in the paint order. A screen reader therefore reads the sentence once as text and once as the notice's link. **A drawer that is a modal over the page closes when the page changes under it** (`hooks/useCloseOnPageChange.ts`, used by `PinnedPanel` and `NotificationsButton`: the path it opened on is compared during render), so a person's link inside it never leaves the drawer covering the profile. Focus does not return to the trigger (the room page's "Pinned" button is gone on the destination); it goes to `#main-content` (the skip link's target), except on a thread route, whose pane or message takes focus itself. Tests that match a whole sentence by text use the link's name (`findByRole("link", { name: /Ada mentioned you/ })`) or the element's `toHaveTextContent`, since `getByText` sees only an element's own text nodes.

- `utils/liveProtocol.ts`: the frame types (the generated `schema.ts` ones, pinned by `expectTypeOf` in `liveProtocol.test.ts`; only an event's `kind` is widened to `string`, because a newer server may add kinds), `parseServerFrame` (lenient: an unknown type or malformed members are ignored, never thrown) and `liveUrl(location, apiBase)`: the socket URL follows the SAME base as the REST calls (`VITE_API_BASE`, `API_BASE` in `api/http.ts`, passed in by `useLiveUpdates`). **The choice (0.4.0 audit L9): derive, don't disable.** An empty base is the page's own host (`ws:` on http, `wss:` on https); a relative base (`/adder`) is a path prefix on that host; an absolute `http(s)://host[:port][/prefix]` base maps to `ws(s)://` on THAT origin, and the server then needs the page's origin in `http.corsHosts` for the Origin check, exactly as REST needs it for CORS (an unusable absolute base falls back to the page's host). Adder's own CSP (`connect-src 'self'`) blocks a cross-origin socket exactly as it blocks the REST calls, so an absolute base only works when the SPA is served from somewhere else, under that host's CSP. A relative base without a leading slash resolves against the page's path, as REST's `fetch` does. The ticket is never in the URL, API-AUTH-002. - `utils/liveClient.ts`: the state machine, no React (`LiveClient`; everything outside is injected: `socketFactory`, `clock`, `mintTicket`, `onFrame`, `onStatus`). Statuses `connecting | live | quiet | down | paused | idle | stopped` (`quiet` = hidden for 5 minutes, the socket open for personal frames only; `idle` = closed on purpose after 8 hours hidden; a suspended tab shown while offline is `down`). Mint, open, the `auth` frame on `open`, `live` on `ready`; one **generation** per socket (every event of an older one is ignored, so a late close or a late mint never touches its successor). Backoff 1, 2, 4, 8, 16, then 30 s, each times a random 0.5 to 1, reset after 60 s live (a socket that flaps does not reset it); a `Retry-After` longer than the step wins (capped at 5 minutes, plus up to 1 s of jitter). `online` and a shown tab reconnect after a random 0 to 1 s, never at once (a whole office coming back must not arrive in one instant). Randomness is `crypto.getRandomValues` through the injected clock. Close codes: 1001 a random 1 to 5 s; 4001 and 4003 re-mint after a random 0 to 1 s (tokens minted together expire together; twice within 10 s: backoff); 4429 and a `429 live-socket-limit` mint pause for 60 s; every other code (1003, 1008, 1009, 1011, 4401, 1006) backs off. A socket that is not `ready` within 10 s, an `error` and a missing pong (an application `ping` every 25 s while visible, a pong or ANY frame within 10 s) are failures. **The hidden tab (1.2 D9, `live.md`):** hidden for 5 minutes the client goes `quiet` (the wanted set turns EMPTY through the ordinary unsubscribe diff, `setRooms` keeps recording what is wanted, the socket stays; the ping is once a minute with no pong timer and "no frame since the last ping" fails at the next tick; a socket that drops meanwhile reconnects and comes up quiet; a 4001 re-mints as ever); hidden for 8 hours (a second timer, both counted from the tab being hidden) it closes with 1000 and goes `idle` (everything stops; shown again it connects afresh). - **The reconnect refetch follows the tab (1.2 branch audit).** `utils/queryClient.ts` builds the app's one query client with `refetchOnReconnect` as a function: a HIDDEN tab, and a tab whose live status is `idle` (hidden 8 hours), does not re-read its mounted queries when the browser comes back `online` (each 401 on such a read would silently refresh the token pair and stretch the 8 h + refresh TTL bound, `security.md`). `useLiveUpdates` reports every live status to it (`reportLiveStatus`). What a hidden tab missed is caught up on becoming visible (TanStack's focus refetch fires only then: its focus manager reads `visibilityState`; the live client reconnects with a `resync`), and the quiet tab's bell is the live channel's own. ## Message edit history

`MessageRevisionDialog` is opened from an edited message’s actions. It requests a bounded page only after opening and displays the prior body in a wrapping plain-text view. The server authorizes each request. The client discards cached pages on room-access and role changes, message or thread deletion, and session changes; an open dialog reacts to those events immediately. `roomKeys.messageRevisions` scopes cache invalidation to the room and message. The new-thread form and the existing tag editor use the same `ThreadTagPicker`; kept drafts accept the optional curated tag ids.

## Reusing a mutation refresh

`liveReplyEcho` holds an exact matching `message.posted`, `message.edited`, `message.reaction_changed`, `thread.updated`, `thread.status_changed`, `thread.owner_changed` or `thread.merged` frame for up to 30 seconds, with at most 32 tracked mutations per query client. `threadRevisionEcho` gives both revisioned editors the same complete `thread.updated` refresh (`roomKeys.threads(roomId)`, `roomKeys.rail`, `homeKey`). A message edit covers the source room’s thread tree (including revision pages and quote drafts), pins, rail and Home. Cross-room quotes refresh through the live invalidator even when it holds the correlated edit. The writer confirms only after every active query covered by its refresh is successful, idle and fresh. Session changes discard earlier correlation state. When UUID generation is unavailable, tracking is full, or API origins differ, the write and live event follow their usual paths.

For a thread merge, the writer refreshes the room thread tree, workflow, workflow editor and Home using the same coverage as `thread.merged`. A delayed completion can open the target while the source pane is current in the same session, and it uses the latest list filters. The thread list stays mounted and owns the room workflow read. The new thread pane and its side panel subscribe to that query without a mount refetch. A lost response releases the held event, and the source stays readable.

The room member add and remove actions correlate their own room-level events after the broad room and Home refresh succeeds. The LiveClient still processes membership hints for subscription recovery before the invalidator checks the echo. A lost response releases the event and keeps draft edits and count feedback tied to the actual HTTP result. Room revocation keeps its immediate cache handling.

For single-message deletion, the writer starts the same refresh on the first confirmed signal, an HTTP `204` or a matching `message.deleted`. Room, thread and message must all match. The deleting tab can show and focus the tombstone while its HTTP response is still pending. A network error after the deletion no longer leaves an error under the tombstone. The existing live invalidator still handles other viewers, permissions, notices and reconnects.

Thread deletion also starts its refresh on the first committed signal, matching the room and thread number. The writer can return to the room with its list filters after a lost response if the live event confirmed deletion. Both paths clear cached deleted conversations and their merged histories, related search hits, revision history, previews, and quote excerpts. The other readers still receive the live event and clear their cached content. The room list and numeric thread routes share the main error boundary, so closing the pane keeps the already refreshed list and header mounted. A pathname change still clears a previously caught error.
