# Web internals (read on demand)

Mechanism and narrative text kept out of `web/CLAUDE.md` so that file stays a lean always-loaded-in-`web/` rule set. The binding rules (every never/must/always) stay in `web/CLAUDE.md` as one-liners; this doc holds the mechanics behind them. **Read the relevant section before changing the transport/session layer, the user/feature-flag pages, the language switcher, the colour tokens or logo, or the changelog wiring.**

### `http.ts` — the transport's refresh internals

- **`http.ts`** (transport): `authedFetch()` with the **single-flighted silent refresh** — on a
  401 it exchanges the stored refresh token once (concurrent 401s from the same session share one
  in-flight `/refresh` call) and retries once; a DEFINITIVE rejection (no refresh token, or
  401/403 from the server) clears the originating session and signs out only if that session is
  still current, while a TRANSIENT failure (network/timeout/5xx/429/malformed body) keeps the
  session so a later retry can succeed — **never collapse the two** (a network blip must not
  erase a valid session). Stale requests and refresh completions must not publish credentials,
  clear a newer login or retry across session identities. **The server rotates the refresh token** (each works once, plus a
  60 s server-side replay grace for a lost response; after that a replay is a 401), so two tabs on one session can race on
  `/refresh`: `doRefresh` serialises them with a Web Lock (`adder.auth.refresh`, where the browser has `navigator.locks`; a lock
  that cannot be acquired falls back to an unserialised refresh) and, inside it and again after a 401/403, adopts a pair already
  stored by another tab (same session identity, different refresh token) instead of replaying or clearing; a different login (new identity) is never adopted. **Why a 401 can now come at any time:** the server checks every access token against the user row per request (`security.md` "JWT model"), so a delete, a demotion/promotion, a password change or a logout elsewhere turns the NEXT request into a 401 (one text). The transport needs no special case: the 401 -> silent refresh -> retry path handles all of them - a role change refreshes successfully into the NEW roles (`persistRefreshedSession` republishes them and `notifyAuthChange` re-renders the nav and `RequireAdmin`, pinned in `http.test.ts`), a delete or password change makes the refresh a DEFINITIVE rejection and signs the user out. `ApiError` (status + parsed body; read
  RFC 7807 fields via the `detail`/`instance`/`type` getters, never hand-cast `err.body`), and the two
  standard wrapper shapes **`jsonRequest<T>()`/`voidRequest()`** every ordinary endpoint wrapper
  uses, plus **`buildQuery()`** — the query-string builder behind the list wrappers (skips
  null/undefined/""; `false` and `0` ARE sent, so an omit-when-false param is passed as
  `value || undefined` at the call site). Reach for the raw `authedFetch`/`safeJson` primitives
  only when a wrapper genuinely inspects the Response. Every transport fetch carries
  `timeoutSignal()` (30 s, feature-detected for happy-dom) — a hung request rejects with a
  `TimeoutError` DOMException instead of pending forever; new `fetch` call sites in `api/` must
  attach it.

### `session.ts`

- **`session.ts`**: token/roles/userId storage under the `adder.auth.*` localStorage keys, written
  by `persistSession(LoginResponse)` on login/MFA and conditionally by `persistRefreshedSession`
  on refresh, and the render-time accessors (`isAdmin()`, `getUserId()`, …). Components whose
  controls or queries depend on ADMIN use `useAdmin()` from `auth.tsx`; it subscribes to role
  changes from silent refresh and other tabs. A random stored identity distinguishes sign-ins,
  while credential snapshots guard refresh publication; renewing tokens preserves the logical
  session so staggered 401s can reuse the new token.

### Session boundary

- **Session boundary** (`components/SessionBoundary.tsx` + `utils/sessionQueryCache.ts`): bind the
  root `QueryClient` to logical session identity changes, and key the mounted app subtree by that
  identity. A different sign-in, definitive automatic sign-out, explicit sign-out, or a change
  from another tab must synchronously cancel and remove caller-scoped query data and discard
  mounted form/mutation results before the next account renders; an access/refresh token rotation
  within the same identity must retain them. Keep this at the session boundary rather than
  clearing individual page keys, because user/team/account queries all contain caller-specific
  projections. Late requests from the previous identity must not repopulate the new account's UI
  or cache.

### Sign-out and the return destination

Explicit sign-out opens `/login` without a saved return destination, so the next sign-in opens
Home even when a different account signs in. Anonymous access to a protected link still preserves
its path, query and hash. Test logout navigation with the real route guards from a non-home page;
a root-only menu test cannot detect a stale return destination. Reading the signed-out notice
during render must be side-effect free. Acknowledge it only after the login page commits, so a
suspended or retried render cannot discard the notice. The flag carries a reason (`SignedOutReason` in `auth.tsx`: `sessionEnded`, the default, or `passwordChanged`; `pendingSignedOut()` reads it, `consumeSignedOut()` clears it) and `pages/Login.tsx` picks the notice from it. **The self password change signs the device out explicitly** (`pages/ChangePassword.tsx`): the PUT bumps the account's credential revision, which ends every access and refresh token including this device's, so after the success toast the page runs `clearSession()`, `flagSignedOut("passwordChanged")` and `navigate("/login", { replace: true })` (the notice reads "Your password was changed. Sign in with your new password."). No `/logout` call - nothing is left to revoke, and the stale access token would only 401; no broadcast, for the same reason as `UserMenu`'s sign-out.

### Password reset (confirm link)

`pages/ResetPassword.tsx` only REQUESTS a reset (a uniform 202: the server emails a single-use link and changes nothing). The link lands on `pages/ConfirmPasswordReset.tsx` at `/reset-password/confirm#token=…`, which is NOT behind `RedirectIfAuthed` (a signed-in device may finish a reset). The token travels in the URL fragment, so it never reaches a server log or a Referer: the page reads it once into component state, strips the fragment and any query from the address bar and history (`navigate(…, { replace: true })`), keeps it in memory only (never storage) and sends it to nothing but `confirmPasswordReset` (a plain `fetch`, never `authedFetch`, so it can never refresh or retry a session). Loading the page consumes nothing; the form shows for any well-formed 43-character token and an unusable one is learned at submit (401: the token is dropped and "Request another reset link" shows; 429, 400 and network failures keep it for a retry). The new-password rule is `newPasswordValidation` (`utils/userForm.ts`), shared with `ChangePassword.tsx`. On success the page runs `clearSession()`, `queryClient.clear()` and `notifyAuthChange()` and shows the teal notice: no `/logout` call (the reset bumped the credential revision, so nothing is left to revoke) and no return destination.

## User management (`pages/Users|CreateUser|EditUser|ChangePassword.tsx`)

Passwords are generated client-side (`utils/password.ts`) and revealed exactly once: the modal
(`components/OneTimePasswordModal.tsx`) sets `closeOnClickOutside={false} closeOnEscape={false}`,
renders `components/RevealablePassword.tsx` (masked by default, eye toggle, copy), and closing
drops the plaintext from state for good — the server never returns it. The admin Reset-password
action (`hooks/useResetPassword.ts`) reuses the same generate→PUT→reveal flow. `NavLeaf.adminOnly`
gates the Users nav item (the Shell filters by `isAdmin()`); the management routes sit under ONE
`<Route element={<RequireAdmin />}>` in `App.tsx` (`auth.tsx`, beside `RequireAuth` — a regular
user is sent home), so no page redirects itself; their queries additionally stay
`enabled: isAdmin()` so a redirected caller fires no request. UX only — the server's
`requireAdmin` is the rule. The pages live under `/users` (`utils/userLinks.ts` is the one place the family is spelled out; Flow's `/flow-users` rename and its legacy `/users…` redirect do not exist here).

## Feature flags (`pages/FeatureFlags.tsx`, `pages/UserFeatures.tsx`)

success nor failure: it shows the inline gray `role="note"` Alert (`users.featureFlags.bulkNoChange`), never a toast.

answers to the width of the MAIN AREA through a container query (the sidebar and the ADMIN telemetry aside eat the viewport, so a viewport breakpoint would crush the pane): from 46rem
two columns `minmax(18rem, 22rem) 1fr`; below it master-detail through `data-pane="list"|"thread"` on the grid (the list at the room's own route, the pane on the thread routes,
which carry a "Back to threads" link that the wide layout hides); the side panel's `18rem` third column (from 70rem of main area) and its "Details" toggle below that are the thread pane's own grid (`ThreadPane.module.css`, same container; see "The thread side panel"). **Heading outline:** the room name stays the
`PageHeader` h2 (the repo's h2, not the plan's "h1"), the pane's heading `#42 Title` is the h3 (the pane is a labelled `region`), the side panel's sections are h4, the list is a
labelled `nav` with no heading, and message bodies never emit headings; long titles wrap anywhere (`overflow-wrap: anywhere`). **Focus:** a navigation to a thread from a list row or a
started thread carries `focusThreadPaneState` (`utils/roomLinks.ts`) and the pane `section` (`tabIndex={-1}`) takes focus once the thread has loaded (keyed by the thread's id, so a refetch
never pulls it back); a deep link or a reload leaves focus alone, and so does anything that is not a push of its own: a `replace` (a list filter write, the focus toggle) never asks for it, even though a filter write keeps `location.state` (`useNavigationType`), and neither does a jump to a message (`?message=`), whose message takes the focus instead. **Queries:** `["rooms", "threads", roomId, "list", …]` (the rail: 50 a page, Open by default and `-lastActivityAt`; **the list's state lives in the URL**, see "The list's state in the URL" below;
the previous filter's rows stay dimmed and `aria-busy` while the new one loads, and an empty state is only ever the current filter's answer; the page-size picker is left out of
`PaginationBar` by omitting `onPageSizeChange`) and `["rooms", "threads", roomId, "detail", number]`; **the focus view**: `?focus=1` on a thread route sets `data-focus` on the layout grid, which hides the list column at every width (`display: none`: out of the tab order, still mounted, so leaving the view loses nothing) and gives the pane the whole row; the room's own route and the new-thread form ignore it. The pane header's "Focus on this thread" button (`aria-pressed`, a stable name; the pressed state is the signal) writes `focus` by `replace`, keeping the other keys (and the focus on the button: it carries no pane-focus state); the URL is the state, so a reload and a shared link keep it, and nothing remembers it. The list is hidden by the route alone, so a pane that has no thread to show (missing, unreadable, failed) carries its own "Show the thread list" button while the view is on: never a dead end. The workflow is the ONE shared `["rooms", "workflow", roomId]` read
(`hooks/useRoomWorkflow.ts`) for the status pills and the form's fields. A write refreshes the whole `["rooms"]` prefix (threads, rail, workflow `threadCount`s, the room's own header).
**The new-thread draft** is kept per room in memory above the routes (`components/ThreadDraftsProvider.tsx` in the shell, inside the session boundary so a new sign-in starts with none;
`hooks/useThreadDrafts.ts`), written as the form changes while it holds something, so a list row, a tab or "Back to threads" does not lose it; coming back restores it laid over the
room's current fields (`reconcileThreadDraft`), and a started thread or a confirmed discard clears it. `NewThreadForm` seeds its field set ONCE from the workflow read (a background
re-read never adds or drops an input under a draft); a 400 on create also re-reads the workflow, and one about a field says the room's fields may have changed; every 400 shows the server's

body (only fields that hold something are sent; NUMBER and USER travel as JSON numbers; **a URL travels normalised** — `normalizedHttpUrl`: the WHATWG href plus `|{}^\`[]` percent-encoded
(the server parses with `java.net.URI`), and the host must be ASCII letters, digits, `-` and `.`, the server's own rule); `ThreadFieldInput` is the per-type switch and `RoomMemberSelect`
(a `SearchPicker` over `GET /rooms/{id}/members?name=`) its USER input. UX gating only (`utils/threadAccess.ts`): speech is for members of a live room, the server answers 403 and 409.

#### The list's state in the URL (since 0.5.0)

`utils/threadListParams.ts` is the pure half, `hooks/useThreadListParams.ts` the hook. Keys: `scope` (`closed`, `all`; Open omitted), `order` (`newest`, `number`, `status` = the workflow's order; activity omitted), `status` (repeated status keys), `owner` (`me` or a user id), `mention` (only `me` is read: "Mentions me"; any other value is the default), `tag` (repeated hashtags, 1 to 150 characters each, no `#` and no control character: a spelling as typed in a message, or a key as the room's tag list returned it, which can hold `'`, `/` or a space, so the key grammar does not apply; the URL keeps at most 10 distinct, the server's folded limit), `field` (repeated `key:value`) and `page` (a positive integer; 1 omitted).
Parsing drops junk (an unknown value reads as the default, a repeated scalar key reads its first value; `status` and `field` keep every valid value, distinct, at most 20 each; `tag` at most 10) and a write omits defaults, so a URL spells only what differs from the plain list. Keys the list does not own pass through a write. Two of them are the room view's, parsed and written in the same file but deliberately NOT list keys (`hasListKeys`, the remembered query and `withListParams` ignore them, so a link back to the list never lands in the focus view and a restored query never carries a stale jump): `focus` (`parseFocus`: only `focus=1` is on; `writeFocus`) and `message` (`parseMessageAnchor`: a positive integer of at most 15 digits, else none). Neither is remembered.
To add a list key: extend `ThreadListParams`, `DEFAULT_THREAD_LIST_PARAMS`, `LIST_KEYS`, `parseThreadListParams` and `serialize`; `hasListKeys`, `withListParams` and the remembered query follow. A multi-value key (repeated in the URL) needs `.getAll` in the parse and an emptiness check (not `!==`) in `serialize`'s default test; `writeThreadListParams` already deletes every list key and re-adds with `append`, so repeats survive a write. A write to the remembered query files it under the room of the LATEST render (a ref), so a stale handler never writes one room's key with another's params.

**The filter panel** (`components/ThreadFilters.tsx` inside the shared `FilterPanel`, stacked for the narrow rail; storage key `roomThreads`): status (`FilterMultiSelect`, Lettuce's, with `accessiblePill.tsx`: a named, focusable remove button on every pill; the options carry the workflow's `threadCount`), the hashtags (`RoomTagSelect`, a `FilterMultiSelect` over `GET /rooms/{id}/tags`, the most used first: the server searches with the 300 ms debounced term, a leading `#` dropped and at most 50 characters; an option is `#tag (threadCount)` and a pick is the tag as the list spells it; a value the current search does not return, such as the spelling from a hashtag link, stays an option labelled by itself so its pill keeps its name; at most 10 picks; the options sit under `roomKeys.threadTags`, inside the list prefix, so the live hints that refresh the list refresh them), the owner (a "Mine" toggle that writes `owner=me`, disabled without a session user id, and `MemberFilterSelect` over `RoomMemberSelect` for any member; beside "Mine" a "Mentions me" toggle that writes `mention=me`, also disabled without a session user id, and `toApiQuery` resolves it to `mentionedUserId=<the session's id>` exactly as `owner=me` is resolved, never in the parser) and one control per ACTIVE SELECT, MULTI_SELECT or USER field of the workflow (`filterableFields`; the server answers 400 for any other type). Everything the panel draws comes from the URL: `MemberFilterSelect` holds only the id, so a label it did not pick itself (a reload, a shared link) is looked up in the picker's own unfiltered head (the shared `roomMemberPickerKey` cache entry), else it reads `#id`. **`toApiQuery(params, workflow, me)` is the one place the state becomes a request**: `owner=me` resolves to the session's id there (never in the parser, so a shared "my threads" link means the opener's), and a `field` entry the workflow cannot judge (`pruneFieldEntries`: a key that is not an active filterable field, or a value of the wrong shape for its type, `severity:7` on a SELECT, `lead:abc` on a USER field) is DROPPED, not sent (the server would answer 400). Once the workflow is read, `ThreadList` also prunes those entries from the URL and the remembered query by `replace` (same page), so the badge, Clear and the 20-entry cap never count them. A request with field filters waits for the workflow (`toApiQuery` answers `null`; the list shows the spinner, or the load error when the workflow read failed). The badge counts filters: the statuses are one, the owner one, "Mentions me" one, the hashtags one, each field key one; scope and order sit outside the panel. "Clear filters" is the hook's `clear()`: it drops ONLY the panel filters (status, owner, "Mentions me", hashtags, field) and the page; the scope and the order stay, and the remembered query becomes what remains (forgotten when that is the plain list). An empty answer under a panel filter reads "No threads match these filters." without the start-one hint.

- **Writes** (`update(patch)`, `clear()`) go through `hooks/useLiveSearchParams.ts` (Flow's, ported: the functional form gets the LATEST params, so a handler captured by an older render never overwrites a newer change; the setter is stable; two writes in one event compose), use `replace` (a filter is not a history entry) and keep `location.state` (the pane-focus hand-off). A change of anything but the page deletes `page` in the same write, which is why a changed filter's FIRST request is page 1 (nothing is derived or reset in an effect). A page the server answers empty (the list shrank, or a hand-edited `page=99`) steps back to page 1 by `replace`.
- **The remembered query**: the last non-default query of a room, the page left out, is kept under `adder.viewSettings.roomThreads.<id>.query` (a string; the old `roomThreads.<id>.scope|order` keys are no longer read). When the Threads view opens on a URL that spells no list key, the hook reads it at once (so the first request already carries it, never the defaults first) and an effect writes it into the URL by `replace`. Every write updates what is remembered (the plain list remembers nothing), so the restore happens once: choosing the plain list leaves a bare URL AND nothing kept. `clear()` removes the panel filters (status, owner, tag, field) and the page, keeps the scope, the order and the other keys, and updates the remembered query to what remains (forgotten when nothing non-default remains).
- **Links keep the list's keys**: `withListParams(path, search)` (`utils/roomLinks.ts`) carries the normalized `scope`/`order`/`page` of the current URL into the list's rows, "New thread", "Back to threads" (`RoomHome`), the new-thread form's Cancel and the navigation after a started thread. The room's tabs and the rail link to the bare room route on purpose: that is where the remembered query comes back.

### The conversation (messages and the composer)

`ThreadPane` renders the header, then `MessageList` (key = room id and thread number, so a visit starts clean) and `MessageComposer`; `api/messages.ts` has the four wrappers the UI uses (list, post, edit, delete; the single-message GET is not used). The wire types (`MessageResponse`, the page, the request bodies) are the generated `schema.ts` types, pinned equal by `expectTypeOf` in `api/messages.test.ts`; a tombstone has `body: null` and `editedAt: null`.

- **The list** (`["rooms", "threads", roomId, "messages", number]`, a `useInfiniteQuery`): the server pages NEWEST first (`sort=-id`, 50 a load) and `id[lt]` keeps the older ones, so the next page param is the oldest id loaded, offered while a page's `total` (counted after the filter) exceeds its items. The display order is the pages flattened and reversed (oldest at the top, newest at the bottom). A refetch re-reads every loaded page with each cursor taken from the page just read (TanStack v5), so a new message pushing the 50th off page 1 loses nothing. The scroller (`MessageList.module.css`) is a focusable labelled `region` ("Messages", axe `scrollable-region-focusable`) capped at about two thirds of the viewport, so the header above and the composer below stay in reach. It scrolls to the bottom on open (a layout effect on the first non-empty list), after the caller's own post and, since 0.4, when the list grows, or its newest message is replaced or edited (the newest `id` or `editedAt` changes), under a reader who is at the bottom (an `atBottom` ref, updated on the scroller's scroll event: within 48 px of the end; a reader who scrolled up is never moved, and the open, own-post and load-older anchor paths come first and are unchanged): the pane holds `{threadNumber, messageId}` of the 201's message and hands the list `scrollToId`; once the list shows that id or a newer one it scrolls and clears the request (waiting for the id, not for the refetch's timing). "Load older messages" remembers `scrollTop` and `scrollHeight` and restores the reader's place after the prepend (a failed load drops the anchor). "Load older messages" stays enabled and focused while it loads (`aria-busy` and a spinner, never `disabled`; a second press during the load asks for nothing). A failed FIRST read shows the alert with Retry; a failed load of older ones keeps the button. When the load that finishes the history removes the button (the focus was on it), focus moves to the oldest loaded message, unless the reader has moved it meanwhile. No polling and no optimistic update (the live hints of 0.4 arrive as invalidations of this key; the list never cancels a fetch for them). **Refresh scope:** the caller's own post, edit and delete re-read `["rooms","threads",roomId]` and `["rooms","rail"]` (`refreshAfterMessageWrite` in `utils/messageForm.ts`; a message changes no workflow count and no room header); an access refusal (403/404/409) re-reads the whole `["rooms"]` prefix.
- **A jump to a message** (`MessageList`'s `anchorId`, from the pane's `?message=<id>`, a search hit's link; the id is validated as a positive integer, junk reads as none): the list does NOT open at the bottom (`openedOnAnchor`; the own-post, grow-under-a-reader-at-the-bottom and load-older paths above are unchanged, and a reader who was sent to an anchor counts as not at the bottom). An effect loads older pages (`fetchNextPage({ cancelRefetch: false })`, so it never cancels a refetch that is in flight: it waits until nothing is, then asks) until the id is listed, at most 10 loads (`MAX_JUMP_LOADS`), counted from the moment the anchor arrives (the page count then is the baseline, so a reader's earlier "Load older" presses do not spend the budget), and never after a failed load (the alert and the button take over). **Live hints during the search:** the live channel's invalidation (the default, which DOES cancel an in-flight next-page fetch) re-reads the loaded pages and the loop then asks again, so a hint is never lost and nothing extra is invalidated after the loop (pinned in `MessageListJump.test.tsx`). Once listed, a layout effect centres the message inside the scroller (`centreInScroller`: only the scroller moves, never the page), focuses it without a second scroll (the item's `tabIndex={-1}`, found by `data-message-id`), and marks it `data-anchor` for 5 s: a heavy outline plus a tint (a shape, so not colour alone) and a visually hidden `role="status"` line "Found the message by {author}." that is mounted from the first render (also while loading), so the text that appears in it is announced. The jump runs once per anchor (a ref), however often the list is re-read, and a NEW anchor on an open list jumps too. Settled without it, a gray `role="note"` BANNER above the scroller says why (so it stays in view) and the list shows its end, as on any open: `threads.anchor.gone` when every page is loaded and the id is not there (a message of another thread, a stale link; a deleted message is a listed tombstone, so the jump lands on that) or `threads.anchor.tooFar` past 10 loads (the button stays to keep going). `message` stays in the URL after the jump (a reload jumps again, the link stays shareable); in-room links do not carry it. The pane's own focus request is skipped while a `message` is asked for.
- **An item** (`MessageItem.tsx`): the author as a bold run (never a heading: the outline stays the pane's one h3), the time in the browser's zone, an "edited {time}" marker (the time is visible text) and the `message` Markdown variant with hashtag links (below); a tombstone (`deleted`) shows "This message was deleted." or, for `deletedByModerator`, "Removed by a room owner or an administrator." and has no menu. Actions come from `utils/messageAccess.ts` `messageActions` (UX only, the server guards; D2): the author, while a member, edits and deletes their own; a room OWNER or an ADMIN **removes** (never edits) someone else's; a closed thread, an archived room and a tombstone offer nothing. The kebab is `RowActionsMenu` named "Operations for message by {author} on {time}". Delete and Remove ask through `ConfirmActionModal`; a failure closes the dialog and shows under the message (the dialog's message is a paragraph and holds no alert). **Edit** is `MessageEditForm.tsx`, inline: Save or Ctrl/Cmd+Enter (ignored while a save is in flight), an unchanged body is not sent, Cancel on a changed body asks (the shared discard words) and a reload warns while it differs; it ends after the conversation has been re-read; the box is `readOnly` (not disabled) while saving and takes focus back on a failure. **The error of an edit or a delete lives in `MessageItem`** (the editor reports through `onError`), so a refusal that takes the edit action away (the thread closed) removes the editor but not the alert, and `editing` resets so the editor does not return on a reopen. **Focus:** each `li` is `tabIndex={-1}`; after an edit ends (saved or cancelled) and when the message becomes the tombstone of the caller's own delete or removal, focus goes to that message.
- **The composer** (`MessageComposer.tsx`): Enter is a newline (it picks while the list of people to mention is open: "Mentioning" below), Ctrl/Cmd+Enter or Send posts (`isSendShortcut`, ignored during an IME composition), with the 8000-character counter of `EmojiTextarea` (counting the stored text, tokens and all). The body rule is the server's `sanitizeMultiLine` (`messageBodyError` in `utils/threadForm.ts`, shared with the new-thread form: CRLF/CR to LF, leading blank lines and trailing whitespace dropped, 1 to 8000 UTF-16 units, no control characters except `\n`/`\t`, no bidi controls or U+2028/2029). The reply is kept **per thread** in the same in-memory store as the new-thread draft (`useThreadDrafts` gained `getReply`/`setReply`, a blank text clears), the box is keyed by (room, thread) so another thread never inherits the text, and a reload warns while the box holds something (the in-app half of the guard is the kept draft; there is no Cancel). While a post is in flight the box is read-only, not disabled, so the caret stays, and `send()` returns early on a MODULE-LEVEL in-flight map keyed by room and thread (a held Ctrl+Enter cannot post twice, and neither can a composer that was unmounted and mounted again while its post travels: it comes back read-only with the kept draft, and clears the box when the post succeeds if it still shows the same text); a successful post also clears the thread's draft in the store, so one that finishes after the reader navigated away leaves no draft of the sent text. `messageComposeBlock` replaces the box with a note: an archived room, then a closed thread, then (an ADMIN who is not a member; speech is members-only) "Only members of the room can post" with a link to the Members tab. A 409 `thread-closed` (`PROBLEM_TYPES.threadClosed`) says so, keeps the text and re-reads the `["rooms"]` prefix, so the closed note then replaces the box and the draft is there on reopening; a 429 shows the wait message; every failure vocabulary is `utils/messageForm.ts` `messageErrorMessage` (the two 409s are told apart by problem type, 403/404/409 re-read the room via `isAccessRefusal`).

### Hashtag links in messages

`MarkdownView`'s message variant takes a `tagHref(tag)` prop (`MessageItem` passes `tagFilterPath(roomId, message.threadNumber, tag)`); without it a tag is plain text, and the document variant (the changelog) never links one. With it the message renders `remarkHashtags` after gfm and gemoji: a plugin that walks the Markdown tree by hand (no new dependency; `unist-util-visit` is only transitive) and splits each text node into text and `link` nodes marked `data-hashtag`, which the variant's `a` component renders as a react-router `Link` (an in-app navigation: no `target`, no `rel`) around the `#Tag` text. An external link still opens a new tab. The grammar is `utils/hashtags.ts`, a JS regex with the `u` flag (the lookbehind reads code points) and NFC-normalised text, the server's rule (`chat-model.md` "Find (0.5)"); a node is entered unless it is `code`, `inlineCode`, `link`, `linkReference`, `definition`, `html` or `image`, and a bare URL is a `link` through gfm's autolinks, so `https://example.com/#frag` is skipped. A tag in the text of a `[link](…)` stays text where the server indexes it (a link inside a link is invalid HTML): a known difference, with three harmless edge cases of the parsers reading different things (the server the source text, the SPA the unescaped tree): `foo\#a` and `&amp;#a` are indexed by the server and not linked by the SPA (the unescaped text `foo#a` / `&#a` has the hash glued to something), and `https://x.com/a<#b` is linked by the SPA as `b` and not indexed by the server. A tag is text inside its `Link`, never HTML. The link is `tagFilterPath` (`utils/roomLinks.ts`): the thread that is open, `scope=all` and `tag=<as typed>`, the value URL-encoded; the list's other filters are not carried (a status filter would hide threads that have the tag), and the server folds case and accents. One case table pins both sides: `server/src/test/resources/hashtag-cases.json`, read by the server's `HashtagsTest` and by `utils/hashtags.test.ts` through the real Markdown pipeline (distinct by lower case, the first spelling, at most 20, compared after NFC).

### Mentions in messages

A message body names a person with the token `<@id>` (`chat-model.md` "Mentions, notifications, unread, reactions, pins (0.6)"); the body is stored as sent and the SPA turns the token into a name at render. `MarkdownView`'s message variant takes a `mentions` prop (`MessageItem` passes `message.mentions`, `[{userId, name}]`, empty on a tombstone) and, when it is non-empty, adds `remarkMentions` after the hashtag plugin: a hand-written tree walk (no new dependency) that splits each text node on the grammar of `utils/mentions.ts` (`<@([1-9]\d{0,9})>`, the id at most 2147483647) into text and `mention` nodes, each a `span` with `data-mention` (`data.hName`, a custom node type the real pipeline renders). Every node is entered except `code`, `inlineCode`, `definition`, `html` and `image`; unlike a hashtag, a mention in a link's text is shown (a span inside a link is valid HTML). The `span` renderer is part of the ONE module-level components map and reads the names and the reader's id from a context (as `tagHref` does), so a re-render remounts nothing. **The SPA follows the server:** a token becomes `@Name` only when its id is in the message's `mentions`; any other id stays the raw token, so where the two parsers read differently (an escaped `\<@5>`: the SPA reads the unescaped tree, the server the source; a token glued to a bare URL) the reader sees text, never a wrong name. The reader's own mention is marked (`data-self`, a heavier weight and an underline: a shape, not colour alone). The name is a React text child: `**x**`, a link or markup in a display name is text. The document variant (the changelog) never reads a token. One case table pins both parsers: `server/src/test/resources/mention-cases.json`, read by the server's `MentionsTest` and by `utils/mentions.test.ts` through the real Markdown pipeline (every id the server found is shown, nothing else is); the Dockerfile's web stage copies it beside `hashtag-cases.json` because `npm run build` type-checks the tests. `utils/knownNames.ts` is the names the session has seen (a message's `mentions` are remembered by the message variant; the composer's picks join them): an in-memory store provided in the shell above the routes, inside the session boundary (`KnownNamesContext`, `useKnownNames`), so a new sign-in starts with none; it is never the authority for a token.

**Mentioning (the composer).** `components/MentionTextarea.tsx` is the box of all three writers (the reply box, the edit form, the new-thread body) over `EmojiTextarea`. The caller keeps the CANONICAL text, tokens and all (what is stored, sent, counted and kept as a draft: the drafts stay strings); the box SHOWS `@Name` for every token whose name the session knows (`utils/knownNames.ts`: filled by `MarkdownView` from messages' `mentions`, by `MessageEditForm` for the body it edits, and by a pick) and the raw token for one it does not know. `utils/mentionText.ts` is the pure mapping and is table-tested: `toShown` (canonical to shown, in runs that keep ids apart, so two members with one name stay two ids), `editCanonical` (an edit of the shown text back to the canonical one: the changed range is found from the caret the box reports, falling back to the common prefix and suffix when there is none, as for the emoji picker's splice; **an edit that touches any part of a mention removes the whole token**, the typed text going in its place; the box reports its selection from before the edit (`select` events), because the text alone cannot tell typing over a selection from a deletion; a paste is cut to what still fits in the stored text, and an edit the cap cuts to nothing puts the caret back where it was), `mentionQuery` (the `@term` at the caret: the `@` starts the text or follows whitespace, so an address is none; the term is at most 50 characters, no line break, may hold spaces; it never reaches into a mention already placed) and `pickMention` (the token and a space, the caret after it). The list's highlight is clamped to the rows there are, a pick that does not fit in the limit closes the list, and Escape's dismissed `@` is kept as a canonical offset that moves with edits before it and ends when the `@` is replaced or gone (not when the caret merely leaves it). A name containing `<`, `*` or `@` is only ever text: nothing re-parses the shown text. Known limits: a native undo that restores a removed mention brings back its shown text, not its token; a composition that touches a mention removes it mid-composition.
Typing `@` and letters opens a list of the room's members (`listRoomMembers` with `name`, eight rows, `sort=name`, the term debounced 300 ms, under `roomMemberPickerKey(roomId)` so any room refresh re-reads it; until the read for the current term is back the previous rows are narrowed by the term, so a quick Enter never picks someone the letters no longer match). ArrowDown/ArrowUp move (wrapping), Enter or Tab picks (Enter picks whatever else is held, Ctrl/Cmd included, while the list is open; closed, Enter is a newline and Ctrl/Cmd+Enter is the caller's send), Escape closes until that `@` is gone, a click picks and keeps the caret, and nothing opens during an IME composition (`compositionstart` closes it, `compositionend` looks again). ARIA: the textarea keeps its `textbox` role (the combobox role is not allowed on a textarea, and the by-role locators of the composer stay valid) and carries `aria-autocomplete="list"`, `aria-haspopup="listbox"`, `aria-controls` the list and `aria-activedescendant` the highlighted option while it is open; the list is a `listbox` named "People in this room" in a Mantine `Combobox` dropdown (positioned by the Popover, kept in the DOM only while open); a visually hidden `role="status"` line says how many people match or that none do. `EmojiTextarea` gained a `ref` and `measuredLength` (the counter, the native `maxLength` attribute and the picker's check then stand down: `MentionTextarea` enforces the limit on the stored text). **The names store is the session's:** `useSessionKnownNames()` (the shell's) hands back a NEW empty store when the logical session changes (a sign-out, a new sign-in, another tab signing in as someone else), so one account's names never show to the next even where the shell stays mounted; `useKnownNames()` allocates a private fallback only when no shell provides one.

### Search

Two pages, one body: `pages/RoomSearch.tsx` (`/rooms/:id/search`, the room's "Search" tab in `RoomTabs`, inside `RoomPage`) and `pages/Search.tsx` (`/search`, the "Search" leaf of the Overview section in `utils/navigation.ts`, so the sidebar and the palette both get it). Both render `components/SearchBody.tsx`, which owns the URL state, the query and the triage (form, error, loading, count, empty, results, pager); the pages only say which request, which query-key prefix and whether the hit shows its room. `api/search.ts` wraps `GET /rooms/{id}/search` and `GET /search` (types from `schema.ts`).

- **State is the URL** (`utils/searchParams.ts` pure, `hooks/useSearchUrl.ts` over `useLiveSearchParams`): `q` (trimmed), `scope` (`open`, `closed`; **all** is the default and omitted, unlike the thread list's Open) and `page`. A new term and a page are history entries, the scope is a `replace`; anything but the page goes back to page 1 in the same write. Keys the page does not own pass through. A search is **submitted**, not run as you type; submitting the term that is already searched reads it again (the way to retry a failed search).
- **The term is checked before it is sent** (`queryProblem`, the server's `validateSearchQuery` mirrored): no control or hidden direction character (`\p{Cc}`, U+202A-202E, U+2066-2069, U+2028/2029), 2 to 100 code points after trimming, at least one letter or digit. A 400 never echoes the term, so the client is the only place that can say what is wrong; a bad term (typed, or hand-edited into the URL) shows its words under the box and is never requested. The palette offers its Search actions only for a term that passes the same check.
- **The box** (`SearchForm.tsx`): a labelled `type="search"` input, the rules of matching as its description (no stemming; a term of three or more characters matches the start of a word, a shorter one exactly; every term within one message or the title; case and accents ignored), a submit button and the scope control. It follows the URL's term (Back, the palette) without losing focus.
- **Results** (`SearchResults.tsx`): an `ol` of `article`s, one per thread; the thread's title is an h3 whose link goes to the thread and is named by the PLAIN title (`aria-label` `#42 Title`: `<mark>` splits the visible words); the three newest matching messages are links to `threadMessagePath(roomId, number, messageId)` (`?message=<id>`; the thread view reads it); a count (`N matching messages`) heads them. A title-only hit has no messages. In a room the status is the room's workflow pill (as the thread list draws it); across rooms a hit carries no workflow, so it is an Open or Closed pill from `closed`, the room name and an Archived badge for an archived room. A `role="status"` line announces "N threads found". A page the results no longer reach steps back to page 1 by `replace`. No page-size picker (20 a page, the server's maximum).
- **A snippet is a list of typed segments** (`Snippet.tsx`): each `text` is a text node, a `hit` one is wrapped in `<mark>` (Mantine's `Mark`). Never `dangerouslySetInnerHTML`, never Markdown: the text is a fragment of a title or of a message's Markdown source and can hold anything a person typed (`Snippet.test.tsx` pins an `<img onerror>` segment). A snippet is a fragment: the server's `ts_headline` can drop a short word at its edge.
- **Errors** (`searchErrorMessage`, `utils/problems.ts` `searchTimeout` / `searchBusy`): the generic `search` bucket 429 (`about:blank`: wait), `urn:adder:problem:search-timeout` (it took too long: narrow it) and `urn:adder:problem:search-busy` (the server is loaded: retry shortly) each have their own words; a 404 (room route only) means the room is gone, and the room page re-reads the room so it shows its not-found state.
- **Keys** (`utils/roomKeys.ts`): `searchAllKey` = `["search"]` for the search across rooms (`["search", q, scope, page]`) and `roomKeys.search(room)` = `["search", "room", R]` for one room's (`[…, q, scope, page]` appended). **Both sit outside `["rooms"]` and outside the room's thread tree**, so the hints that re-read the tree (`subscribed`, a thread or message hint without its number, an unknown kind, `resync`) never re-read an open search: each re-read would spend a token of the reader's `search` bucket and one of the server's few search slots. Only the frames that take the room away name them: `revoked` (the room's own results and `["search"]`, so a lost room's hits leave an open search across rooms) and `room.deleted` (the room's own); `liveKeys.test.ts` pins that no other frame does. Each reader keeps `staleTime` 30 s and `keepPreviousData` (the previous hits stay dimmed under `aria-busy`); the room page keys its `SearchBody` by the room, so a switch to another room whose record is cached never shows the old room's hits as a placeholder. **Results are not live** (a busy room would spend the reader's bucket on refetches); the session boundary clears them.
- **Links**: `searchPath`, `roomSearchPath(id)` and `threadMessagePath(roomId, number, messageId, search?)` in `utils/roomLinks.ts`; `search` (a URL query) passes the thread list's keys through `listSearch` when a link should keep them, and a search page's own `q`, `scope` and `page` are never carried (they would read as the list's). `searchResultsPath(path, q)` (`utils/searchParams.ts`) builds the palette's links.

### Room settings under live updates

`RoomSettings`' `DetailsForm` is keyed by the room id ALONE, so a change of the room's data under it (a live `room.updated`, the caller's own save, an archive) never re-mounts it or drops a draft. It keeps the server's values it was seeded from in state (`seed`) and applies the thread details form's seed rule to `toRoomDetails(room)`: when they move, the draft follows silently while the form is clean, while it already equals the new values (the caller's own save) and while the form is read-only (archived or not the caller's to change); otherwise the draft is kept and a `RevisionConflictAlert` ("This room changed while you were editing", with Reload, `rooms.settings.moved.*`) says the next save keeps the caller's version (the room PUT carries no revision: last write wins). A save in flight makes both fields `readOnly` (nobody types during it) and the notice is not shown; on success the sent (trimmed) values become the seed, so the refetch of the caller's own save never counts as the room having moved. Reload re-seeds from the room's current values and moves focus to the name field (it reuses `workflows.conflict.reload`, the alert's default label); Cancel resets to the last adopted values (the seed, or the server's if the form followed them); both clear the page-level save error.

### The thread side panel

`ThreadPane` is a grid of three parts in this DOM order: the header, the side panel (`ThreadSidePanel.tsx`) and the conversation. The panel lives INSIDE the pane's labelled `region`, after the h3, because its four sections (Status, Owner, Details, History) are **h4s** and the outline may not skip a level; it is only PLACED beside the conversation. `ThreadPane.module.css` answers to the main area's container (the same one as `RoomHome.module.css`): from **70rem** the panel is a third column (`18rem`, always shown, the conversation keeps about 27rem beside the 22rem list) and the "Details" toggle (`aria-expanded`, `aria-controls`; local state, collapsed by default) is hidden; below it the panel sits between the header and the conversation behind that toggle (`data-open="false"` is `display: none`, so it leaves the tab order and the accessibility tree). - **Who may do what (UX only; the server guards; D1).** `utils/threadAccess.ts`: `isThreadSteward` (the thread's owner while a member, a room OWNER, an ADMIN), `statusMoveBlock` (a move between OPEN statuses is open to every reader; entering or leaving a CLOSED one needs a steward; an archived room blocks all but the current status) and `threadEditBlock` (a closed thread and an archived room refuse the details and the hand-over).

Closing an OPEN thread asks first (`ConfirmActionModal`); reopening and CLOSED to CLOSED go straight through. - **Owner** (`ThreadOwnerSelect.tsx`): for a steward on a live, open thread a `RoomMemberSelect` plus an explicit "Pass on" button (choosing a name never hands the thread over by itself); everyone else, a closed thread and an archived room read the name under the reason ("reopen it first" only for a steward; anyone else gets the plain rule). The pick resets after the refresh, so the picker never shows the old owner for a frame.
- **Details** (`ThreadDetails.tsx` read view, `ThreadFieldValue.tsx`, `ThreadDetailsForm.tsx` editor). The read view shows the active fields with option LABELS, a stored key the workflow dropped as the key plus "(removed option)", a USER as the name in `fieldUserNames` (or `#id`), a URL as a new-tab `noopener` link (http/https only), and "Not set". "Edit details" swaps in the editor (title + the same fields through `ThreadFieldInput`, which marks a removed option too and does not offer it as a new choice). **Draft rules (binding, from the server review):** the draft is seeded from the thread's `revision` (and the workflow's) and re-seeded ONLY when that revision changes under a CLEAN form, after Reload, or by closing and reopening the editor after its own save; a refetch caused by a status or owner change, a message or a focus never touches a dirty draft (those do not bump the revision). ### The live channel

One WebSocket per tab, opened by `useLiveUpdates` (`hooks/useLiveUpdates.ts`) in `Shell`, beside `useRailRooms`; the protocol, the close codes and the catalog are `live.md`. Writes stay REST: a hint says THAT something changed, the SPA refetches through the ordinary reads. The files, all under `web/src/`:

- `api/live.ts`: `mintLiveTicket()` (`authedFetch` + `timeoutSignal()`, reading the response itself so a refusal is a `LiveMintError` carrying `retryAfterMs`).
- `utils/liveProtocol.ts`: the frame types (the generated `schema.ts` ones, pinned by `expectTypeOf` in `liveProtocol.test.ts`; only an event's `kind` is widened to `string`, because a newer server may add kinds), `parseServerFrame` (lenient: an unknown type or malformed members are ignored, never thrown) and `liveUrl(location, apiBase)`: the socket URL follows the SAME base as the REST calls (`VITE_API_BASE`, `API_BASE` in `api/http.ts`, passed in by `useLiveUpdates`). **The choice (0.4.0 audit L9): derive, don't disable.** An empty base is the page's own host (`ws:` on http, `wss:` on https); a relative base (`/adder`) is a path prefix on that host; an absolute `http(s)://host[:port][/prefix]` base maps to `ws(s)://` on THAT origin, and the server then needs the page's origin in `http.corsHosts` for the Origin check, exactly as REST needs it for CORS (an unusable absolute base falls back to the page's host). Adder's own CSP (`connect-src 'self'`) blocks a cross-origin socket exactly as it blocks the REST calls, so an absolute base only works when the SPA is served from somewhere else, under that host's CSP. A relative base without a leading slash resolves against the page's path, as REST's `fetch` does. The ticket is never in the URL, API-AUTH-002. Tests: `liveProtocol.test.ts`, `useLiveUpdates.base.test.tsx`.
- `utils/liveClient.ts`: the state machine, no React (`LiveClient`; everything outside is injected: `socketFactory`, `clock`, `mintTicket`, `onFrame`, `onStatus`). Statuses `connecting | live | down | paused | idle | stopped` (`idle` = closed on purpose after 5 minutes hidden; a suspended tab shown while offline is `down`). Mint, open, the `auth` frame on `open`, `live` on `ready`; one **generation** per socket (every event of an older one is ignored, so a late close or a late mint never touches its successor). Backoff 1, 2, 4, 8, 16, then 30 s, each times a random 0.5 to 1, reset after 60 s live (a socket that flaps does not reset it); a `Retry-After` longer than the step wins (capped at 5 minutes, plus up to 1 s of jitter). `online` and a shown tab reconnect after a random 0 to 1 s, never at once (a whole office coming back must not arrive in one instant). Randomness is `crypto.getRandomValues` through the injected clock. Close codes: 1001 a random 1 to 5 s; 4001 and 4003 re-mint after a random 0 to 1 s (tokens minted together expire together; twice within 10 s: backoff); 4429 and a `429 live-socket-limit` mint pause for 60 s; every other code (1003, 1008, 1009, 1011, 4401, 1006) backs off. A socket that is not `ready` within 10 s, an `error` and a missing pong (an application `ping` every 25 s while visible, a pong or ANY frame within 10 s) are failures. Hidden for 5 minutes closes with 1000 and goes `idle` (everything stops; shown again it connects afresh); `offline` closes and goes `down` without retrying, `bindBrowserSignals` (bound AFTER `start()`) feeds both. The caller's wanted rooms go in through `setRooms` (open room first, trimmed to `maxSubscriptions`) and leave as a diff (unsubscribe first, then subscribe), coalesced for 100 ms so quick navigation stays far below the server's 30 inbound frames per 10 s (`ready` subscribes at once); a room the server `refused` or `capped` is not asked for again until `forgetRefused()` (the hook calls it when the OPEN room changes), and a `revoked` room is dropped from the socket's set.
- `utils/liveKeys.ts`: `keysForFrame` (the table below) and `createLiveInvalidator(queryClient, clock)`. Focused keys settle 300 ms after the last hint and are flushed within 1 s of the first; the aggregate keys (`["rooms","rail"]`, `["rooms","list"]`, a room's thread list) at most once per 3 s; `resync`, `ready` and `subscribed` (the frames that mean "you may have missed something") wait a random 0 to 2 s, so tabs reconnecting after a restart do not refetch together. Only the aggregates are stamped with their last flush; a wider re-read stamps the aggregates it covers (`["rooms","threads",R]` its list, `["rooms"]` the rail and the rooms list), so the 3 s gap holds. **It NEVER cancels**: `invalidateQueries` cancels an in-flight fetch by default (a "Load older messages" click would be dropped and its scroll anchor left armed), so while `queryClient.isFetching({queryKey})` is above 0 the key is re-queued (300 ms) and invalidated once it is idle; `invalidateQueries` refetches only ACTIVE queries, the rest are marked stale. The caller's own writes still refetch through `refreshQueriesAfterMutation`, so the writer tab reads twice (accepted, A7); own echoes are not skipped.
- `utils/roomKeys.ts`: the key PREFIXES of a room's data, spelled once. The readers (`useQuery`), the refresh-after-write calls and `keysForFrame` all build from it, so a rename cannot desync a hint from its page; `liveKeys.test.ts` checks every hint key is a prefix of a reader's key and that no source spells a prefix by hand. A new reader of room data takes its key from `roomKeys` (a new part is added there).
- `hooks/useLiveUpdates.ts`: the wanted set (the open room from `matchPath("/rooms/:id/*")` + `parseRoomId`, then the ACTIVE rail's ids; the archived rail and "All rooms" keep refreshing on focus) and the status. It runs inside `SessionBoundary`/`RequireAuth` and keys the client on the session IDENTITY: a new sign-in is a new socket, sign-out closes it (1000), a token rotation keeps it. Its third argument (`clock`, `socketFactory`, `mintTicket`) is for tests.
- `components/LiveStatus.tsx`: see `web/CLAUDE.md` (the shell header). The 5 s grace means a token expiry or a server restart reads as nothing.
- `vite.config.ts`: the `/api` proxy has `ws: true` and no `changeOrigin` (the Host is kept, so the server's Origin check matches). The CSP is unchanged (`connect-src 'self'` covers the same-host socket).

**The key map** (R = room id, N = thread number; every key is a prefix; the unit of truth is `liveKeys.test.ts`):

| Frame / kind | Invalidates |
|---|---|
| `thread.created` | threads list R, workflow R, workflow-edit R, rail |
| `thread.updated`, `thread.owner_changed` | thread detail R/N, thread events R/N, threads list R, rail |
| `thread.status_changed` | the above + workflow R, workflow-edit R |
| `message.posted` | messages R/N, thread detail R/N, threads list R, rail |
| `message.edited` | messages R/N, threads list R (an edit can add or drop a hashtag), pins R (a pinned body shows in the panel) |
| `message.deleted` | messages R/N, thread detail R/N, threads list R, pins R (a deleted message loses its pin) |
| `room.pin_changed` | pins R (`["rooms","pins",R]`) |
| `room.created` | rail, rooms list |
| `room.updated`, `archived`, `unarchived` | room detail R, rail, rooms list |
| `room.workflow_updated` | workflow R, workflow-edit R, threads list R, `["rooms","threads",R,"detail"]`, `["rooms","threads",R,"events"]` |
| `room.member_added`, `member_role_changed`, `member_removed` | `["rooms","members",R]` (table and picker), room detail R, rail, rooms list |
| `revoked {R}` | what `room.deleted` re-reads (next row), `["search","room",R]` and `["search"]` (an open search across rooms) |
| `room.deleted` | room detail R, `["rooms","threads",R]`, members R, workflow R, workflow-edit R, pins R, rail, rooms list, `["search","room",R]` |
| an unknown kind with a room | the same, without the search key |
| `subscribed` (per acked R) | room detail R, `["rooms","threads",R]`, members R, workflow R, workflow-edit R |
| `ready` | rail, rooms list |
| `resync` | `["rooms"]` |

`revoked` goes through the same settle, so the caller's own Leave or Delete navigates first and no not-found flashes (`RoomMembers.test.tsx` pins it). The `subscribed` ack and `ready` close the gap between a page's own first read and the subscription becoming active, so a page load (and a reconnect) re-reads what is on screen once more, behind the 0 to 2 s spread. **Skipping a key whose cached data is newer than the socket's open time was considered and rejected**: a fetch that completes after the socket opened may still have STARTED (and read the server) before the subscription was active, so an event in that window would be lost until the next hint or focus; the extra read costs one request per active query and is the whole point of the gap-closing ack.
